# 0058. 依頼とターンの対応を、プロセスを知らない型にして、状態の軸で定める

## Context

セッションのワーカー（`dispatcher.go` の `worker`）は、プロセス、受信箱、依頼とターンの対応、認証情報の更新、
使用量、知らせを一つの型に持っていた。どの依頼をいつ送り、ターンの結果をどの依頼に返し、停止で何を止めるかは、
`running`、`forPrompts`、`turn`、`queue`、`sent`、`current`、`background` の組み合わせで暗黙に表され、ADR 0017 の
あとに 0028、0030、0031、0039 などが場面ごとに足してきた。判定はプロセスへの呼び出しと混ざり、試験は偽のプロセスを
動かす結合の試験だけだった（Issue #286、#283 の H）。

## Decision

- 依頼とターンの状態を、ターン（ない、依頼のターン、エージェントのターン）、取り込まれた依頼、送ってまだ取り込まれて
  いない依頼、待ち行列の依頼、バックグラウンドの処理の軸で表し、出来事ごとの遷移を表にする（`requests.md` の
  「依頼とターンの状態」）。`running` と `forPrompts` の二つのフラグは、ターンの軸の三つの値にする。
- その状態と判定を、プロセスを知らない型 `requestTurns`（`request_turns.go`）に切り出す。ワーカーはプロセスの出来事を
  渡し、返された判定のとおりに送り、止め、知らせる。試験は軸の値の組み合わせで書く。
- 振る舞いは変えない。

## Alternatives

- **ワーカーをプロセスの持ち主と依頼の持ち主の二つのゴルーチンに分ける**：判定は分かれるが、二つの間の受け渡しに
  順番の問題が新しく生まれる。今の一つのゴルーチンのまま、状態だけを型に分ける方が小さい。
- **状態を一つの列挙（状態機械の状態）にする**：軸が同時に成り立つ（ターンの間にバックグラウンドの処理も待ち行列も
  ある）ので、一つの値にすると組み合わせの数だけ値が要る。軸ごとに分ける。
- **文書の表だけを作り、コードは変えない**：表と判定が別々の所にあると食い違っても気づけない。判定を一つの型に
  集め、表と同じ組み合わせで試す。
