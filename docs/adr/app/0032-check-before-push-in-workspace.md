# 0032. 作業領域の pre-push フックで、push の前にターゲットの検査を通す

## Context

conventions は、push の前に手元で CI と同じ検査を通すと決めている。ターゲットでは、それは `make check` である
（ターゲットの契約の検査）。それでも、`make check` が落ちたのにコマンドを `;` でつないでいたため、そのまま
`git commit` と `git push` まで進み、CI で初めて気づいたことがあった（Issue #141 の A4、Issue #142）。

## Decision

- control-plane は、作業領域の `.git/hooks/` に、`commit-msg`（ADR 0021）と並べて `pre-push` を置く。
- `pre-push` は、push する ref（消すものは除く）がどれも今の HEAD のコミットで、作業ツリーに HEAD とのずれ
  （コミットしていない変更と、ignore されていない追跡していないファイル）がないときにだけ、ターゲットの一番上で
  `make check` を回し、通れば push を続ける。どちらかを満たさないとき、または検査が落ちたときは push を断る。
  Makefile のないリポジトリでは検査を回さない。
- フックの中では、git がフックに渡すリポジトリの場所の変数（linked worktree での `GIT_DIR` など）を外してから
  検査を回す。検査が自分で作るリポジトリで git を動かしても、作業領域を指さないように。
- ハーネスの契約に、push の前にこのフックが検査を回すことを書く。

## Alternatives

- **決まりのままにする**：決まりはあって、破られた（仕組みで守る）。
- **`prctl push` を足し、検査が通ったときだけ push させる**：`git push` を直に使えば素通りし、それを止めるには
  結局 hook が要る。
- **harness の PreToolUse の hook で、Bash の `git push` の前に検査の結果を確かめる**：コマンドの字面から push を
  見つけることになり、スクリプトの中の push やほかの書き方を逃す。検査の出力も、ツールの結果としてエージェントに
  見えない。git のフックなら、push がどこから来ても同じに働く。
- **検査を、push するコミットの一時的な worktree で回す**：作業ツリーによらず、push するものそのものを確かめ
  られる。ただし、ターゲットによっては依存物の取り込みなど、作業ツリーの外の準備が要り、時間もかかる。push する
  ものが HEAD で、作業ツリーにずれがないことを求めれば、作業ツリーでの検査が push するものの検査になる。
  ずれを断ることは、意図しないファイルが残っていることに気づく機会にもなる。
- **一度通した木（tree）を覚えて、同じ木の push では検査を回さない**：同じ木を push し直すことはまれで、覚える
  場所と消し方を増やすほどの得がない。

## Consequences

- control-plane 経由では、検査の通らないコミット、HEAD でないコミット、作業ツリーにずれのあるときの push は断られる。
  push には検査の時間がかかる。
- エージェントが push の前に自分で `make check` を回すと、検査は二度回る。
- フックはリポジトリにはコミットされず、`core.hooksPath` を設定しているターゲットと、`git push --no-verify` では
  働かない。devcontainer で直接動くときも働かない。
- このフックは作業領域を作るときに置くので、それより前に作った作業領域にはない。
