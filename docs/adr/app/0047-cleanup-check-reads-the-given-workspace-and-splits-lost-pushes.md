# 0047. `acp cleanup-check` は渡された作業領域を判定し、push したコミットが外れた理由を別の種類にする

## Context

ADR 0045 の `acp cleanup-check` には、Issue #225 に残した次の問題があった。

- 作業ディレクトリから作業領域の根を解いていたので、作業領域の外に clone したリポジトリ（`/tmp` など）の中で動かすと、
  そのリポジトリを判定して「片付けを止めるものはありません」と返す。Bash の作業ディレクトリはターンをまたいで
  残るので、`prctl worktree` などで外に入ったまま回すことは起こりうる。締めの手順（conventions の ADR 0031）が
  この出力に頼るようになり、取り違えは作業を失うことにつながる。
- GitHub のトークンを gh の `hosts.yml` の形から読んでいたが、書く側（`internal/adapter/docker/credentials.go`）と
  形を照らす試験がなかった。
- 理由の種類 `lost-commits` は、手元のブランチの push していないコミットと、push したブランチで最後に push した
  コミットがリモートから外れたもの（ほかの書き手の force push など）の両方で出ていた。締めでの扱いは前者が
  「作業領域にしかないもの」、後者が「人が解くもの」と分かれ、エージェントが出力から見分けられなかった。

## Decision

- control-plane は、エージェントのコンテナに作業領域のパスを `ACP_WORKSPACE` で渡す（作業ディレクトリと同じ）。
  `acp cleanup-check` は、作業ディレクトリによらずそこを判定する。作業ディレクトリから根を解く処理（`Root`）は
  外す。
- トークンを読む処理（`ReadGitHubToken`）を、書く処理の隣（`internal/adapter/docker/credentials.go`）に置き、書いた
  ものを読んで戻る試験で形を照らす。
- push したブランチの最後に push したコミットがどこにも入っていない理由を、`lost-push` として `lost-commits` から
  分ける。判定の解説の「消すと失われる（push したコミット）」と「消すと失われる（push していないコミット）」に
  それぞれ当たる。ハーネスの契約の種類の表は、一つの種類に一つの締めでの扱いを対応させる。
- 片付けの知らせ（保持期間ごとの促しと、今すぐの片付けの返事）の締めの案内は、締めると片付けられる状態になるとは
  言わず、解けずに残るものを知らせると言う（conventions の ADR 0031 の締めの終わり方）。

## Alternatives

- **作業領域のパスを渡さず、作業ディレクトリの根が `/workspace/` の下かを確かめる**：ターゲットが宣言した隣の
  マーケットプレイスも `/workspace` の下に見えるので、取り違えを防げない。
- **手順に「作業領域の根で回す」と書く**：守られなかったときに、黙って誤った答えを返す形が残る。
- **トークンをそのまま読めるファイルにも書き、契約に載せる**：認証情報のファイルが増え、契約が広がる。照らす
  試験で足りる。
- **`lost-commits` を一つのまま、契約に見分け方を書く**：判定がすでに分けて判定しているものを、エージェントが
  `kept` を写して判定し直すことになる。
- **契約の「締めでの扱い」の列を試験で確かめる**：判断が要らず誤って落ちにくいが、まだ破られたことがない。種類を
  足すと表の行を足すことになり、そのときに列もレビューで見られるので、今は足さない。

## Consequences

- `ACP_WORKSPACE` がない環境では、`acp cleanup-check` は判定せずに終了コード 2 で終わる。
- 理由の種類が 9 つになる。`lost-push` は、強制（`:fire:`）では消せる理由のまま。
- 種類を足したり分けたりしたら、ハーネスの契約の表の行と「締めでの扱い」の列も直す（ADR 0045 のとおり）。
