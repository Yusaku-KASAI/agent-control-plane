# 0053. GitHub App の届く範囲はインストールで絞り、トークンの発行では絞らない

## Context

GitHub App はエージェント（ターゲットとロールの組）ごとに作る（ADR 0011）。control-plane はインストールトークンを
リポジトリも権限も指定せずに発行するので、トークンはインストールの範囲のすべてのリポジトリに、App の権限のまま届く。
運用の手順は App をターゲットのリポジトリに入れるとだけ書き、インストールの範囲を限っていなかった。そのため App を
「All repositories」で入れると、トークンが手元のほかのリポジトリにも App の権限のまま届く。どのロールでも非公開の
中身を読め、ロールによっては Issue や PR に書け、developer なら守りのないブランチ（既定のブランチの守りを用意する前の
新しいターゲットを含む）に push できる（Issue #311）。

GitHub で届く範囲を絞れる所は次のとおり。

| どこで | 絞れるもの |
| --- | --- |
| App の設定 | 権限（App ごとに一組で、どのインストールとリポジトリにも同じにかかる） |
| インストール | 届くリポジトリ（「All repositories」か「Only select repositories」）。アカウントごとに一つ |
| トークンの発行 | リポジトリ（`repositories`、`repository_ids`）と権限。インストールの範囲より広げられない |

## Decision

- App は、そのエージェントのターゲットのリポジトリだけを選んでインストールする（「Only select repositories」）。
  運用の手順に書く。
- トークンの発行では、リポジトリも権限も絞らない。届く範囲は、インストールの範囲と App の権限で決まる。

## Alternatives

- **発行時に `repositories` をエージェントのターゲットに絞る**：App がエージェントごとなので、インストールを選んで
  入れていれば届く範囲は変わらない。効くのは、インストールの範囲を広く入れてしまったとき（「All repositories」か、
  選んだ中にほかのリポジトリがある）の保険だけで、それも運用の手順で防げる。リポジトリ名は片付けの `branches.go` と
  同じくターゲットの origin から読めるので、手間は小さい。保険を仕組みにするかは、発行の応答で気づく形（下の項目）と
  比べて Issue #315 で決める。
- **新しいターゲットの手順に、守りを用意するまですでにある App が届かないことを確かめる段を足す**：インストールを
  選んで入れていれば、すでにある App は新しいリポジトリに届かない。作ったばかりのリポジトリはテンプレートの中身だけで
  シークレットもなく、守りのない間に push されても履歴に残り戻せる。
- **発行の応答の `repository_selection` が `selected` でなければ失敗させる**：リポジトリ名は要らず、「All repositories」で
  入れたことに control-plane が気づける。この判断の範囲（運用の手順に書くこと）の外として、入れるかを Issue #315 で決める。
- **App を一つにして発行時にエージェントごとに絞る**：ADR 0011 で採らなかった（デバイスフローでは絞れず、名義も
  分けられない）。

## Consequences

- 今ある App で Repository access が「All repositories」のものは、人が「Only select repositories」に変えて、
  そのエージェントのターゲットだけを選ぶ。
- 届く範囲を守るのは、App を入れる人の操作だけになる。「All repositories」で入れても control-plane は気づかない（気づけるようにするかは Issue #315）。
- 一つの App を複数のリポジトリに入れる使い方（一つのエージェントが複数のリポジトリを扱う）を足すときは、発行時に
  絞るかを決め直す。
- 「Only select repositories」で入れた App のトークンがほかのリポジトリに届かないことは、GitHub の仕様として読んだ
  だけで、試していない。
