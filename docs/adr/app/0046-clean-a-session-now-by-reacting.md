# 0046. 人は、スレッドの最初のメッセージへの `:wastebasket:` でセッションを今すぐ片付けさせ、`:fire:` で失われるものを承知で片付けさせる

## Context

片付け（ADR 0026）は、使われないまま保持期間（既定 30 日）が過ぎたセッションだけを、残す理由がなければ消す。
人が「締めて」と頼み、エージェントが片付けられる状態にしても、保持期間まで残る。ADR 0026 は「人がコマンドで片付ける」を
自動で十分として選ばなかった。

片付けの役割の分け方（#220）で、リモートのブランチを消すのは control-plane だけになった。エージェントは、どこにも
入っていないブランチを、中身を Issue に残しても消さない。そのため、人がそれを承知して消すやり方が要る。人が一つの
セッションを手で片付けるやり方（どのディレクトリ、会話の履歴、ブランチを消すか）も、どこにも書かれていなかった（#208）。

## Decision

- スレッドの最初のメッセージ（ルート。途中から依頼したスレッドでも、依頼のメッセージではない）に `:wastebasket:` を付けると、control-plane はそのスレッドの
  セッションを、保持期間によらず片付けの判定にかける。理由がなければ消して、消したものと、続けると新しいセッションに
  なることをスレッドに知らせる。理由があれば、理由を挙げて残したことを返す。
- `:fire:` を付けると、失われる理由（作業ツリーの変更、stash、途中の操作、どこにも入っていないコミットとブランチ）が
  あっても消す。消したことの知らせに、承知のうえで捨てたものを挙げる。強制として受けるのは、次のすべてを満たすとき
  だけで、そうでなければ `:wastebasket:` と同じく理由を知らせて残す。人が知らせた理由を見てから承知したことにし、
  称賛などで何気なく付けた `:fire:` で、知らせていない作業が消えないようにするため。
  - その理由を、`:wastebasket:` を付けた本人に知らせた。保持期間ごとの促しや、ほかの人の `:wastebasket:`、強制として
    受けなかった `:fire:` で知らせたときは数えない（本人の強制が開いている PR だけで止まったときは、本人への知らせを
    残す。知らせていない理由で止まったときは、ロックの前か下かによらず残さない）。
  - 知らせるために作業領域を読んでから、使っていない。`:wastebasket:` の判定の始めに読んだ最後に使った時刻
    （`last_used_at`）を知らせと一緒に持ち、`:fire:` のときの値と同じときだけ受ける。判定には数秒から数十秒
    かかるので、知らせた時刻とではなく、読んだ値が変わっていないかで比べる。作業領域が変わるのはエージェントが
    使ったときで、ワーカーはターンを始めたときと終えたとき（プロセスが落ちたときや、control-plane が止まって
    中断したときも）と、バックグラウンドの処理が終わったとき（止めたときも）に、最後に使った時刻を記録に書く。
    休んでいるワーカーが受けた依頼の作業も、こうして知らせたあとの使用として見る。
  - 知らせてから、読む時間（10 秒）より後に付けた。`:wastebasket:` とほぼ同時に付けたときや、イベントが再送された
    ときに効かないようにするため。知らせた時刻は、`:wastebasket:` のイベントの時刻（Slack の時計）に判定にかかった
    時間を足したものとして持ち、`:fire:` のイベントの時刻と比べる。control-plane と Slack の時計がずれていても、
    続けざまの `:fire:` が通らず、強制が効かなくもならないようにするため。control-plane の時計でも、`:fire:` を
    受け取ったのが知らせてから読む時間より後であることを求める。切断のあとなどに、1 分あけて付けた二つが続けて
    届いたときに、理由を見ていない `:fire:` が通らないようにするため。
  - 知らせてから 1 時間のうちに付けた（同じく Slack の時計で比べる）。日をまたいで習慣で付けた `:fire:` を、理由を
    量ったばかりとはみなさない。
  - 今の理由が、どれも知らせた理由にある。ロックの下で判定し直したときも同じ。ほかの書き手の push などで知らせた
    あとに増えた理由があれば消さない。消すブランチの理由は、その先頭も含めて比べるので、知らせたあとに同じ
    ブランチへ push されていれば、知らせ直す。
- 本人への知らせ（誰に、いつ、どの理由を）は、セッションの記録ではなく、control-plane のメモリに 1 時間持つ。
  休んでいるワーカーは記録のロックを持ち続けるので、記録に書くには手放させることになり、何も消さない
  `:wastebasket:` でもコンテナを止めてしまうため。再起動で消えたら、`:wastebasket:` から付け直す。
- 強制として受けない `:fire:` は、消さずに理由を知らせる。残す理由がないときも消さず、`:wastebasket:` を案内する。
  称賛の `:fire:` で、続けたい会話が消えないようにするため。

- ワーカーは、ターンを終えたあとも `sessions.idle_timeout` のあいだロックを持つ。判定はロックを持たずに行い、消す
  ことになったときだけ、ターンも待っている依頼もバックグラウンドの処理もないワーカーを、その場で休ませてロックを
  放させる（`Dispatcher.Release`）。「締めて」のすぐあとの片付けが効くようにし、何も消さないリアクション（称賛の
  `:fire:`、理由のある `:wastebasket:`）では、次の依頼が使うコンテナを止めないようにするため。作業中なら消さず、
  そう知らせる。
- 判定できなかったとき（GitHub の API、認証情報、ワーカーの手放し、記録の書き込みの失敗）は、そうスレッドに
  知らせ、しばらくしてからリアクションを付け直すよう案内する。スレッドに投稿できなかったときは、投稿し直さない。
  記録を読めないときは、宛先が分からないので知らせない。
- 同じセッションの片付け（続けて付けたリアクション、保持期間による片付け）は、プロセスの中で一つずつ動かす。あとの
  ものは、先のものが消したか残したかを見て判定する。
- 消す手順は保持期間による片付けと同じで、ロックの下で記録と理由を確かめ直す。その間に使われていれば消さず、
  そう知らせる。セッションがない（片付けたあとなど）スレッドへのリアクションは何もしない。
- リアクションはエージェントごとの Bot が受けるので、同じスレッドで複数のエージェントを使っていれば、それぞれの
  セッションを判定する。
- 効くのは、そのエージェントに依頼できる人のリアクションだけ（ADR 0039 と同じ）。
- 最初のメッセージの ts はスレッドの ts なので、Bot はメッセージを覚えていなくても Slack に聞かずにセッションを決められ、
  再起動のあとでも効く。
- 残した知らせ（保持期間ごとの促しと、今すぐの片付けの返事）は、エージェントに「締めて」と頼むことと、`:wastebasket:` を
  案内する。

## Alternatives

- **依頼のメッセージ（どれでも）へのリアクションにする**：メッセージからスレッドを知るには、Bot が覚えている（24 時間、
  再起動で消える）か、Slack に聞く必要がある。片付けたいのは、使われなくなって時間がたったスレッドであることが多い。
- **強制を、残した知らせのメッセージへのリアクションにする**：知らせの ts を記録に持てば、再起動のあとでも見分けられ、
  承知を知らせた理由の一覧に結びつけやすい。ただ、知らせる側（`SessionNotifier`）が投稿の ts を返すようにポートを
  変え、知らせのたびに記録を書き換えることになる。人は、知らせが流れた長いスレッドでそのメッセージを探すことになる。
  付ける所を最初のメッセージにそろえ、知らせたことと理由は control-plane が覚えておく方が小さい。
- **残した知らせに付けるボタン（Slack の Block Kit）で強制する**：押せるのが理由を挙げた知らせの上だけになり、承知を
  理由に結びつけやすい。ただ、Slack アプリのインタラクティビティを有効にし、知らせを blocks にし、ボタンの操作を受ける
  アダプタを足すことになる。ボタンなら、読む時間や時計のずれ、続けて届くリアクションの扱いの多くが要らなくなる。
  それでも、停止（ADR 0039）と同じリアクションの操作でそろえ、知らせた本人、時刻、理由を control-plane が覚えて
  比べる方を選んだ。条件が増えて扱いが重くなれば、強制だけをボタンに移すことを見直す。
- **本人への知らせをセッションの記録に持つ**：再起動のあとも強制が効く。ただ、休んでいるワーカーが記録のロックを
  持つあいだは書けず、「締めて」のすぐあとの `:fire:` が効かない。書くためにワーカーを手放させると、何も消さない
  `:wastebasket:` でもコンテナが止まる。窓が 1 時間なので、再起動で消えても付け直せば足りる。
- **知らせたときの作業領域の写し（変更の中身のハッシュ、stash、ブランチの先頭、途中の操作）を持ち、ロックの下で
  読み直した写しと同じときだけ強制する**：ワーカーが作業の変わりうる時点をすべて `last_used_at` に書くことに
  頼らずに、知らせたものだけを捨てられる。ただ、作業領域を読むコンテナ（ADR 0043）と `SessionWorkspace` の
  ポートを、変更の中身まで読むように広げることになる。ワーカーは作業が変わりうる時点（ターンの始めと終わり、
  プロセスの停止、バックグラウンドの処理の終わり）で書く方が小さい。書き漏れが見つかれば、この形を見直す。
- **知らせた時刻を control-plane の時計だけで持ち、リアクションの時刻と比べる**：時刻が一つで済むが、二つの時計を比べることになる。control-plane の時計が遅れていれば続けざまの `:fire:` が強制として通り、
  進んでいれば強制がいつまでも効かない。Docker Desktop の VM の時計がどれだけずれるかは確かめていない。
- **知らせの投稿の ts を `SessionNotifier` から返し、`:fire:` の時刻と比べる**：Slack の時計どうしで、届くまでの
  遅れにもよらずに比べられる。ただ、ポートを変え、Slack 以外の知らせ先にも ts を持たせることになる。
  `:wastebasket:` の時刻に判定にかかった時間を足し、control-plane の時計でも読む時間を見れば足りる。
- **`:fire:` を、理由を知らせる前でも受ける**：称賛などで何気なく付けると、確かめないまま作業が消える。
- **休んでいるワーカーを手放させず、idle_timeout のあとに付け直してもらう**：「締めて」のすぐあとに付けても、
  いつも断られる。
- **本文を `:wastebasket:` か `:fire:` で始めてメンションする**（流し込みの `:zap:` と同じ形）：スレッドの一番下から
  頼め、メンションしたエージェントのセッションだけを片付けられる。ただ、エージェントへの依頼と control-plane への
  指示が同じ入口に混ざり、頼みのメッセージがスレッドに残る。停止（ADR 0039）と同じリアクションの操作にそろえる。
- **CLI のコマンド（#23）で片付ける**：依頼者は主に Slack から使う。CLI は #23 で、同じ `CleanNow` を呼べる。
- **強制では開いている PR も閉じる**：人がレビューの途中の PR を誤って閉じうる。PR は GitHub で閉じれば、`:fire:` で
  片付けられる。
- **締めたら、人の操作なしで（または短い保持期間で）片付ける**：締めたセッションも続けられる（conventions の用語集の
  「締め」）ので、続けたい会話を人の意思なしに失う。締めたことを control-plane が知る道も要る。
- **エージェントに片付けさせる**（締めの最後に control-plane を呼ぶ）：エージェントのコンテナから control-plane に
  届く道を作ることになり、#220 で避けた形になる。

## Consequences

- 人は「締めて」と頼んだあと、`:wastebasket:` で保持期間を待たずに片付けられる。片付けると、同じスレッドへの次の依頼は
  前の会話を引き継がない新しいセッションになる。
- control-plane は、知らせた理由の中身が Issue などに残っているかまでは確かめずに消す。
- 片付けの判定は GitHub の API と作業領域を読むコンテナ（ADR 0043）を使うので、返事まで数秒から数十秒かかる。
  control-plane が止まるときは取り消される。途中まで消したものは、リアクションを付け直すか、保持期間を過ぎた片付けで
  消し直す（ADR 0026 の消す順）。それまでは、そのスレッドの依頼が会話の再開に失敗しうる。
- リアクションの名前と、それを案内する文面は usecase が持つ。知らせる先が Slack だけのあいだは、アダプタに分けない。
- 同じリアクションの付け直しは、外してから付ける（Slack は同じ人の同じリアクションを一つだけ持つ）。知らせの文面は
  そう案内する。
- 判定できなかったときもスレッドに返事があるので、人は、効かなかったのか、まだ動いているのかを見分けられる。
  Bot のログにだけ出る失敗は、スレッドに投稿できなかったときと、記録を読めなかったときだけになる。
- control-plane を再起動すると、`:wastebasket:` で知らせた理由を忘れるので、そのあとの `:fire:` は
  `:wastebasket:` からのやり直しを返す。
- Slack アプリのスコープとイベント（`reactions:read`、`reaction_added`）は変わらない。
