# 0063. Slack の Web API の呼び出しを時間で区切って再試行し、投稿できなかった返事は知らせる

## Context

2026-10-30 に、Slack から依頼した 52 分のターンの最後の回答がスレッドに出なかった。状態メッセージは「完了」に
なっていた。同じころ、エージェントのコンテナから GitHub への接続が何度も失敗していた（TLS handshake timeout、
connection refused、network is unreachable）。control-plane のログはエージェントから読めず、依頼者はネットワークの
不調と見ている（#348）。

コードでは、返事が失われうる場面が二つあった。

- `slackbot.Bot` の Web API のクライアントは slack-go の既定のままで、HTTP クライアントにタイムアウトがなく、再試行も
  しない。答えの返らない呼び出しは、いつまでも待つ。返事の投稿は止まるときにも取り消さない文脈で呼ぶので、終わらない。
- 返事の投稿が失敗しても、`HandleMessage` はそのまま `:white_check_mark:` を付けた。依頼者には答えたように見え、
  失敗はログにだけ残る。

## Decision

- Web API のクライアントは、呼び出しを 1 回 30 秒で区切り、答えが返らなかったもの（タイムアウト、接続できない）と
  サーバーのエラー（5xx）を、1 秒から倍にして 30 秒までの間を置いて 6 回まで再試行する。間は合わせて約 1 分になる。
  レート制限（429）は Slack の `Retry-After` に従って再試行する。Slack が断ったもの（`invalid_blocks` など）は、
  同じものを送り直しても通らないので再試行しない。返事、知らせ、状態メッセージ、リアクションのどの呼び出しにも効く。
- 再試行は slack-go の `OptionRetryConfig` に任せ、どれを再試行するかの判定だけを自分で持つ。slack-go の接続の
  エラーの判定は、エラーの文面の `connection reset`、`connection refused`、`EOF` だけを見て、タイムアウトや
  届かないネットワークを再試行しない。
- 再試行しても返事を投稿できなかったら、`HandleMessage` は、投稿できなかったことと、もう一度依頼すれば回答を書き直す
  ことを短く投稿し、依頼のメッセージに `:warning:` を付ける。Slack が返事を断ったときは、短い知らせは通りうる。

## Alternatives

- **返事の投稿だけを自分のループで再試行する**：返事のほかの呼び出し（終わりの状態メッセージ、リアクション）は
  一度で失敗したままになり、答えたかを表すリアクションも同じ不調で失われる。クライアントで再試行すれば一か所で済む。
- **失敗した返事をファイルに持ち、つながったら送る**：再起動をまたいでも失わないが、持つ場所、送り直す時機、古くなった
  返事の扱いを足すことになる。回答はセッションの会話に残り、もう一度依頼すれば書き直せるので、知らせれば足りる。
- **slack-go の既定の再試行（`AllBuiltinRetryHandlers`）を使う**：上のとおり、今回の失敗の形（タイムアウト、届かない
  ネットワーク）を再試行しない。

## Consequences

- 1 分ほどの不調なら、返事は遅れて届く。それより長い不調では、返事も知らせも `:warning:` も届かず、失敗はログにだけ
  残る。
- Slack が受け取ったあとに答えが返らずに区切った呼び出しは、送り直すので、同じ返事が二度出ることがある。失うよりは
  よいとする。
- 止めるとき（`stop_grace_period` は 1 分）に Slack とつながらなければ、返事の再試行の途中で止まることがある。
