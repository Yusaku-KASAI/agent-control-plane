# 0044. control-plane が作業領域のファイルを直に読むときは、読む元のディレクトリの中の通常のファイルだけを大きさの上限つきで読み、マウントする隣のマーケットプレイスはホストのターゲットの宣言からだけ決める

## Context

エージェントのコンテナを起こすとき（`internal/adapter/docker/plugins.go` の `declaredPlugins`）、control-plane は
作業領域の `.claude/settings.json` と、ツリーの中のマーケットプレイスの `.claude-plugin/marketplace.json` を、自分の
プロセスで `os.ReadFile` で読んでいた。作業領域はエージェントが書ける。これらのファイルを名前付きパイプにされると
読みが止まり、`/dev/zero` へのシンボリックリンクにされると読みが終わらない。作業領域の外のファイル（control-plane の
コンテナにある秘密のファイルなど）へのシンボリックリンクにされると、それを読む。マーケットプレイスのディレクトリを
外へのシンボリックリンクにしても同じ（#229）。

さらに、設定の `directory` のマーケットプレイスのパスで、ターゲットの隣のリポジトリ（隣のマーケットプレイス）を名指すと、
control-plane はそのディレクトリをエージェントのコンテナに読み取り専用でマウントする。パスも、途中のシンボリック
リンク（作業領域に置いたもの）もエージェントが書けるので、ほかのセッションの作業領域や、作業領域から外へのリンクの先を、
隣のマーケットプレイスとして読ませ、マウントさせられた。

control-plane のプロセスでエージェントの書いたファイルの中身を読む所は、ほかにない。片付けの判定で作業領域の状態を
読む所は、使い捨てのコンテナに移した（ADR 0043）。セッションの記録は作業領域の外にあり、エージェントのコンテナからは
見えない。エージェントの Claude Code の設定ディレクトリ（エージェントが書ける）は、片付けで名前を走査して消す
（`SessionFiles`）が、中身は読まず、消すのはそのセッションの ID で始まる名前のものだけ。

## Decision

- control-plane のプロセスで作業領域のファイルを読むときは、`readUntrusted` で読む。
  - 読む元のディレクトリ（作業領域、ホストのターゲットの checkout、隣のマーケットプレイス）を `os.Root` で開き、その中だけを読む。シンボリック
    リンクは、相対パスで、たどった先がその中に留まるものだけをたどる（`os.Root` は絶対パスのリンクをたどらない）。
  - 待たずに開き、開いたものが通常のファイルかを確かめる。名前付きパイプでも止まらず、デバイスは読まない。確かめる
    のは開いたもの自体なので、確かめてから読むまでの差し替えは起きない。
  - 読むのは決めた大きさ（設定とマーケットプレイスのファイルは 1 MiB）まで。一つのコンテナのためには、マーケット
    プレイスを一度ずつ読み、読む量の合計も 4 MiB までにする。設定がプラグインを数多く有効にしても、リンクで一つの
    マーケットプレイスを多くのパスで名指しても、読みと解析を数で膨らませないため。超えたらエラーにする。
- 宣言を読む元を、マーケットプレイスの置き場で分ける。
  - ターゲット自身の中のマーケットプレイスは、今までどおり作業領域（セッションの clone）の設定の宣言から決め、作業
    領域の中を読む。作業中のブランチの版をそのセッションで使えるようにするため（ハーネスの契約の作業領域とブランチ）。
  - 隣のマーケットプレイス（エージェントのコンテナにマウントするもの）は、ホストのターゲットの checkout の設定の宣言
    からだけ決める。中身がホストのものなので、宣言もホストのものに合わせる。作業領域の設定が隣を名指しても、読まず、
    マウントしない。
- 断ったら、今までの読めないファイルと同じくエラーにして、コンテナを起こさない（その依頼は失敗として返る）。

## Alternatives

- **片付けの判定と同じく、使い捨てのコンテナで読む**：コンテナを起こすたびに、もう一つコンテナを起こすことになり、
  依頼の待ちが延びる。読むのは JSON だけで、git のように設定でコマンドを動かすこともないので、読み方を縛れば足りる。
- **ツリーの中のマーケットプレイスを、エージェントのコンテナの中で解く**（隣のものはマウントを決めるので、コンテナの
  外で決めるほかない）：control-plane のバイナリをエージェントのコンテナにも渡し、claude の起こし方を包むことになり、
  ターゲットのイメージの契約（引数のコマンドをそのまま実行する）にも関わる。JSON を縛って読むより大きい。
- **宣言を、エージェントが書けない所（ホストのターゲットの checkout か、clone した直後の `Prepare`）から読む**：
  ファイルの差し替えは起きない。ただ、ターゲット自身の中のマーケットプレイスは、作業領域の中（作業中のブランチの版）
  をそのまま使う（ハーネスの契約の作業領域とブランチ）。プラグインを変える作業を、そのセッションの次の依頼で試せなく
  なる。
- **`os.ReadFile` の前にパスを `filepath.EvalSymlinks` で解いて、作業領域の中かを確かめる**：確かめてから読むまでに
  シンボリックリンクを差し替えられる。`os.Root` は、開くときに一段ずつ外に出ないことを確かめる。
- **読むファイルにシンボリックリンクを一切許さない（途中のディレクトリも）**：ターゲットが、まだ分けていない
  マーケットプレイスをシンボリックリンクで置く形（target-template ADR 0007）を壊す。
- **読むファイル自体のシンボリックリンクだけを断る（`Lstat` で確かめ、開いたものと同じかを確かめ直す）**：外に出ない
  ことは `os.Root` が、止まらないことは待たずに開いて開いたものを確かめることが守るので、足すものがない。手順と試験と、
  ターゲットへの条件が増える。
- **隣のマーケットプレイスも作業領域の宣言から決め、リンクを解いた先がターゲットの親の中にあり、`sessions.root` の
  外にあるものだけにする**：エージェントが書ける場所を並べて断る形になり、並べ漏れが穴になる（ボリュームなしで
  ターゲットの親の下に置いた `claude.config_dir` など、エージェントが書ける bind の置き場）。
- **隣のマーケットプレイスを、名前（ターゲットの親の直下のディレクトリ）だけで決める**：まだ分けていない
  マーケットプレイスをリンクで置く形（同じく ADR 0007）を壊す。

## Consequences

- リポジトリの外を指すシンボリックリンクで設定かマーケットプレイスのファイルを置いたターゲットは、プラグインを読み
  込めず、依頼が失敗する。設定かマーケットプレイスのファイルが 1 MiB を超えるターゲットも同じ。
- 隣のマーケットプレイスを足すか変える宣言も、そのプラグインを有効や無効にする宣言も、ホストのターゲットの checkout
  に入るまで（マージして、手元に取り込むまで）、セッションでは効かない。
- `sessions.root` をターゲットの親ディレクトリの中に置いても（例の設定のとおり）、エージェントがそこを隣のマーケット
  プレイスとして名指すことはできない。
- 作業領域のファイルを control-plane のプロセスで新しく読むときは、`readUntrusted` を使う。
- ターゲットが置くファイルへの条件は、ターゲットの契約の「プラグイン、ロール、Claude Code の設定」に、隣の
  マーケットプレイスの宣言をどこから読むかは、ハーネスの契約（作業領域とブランチ）にだけ書く。
