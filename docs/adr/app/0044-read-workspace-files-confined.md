# 0044. control-plane が作業領域のファイルを直に読むときは、読む元のディレクトリの中の通常のファイルだけを、大きさの上限つきで読む

## Context

エージェントのコンテナを起こすとき（`internal/adapter/docker/plugins.go` の `declaredPlugins`）、control-plane は
作業領域の `.claude/settings.json` と、ツリーの中のマーケットプレイスの `.claude-plugin/marketplace.json` を、自分の
プロセスで `os.ReadFile` で読んでいた。作業領域はエージェントが書ける。これらのファイルを名前付きパイプにされると
読みが止まり、`/dev/zero` へのシンボリックリンクにされると読みが終わらない。作業領域の外のファイル（control-plane の
コンテナにある秘密のファイルなど）へのシンボリックリンクにされると、それを読む。マーケットプレイスのディレクトリを
外へのシンボリックリンクにしても同じ（#229）。

control-plane のプロセスでエージェントの書いたものを読む所は、ほかにない。片付けの判定で作業領域の状態を読む所は、
使い捨てのコンテナに移した（ADR 0043）。セッションの記録は作業領域の外にあり、エージェントのコンテナからは見えない。

## Decision

- control-plane のプロセスで作業領域のファイルを読むときは、`readUntrusted` で読む。
  - 読む元のディレクトリ（作業領域か、隣のマーケットプレイス）を `os.Root` で開き、その中だけを読む。シンボリック
    リンクは、たどった先がその中に留まるものだけをたどる。
  - 読むファイル自体はシンボリックリンクにせず、通常のファイルだけを読む。開くときは待たずに開き、開いたものが
    確かめたものと同じ通常のファイルかを確かめ直す（確かめてから開くまでに置き換えられたとき）。
  - 読むのは決めた大きさ（設定とマーケットプレイスのファイルは 1 MiB）まで。超えたらエラーにする。
- 断ったら、今までの読めないファイルと同じくエラーにして、コンテナを起こさない（その依頼は失敗として返る）。

## Alternatives

- **片付けの判定と同じく、使い捨てのコンテナで読む**：コンテナを起こすたびに、もう一つコンテナを起こすことになり、
  依頼の待ちが延びる。プラグインの場所から、エージェントのコンテナのマウントが決まるので、エージェントのコンテナの
  中で読む形にもできない。読むのは JSON を二つだけで、git のように設定でコマンドを動かすこともないので、読み方を
  縛れば足りる。
- **`os.ReadFile` の前にパスを `filepath.EvalSymlinks` で解いて、作業領域の中かを確かめる**：確かめてから読むまでに
  シンボリックリンクを差し替えられる。`os.Root` は、開くときに一段ずつ外に出ないことを確かめる。
- **読むファイルにシンボリックリンクを一切許さない（途中のディレクトリも）**：ターゲットが、まだ分けていない
  マーケットプレイスをシンボリックリンクで置く形（target-template ADR 0007）を壊す。

## Consequences

- `.claude/settings.json` をシンボリックリンクにしたターゲットは、プラグインを読み込めず、依頼が失敗する。読む
  ファイル自体は、通常のファイルとして置く。
- 設定かマーケットプレイスのファイルが 1 MiB を超えるターゲットは、依頼が失敗する。
- 作業領域のファイルを control-plane のプロセスで新しく読むときは、`readUntrusted` を使う。
