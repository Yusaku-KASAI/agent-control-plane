# 0052. 締めを促す閾値の既定を 40 万トークンに決め、自動では締めない

## Context

ADR 0049 は、コンテキストの大きさが閾値（`sessions.suggest_closing_at`）以上なら、終わった状態メッセージで締めを
促すと決め、既定の 40 万を仮の値として、記録で見直すとした（Issue #245）。

入れてからの 2026-10-25 の記録（手元のセッションの会話の記録で、メインのエージェントの API の呼び出しが読んだトークン数の
最大と、Slack の状態メッセージ）は次のとおりだった。

- 一つの依頼か、続けて少しの依頼をこなしたセッションは、最大が 8 万〜32 万だった（10 件）。どれにも行は出なかった。
- いくつもの別の作業を何時間も続けたセッションは、最大が 48 万と 60 万だった。48 万のセッションでは、終わった状態メッセージに
  約 40 万、46 万、48 万の行が出た。行が出たあとの依頼は、32 分で $6.68、2 分で $1.30 だった。
- ADR 0049 の前（Issue #240）は、85 万〜97 万まで増えたセッションに費用が集まっていた。
- 実際の API の呼び出しで `message.usage` に値が入り、Slack の状態メッセージに行が出ることも、この記録で確かめられた
  （ADR 0049 の Consequences では確かめていなかった）。

## Decision

- 既定の閾値は 40 万のままにし、仮の値とはしない。一つの作業のセッション（32 万まで）には出ず、いくつもの作業を続けた
  セッションには出て、#240 の 85 万〜97 万に届く前に知らせられている。
- 閾値を超えても、control-plane は自動で締めることも、新しいセッションに切り替えることもしない。知らせるだけにする。

## Alternatives

- **閾値を超えたら control-plane が自動で締めるか、新しいセッションに切り替える**：依頼者が頼まなくても費用が下がる。
  ただ、作業の区切りは依頼者とエージェントにしか分からず、途中の作業（開いている PR、レビューの往復）を切りうる。
  締めはスレッドの会話を捨てることなので、依頼者が決める。
- **閾値を下げる（30 万など）**：早く知らせられるが、一つの作業を続けるだけのセッション（32 万まで）にも出て、締める
  区切りでないときの知らせが増える。
- **閾値を上げる（60 万など）**：知らせは減るが、行が出たあとの 1 回あたりの費用がそれだけ大きくなってから知らせる
  ことになる。48 万のセッションには出なかった。
- **記録がもっと増えるまで仮のままにする**：1 日の記録だけだが、一つの作業とそうでないものの分かれ目は 32 万と 48 万の
  あいだにはっきり出ている。設定で変えられるので、合わなくなったら決め直す。

## Consequences

- `acp.example.yaml` と `internal/adapter/config` の既定値は変えない。
- 見たのは 2026-10-25 の 1 日の記録で、`usage_log` の `context_tokens` は読んでいない（ホストのデータベースにあり、
  エージェントのコンテナからは読めない）。作業の進め方が変わり、一つの作業でも 40 万を超えるようになったら、
  決め直す。
