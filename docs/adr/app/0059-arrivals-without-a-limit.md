# 0059. ワーカーの受け取り待ちの依頼は、数で断らず、依頼ごとの停止ではそれだけを取り消す

## Context

`Dispatcher` はワーカーに依頼を 32 件までのチャネル（受信箱）で渡していた。ワーカーはふだんすぐ受け取って上限のない
待ち行列に移すので、チャネルがいっぱいになるのは、ワーカーが受け取れない間（エージェントを起動しているときなど）
だけだった。そのため、次の三つの例外が受信箱で起きていた（Issue #286 に PR #296 と #298 のレビューから積まれていた）。

- 受け取れない間だけ、33 件目からの依頼を断る（`ErrInboxFull`、HTTP API の `inbox_full`、Slack の文面）。ふだんは上限が
  ないので、同じ数の依頼が、届いた時によって断られたり断られなかったりする。
- 依頼ごとの停止（ADR 0039）で、ワーカーは止める依頼を探す前にチャネルの依頼を受け取り、ターンがあれば流し込む依頼を
  エージェントに送っていた。そのため、まだ送っていない流し込む依頼を止めると、送ってから止めることになり、前の依頼の
  作業（実行中のターン）も止まった。
- 文書の「受信箱」が、ADR ではチャネルと待ち行列を合わせたもの、構成の説明ではチャネルだけを指していた。

## Decision

- `Dispatcher` からワーカーへは、上限のない一覧（受け取り待ちの依頼）で渡す。ワーカーは知らせを受けて、来た順に一つずつ受け取る。
  依頼を数で断ることはなくし、`ErrInboxFull`、`inbox_full`、その文面を消す。
- 依頼ごとの停止で、止める依頼がまだ受け取り待ちなら、`Dispatcher.StopRequest` が同じロックの下でそれだけを取り消す。
  ワーカーには渡さないので、流し込む依頼が送られて作業を止めることはない。
- 文書では、ワーカーがまだ受け取っていない依頼を「受け取り待ちの依頼」と呼び、「受信箱」は使わない。ふつうの言葉の
  「届いた」は状態の名前にしない。ADR の「受信箱」は、受け取り待ちと待ち行列を合わせたものと読む。コードの名前は `arrivals`。
- セッションの停止（`Stop`）が受け取り待ちの依頼を取り消すかは変えない（Issue #288 で確かめる）。

## Alternatives

- **チャネルを大きくする**：上限がある限り、受け取れない間だけ断る例外は残る。
- **ワーカーが止める依頼を探す前に受け取り待ちの依頼を受け取り、止める依頼だけは送らない**：ワーカーが停止と受け取り
  待ちの依頼のどちらを先に受けるかで結果が変わり（select の選び方）、受け取って送ったあとに停止が来ると、同じ例外が
  起きる。ロックの下で `Dispatcher` が取り消し、ワーカーは一つずつ受け取れば、順によらない（まとめて受け取ると、
  前の依頼を送る間に後ろの依頼が受け取り待ちでなくなる）。
- **待ち行列にも受け取り待ちにも上限を持たせ、ふだんも断る**：依頼できるのは `allowed_users` の人と API トークンを持つ
  人だけなので、今は持たせない。Bot どうしの依頼を入れるときに見直す（Issue #25）。
