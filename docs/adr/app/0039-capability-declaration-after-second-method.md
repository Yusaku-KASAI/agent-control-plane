# 0039. 外部の認証の機能を宣言して割り当てる仕組みは、二つ目の提供方式が要るまで作らない

## Context

ADR 0006 は、拡張が外部サービスの機能を必須とあれば使うものに分けて宣言し、どの方式で提供するかを control-plane
が環境ごとに割り当てるとした。必須の機能がそろわない環境では、その拡張を有効にしない。

今の control-plane には、機能を宣言する仕組みも割り当てる仕組みもない（Issue #75）。

- 外部サービスごとに提供方式は一つだけで、エージェントの設定（`agents[].github`、`agents[].slack`）があれば
  その認証情報を発行して渡す。どれも任意で、Claude Code の認証だけは必ずある。
- 拡張は、渡された認証情報の有無で使える機能を決める。たとえば slack プラグインは、`SLACK_BOT_TOKEN_FILE` が
  あれば読み書きし、なければ人が用意した代わりの手段（`SLACK_WEBHOOK_URL` など）を使う。
- 使っているのは依頼者一人の手元だけで、環境は一つしかない。

## Decision

- 機能の宣言と割り当ての仕組みは、同じ外部サービスに二つ目の提供方式（MCP、webhook など）を control-plane が
  渡す必要が出るまで作らない。そのときに ADR 0006 の形で作る（Issue #26）。
- それまでは、control-plane はエージェントの設定にある外部サービスの認証情報を渡し、何を渡すかはハーネスの契約に
  書く。拡張は、渡された認証情報の組み合わせで動きを変える（ADR 0006 のこの点は変えない）。
- 必須の認証情報がないときに拡張を無効にする仕組みは持たない。拡張は、使えない操作を頼まれたら、使えないと
  答える。

## Alternatives

- **今、宣言と割り当ての仕組みを作る**：提供方式が一つずつしかないので、割り当てる選択肢がない。使う場面が
  来る前に形を決めると、実際の方式の違い（MCP は読めるが投稿したメッセージを特定できない、など）に合わない
  おそれがある（使ってから共通にする）。
- **ADR 0006 を置き換えて、機能の宣言をやめる**：環境が増えれば、同じ拡張を方式の違う環境で動かす要は残る。
  方向は残し、作る時期だけを決める。

## Consequences

- control-plane に、機能と提供方式の対応を管理するものは要らない。外部サービスを足すときは、発行元を一つ足す。
- 拡張が要る認証情報を受け取ったかは、拡張が動いて初めて分かる。設定の抜けは起動時に見つからない。
