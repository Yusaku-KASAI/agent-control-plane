# 0055. 依頼を待つ人のいないターンの回答をどう出すかは、usecase の AgentAnswers が決める

## Context

エージェントが自分で始めたターンの回答を、出すか、持つか、捨てるか（ADR 0028、0029）と、中断の知らせの文面（ADR 0024）
は、Slack のアダプター（`slackbot/status.go`）が、状態メッセージを書き換える処理と同じ所で判定していた。層の決まりは
アダプターに判定を置かないとしている（`layers.md`）。判定は Slack の状態メッセージの持ち物（持っておいた回答、15 秒の
待ち）に結びつき、ほかの入口では使えず、試験も Bot を通すものだった（Issue #286、#283 の H）。

## Decision

- 判定を usecase の `AgentAnswers`（`agent_answers.go`）に移す。`AgentAnswers` は `SessionObserver` を満たして
  `sessionObserver` を包み、出来事をそのまま渡したあとで、出すと決めた文面を `SessionNotice` として渡す。持っておいた
  回答、15 秒の待ち、使用上限を知らせたかも、ここが持つ。
- Bot は、状態メッセージを見せることと、`SessionNotice` の文面を投稿することだけを持つ。
- 止まるときは、`Dispatcher.Close` が最後の出来事のあとに `AgentAnswers.Flush`（`ObserverFlusher`）を呼び、待っている回答を出す。Bot の書き込みの待ちより前に必ず通る。`Flush` を `SessionObserver` の契約に含めず、任意のインターフェースにするのは、
  持っておくものを持たない observer（`sessionObserver` や試験の偽物）に、何もしない `Flush` を持たせないため。
  `AgentAnswers` がそれを満たすことはコンパイルで確かめる。
- 振る舞いは変えない。

## Alternatives

- **判定を純粋な関数にして usecase に置き、Bot が状態と待ちを持って呼ぶ**：判定は usecase に移るが、持っておいた回答と
  待ちのタイマーがアダプターに残り、アダプターが判定の結果に合わせて状態を書く。状態と判定を一か所に置く方がよい。
- **判定をワーカーに置く**：ワーカーはすでにプロセス、依頼とターン、認証情報、使用量を持つ（Issue #286）。知らせの判定は
  ワーカーの状態を見ず、ワーカーが出す出来事だけで決まるので、出来事の受け手の側に分ける。
- **決めた文面を、出来事（`SessionEvent`）でなく投稿の別のポートで渡す**：出来事の型に、事実でない投稿の指示が
  混ざらずに済む。ただし、今ある投稿のポート（`SessionNotifier`）は同期で、Bot の書き込みの待ち（`Wait`）に乗らない
  ので、止まるときに出す回答の保証の経路が二つになる。状態メッセージの書き換えと同じ経路で、出来事と同じ順に届く
  方を選んだ。
- **文面と記号をどの層が持つかを `layers.md` に決め、判定はアダプターに残す**：持つか捨てるかは Slack に固有ではなく、
  チャットに知らせる入口ならどれにも要る。
