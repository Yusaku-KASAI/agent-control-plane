# 0043. 片付けの判定で作業領域を読む git は、エージェントのイメージの使い捨てのコンテナで、ネットワークも認証情報もなしに期限つきで回す

## Context

片付けの判定（ADR 0026）は、作業領域の状態（作業ツリーの変更、stash、途中の操作、push したブランチ、ローカルの
ブランチ）を、control-plane のプロセスから git で読んでいた。作業領域はエージェントが書ける。git は、グローバルと
システムの設定を外しても、リポジトリの設定（`.git/config`、linked worktree の `config.worktree`）を読み、そこに
名指されたコマンドを動かす（`core.fsmonitor`、`.gitattributes` と組むフィルタの `clean` と `process` など）。
そのため、エージェントが書いた設定のコマンドが、control-plane のプロセスとして、コンテナの隔離の外で動きえた
（#226。`core.fsmonitor` はレビューで確かめた）。control-plane のコンテナには、GitHub App の秘密鍵などの秘密の
ファイルがマウントされている。ほかにも、`core.worktree` で作業領域の外を作業ツリーとして読ませられ、作業領域の
ファイルを名前付きパイプにすると、git も Go の読みも止まり、期限のない片付けのループごと止まる。

control-plane が作業領域で git を回すのは、この判定と、セッションを作るときの clone と fetch（`Prepare`）だけ。
`Prepare` は記録のないときに新しい clone にだけ回り、エージェントが書く前に終わるので、ここでは扱わない。

## Decision

- 作業領域の状態は、片付けの判定のたびに、使い捨てのコンテナで読む。
  - イメージは、そのセッションのエージェントのターゲットのイメージ（git があることはターゲットの契約）。
  - 中で動かすのは control-plane 自身のバイナリの `acp workspace-state`。作業ディレクトリの作業領域の状態を、今までと
    同じ読み方（`gitworkspace` の `State`）で読み、JSON で出す。
  - 作業領域は、エージェントのコンテナと同じ `/workspace/<ターゲットのディレクトリ名>` に読み取り専用でマウントする。
    git がエージェントのコンテナで記録したパスが、そのまま開ける。
  - ネットワークなし、ケーパビリティなし、`no-new-privileges`、読み取り専用のルート。認証情報も環境変数も渡さない。
  - 期限は 2 分。過ぎたらエラーにして、そのセッションはその回は判定しない（GitHub の API が失敗したときと同じ）。
    どの終わり方でもコンテナを消す。`acp serve` の起動時の残りの片付けでも、ラベル `acp.workspace-state` のものを消す。
- control-plane は、起動のたびに自分のバイナリを `tools.dir`（ボリュームは `tools.volume`、compose では `acp-tools`）に
  置き、そのコンテナに `/run/acp/bin` として読み取り専用でマウントする。#224（エージェントが判定を見るコマンド）でも、
  同じ置き場をエージェントのコンテナに渡せる。
- 作業領域を読む事実と判定の分け方は変えない。コンテナが返すのは事実だけで、判定は usecase の `reasons` が行う。
- コンテナの中ではエージェントが設定に書いたコマンドも動くので、返る事実（と、知らせの文面に入るブランチの名前）は
  エージェントが左右できるものとして扱う。判定がそれで決めるのは、そのセッション自身のもの（そのセッションの作業
  領域と、そのセッションが持つ名前のブランチ）を残すか消すかだけで、エージェントはそれらをどのみち自分で消せる。
  ほかのものに触れる判断には使わない。読む出力は、標準出力 4 MiB、標準エラー 16 KiB までにする。返る事実のうち、
  GitHub の API のパスと知らせの文面に入るもの（ブランチの名前、コミット、途中の操作）は、git が書きうる形
  （ブランチの名前の決まり、16 進のコミット、知っている操作）か確かめ、外れたらその回は判定しない。
- ターゲットのイメージは、エントリポイントを上書きされ、読み取り専用のルート、ネットワークなし、イメージのユーザーで
  git を動かせればよい。ターゲットの契約の「イメージ」に書く。

## Alternatives

- **control-plane の git に、コマンドを動かす設定を打ち消す値を渡す**（`core.fsmonitor=false` など）：フィルタは名前ごと
  に決まり、打ち消す値を前もって並べられない。設定を読んでから打ち消すと、読んでから動かすまでの間に書き換えられる。
  `core.worktree`、`commondir`、名前付きパイプも別々に塞ぐことになり、知らない道が残る。
- **git の代わりに、外のコマンドを動かさない git の実装（Go のライブラリなど）で読む**：無視の規則や worktree の
  扱いが git と違いうる。読みが止まる道も別に塞ぐ必要がある。依存も増える。
- **control-plane のイメージでコンテナを起こす**：git と `acp` が入っていてバイナリを置かずに済むが、control-plane が
  自分のイメージの名前を知る必要がある。エージェントが worktree を作った git と版が違いうる。#224 でエージェントの
  コンテナにもバイナリを渡すので、置き場はどのみち要る。
- **control-plane のプロセスの中で、別のユーザーや名前空間に落として回す**：control-plane のコンテナに秘密のファイルが
  あり、隔離を自分で組むことになる。Docker の隔離を使う方が確か。
- **判定のたびではなく、エージェントのコンテナが止まる前に状態を書き出させる**：エージェントが書いた結果を信じる
  ことになり、止まり方（強制の削除など）によっては書かれない。

## Consequences

- 判定のたびに、期限が過ぎたセッションごとにコンテナを一つ起こす。片付けは 1 時間ごとで、判定するのは保持期間を
  過ぎたセッションだけなので、数は少ない。
- 片付けは、エージェントのターゲットのイメージが手元にあることを前提にする。イメージを消したエージェントのセッションは、
  判定に失敗し、その回は消されない（エラーとして記録される）。
- `acp.yaml` に `tools` が要る。ない設定では `acp serve` が起動しない。compose の `acp-tools` ボリュームも要る。
  置き場はスティッキーにせず、`ACP_UID` を変えても前のバイナリを置き換えられるようにする。
- control-plane とターゲットのイメージは同じアーキテクチャで動く前提になる（同じ Docker の上で動くので、ふつうは同じ）。
  バイナリは静的にビルドしている（`Dockerfile` の `CGO_ENABLED=0`）。
- ADR 0042 の、記録されたパスの末尾で worktree を探す処理は、コンテナの中では記録がそのまま当たるので、最も長い末尾
  （記録そのもの）で見つかる。作業領域の外に出る在りかを使わない確かめは、そのまま残す。
