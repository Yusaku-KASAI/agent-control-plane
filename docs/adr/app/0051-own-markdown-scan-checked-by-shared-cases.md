# 0051. Slack に投稿する前の Markdown の直しは、パーサーに置き換えず、slack プラグインの検知と同じ例で確かめる

## Context

control-plane は、Slack に投稿する前に、裸の URL を `<…>` で囲み、文字の行のすぐ下の表の前に空行を足す
（ADR 0050）。直す場所は、行ごとの手書きの走査で見つける。ADR 0050 は、パーサーを選ばなかった理由に「直す形が
増えるか、走査の誤りが続くなら、そのときに置き換える」と書いた。

そのあと、走査の誤りが続いた（#258）。PR #249 と #257 のレビューで、リンクの表示の文の中の URL、閉じない `[`、URL の
中の URL、引用やリストの記号の後ろのフェンス、フェンスの中の `- ```` の行、クエリの角括弧などを直した。残っていたのは、
引用やリストの項目の中で閉じを書き忘れたフェンスが、メッセージの最後まで開いたままになることだった。

slack プラグインには、Slack で崩れる形を見つける `check-markdown`（Python）ができた（platform の ADR 0028）。同じ
見分け（コード、フェンス、リンク）を Go と Python の二か所で手で書いていて、二つが同じに読むかを確かめる試験はなかった。

依頼者は、一般的な Markdown ではなく Slack に特有の読み方があるなら、ライブラリの実装の中身も参考にしつつ、個別に
実装すればよい、と考えた（2026-10-25）。

## Decision

- 直しは、パーサーのライブラリに置き換えず、手書きの走査のまま保つ。誤りの元だった見分けは、CommonMark の規則に
  倣って直す。
  - コードブロックは、閉じの行まで続く。間の行がどの引用とリストの項目にあるかは見ない。引用の印のない行や、
    ヒアドキュメントの `EOF` のような字下げできない行も、コードとして読む。閉じの行がどこにもないフェンスだけ、
    CommonMark に倣い、引用の中のものは引用が終わると（引用の印の少ない行）、リストの項目の中のものはその項目が
    終わると閉じる。閉じを書き忘れても、そのあとの本文を直す。
  - 閉じのないフェンスの項目の終わりは、ブロックを持つ項目の兄弟（項目の内容より浅く字下げした、同じ桁の同じ種類の
    印。箇条書きは同じ記号、番号付きは同じ区切り）の行にする。ほかの浅い行は、コードの続きとみなす。
  - リストの項目は、項目の印の行から印の桁と種類と内容の字下げを取って追い、内容より浅い文字の行で終わるとみなす。
    CommonMark では字下げのない続きの行（遅延の続き）も項目に入るが、それも項目の終わりとみなす。
  - 引用の中のリストは引用ごとに追い、リストの項目の中の引用が終わると、その項目の読みに戻る。
  - フェンスの印の前の引用の印と項目の印は、順を問わずに読む（`- > ````）。字下げのタブは、次の 4 の倍数の桁まで
    進める。
  - slack プラグインの `check-markdown` も、同じ規則で読む（[platform の ADR 0029](../../../platform/docs/adr/0029-check-markdown-follows-commonmark-on-shared-cases.md)）。
  - 参照形式のリンク（`[…][…]`）は、今のまま表示の文とみなし、中の URL を変えない。Slack の markdown ブロックが
    参照形式を読むかは確かめていない。エージェントが書くことはまれで、読まないとしても、URL が囲まれずに残るだけで
    文は壊れない。
- 二つが同じに読むことは、control-plane の試験で確かめる。slack プラグインの例の一覧（`tests/markdown-cases.json`。
  文と、`check-markdown` が知らせる行）の文をすべて直し、直した文が control-plane の試験に書いた期待と合うことと、
  直した文に `check-markdown` が裸の URL とすぐ上が文字の行の表を知らせないことを確かめる。
- 一覧の持ち主は slack プラグインにし、control-plane の振る舞い（直した文）は一覧に置かない。control-plane は
  プラグインを前提にしてよいが、逆は前提にしない。区切りの間で値が合っていることの試験は、両側を前提にしてよい
  control-plane に置く（conventions の「検査にするものと置き場所」）。

## Alternatives

- **パーサーのライブラリ（goldmark など）で直す場所を見つける**：構文の見分けはライブラリが正しく持つ。ただ、依存が
  一つ増え、構文木から元の文の位置へ戻すには節ごとの扱いが要り、URL の終わりは Slack に合わせて自分で決めるので
  自動リンクの規則も使えない（ADR 0050）。直す形は二つのままで、誤りは規則を倣えば直せる種類だった。Python の側にも
  同じ見分けが要るので、二つの言語でライブラリをそろえることにもなる。
- **直しも検知も一か所（slackctl か control-plane）に置き、もう一方はそれを呼ぶ**：見分けが一つになる。ただ、
  control-plane は Go のライブラリで投稿し、プラグインのコマンドを呼ぶ形にはしていない（ADR 0050 の Alternatives）。
  エージェントは control-plane を通らずに `slackctl post` で投稿する（platform の ADR 0028）。二つの処理を残し、同じ
  例で確かめる方が、今の置き場所を変えずに食い違いを止められる。
- **一覧に直した文も置き、両側の試験がそれぞれ読む**：どちらの試験も自分の言語の中で済み、Go の試験が python3 に
  頼らない。ただ、platform が control-plane の振る舞いを持ち、control-plane の直しを変えるたびにプラグインの例と試験を
  直すことになり、前提の向きに反する。control-plane の試験は、すでに platform を前提にしてよく、検査の環境には
  python3 がある。
- **遅延の続きまで CommonMark どおりに追う**：段落の続きかどうかを見分ける必要があり、走査が大きくなる。遅延の続きの
  あとに字下げしたフェンスを書くことはまれなので、足りない例が出たら考える。
- **閉じの行のあるフェンスも、CommonMark どおり引用やリストの項目の終わりで閉じる**：CommonMark に忠実になるが、
  閉じの行のあるフェンスの中に、引用の印のない行や、項目より浅い行（ヒアドキュメントの `EOF`、その中のリスト）が
  あると、そこでブロックが閉じ、書き手の閉じの行が新しいフェンスを開いて、あとの本文をすべてコードとして読む。
  レビューで、こうした後退が形を変えて続いた。閉じの行まではコードとする読み（ADR 0050 のまま）は、閉じたフェンスを
  誤らない。Slack はリストの項目の中のフェンスをコードブロックとして読まないので、そこで CommonMark に合わせる理由も
  弱い。

## Consequences

- 閉じのあるフェンスの読みは ADR 0050 のときと変わらない。閉じのないフェンスの中に、あとのフェンスの閉じと同じ
  形の行があると、そこまでをコードとして読む（ADR 0050 のときと同じ）。
- 閉じのないフェンスは、次の兄弟の項目の印の行か引用の終わりまで開いたままになる。そのあいだの字下げのない本文は、
  コードとして読む。兄弟の項目と同じ形の行をコードの中に字下げせずに書くと、閉じ忘れと見分けられない。
- 引用やリストの項目の中で閉じを書き忘れたフェンスのあとも、URL と表を直す。`check-markdown` も、そのあとを読む。
- 直す形か見つける形を変えるときは、`tests/markdown-cases.json` に例を足し、control-plane の試験と slackctl の試験の
  両方を通す。control-plane が直す例の期待は、control-plane の試験に、例の名前で書く。
- control-plane の試験（`go test`）は、python3 で `check-markdown` を動かす。
