# 0027. 既定のブランチのルールセットで、PR に承認を 1 件求め、バイパスは管理者に PR のときだけ許す

## Context

ADR 0025 は、既定のブランチへの変更を PR 経由に限り、PR は人が確かめてからマージするとした。ルールセットは
PR 経由と CI（`check`）を求めていたが、承認の数は 0 だった。PR を作るエージェント（developer）の GitHub App は
Contents と Pull requests を書けるので、その認証情報で自分の PR をマージでき、人の確認は手順の約束でしか
守られていなかった。依頼者は一人なので、依頼者が自分で作った PR を承認する人はいない。エージェントが作った PR は、
作者が App なので依頼者が承認できる。

## Decision

- 既定のブランチのルールセットで、PR に承認を 1 件求める。
- ルールセットのバイパスは、リポジトリの管理者（人）にだけ、PR のとき（for pull requests only）に限って許す。
  既定のブランチへの直接の push はバイパスさせない。バイパスは必須の検査（`check`）も飛ばすので、バイパスする
  ときは人が検査の結果を見てからマージする。

## Alternatives

- **承認を求めず、人の確認を手順で守る**：エージェントの認証情報だけでマージでき、手順を誤ると人の目を通らずに
  入る。
- **バイパスを許さない**：依頼者が自分で作った PR は、承認する人がいないのでマージできない。
- **エージェントの App から Pull requests の書き込み権限を外す**：PR を作れなくなる。

## Consequences

- 承認のない PR は、エージェントの認証情報だけではマージできない。developer は自分の PR を承認できず、
  reviewer は Contents を書けないので、その承認は数に入らない。
- 承認のあとの push で承認は取り消されず、最後の push の承認も求めていない。そのため、人が承認したあとに
  エージェントが足したコミットは、人の目を通らずにマージされうる。
- 人がマージするには、承認するか、管理者として PR のバイパスを使う。どちらも人の操作になる。
- Contents を書ける GitHub App をほかのロールに足すときは、その App の承認が数に入りうるので、承認させない
  ことを確かめる。
