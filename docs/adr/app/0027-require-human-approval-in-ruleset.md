# 0027. 既定のブランチへのマージには人の承認を求め、承認は push で取り消し、バイパスは管理者に PR のときだけ許す

## Context

ADR 0025 は、既定のブランチへの変更を PR 経由に限り、PR は人が確かめてからマージするとした。ルールセットは
PR 経由と CI（`check`）を求めていたが、承認の数は 0 だった。PR を作るエージェント（developer）の GitHub App は
Contents と Pull requests を書けるので、その認証情報で自分の PR をマージでき、人の確認は手順の約束でしか
守られていなかった。

承認の数を求めるだけでは、承認する主体を人に限れない。reviewer の GitHub App も Pull requests を書けるので
レビューで承認でき、その承認が数に入るかは App の権限次第になる。数に入れば、エージェントだけで承認とマージが
そろう。承認する主体を絞る仕組みは、リポジトリの持ち主に
よって違う。個人のリポジトリでは CODEOWNERS（コードオーナーの承認を求める）、organization のリポジトリでは
ルールセットの必須のレビュアー（team を指定する）が使える。依頼者は一人なので、依頼者が自分で作った PR を承認する
人はいない。エージェントが作った PR は、作者が App なので依頼者が承認できる。

## Decision

- 既定のブランチのルールセットで、PR に承認を 1 件求め、承認する主体を人に限る。
  - 個人のリポジトリ：`.github/CODEOWNERS` に、すべてのファイルの持ち主として人（GitHub のユーザー）だけを書き、
    ルールセットでコードオーナーの承認を求める（Require review from Code Owners）。
  - organization のリポジトリ：人だけの team を、ルールセットの必須のレビュアー（Required reviewers）に指定する。
- 新しいコミットが push されたら、それまでの承認を取り消す（Dismiss stale pull request approvals when new commits
  are pushed）。
- ルールセットのバイパスは、リポジトリの管理者（人）にだけ、PR のとき（for pull requests only）に限って許す。
  既定のブランチへの直接の push はバイパスさせない。バイパスは必須の検査（`check`）も飛ばすので、バイパスする
  ときは人が検査の結果を見てからマージする。
- ルールセットの `require_extra_approval_for_unattributed_changes` は、有効でも、この守りには数えない。

## Alternatives

- **承認を求めず、人の確認を手順で守る**：エージェントの認証情報だけでマージでき、手順を誤ると人の目を通らずに
  入る。
- **承認の数だけを求める**：App（reviewer など）の承認が数に入るかが、App の権限に左右される。
- **エージェントの App から承認できる権限を外す**：reviewer は PR にレビューを残すために Pull requests を書く
  必要があり、developer は PR を作るために要る。
- **バイパスを許さない**：依頼者が自分で作った PR は、承認する人がいないのでマージできない。
- **承認を取り消さない**：人が承認したあとにエージェントが足したコミットが、人の目を通らずにマージされうる。

## Consequences

- エージェントの認証情報だけでは、既定のブランチにマージできない。エージェントの App は CODEOWNERS の持ち主にも
  人だけの team にも入れないので、その承認はコードオーナーの承認にも必須のレビュアーの承認にも数えられない。
- CODEOWNERS は PR の base ブランチ（ここでは既定のブランチ）の版が使われるので、PR の中で CODEOWNERS を書き換えても、
  その PR の承認の条件は変わらない。CODEOWNERS を変える PR も、人の承認がないとマージできない。
- CODEOWNERS の行が誤っている、持ち主の名前が変わった、持ち主が書き込みの権限を失った、のどれでも、その行は黙って
  無視され、コードオーナーの承認が求められなくなる。守りが外れる側に倒れるので、CODEOWNERS を変えたら
  `gh api repos/<owner>/<repo>/codeowners/errors` で誤りがないことを確かめる。
- 人が承認したあとにエージェントがコミットを足すと承認が取り消されるので、マージには足したコミットを含めた承認が
  もう一度要る。
- 人がマージするには、承認するか、管理者として PR のバイパスを使う。どちらも人の操作になる。
- ターゲットごとに、持ち主に合わせて CODEOWNERS かレビュアーの team を用意し、ルールセットを合わせる必要がある。
