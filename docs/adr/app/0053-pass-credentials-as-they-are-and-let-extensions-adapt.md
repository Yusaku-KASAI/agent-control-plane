# 0053. 外部サービスの認証情報は、外部サービスごとに一つの方式で渡し、拡張は渡されたものの有無で動きを変える

## Context

ADR 0006 は、拡張が要る機能（Slack の読み取り、投稿、スレッドへの返信など）を宣言し、どの方式（Bot トークン、
MCP、Webhook など）で提供するかを control-plane が環境ごとに割り当てると決めた。その仕組みは作っておらず、
今の姿は次のとおり。

- control-plane が渡す外部サービスの認証情報は、外部サービスごとに一つの方式だけ（GitHub は GitHub App の
  インストールトークン、Slack は Slack アプリの Bot トークン）。エージェントごとに設定がなければ渡さない。
- 拡張は、渡された認証情報の有無で使える操作を決める。slack プラグインは `SLACK_BOT_TOKEN_FILE` があれば
  Web API を使い、人が対話で使うときは自分で用意した `SLACK_BOT_TOKEN` や `SLACK_WEBHOOK_URL` も読む。
- 使っているのは依頼者一人で、外部サービスごとに方式を選び分ける環境はない。

決めたことが今の姿と違うので、全体像（`docs/overview.md`）が実装のない考え方を掲げていた。

## Decision

- control-plane は、外部サービスごとに一つの方式で、エージェントごとに設定された認証情報を渡す。渡さないものの
  環境変数は設定しない（ハーネスの契約の認証情報）。
- 拡張は、機能を宣言しない。渡された認証情報（と、人が対話で用意したもの）の有無を見て、使える操作を決める。
- 機能と提供方式の対応を管理する仕組みは、control-plane に置かない。

## Alternatives

- **ADR 0006 を目指す姿として残す**：方式を選び分ける要る環境が今はなく、実装のない考え方を全体像に並べ続ける
  ことになる。要る環境が出たら、そのときに決め直せばよい。
- **ADR 0006 の仕組みを作る**：機能の宣言、割り当て、伝え方の三つの仕組みが要るが、使う場面がない。

## Consequences

- 外部サービスに新しい方式を足すときは、control-plane の発行元と、拡張の「何があれば何ができるか」の両方を
  直す。
- 拡張が要る認証情報がない環境では、拡張がその操作を断る（拡張ごと無効にはならない）。
