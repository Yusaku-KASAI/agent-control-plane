# 0035. セッションのロックは、ストアの中で持ち、flock は重ねて取る

## Context

ADR 0009 で、同じセッションのターンは同時に一つだけ実行し、ファイルロックで守ると決めた。ロックは
`<sessions.root>/<ID>/.lock` への flock で、セッションを作る間（Dispatcher）、ワーカーが動いている間、片付けが
消す間に取る。`sessions.root` は `ACP_HOST_ROOT` の下に置き、`compose.yaml` はそれをホストのディレクトリの
bind mount にする（ADR 0014）。

Docker Desktop の bind mount（fakeowner）の上では、flock が取り合いにならない。2026-10-17 に、手元の
control-plane のコンテナで `sessions.root` が fakeowner であることを確かめた。エージェントのコンテナの作業領域
（同じ種類のマウント）で、別のプロセスの間でも、一つのプロセスが別々に開いた二つの記述子の間でも、二つ目の
flock が取れることを確かめた。手元では、ロックが何も守っていなかった（Issue #158）。

セッションの記録を読み書きするのは `acp serve` の一つのプロセスだけである（ADR 0014 で、CLI が直接実行する
形をなくした）。

## Decision

- ストア（`internal/adapter/filesession` の `Store`）は、セッションの ID ごとに、誰が持っているかを覚える。
  持たれていれば、flock を取りにいかずに、使われていると返す。これが守るのは一つのストアの中なので、`acp serve` は
  ストアを一つだけ作り、セッションを作る処理（Dispatcher）と片付けに同じものを渡す。
- flock は今までどおり重ねて取る。flock が効くファイルシステムでは、ほかのプロセス（誤って二つ動かした
  `acp serve` など）とも取り合いになる。どちらのロックも、プロセスが落ちれば残らない。
- 持ち主は、ロックを取るたびに作る印で見分ける。`Remove` がディレクトリを移したら、その ID を手放したことに
  する。古い持ち主がロックを外しても、そのあとに取った新しい持ち主を外さない。移したファイルの flock が新しい
  セッションに及ばないのと同じ振る舞いにする。
- 試験では、flock が何もしないファイルシステム（fakeowner）を、flock を差し替えて作り、それでも二つ目が断られる
  ことを確かめる。

## Alternatives

- **ロックのファイルを bind mount の外（control-plane のコンテナのボリューム）に置く**：flock だけで守れるが、
  セッションのディレクトリとロックの置き場所が分かれ、消したセッションのロックのファイルの片付けが要る。
  一つのプロセスが一つのストアだけを使う今は、ストアの中のロックで足りる。
- **ストアの中のロックだけにし、flock をやめる**：flock が効く所でも、二つ目のプロセスを止められなくなる。
  取るのは手間ではないので重ねる（多層の防御）。
- **`sessions.root` を bind mount ではなくボリュームにする**：作業領域はエージェントのコンテナにホストのパスで
  マウントするので、ホストのディレクトリに置く必要がある（ADR 0014）。

## Consequences

- 手元（Docker Desktop）でも、同じセッションのターンと片付けが重ならない。
- `acp serve` を二つ動かすと、fakeowner の上では、二つの間は守られない。二つ動かすことは想定しない。
- ストアを使うプロセスやストアが増えるとき（別のコマンドが記録を書く、構成要素ごとにストアを作るなど）は、この決定を
  見直す。
