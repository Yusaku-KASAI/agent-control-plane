# 0042. 片付けの判定で、作業領域の中のほかの worktree の作業ツリーの変更、途中の操作、detached HEAD も見る

## Context

片付けの判定（ADR 0026）は、作業ツリーの変更、途中の操作、detached HEAD を、作業領域の主の worktree でしか見て
いなかった。サブエージェントが `isolation: worktree` で作る worktree（作業領域の中の `.claude/worktrees/` の下。
ターゲットの `.gitignore` で ignore する）は、変更があると残る。そこにコミットしていない変更や、detached HEAD の
コミットを残したまま保持期間が過ぎると、作業領域ごと消えていた。worktree のブランチは `refs/heads` にあるので、
そこにコミットした作業は、今までもローカルのブランチとして見ていた。

git は worktree のパスを絶対パスで記録する。worktree を作るのはエージェントのコンテナの中なので、記録された
パスはコンテナから見たもの（`/workspace/<名前>/...`）で、control-plane から見た作業領域のパスとは違う。そのため
`git worktree list` のパスでも、worktree の `.git` ファイルでも、control-plane からは worktree を開けない。

## Decision

- 作業ツリーの変更、途中の操作は、主の worktree と、作業領域の中にある、ほかの worktree のどれかにあれば「ある」とする。
  detached HEAD は、主の worktree と、作業領域の中にあるほかの worktree のそれぞれで見て、ほかにないコミットを持つ
  ものを加える。
- ほかの worktree は、主のリポジトリの `.git/worktrees/<名前>`（管理ディレクトリ）から見つける。記録されたパスの
  末尾のうち、作業領域の下にあって、その `.git` ファイルが同じ管理ディレクトリを指す最も長いものを、その worktree の
  ファイルの在りかとする。git には `--git-dir`（管理ディレクトリ）と `--work-tree`（見つけた在りか）で渡す。
- 記録はエージェントが書けるので、`..` とシンボリックリンクをたどったあとに作業領域の外に出る在りかは使わない。
  ほかの worktree の記録から、外の場所を `--work-tree` にして control-plane の git に読ませないため。リポジトリの
  設定（`core.worktree` など）や `commondir` から外を読ませる道は、ほかの worktree によらずあり、作業領域の設定を
  control-plane の git がどう扱うか（#226）で扱う。
- `HEAD` のない管理ディレクトリ（途中で止まった `git worktree add` の残りなど）は、git が worktree とみなさないので
  見ない。
- 在りかが見つからない worktree（ファイルを消したもの、作業領域の外にあるもの）は、作業ツリーの変更、途中の操作、
  detached HEAD のどれも見ない。作業領域の外の worktree は、`prctl worktree pr` が PR を読むためにコンテナの
  `/tmp` に作るものがふつうで、その detached HEAD はほかの人の PR のコミットを持つ。数えると、スカッシュでマージされた
  か閉じた PR のコミットで、セッションが残り続ける。
- 残す理由は変えない。作業ツリーの変更、途中の操作、detached HEAD の知らせの文面に、サブエージェントなどの
  worktree を含むことを書き、主の worktree のほかも見ることを示す。

## Alternatives

- **`git worktree list --porcelain` のパスを使う**：コンテナから見たパスなので、control-plane では開けない。
- **ハーネスの契約の作業ディレクトリ（`/workspace/<名前>`）を前提にして、記録されたパスの頭を外す**：おとりの
  `.git` ファイルを見分ける処理が要らず、より単純になる。ただ、作業領域のアダプタが、コンテナでのマウントの形を
  前提にすることになり、作業ディレクトリの形を変えると、それまでに作った worktree が読めなくなる。末尾で探す形は、
  マウントの形を知らずに読め、作業ディレクトリが変わっても読める。
- **worktree を相対パスで記録させる（`worktree.useRelativePaths`）**：git 2.48 から。control-plane のイメージと
  ターゲットのイメージの git（Debian trixie は 2.47）では使えず、ターゲットのイメージにも条件を課す。
- **管理ディレクトリが残っていれば、中を読まずに残す**：Claude Code は変更のない worktree を消すので、残っていること
  自体が手がかりになり、エージェントが書ける記録をたどらずに済む。ただ、コミットを残しただけの worktree や、
  `prctl worktree pr` の消し忘れでも残り、残し過ぎる。
- **作業領域をコンテナの中でもホストと同じパスにマウントし、記録をそのまま使う**：ハーネスの契約の作業ディレクトリ
  （`/workspace/<名前>`）を変え、docker のアダプタに条件を課し、ホストのパスがエージェントに見える。
- **作業領域の外の worktree の detached HEAD も、GitHub に問い合わせて見る**：detached HEAD には名前がなく、ブランチと
  同じ問い合わせ（同じ名前のブランチの PR）ができない。フォークからの PR のコミットは、どこに入っているかを決められない。
- **判定の git を、エージェントと同じ形に作業領域をマウントした使い捨てのコンテナで回す**：記録されたパスがその
  まま開け、作業領域の設定のコマンドもコンテナの中で動く（#226）。ただ、片付けのたびにセッションごとにコンテナを
  起こす重さと、片付けが docker とターゲットのイメージに依ることになる。#226 でこの形を選ぶなら、在りかを末尾で
  探す処理は要らなくなる。
- **ほかの worktree は見ずに、締めの手順でエージェントが消す**：締めを頼まれないまま保持期間が過ぎたセッションでは
  失われる。判定を一か所に置くことにも合わない（#220）。

## Consequences

- 変更を残したサブエージェントの worktree があるセッションは、その変更を片付けるまで残る。隔離して動くロール（guide、
  reviewer、pm）が自分の worktree に試しの編集を残したときも残る。
- 作業領域の中のほかの場所にコピーした worktree などで、`.git` ファイルが同じ管理ディレクトリを指すものが二つあると、
  長い方の末尾で見つかったものだけを見る。
- worktree を作業領域の外に作ったときは、その作業ツリーはコンテナの書き込み層にあり、片付けを待たずにコンテナを
  消すと失われる。control-plane からは読めないので、見ない。そこで detached HEAD にだけ作ったコミットも見ず、
  作業領域を消すと失われる。作業領域の中の worktree でも、ファイルを消したあとは同じ。
