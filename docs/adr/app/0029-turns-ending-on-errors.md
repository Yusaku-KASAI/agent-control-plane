# 0029. エージェントがエラーで終えたターンを失敗として知らせ、使用上限で止まったことを書き分ける

## Context

control-plane は、ターンの結果を stream-json の `result` の `subtype` だけで見ていた。Claude Code は、API の要求が
断られてターンを終えたときも `subtype` を `success` にし、`is_error` を立て、`result` に断られた理由の文面を入れる。
そのため、使用上限で止まったターンも成功として扱い、状態メッセージは「完了」になり、上限の文面がふつうの回答として
返っていた。

Claude Code（2.1.292）は、アカウントの使用上限の状態が変わると `rate_limit_event` を出す。`rate_limit_info.status` が
`rejected` なら要求が断られている。戻る時刻（`resetsAt`）と上限の種類も載る。上限で止まったときの `result` の文面
（例：`You've hit your session limit · resets 2pm (Asia/Tokyo)`）は、戻る時刻を依頼者の時刻で含む。

## Decision

- `result` の `is_error` が立っているか、`subtype` が `error` で始まる（`error_during_execution` は中断として扱うので除く）
  ターンを、エラーで終わったターンとする。
- 最後に受けた `rate_limit_event` が `rejected` のままエラーで終わったターンを、使用上限で止まったターンとする。
- エラーで終わったターンは、状態メッセージで失敗（使用上限なら「使用上限で停止」）と示す。依頼への返事と、
  エージェントが自分で始めたターンの知らせには、エラーであることと、エージェントの文面（上限なら戻る時刻を含む）を
  書く。上限のときは、戻ったあとにもう一度依頼すれば続きから進むことを添える。
- HTTP API の応答には `error` と `usage_limited` を載せ、`acp run` は終了コード 1 で終わる。
- 上限が戻ったときに自動で再開することは、ここでは決めない（定期実行と同じ「決めた時刻にエージェントを起こす」
  仕組みとして、あわせて決める）。

## Alternatives

- **`result` の文面で上限かを判定する**：文面は言い回しが変わる。`rate_limit_event` の状態という構造化された事実で
  決める方が確か。
- **戻る時刻を `resetsAt` から control-plane が書く**：control-plane は依頼者のタイムゾーンを知らない。エージェントの
  文面は依頼者の時刻で書かれているので、それを引用する。

## Consequences

- 上限で止まったことが、状態メッセージと返事の両方で失敗として分かる。
- `rate_limit_event` が上限の `result` より後に出る場合は、上限ではなく、ただのエラーとして知らせる。上限で止まった
  ときの実際の出力の順は、実物では確かめていない。
- 上限が戻っても、人がもう一度依頼するまでセッションは動かない。
