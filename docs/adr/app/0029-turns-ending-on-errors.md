# 0029. エージェントがエラーで終えたターンを失敗として知らせ、使用上限で止まったことを書き分ける

## Context

control-plane は、ターンの結果を stream-json の `result` の `subtype` だけで見ていた。Claude Code は、API の要求が
断られてターンを終えたときも `subtype` を `success` にし、`is_error` を立て、`result` に断られた理由の文面を入れる。
そのため、使用上限で止まったターンも成功として扱い、状態メッセージは「完了」になり、上限の文面がふつうの回答として
返っていた。

Claude Code（2.1.292）の出力のスキーマには、次のものがある。
- `result` の `is_error`：ターンの最後のメッセージが API エラーのとき、または `subtype` が `error_max_turns` などの
  とき立つ。
- `result` の `api_error`：ターンを終わらせた API エラーの種類。アカウントのプランの上限か、追加の利用分の上限で
  断られたときは `usage_limit_reached`。スキーマでは `@internal` と印が付いている。
- `rate_limit_event`：使用上限の状態が変わると出る。`rate_limit_info.status` が `rejected` なら上限に達している。
  追加の利用分で動いている間（`isUsingOverage`）は、`rejected` でも要求は通る。戻る時刻（`resetsAt`、Unix 秒）を
  過ぎた `rejected` は古い。
- `subtype` の `error_during_execution`：中止のほか、ターンの途中の例外や準備の失敗でも出る。

上限で止まったときの `result` の文面（例：`You've hit your session limit · resets 2pm (Asia/Tokyo)`）は、戻る時刻を
エージェントのコンテナのタイムゾーンで含む。

上限に達すると、バックグラウンドの処理が一つ終わるたびにエージェントが自分でターンを始め、そのたびに断られる。

## Decision

- `is_error` が立っているか、`subtype` が `error` で始まるターンを、エラーで終わったターンとする。
  `error_during_execution` は、これまでどおり中断として扱う。
- エラーで終わったターンのうち、次のものを使用上限で止まったターンとする。
  - `api_error` が `usage_limit_reached` のもの。
  - `api_error` がなく、最後に受けた `rate_limit_event` が `rejected` で、追加の利用分を使っておらず、戻る時刻を
    過ぎていないもの。
- エラーで終わったターンは、状態メッセージで失敗と示す。使用上限なら「使用上限で停止」と示す。
- 依頼への返事と、エージェントが自分で始めたターンの知らせには、エラーであることを書き、エージェントの文面を
  引用する。上限なら、文面に戻る時刻が入っている。上限のときは、戻ったあとにもう一度依頼すれば続きから進むことを
  添える。
- エージェントが自分で始めたターンのエラーの知らせは、バックグラウンドの処理が残っていても、すぐ投稿する。ADR 0028 で
  持っておく回答には含めない。
- 同じセッションで使用上限の知らせを出したあとは、上限で止まり続けている間、エージェントが自分で始めたターンが
  上限で止まっても、状態メッセージだけを変える。上限ではない結果で終わるターンがあれば、次の上限はまた知らせる。
- HTTP API の応答には `error` と `usage_limited` を載せ、`acp run` は終了コード 1 で終わる。
- 上限が戻ったときに自動で再開することは、ここでは決めない。定期実行と同じ「決めた時刻にエージェントを起こす」
  仕組みとして、あわせて決める。

## Alternatives

- **`result` の文面で上限かを判定する**：文面は言い回しが変わる。型の付いた `api_error` を先に使う。
- **`rate_limit_event` だけで判定する**：追加の利用分で動いている間や、古い `rejected` が残っている間に、ほかの
  エラーまで上限と判定してしまう。`api_error` がないとき（古い Claude Code など）の補いにだけ使う。
- **戻る時刻を `resetsAt` から control-plane が書く**：control-plane は依頼者のタイムゾーンを知らない。エージェントの
  文面を引用する。

## Consequences

- エラーの知らせをすぐ投稿する理由：処理が残る間に回答を持っておくと、上限で断られ続けている間、処理が尽きるまで
  依頼者は止まったことを知らない。

- 上限で止まったことが、状態メッセージと返事の両方で失敗として分かる。
- `api_error` は `@internal` なので、Claude Code の更新で変わりうる。`api_error` がなくなれば `rate_limit_event` での
  判定に戻る。上限の `api_error` の名前が変われば、上限ではない種類とみなし、`rate_limit_event` も見ないので、
  ただのエラーとして知らせる。どちらの場合も失敗としては表示され、戻る時刻はエージェントの文面で伝わる。
- 上限で止まり続けている間に上限の種類や戻る時刻が変わっても、間に上限ではない結果のターンがなければ、新しい
  知らせは出ない。そのときは状態メッセージだけが変わる。
- 文面の時刻は、エージェントのコンテナのタイムゾーンの時刻になる。イメージにホストの `TZ` を入れていれば、依頼者の
  時刻と一致する。
- 中断ではないのに `error_during_execution` で終わったターンは、中断として知らされる。
- 上限が戻っても、人がもう一度依頼するまでセッションは動かない。
- 上限で止まったときの実際の出力は、実物では確かめていない。
