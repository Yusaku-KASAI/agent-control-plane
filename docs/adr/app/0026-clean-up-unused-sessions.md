# 0026. 使われないセッションは保持期間を過ぎたら control-plane が丸ごと消してスレッドに知らせ、続きがありうるか消すと作業が失われるものは残して促す

## Context

セッションの記録と作業領域、認証情報のディレクトリ、エージェントの会話の履歴、リモートのブランチは、
セッションを作るたびに増え、消す仕組みがなかった。Slack ではセッション ID がスレッドから決まるので、記録だけを
消すと、同じスレッドからの次の依頼は同じ ID で新しいセッションを作る。そのとき同じ ID の会話の履歴が残っていると
`--session-id` で始められず、同じ名前のブランチがリモートに残っていると push がぶつかる。

セッションが触るブランチは、`acp/<ID の先頭8文字>` とそれに `-<内容>` を付けたものに限らない。別のセッションが
作った PR のブランチを取ってきて更新することもある。また、PR を作らずに終わった作業や、push していない
コミットは、作業領域を消すとどこにも残らない。

## Decision

control-plane は `acp serve` の起動時と 1 時間ごとに、保持期間を過ぎたセッションを、残す理由がなければ消す。
コマンドや API は作らない。

### 状態の軸

軸は、それぞれの対象の上で、値が互いに重ならず、すべての場合を尽くす。同時に成り立ちうる性質は、「ある / ない」の
別の軸にする。括弧内の条件は、その軸が定義される範囲。

「ほかにないコミット」とは、`origin` の remote-tracking ブランチにも `refs/acp/target`（下記）にもないコミット。

PR について、次の言葉を区別して使う。

- **head ブランチ**：PR のマージ元のブランチ。**base ブランチ**：マージ先のブランチ。
- **head コミット**：head ブランチの先頭のコミット。閉じた PR では、閉じたときの先頭。あるコミットが「head コミットに
  入っている」とは、head コミットから履歴をたどってそのコミットに行き着くこと。

#### セッション（対象：セッションのディレクトリ）

| 軸 | 値 |
| --- | --- |
| 記録 | ある / ない |
| ロック | 取れる / 取れない（プロセスが動いている） |
| 期限（記録がある） | 最後に使ってから `sessions.retention`（既定 30 日）以内 / 超過 |
| 作業領域（記録がある） | git のリポジトリ / そうでない（`.git` がない） |
| 作業ツリーの変更（git のリポジトリ） | ない / ある（コミットしていない変更か、ignore されていない追跡していないファイル） |
| stash（同） | ない / ある |
| 途中の操作（同） | ない / ある（rebase、merge、cherry-pick、revert、bisect） |
| HEAD（同） | ブランチを指す / detached で、ローカルのブランチにもないほかにないコミットを持つ / detached で、持たない |
| GitHub（記録がある） | 読める / 読めない（GitHub App がない、ターゲットの `origin` が GitHub でない） |

#### ブランチ（対象：ローカルのブランチ、push したブランチ、セッションの名前でリモートにあるブランチの和。名前で同じものとする）

| 軸 | 値 |
| --- | --- |
| 名前 | セッションのもの（`acp/<ID の先頭8文字>` と、それに `-<内容>` を付けたもの、ADR 0012）/ ほか |
| push の記録 | 一度でもある（remote-tracking ブランチの reflog に `update by push` がある）/ ない |
| ローカル | ない / あり、ほかにないコミットを持つ / あり、持たない |
| リモート（GitHub を読める） | ある / ない |
| このブランチを head ブランチとする開いている PR（GitHub を読める） | ある / ない |
| このブランチを base ブランチとする開いている PR（GitHub を読める、リモートにある） | ある / ない |

#### コミット（対象：ブランチとコミットの組。ほかにないコミットを持つローカルのブランチとその先頭、push したブランチと最後に push したコミット、セッションの名前でリモートにあるブランチとその先頭）

| 軸 | 値（上から順に、最初に当たるもの） |
| --- | --- |
| 行き先（GitHub を読める） | 既定のブランチ / 同じ名前のブランチを head ブランチとする、マージした PR の head コミット / 同じく、マージせずに閉じた PR の head コミット / リモートの同じ名前のブランチ / どこにもない |

最後に使った時刻（期限）は記録の `last_used_at` に持たせ、作ったとき、依頼を受けてロックを取ったとき、ターンを
終えたときに書く。ターンが失敗したり中断したりしても、依頼を受けた時点で使ったことになる。GitHub を読めるのに
GitHub の API が失敗したときは、その回はそのセッションを判定しない。

### 判定

- 記録がなく、ロックが取れる：ディレクトリを消す。セッションはロックを持ったまま作るので、作るのに失敗した残りか、
  片付けと入れ違った依頼が作ったロックだけのもの。
- 記録があり、期限が以内：何もしない。
- 記録があり、期限が超過：次の理由のどれかに当たれば残し、理由を挙げて保持期間ごとに 1 回スレッドで知らせる（下記）。
  当たらなければ消す。
- ロックが取れなければ、記録の有無によらず、その回は消さない。理由に当たらないなら知らせもしない。

| 理由 | 状態 |
| --- | --- |
| 続きがありうる | 名前：セッションのもの、または push の記録：一度でもある。かつ、head ブランチとする開いている PR：ある |
| 消すと失われる（作業領域） | 作業ツリーの変更：ある、stash：ある、途中の操作：ある、HEAD：detached でほかにないコミットを持つ、のどれか |
| 消すと失われる（push していないコミット） | ローカル：あり、ほかにないコミットを持つ。かつ、GitHub：読めない、またはローカルの先頭の行き先：どこにもない |
| 消すと失われる（push したコミット） | push の記録：一度でもある、GitHub：読める、最後に push したコミットの行き先：どこにもない |
| 消すと失われる（消すブランチ） | 名前：セッションのもの、リモート：ある、head ブランチとする開いている PR：ない、リモートの先頭の行き先：リモートの同じ名前のブランチ |
| 消すと PR が閉じる | 名前：セッションのもの、リモート：ある、base ブランチとする開いている PR：ある |

作業領域が git のリポジトリでなければ、作業ツリーの変更・stash・途中の操作はなく、HEAD は当たらず、ローカルの
ブランチと push したブランチはないものとする。

- 続きがありうるのは、レビューに応える依頼がスレッドに来うるから。
- 名前がセッションのものかどうかは、リモートのブランチを消すかどうかと、その PR を続きとみなすかに使い、コミットが
  残っているかの判断には使わない。消さないブランチの内容はリモートに残るので、そのブランチでは、セッションの
  コミットがそこに入っているか（行き先：リモートの同じ名前のブランチ）で判断する。
- 行き先は上から順に最初に当たるものなので、「リモートの同じ名前のブランチ」は、既定のブランチにも、同じ名前の
  ブランチを head ブランチとするマージした PR やマージせずに閉じた PR の head コミットにも入っていないことを表す。リモートの先頭は、そのブランチ自身に入っているので、
  「どこにもない」にはならない。

### 消すもの

記録、作業領域（ローカルのブランチ、作業ツリーを含む）、認証情報、会話の履歴、セッションの名前でリモートにある
ブランチ。リモートのほかのブランチと PR は消さない。

### 判定を支える仕組み

- **セッションの名前でリモートにあるブランチ**は、GitHub の API で名前の前方一致（`matching-refs`）で探す。作業領域が知らない
  ブランチも含めるので、同じ ID で作り直したセッションの push がぶつかるブランチを残さない。
- **push したブランチ**を reflog の `update by push` で決めるのは、fetch や switch をしただけのブランチを入れないため。
  名前で決めると、別のセッションの PR のブランチに push したときに見落とす。最後に push したコミットは、その項目の
  コミットで、fetch で remote-tracking ブランチが動いたあとも変わらない。
- 作業領域を作るとき、作業領域の git の設定で remote-tracking ブランチの reflog を消えないようにする
  （`gc.refs/remotes/*.reflogExpire` と `reflogExpireUnreachable` を `never`）。既定では、今の先頭から辿れない
  項目（force push のあとなど）は 30 日、ほかは 90 日で消え、保持期間より先に push の記録が消えうる。
- 作業領域を作るとき、clone した時点の HEAD（ターゲットでチェックアウトしていたコミット）を `refs/acp/target` に
  残す。そのコミットはターゲットの作業で、clone のブランチには `origin` にないターゲットのローカルのコミットが
  ありうる。数えないと、すべてのセッションが残り続ける。
- ブランチの事実（リモートにあるか、先頭、開いている PR、各コミットの行き先）は、エージェントの GitHub App の
  トークンで GitHub の API から読む。アダプタは事実だけを返す。squash でマージされてブランチが消え、prune されると、
  そのコミットはどの remote-tracking ブランチにもないが、同じ名前のブランチを head ブランチとする、マージした PR の
  head コミットに入っている。
- 判定はユースケースの 1 か所で行う。事実から残す理由のリストを作り、残すか消すかと知らせる文面は、その理由から
  決める。

### 消す手順

- 判定は、まずロックを取らずに行う。GitHub の応答を待つ間、依頼を待たせない。
- 消すときはロックを取り、記録を読み直して、その間に使われていないことと、残す理由がないことをもう一度確かめる。
- 消す順は、リモートのブランチ、認証情報と会話の履歴、最後に記録と作業領域。記録を消すまでは ID がこのセッションを
  指したままなので、途中で失敗しても次の片付けでやり直せ、古いものが残ったまま同じ ID の新しいセッションが始まる
  ことはない。記録と作業領域は、ディレクトリを一度に別の名前へ移してから消す。
- 依頼の側は、ロックを取ったあとに記録を読み直し、使った時刻を書いて保存し直す。読む前に片付けで消えていたら、
  同じ ID で作り直す。

### スレッドへの知らせ（セッションが Slack のスレッドで始まった場合だけ）

- 消したら、何を消したか（作業領域、会話の履歴、消したブランチ）と、続けると新しいセッションになることを知らせる。
  知らせるのに失敗しても、消したことは取り消さない。
- 残したら、残す理由を挙げて片付けるよう促す。知らせた時刻を記録の `kept_notified_at` に持たせ、それが保持期間より
  前のときだけ知らせる（保持期間ごとに 1 回）。知らせるのに失敗したら時刻を書かず、次の回にもう一度知らせる。

## Alternatives

- **最後に使った時刻を記録ファイルの更新時刻で代用する**：記録の形式を変えずに済むが、ファイルのコピーや復元で
  時刻が変わり、何をしたときに変わるのかがコードから読み取りにくい。知らせた時刻はどのみち記録に持たせる必要がある。
- **今あるセッションを片付けが見分けて扱う**（`last_used_at` のない記録は最初に見た時刻から数える、clone の
  ブランチを reflog の最初の項目で見分けるなど）：一度しか要らない判定がコードに残り続ける。今あるセッションは
  導入するときに一度だけ人が片付ける。
- **セッションが push したブランチを名前（`acp/<ID の先頭8文字>` と `-<内容>`）で決める**：別のセッションの PR の
  ブランチを更新したときに、そのブランチの PR や作業を見落とす。
- **upstream を持つローカルのブランチを、セッションが触ったブランチとする**：確かめるために switch しただけの
  ブランチも upstream を持つ。`-u` なしの push を拾うには、push する前から upstream を設定しておくなどの決まりが
  要り、エージェントへの指示も増える。
- **セッションが push した片付いたブランチは、名前によらずすべて消す**：ほかのセッションや人がまだ使うブランチまで
  消してしまう。
- **セッションが作っていないブランチは、head ブランチとする開いている PR だけを見る**：そのブランチに push したあと、人がマージせずに
  消すと、セッションのコミットはどこにもなくなるのに、作業領域ごと消してしまう。
- **マージせずに閉じた PR の head コミットに入っているコミットも失われるとみなす**：GitHub は閉じた PR からブランチを戻せる。
  閉じた PR が残り続け、セッションが消えなくなる。
- **作業ツリーは見ずに消す**：ターンが中断したり失敗したりして途中で終わったセッションは、コミットしていない変更や
  stash、rebase の途中の状態を持つ。それを黙って消すことになる。
- **残すか消すかと知らせる文面を、それぞれの条件式で決める**：同じ判定が何か所にも分かれ、抜けている状態に
  気づきにくい。
- **clone のブランチを作業領域を作るときに消す**：`refs/acp/target` を残すのと同じく一度の操作で済むが、
  エージェントから見える作業領域の形が、clone したときの形と変わる。
- **PR を作っていない作業も消す**：PR にしないまま終わった作業や、push していないコミットが黙って失われる。
- **作業領域だけを消し、記録と会話の履歴は残す**：一番大きいのは作業領域だが、会話の履歴とブランチも溜まり続ける。
  作業領域のないセッションを再開すると、作業ディレクトリのない会話を続けることになる。
- **開いている PR があっても消す**：ブランチを消すと、それを head ブランチや base ブランチとする PR は閉じられる。人が確かめる前の PR を勝手に閉じることになる。
- **残したことを、片付けのたびに知らせる**：1 時間ごとにスレッドに同じ知らせが並ぶ。
- **人がコマンドで片付ける**：忘れれば溜まり続ける。対象の決め方が決まっていれば、自動で十分。

## Consequences

- 保持期間を過ぎたセッションに同じスレッドから依頼すると、前の会話を覚えていない新しいセッションとして始まる。
- 残す理由があるセッションは、それが片付くまで残り、1 時間ごとに作業領域と GitHub の API で確かめられる。
  作業ツリーに追跡していないファイルを残すだけでも残る。
  GitHub App のないエージェントのコミットは push できないので、そのセッションは人が片付けるまで残る。
- 同じブランチに複数のセッションが push していると、ブランチを消すのはそれを作ったセッションだけ。ほかのセッションは、
  そのブランチを head ブランチとする開いている PR があるあいだと、自分のコミットがどこにもなくなったときに残る。
- セッションが作っていないブランチは、片付いても GitHub に残る。
- detached HEAD のコミットは、リモートに問い合わせない。`refs/pull/<番号>/head` や fork から取ってきて detach した
  コミットにさらにコミットしたセッションは、人が片付けるまで残る。
- `origin` 以外のリモートに push した作業は見ない。そのコミットは「どこにもない」とみなして残す。
- 判定のたびに、ブランチとコミットごとに GitHub の API を何度か呼ぶ。閉じた PR の多いブランチに push したセッション
  では、呼ぶ回数が増える。
- remote-tracking ブランチは、リモートのブランチが消えたあとに `git fetch --prune` などで消え、push の記録も
  一緒に消える。ローカルのブランチとリモートのブランチの名前が違う（`git push origin HEAD:<名前>` で push した）
  と、消えたブランチをローカルの名前で GitHub に問い合わせることになり、マージ済みでも分からない。そのセッションは、
  コミットがどこにもないとして人が片付けるまで残る。
- 同じブランチに push したあと、誰かがそのブランチを rebase して force push すると、前に push したコミットは内容が
  同じでも別のコミットになり、PR の head コミットに入らなくなる。PR をマージしたあとも、そのコミットは「どこにも
  ない」とみなされ、そのセッションは人が片付けるまで残り続ける（保持期間ごとに知らせる）。
- この仕組みより前に作ったセッションには、`last_used_at`、`refs/acp/target`、reflog を残す設定がない。そうした
  セッションは、この版の `acp serve` を起動する前に一度だけ人が片付ける。片付けないと、`last_used_at` がないので
  起動後の最初の片付けで期限切れとして扱われ、残す理由がなければ会話の履歴ごと消える。clone のブランチに
  ターゲットのローカルのコミットがあるものは、コミットがどこにもないとして残り続ける。
- エージェントを設定から外すと、そのセッションはブランチを扱えないので消えず、片付けのたびにエラーとして記録される。
- 片付けがセッションを消している間に同じセッションへの依頼が来ると、その依頼はセッションが使われていると返される。
- 会話の履歴を消す途中で失敗すると、記録が残ったまま履歴の一部が欠け、次の片付けで消えるまで、そのセッションは
  再開に失敗することがある。
- 同じスレッドへの 2 つ目の依頼が、1 つ目がセッションを作っている間に届くと、セッションが使われていると返される。
