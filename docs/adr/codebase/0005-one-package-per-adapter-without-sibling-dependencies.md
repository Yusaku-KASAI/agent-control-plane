# 0005. アダプターは一つのパッケージにし、ほかのアダプターに依存させない

## Context

ADR 0001 は、adapter → usecase → domain の依存の向きを depguard で検査すると決めた。アダプターどうしの依存は
決めておらず、depguard も adapter から `cmd` への依存しか断っていなかった。今はアダプターどうしの依存はないが、
検査がないので黙って入りうる。アダプターは usecase のポートを実装するか、usecase を呼ぶ入口になるだけで、
アダプターどうしは組み立ての場所（`cmd/acp`）がつなぐ（Slack の `slackauth.Source` を `slackbot` に渡すなど）。

depguard は、import するパスを接頭辞で比べる。「自分の下のパッケージは許し、ほかのアダプターは断る」は、
アダプターごとに規則を書かないと表せない。

## Decision

- アダプターは、ほかのアダプターに依存しない。アダプターどうしをつなぐのは `cmd/acp` だけにする。
- 一つのアダプターは `internal/adapter` の下の一つのパッケージにし、下にパッケージを作らない。一つの技術を、
  関心ごとに複数のアダプターに分けてよい。
- depguard の一つの規則で、`internal/adapter` の下のファイルが `internal/adapter` の下のほかのパッケージを import
  することを断る。パッケージの外部の試験はそのパッケージ自身を import するので、試験のファイルは規則から外す。

## Alternatives

- **depguard の規則をアダプターごとに書く**：下のパッケージを許せ、試験のファイルも覆えるが、アダプターを足すたびに
  規則を足す必要があり、足し忘れると黙って検査が外れる。
- **`go list` で試験も含めた依存を調べる検査を自分で書く**：下のパッケージを許せ、試験のファイルも覆えるが、自分で
  書いた検査を保つ手間が増える。今は下のパッケージも、試験からほかのアダプターへの依存もない。
- **文書に書くだけにする**：検査で守れる決まりで、黙って入ると気づく機会がない。

## Consequences

- アダプターが大きくなったからといって下のパッケージに分けると、規則に断られる。分けるなら、別のアダプターに
  するか、この判断を見直す。
- アダプターどうしは型や道具を共有できない（docker の `Runner` と `WorkspaceReader` が共有する Docker の API の
  インターフェースなど）。共有するものがある関心は、一つのアダプターに残すか、この判断を見直す。
- 試験のファイルからほかのアダプターへの依存は、検査では見つからない。
