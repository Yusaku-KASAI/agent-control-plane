# 0016. チャットからの依頼は受信方式に依存しない形で受け、Slack は Socket Mode から始める

## Context

Slack からエージェントに依頼したい。エージェントは Bot ごとに分ける（ADR 0002）。Slack のイベントの
受け方には Socket Mode と Events API があり、トークンを払い出せないワークスペースでは、MCP で読み取った
メッセージをポーリングするしかない場合もある。返信に使える手段とできることも環境によって違う（ADR 0006）。

## Decision

- チャットからの依頼の処理（依頼者の確認、受付の合図、ターンの実行、返信）は、受信方式に依存しない
  ユースケースにする。受信方式ごとのアダプターはメッセージを渡すだけ、返信は返信用のインターフェースに任せる。
- Slack は、エージェントごとの Slack アプリで Socket Mode を使って受信し、Bot トークンで返信する。
  受付の合図にはリアクションを付ける。
- スレッドとエージェントから UUIDv5 でセッション ID を決め、スレッドの中のメンションは同じセッションを
  続ける。同じスレッドでも Bot が違えば別のセッションになる。
- 依頼できるのは、エージェントごとに許可した Slack のユーザーだけにする。
- トークンは `ACP_SECRETS_DIR` の下のファイルに置き、設定ファイルからパスで指す。

## Alternatives

- **Events API で受ける**：公開された URL が要り、手元の PC で動かすのに向かない。サーバーに移したあとに
  受信用のアダプターとして加えられる。
- **1 つの Slack アプリで全エージェントを受ける**：ADR 0002 で見送った。
- **ワークスペースの誰でも依頼できる**：エージェントは push や PR の作成までできるため、依頼できる人を絞る。

## Consequences

- MCP の読み取りによるポーリングや Events API は、同じユースケースを呼ぶアダプターとして追加できる。
  返信にスレッドへの投稿ができない手段を使う場合は、その制約をアダプター側で扱う。
- 長い結果は Slack の上限に合わせて切り詰める。
- Slack が同じイベントを再送すると、同じセッションのターンが重なり、後の方は「処理中」と返す。
