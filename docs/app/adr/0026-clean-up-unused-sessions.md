# 0026. 使われないセッションは保持期間を過ぎたら control-plane が丸ごと消してスレッドに知らせ、ほかにない作業があるものは残して促す

- Status: Accepted
- Date: 2026-10-07

## Context

セッションの記録と作業領域、認証情報のディレクトリ、エージェントの会話の履歴、リモートのブランチは、
セッションを作るたびに増え、消す仕組みがなかった。Slack ではセッション ID がスレッドから決まるので、記録だけを
消すと、同じスレッドからの次の依頼は同じ ID で新しいセッションを作る。そのとき同じ ID の会話の履歴が残っていると
`--session-id` で始められず、同じ名前のブランチがリモートに残っていると push がぶつかる。

セッションが触るブランチは、`acp/<ID の先頭8文字>` とそれに `-<内容>` を付けたものに限らない。別のセッションが
作った PR のブランチを取ってきて更新することもある。また、PR を作らずに終わった作業や、push していない
コミットは、作業領域を消すとどこにも残らない。

## Decision

control-plane は `acp serve` の起動時と 1 時間ごとに、セッションごとに次を判定し、残す理由がなければ消す。
コマンドや API は作らない。

### 判定（どれかに当てはまれば残す）

1. **最近使った**：最後に使ってから `sessions.retention`（既定 30 日）たっていない。最後に使った時刻は記録の
   `last_used_at` に持たせ、作ったとき、依頼を受けてロックを取ったとき、ターンを終えたときに書く。ターンが失敗したり
   中断したりしても、依頼を受けた時点で使ったことになる。
2. **使われている**：ロックが取れない（動いている）。
3. **続きがありうる**：セッションが push したブランチから、開いている PR がある。レビューに応える依頼が
   スレッドに来うる。
4. **消すと作業が失われる**：
   - **作業領域**：いずれかのローカルのブランチか、detached HEAD に、ほかに残っていないコミットがある。ほかに残って
     いるとは、remote-tracking ブランチか `refs/acp/target`（下記）にあること。detached HEAD では、ローカルの
     ブランチにあることでもよい。同じ名前のブランチがリモートから消えているときは、先頭が既定のブランチか閉じた（マージを含む）PR の head に入っていることでもよい。
   - **セッションが作ったリモートのブランチ**（下記の消すもの。リモートから消えたものも含む）：先頭が既定のブランチ
     にも閉じた PR の head にも入っていない。または、開いている PR の base になっている（消すとその PR が閉じる）。

判定 3、4 に当たるものを「ほかにない作業」と呼ぶ。期限が過ぎたセッションは、まずロックを取らずに判定 3、4 を
確かめ、当たれば保持期間ごとに 1 回スレッドで知らせる（下記）。当たらなければロックを取って消す（判定 2）。

### 消すものと残すもの

| | 消す | 残す |
| --- | --- | --- |
| control-plane の持ち物 | 記録、作業領域（ローカルのブランチ、コミットしていない変更を含む）、認証情報、会話の履歴 | — |
| リモートのブランチ | セッションが作ったもの（`acp/<ID の先頭8文字>` と、それに `-<内容>` を付けたもの、ADR 0012） | それ以外。push していても、ほかのセッションや人が使っているかもしれない |

セッションが作っていないブランチは消さないので、そこに push した作業はリモートに残る。そうしたリモートの
ブランチは判定 4 で見ない（作業領域のローカルのブランチは、名前によらず見る）。PR のないことや既定のブランチに入っていないことで残すと、確かめるためにチェックアウト
しただけの `develop` のように、ほぼ常に既定のブランチより進んでいるブランチのせいで、セッションが消えなくなる。

### 判定を支える仕組み

- **セッションが push したブランチ**（判定 3）は、名前ではなく作業領域の git の記録で決める。`origin` の
  remote-tracking ブランチのうち、reflog に `update by push` があるもの。fetch や switch をしただけのブランチは
  入らない。リモートの既定のブランチは除く。名前で決めると、別のセッションの PR のブランチに push したときに
  見落とす。
- 作業領域を作るとき、作業領域の git の設定で remote-tracking ブランチの reflog を消えないようにする
  （`gc.refs/remotes/*.reflogExpire` と `reflogExpireUnreachable` を `never`）。既定では、今の先頭から辿れない
  項目（force push のあとなど）は 30 日、ほかは 90 日で消え、保持期間より先に push の記録が消えうる。
- 作業領域を作るとき、clone した時点の HEAD（ターゲットでチェックアウトしていたコミット）を `refs/acp/target` に
  残し、判定 4 ではこれも「ほかに残っている」に数える。そのコミットはターゲットの作業で、clone のブランチには
  `origin` にないターゲットのローカルのコミットがありうる。数えないと、すべてのセッションが残り続ける。
- ブランチの状態は、エージェントの GitHub App のトークンで GitHub の API から確かめる。リモートから消えた
  ブランチは、作業領域にある先頭（remote-tracking ブランチか、同じ名前のローカルのブランチ）で判断する。squash で
  マージされてブランチが消え、prune されると、そのコミットはどの remote-tracking ブランチにもないが、閉じた PR の
  head に含まれる。既定のブランチと共通の履歴がないブランチは、既定のブランチに入っていないとみなす。
- GitHub App がないエージェントや、`origin` が GitHub でないターゲットでは、ブランチの状態を確かめない。判定 3 と、
  GitHub で確かめる判定 4 の部分は当てはまらず、作業領域は remote-tracking ブランチと `refs/acp/target` だけで
  判断する。
- 作業領域が git のリポジトリでなければ（`.git` がなければ）、作業領域に失われる作業はないとみなす。
- 記録のないセッションのディレクトリは、ロックが取れればすぐ消す。セッションはロックを持ったまま作るので、
  ロックが取れて記録がないなら、作るのに失敗した残りか、片付けと入れ違った依頼が作ったロックだけのディレクトリ。

### 消す手順

- 判定 3、4 は、まずロックを取らずに確かめる。GitHub の応答を待つ間、依頼を待たせない。
- 消すときはロックを取り、記録を読み直して、その間に使われていないこと（判定 1）と、判定 3、4 にもう一度
  当てはまらないことを確かめる。
- 消す順は、リモートのブランチ、認証情報と会話の履歴、最後に記録と作業領域。記録を消すまでは ID がこのセッションを
  指したままなので、途中で失敗しても次の片付けでやり直せ、古いものが残ったまま同じ ID の新しいセッションが始まる
  ことはない。記録と作業領域は、ディレクトリを一度に別の名前へ移してから消す。
- 依頼の側は、ロックを取ったあとに記録を読み直し、使った時刻を書いて保存し直す。読む前に片付けで消えていたら、
  同じ ID で作り直す。

### スレッドへの知らせ（セッションが Slack のスレッドで始まった場合だけ）

- 消したら、何を消したか（作業領域、会話の履歴、消したブランチ）と、続けると新しいセッションになることを知らせる。
  知らせるのに失敗しても、消したことは取り消さない。
- 判定 3 か 4 で残したら、その理由（開いている PR、片付いていないブランチ、push していないコミット）を挙げて、
  片付けるよう促す。知らせた時刻を記録の `kept_notified_at` に持たせ、それが保持期間より前のときだけ知らせる
  （保持期間ごとに 1 回）。知らせるのに失敗したら時刻を書かず、次の回にもう一度知らせる。

## Alternatives

- **最後に使った時刻を記録ファイルの更新時刻で代用する**：記録の形式を変えずに済むが、ファイルのコピーや復元で
  時刻が変わり、何をしたときに変わるのかがコードから読み取りにくい。知らせた時刻はどのみち記録に持たせる必要がある。
- **今あるセッションを片付けが見分けて扱う**（`last_used_at` のない記録は最初に見た時刻から数える、clone の
  ブランチを reflog の最初の項目で見分けるなど）：一度しか要らない判定がコードに残り続ける。今あるセッションは
  導入するときに一度だけ人が片付ける。
- **セッションが push したブランチを名前（`acp/<ID の先頭8文字>` と `-<内容>`）で決める**：別のセッションの PR の
  ブランチを更新したときに、そのブランチの PR や作業を見落とす。
- **upstream を持つローカルのブランチを、セッションが触ったブランチとする**：確かめるために switch しただけの
  ブランチも upstream を持つ。`-u` なしの push を拾うには、push する前から upstream を設定しておくなどの決まりが
  要り、エージェントへの指示も増える。
- **セッションが push した片付いたブランチは、名前によらずすべて消す**：ほかのセッションや人がまだ使うブランチまで
  消してしまう。
- **clone のブランチを作業領域を作るときに消す**：`refs/acp/target` を残すのと同じく一度の操作で済むが、
  エージェントから見える作業領域の形が、clone したときの形と変わる。
- **PR を作っていない作業も消す**：PR にしないまま終わった作業や、push していないコミットが黙って失われる。
- **作業領域だけを消し、記録と会話の履歴は残す**：一番大きいのは作業領域だが、会話の履歴とブランチも溜まり続ける。
  作業領域のないセッションを再開すると、作業ディレクトリのない会話を続けることになる。
- **開いている PR があっても消す**：ブランチを消すと PR は閉じられる。人が確かめる前の PR を勝手に閉じることになる。
- **残したことを、片付けのたびに知らせる**：1 時間ごとにスレッドに同じ知らせが並ぶ。
- **人がコマンドで片付ける**：忘れれば溜まり続ける。対象の決め方が決まっていれば、自動で十分。

## Consequences

- 保持期間を過ぎたセッションに同じスレッドから依頼すると、前の会話を覚えていない新しいセッションとして始まる。
  作業領域にあってコミットしていない変更は失われる。
- ほかにない作業があるセッションは、その作業が片付くまで残り、1 時間ごとに作業領域と GitHub の API で確かめられる。
  GitHub App のないエージェントのコミットは push できないので、そのセッションは人が片付けるまで残る。
- 同じブランチに複数のセッションが push していると、ブランチを消し、PR のないことなどで残るのは、それを作った
  セッションだけ。ほかのセッションは、そのブランチから開いている PR があるあいだ残る。
- セッションが作っていないブランチは、片付いても GitHub に残る。
- remote-tracking ブランチは、リモートのブランチが消えたあとに `git fetch --prune` などで消え、push の記録も
  一緒に消える。ローカルのブランチとリモートのブランチの名前が違う（`git push origin HEAD:<名前>` で push した）
  と、消えたブランチをローカルの名前で GitHub に問い合わせることになり、マージ済みでも片付いたと分からない。
  そのセッションは、push していないコミットがあるとして人が片付けるまで残る。
- この仕組みより前に作ったセッションには、`last_used_at`、`refs/acp/target`、reflog を残す設定がない。そうした
  セッションは、この版の `acp serve` を起動する前に一度だけ人が片付ける。片付けないと、`last_used_at` がないので
  起動後の最初の片付けで期限切れとして扱われ、ほかにない作業がなければ会話の履歴ごと消える。clone のブランチに
  ターゲットのローカルのコミットがあるものは、push していないコミットがあるとして残り続ける。
- エージェントを設定から外すと、そのセッションはブランチを扱えないので消えず、片付けのたびにエラーとして記録される。
- 片付けがセッションを消している間に同じセッションへの依頼が来ると、その依頼はセッションが使われていると返される。
- 会話の履歴を消す途中で失敗すると、記録が残ったまま履歴の一部が欠け、次の片付けで消えるまで、そのセッションは
  再開に失敗することがある。
- 同じスレッドへの 2 つ目の依頼が、1 つ目がセッションを作っている間に届くと、セッションが使われていると返される。
