# 0026. 使われないセッションは保持期間を過ぎたら control-plane が丸ごと消してスレッドに知らせ、ほかにない作業があるものは残して促す

- Status: Accepted
- Date: 2026-10-07

## Context

セッションの記録と作業領域、認証情報のディレクトリ、エージェントの会話の履歴、リモートのブランチは、
セッションを作るたびに増え、消す仕組みがなかった。Slack ではセッション ID がスレッドから決まるので、記録だけを
消すと、同じスレッドからの次の依頼は同じ ID で新しいセッションを作る。そのとき同じ ID の会話の履歴が残っていると
`--session-id` で始められず、同じ名前のブランチがリモートに残っていると push がぶつかる。

セッションが触るブランチは、`acp/<ID の先頭8文字>` とそれに `-<内容>` を付けたものに限らない。別のセッションが
作った PR のブランチを取ってきて更新することもある。また、PR を作らずに終わった作業や、push していない
コミットは、作業領域を消すとどこにも残らない。

## Decision

- 片付けの単位はセッション。記録、作業領域、認証情報、会話の履歴、そのセッションが作ったブランチをまとめて消す。
- 対象は、最後に使ってから `sessions.retention`（既定 30 日）を過ぎたセッション。最後に使った時刻は記録の
  `last_used_at` に持たせ、作ったとき、依頼を受けてロックを取ったとき、ターンを終えたときに書く。ターンが失敗したり
  再起動で中断したりしても、依頼を受けた時点で使ったことになる。
- `last_used_at` のない今ある記録は、片付けが最初に見た時刻を書き込み、そこから保持期間を数える。
- 記録のないセッションのディレクトリは、ロックが取れればすぐ消す。セッションはロックを持ったまま作るので、
  ロックが取れて記録がないなら、作るのに失敗した残りか、片付けと入れ違った依頼が作ったロックだけのディレクトリ。
- **セッションが触ったブランチ**は、名前ではなく作業領域で決める。作業領域のローカルのブランチのうち、
  `origin` に upstream を持つものの upstream が、そのセッションが触ったブランチ。リモートの既定のブランチは除く。
- 作業領域を作るとき、clone が作ったブランチ（ターゲットでチェックアウトしていたブランチ）を消し、セッションの
  ブランチ（`acp/<ID の先頭8文字>`）に `origin` の同じ名前のブランチを upstream として設定しておく。clone の
  ブランチはターゲットの作業で、セッションのものではない。upstream は、エージェントが `-u` を付けずに push しても
  セッションが触ったブランチとして扱うため。今ある作業領域に残っている clone のブランチは、reflog の最初の項目が
  clone であることで見分けて除く。
- 作業領域が git のリポジトリでなければ（`.git` がなければ）、ほかにない作業はないとみなす。
- **ほかにない作業**があるセッションは、何も消さずに残す。
  - 開いている PR の head か base であるブランチ。
  - 開いている PR がなく、既定のブランチにも入っていないブランチ。閉じた PR があっても、その PR の head より
    あとに push したものはこれに入る。既定のブランチと共通の履歴がないものも入る。
  - push していないコミットがあるローカルのブランチ。detached HEAD にしかないコミットも含む。
- 片付いたとみなすブランチは、既定のブランチに入ったものと、今の先頭を head とする PR が閉じた（マージされた
  ものを含む）もの。ブランチの状態は GitHub の API で確かめる。リモートから消えたブランチは、ローカルの先頭で
  判断する。squash でマージされてブランチが消え、prune されると、そのコミットはどの remote-tracking ブランチにも
  ないが、閉じた PR の head なので片付いている。
- GitHub から消すのは、片付いたブランチのうち、そのセッションが作ったもの（`acp/<ID の先頭8文字>` と、それに
  `-<内容>` を付けたもの、ADR 0012）だけ。ほかのブランチは、作った人やセッションがまだ使っているかもしれない。
- `acp serve` が起動時と 1 時間ごとに片付ける。コマンドや API は作らない。
- ほかにない作業があるかは、ロックを取る前に確かめる。GitHub の応答を待つ間、依頼を待たせない。
- 消すときはセッションのロックを取る。取れない（動いている）セッションは飛ばす。ロックを取ったら記録を読み直し、
  その間に使われていれば消さない。ほかにない作業がないことも、ロックを持ったままもう一度確かめる。消す順は、
  ブランチ、認証情報と会話の履歴、最後に記録と作業領域。記録を消すまでは ID がこのセッションを指したままなので、
  途中で失敗しても次の片付けでやり直せ、古いものが残ったまま同じ ID の新しいセッションが始まることはない。
  記録と作業領域は、ディレクトリを一度に別の名前へ移してから消す。
- 依頼の側は、ロックを取ったあとに記録を読み直し、使った時刻を書いて保存し直す。読む前に片付けで消えていたら、
  同じ ID で作り直す。
- リモートのブランチは、エージェントの GitHub App のトークンで GitHub の API から確かめて消す。GitHub App が
  ないエージェントは push できないので、ブランチは扱わない。
- スレッドに知らせる（セッションが Slack のスレッドで始まった場合だけ）：
  - 消したら、何を消したか（作業領域、会話の履歴、消したブランチ）と、続けると新しいセッションになることを知らせる。
    知らせるのに失敗しても、消したことは取り消さない。
  - ほかにない作業があって残したら、その作業（開いている PR、PR も既定のブランチへの取り込みもないブランチ、
    push していないコミット）を挙げて、片付けるよう促す。知らせた時刻を記録の `kept_notified_at` に
    持たせ、それが保持期間より前のときだけ知らせる（保持期間ごとに 1 回）。知らせるのに失敗したら時刻を書かず、
    次の回にもう一度知らせる。

## Alternatives

- **最後に使った時刻を記録ファイルの更新時刻で代用する**：記録の形式を変えずに済むが、ファイルのコピーや復元で
  時刻が変わり、何をしたときに変わるのかがコードから読み取りにくい。知らせた時刻はどのみち記録に持たせる必要がある。
- **`last_used_at` のない記録は、すぐ期限切れとして扱う**：導入した直後の最初の片付けで、古いセッションが知らせる
  間もなくまとめて消える。保持期間をもう一度待つ方が驚きが少ない。
- **セッションが触ったブランチを名前（`acp/<ID の先頭8文字>` と `-<内容>`）で決める**：別のセッションの PR の
  ブランチを更新したときに、そのブランチの PR や作業を見落とす。
- **セッションが触った片付いたブランチは、名前によらずすべて消す**：エージェントが確かめるためにチェックアウト
  しただけの `develop` や、ほかのセッションがまだ使うブランチまで消してしまう。
- **upstream を持たない、push 済みのローカルのブランチも数える**：push したことを確かめるには、remote-tracking
  ブランチの reflog などに頼ることになる。セッションのブランチには upstream を設定しておけば、`-u` なしの push を
  見落とすのは追加のブランチだけで、その作業はリモートに残る。
- **clone が作ったブランチを reflog だけで見分ける**：reflog の項目は `git gc` で 90 日を過ぎると消え、PR を待って
  長く残る作業領域では見分けられなくなる。
- **PR を作っていない作業も消す**：PR にしないまま終わった作業や、push していないコミットが黙って失われる。
- **作業領域だけを消し、記録と会話の履歴は残す**：一番大きいのは作業領域だが、会話の履歴とブランチも溜まり続ける。
  作業領域のないセッションを再開すると、作業ディレクトリのない会話を続けることになる。
- **開いている PR があっても消す**：ブランチを消すと PR は閉じられる。人が確かめる前の PR を勝手に閉じることになる。
- **残したことを、片付けのたびに知らせる**：1 時間ごとにスレッドに同じ知らせが並ぶ。
- **人がコマンドで片付ける**：忘れれば溜まり続ける。対象の決め方が決まっていれば、自動で十分。

## Consequences

- 保持期間を過ぎたセッションに同じスレッドから依頼すると、前の会話を覚えていない新しいセッションとして始まる。
  作業領域にあってコミットしていない変更は失われる。
- 導入したあと、今あるセッションが消えるのは、早くても保持期間が過ぎてから。
- ほかにない作業があるセッションは、その作業が片付くまで残り、1 時間ごとに作業領域と GitHub の API で確かめられる。
  GitHub App のないエージェントのコミットは push できないので、そのセッションは人が片付けるまで残る。
- 同じブランチを複数のセッションが更新していると、どのセッションもそのブランチの作業が片付くまで残る。
  ブランチを消すのは、それを作ったセッションだけ。
- セッションが作っていないブランチは、片付いても GitHub に残る。
- 今ある作業領域のセッションのブランチには upstream がない。`-u` なしで push していると、そのブランチは
  セッションのものとして扱われず、リモートに残る。同じ ID で作り直したセッションの push がぶつかりうる。
- 今ある作業領域では、clone から 90 日を過ぎて gc が走ると、clone のブランチを見分けられなくなる。そのブランチに
  ターゲットのローカルのコミットがあれば、セッションは残り続ける。
- セッションのブランチは push する前から upstream を持つので、`git status` は upstream が消えていると表示する。
- エージェントを設定から外すと、そのセッションはブランチを扱えないので消えず、片付けのたびにエラーとして記録される。
- 片付けがセッションを消している間に同じセッションへの依頼が来ると、その依頼はセッションが使われていると返される。
- 会話の履歴を消す途中で失敗すると、記録が残ったまま履歴の一部が欠け、次の片付けで消えるまで、そのセッションは
  再開に失敗することがある。
- 同じスレッドへの 2 つ目の依頼が、1 つ目がセッションを作っている間に届くと、セッションが使われていると返される。
