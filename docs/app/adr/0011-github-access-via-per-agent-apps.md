# 0011. GitHub へのアクセスはエージェントごとの GitHub App のトークンで行う

- Status: Accepted
- Date: 2026-10-01

## Context

エージェントにコミットの push や PR の作成をさせる。ロールごとの権限は渡す認証情報で分ける（ADR 0003）。
control-plane を動かす場所によって、シークレットを置けるかどうかが変わる（ADR 0007、0008）。

GitHub App のトークンの取り方には次の 2 つがある。

| | 秘密鍵から発行するインストールトークン | デバイスフローで得るユーザーアクセストークン |
| --- | --- | --- |
| 事前に置くもの | App の秘密鍵 | client ID のみ |
| 有効期間 | 1 時間 | 8 時間。更新トークン（6 か月）で、シークレットなしに更新できる |
| 権限 | App の権限の範囲で、発行時にリポジトリと権限を絞れる | App とユーザーの両方が持つ権限だけ |
| 操作の名義 | `<App名>[bot]` | ユーザー（App 経由） |

## Decision

- エージェントごとに GitHub App を用意し、その App のトークンだけをそのエージェントに渡す。
- トークンは control-plane がターンごとに発行し、コンテナには `GH_TOKEN` として渡す。コンテナ内の git は
  `gh` を認証に使い、SSH 形式のリモートも HTTPS で扱う。
- 発行方法は差し替えられるようにする。まず秘密鍵からインストールトークンを発行する方法を実装し、
  シークレットを置けない環境向けにデバイスフローを後から加える。

## Alternatives

- **エージェントごとの fine-grained PAT**：有効期間が長く、漏れたときの影響が大きい。
- **開発者自身の `gh` のトークンを渡す**：開発者の全権限をエージェントが持ち、ロールごとに分けられない。
- **App は 1 つにして、発行時にエージェントごとに絞る**：デバイスフローでは発行時に絞れないため、
  エージェントごとに権限を分けられない。PR の名義もすべて同じになる。

## Consequences

- コンテナはトークンの発行方法を区別しない。違いは操作の名義と有効期間だけになる。
- トークンはターンの開始時に発行するので、セッションの長さには影響されない。1 ターンが有効期間を超える
  場合は、コンテナから control-plane にトークンを取りに行く仕組みが要る。
- エージェントを増やすたびに GitHub App を作り、インストールする必要がある。
- 秘密鍵を使う方法では、control-plane を動かすホストに秘密鍵を置く。
