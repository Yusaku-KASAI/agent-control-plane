# 0011. CI の検査は、関心ごとのビルドのステージとして、入力が変わらなければキャッシュを当てる

- Status: Accepted
- Date: 2026-10-08

## Context

CI は devcontainer のイメージをビルドして Docker に読み込み、その中で `make check` を実行していた（ADR 0005）。
イメージの書き出しと読み込みに毎回約1分半かかり、関係のない変更でもすべての検査をやり直していた。レジストリには
イメージを置かない（パッケージを書ける権限や置き場所を増やさない）。

## Decision

- 検査を関心ごとに分ける（`check-go`、`check-platform`、`check-target`）。`make check` はその全部。
- CI は関心ごとのジョブで、Dockerfile の同じ名前のステージを、イメージを書き出さずにビルドする。各ステージは、
  その検査が読むファイルだけをコピーしてから検査を実行するので、それらが変わらなければ層のキャッシュが当たり、
  前回の結果を通ったものとして使う。control-plane のイメージのビルドも同じ形のジョブにする。
- キャッシュが当たると、新しく公開された脆弱性を拾えないので、週に1回、`check-go` だけキャッシュを使わずに実行する。
- 必須のチェックは、すべてのジョブの結果をまとめる `check` の1つにする。前段が失敗するとスキップ扱いで通って
  しまうので、`check` は必ず動き、結果を見て失敗する。

## Alternatives

- **パスで絞り込んでジョブを飛ばす**：飛ばしたジョブが必須のチェックとして待ち続ける。どの変更がどの検査に
  効くかを、ステージのコピーとは別の場所に書くことになる。
- **イメージをレジストリに置き、CI はそれを取ってきて中で実行する**：レジストリの権限と置き場所が増える。
- **1つのジョブで全部の検査のステージをビルドする**：どの関心の検査が落ちたかが、チェックの一覧で分からない。

## Consequences

- 検査が読むファイルを増やしたときは、そのステージのコピーにも足す。足し忘れると、そのファイルの変更で検査が
  やり直されない。
- キャッシュはジョブごとに GitHub Actions に残る（リポジトリごとの上限がある）。キャッシュがないときは約5分かかる。
