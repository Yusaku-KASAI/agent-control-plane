# 0005. ドキュメントは届く先で区切り、区切りをまたぐのは契約と用語集だけにし、区切りの中は種類で分ける

- Status: Accepted
- Date: 2026-10-11

## Context

ドキュメントは関心（app / codebase / target / platform）でディレクトリを分け、全体の狙いや設計はこのリポジトリに
置いてきた。2つ目のターゲット（txt-crypter）で、エージェントは control-plane のリポジトリを読めないため、
自分がどこでどう動いているか（control-plane 経由か、devcontainer で人と直接か、認証情報が読み取り専用で渡される
ことなど）を知らず、push の失敗を切り分けられなかった。同じ症状で、control-plane のコードと ADR を読める
control-plane-dev は原因を見つけた。エージェントに要る知識が、エージェントに届かない場所にあった。

また、一つの文書に手順、事実、理由が混ざり（README の準備の手順と仕組みの説明など）、同じ言葉が場所によって
別の意味で使われ（PR の「head」がブランチもコミットも指すなど）、ADR が増えて `Amended by` をたどらないと
今の姿が分からない、といったことが起きていた。

## Decision

### 区切り（Bounded Context）は届く先で決める

知識は、届く先（誰が読めるか）と持ち主が同じものを一つの区切りにまとめる。

| 区切り | 置くもの | 届く先 |
| --- | --- | --- |
| platform | 共通のルール、ロール、スキル、ハーネスの契約、用語集 | すべてのエージェント（プラグインで配る） |
| target-template | ターゲットの契約（イメージの要件、`make check`、CLAUDE.md の骨組み）、devcontainer、CI | すべてのターゲット（テンプレートから作る） |
| control-plane | アプリの仕組み、設定、運用の手順、Go の書き方 | control-plane の開発者 |
| 各ターゲット | プロダクトの前提（目的、使われ方、公開方法、守る互換）、そのリポジトリの判断 | そのターゲットのエージェント |

切り出すまでは、このリポジトリの `docs/platform/` と `platform/`、`docs/target/` と `.devcontainer/` などが、
それぞれ platform と target-template の区切りに当たる。

### 区切りをまたぐのは、契約と用語集だけ

- **ハーネスの契約**：control-plane がエージェントのコンテナに渡すもの（環境変数、マウント、認証情報、作業の
  ブランチ、報告の仕方）と、その制約。作るのは control-plane だが、使うエージェントに届くよう platform に置き、
  control-plane はそれに合わせて作る（Published Language）。
- **ターゲットの契約**：ターゲットが何を用意すれば control-plane で動くか。target-template に置き、control-plane は
  それを前提にする。
- 契約は先に書き（Schema-First）、実装やターゲットとの食い違いは検査で見つける。
- **用語集**：区切りをまたいで使う言葉（ターゲット、エージェント、ロール、セッション、ハーネスなど）は、どこにでも
  届く platform に一つだけ置く。一つの区切りの中だけで使う言葉は、その区切りの参照の文書で定める。一つの言葉は
  一つの意味で使う。

### 区切りの中は、文書の種類で分ける（Diátaxis ＋ ADR）

| 種類 | 書くもの |
| --- | --- |
| 手順 | 目的を果たすための手順（準備、追加、移行、復旧） |
| 参照 | 事実の一覧（設定、契約、プラグイン、用語） |
| 解説 | 今の姿と考え方。ADR をたどらなくても今の姿が分かるようにまとめる |
| ADR | 判断と、選ばなかった案と、理由 |

- 1 つの文書は 1 つの話題の 1 つの種類だけを持つ。変わる理由が 2 つあれば分ける。
- 種類ごとにディレクトリを分けるかは、文書の数で決める。
- チュートリアルは置かない。

### 届け方は段階的にする（Progressive Disclosure）

- 入口（README、CLAUDE.md、各区切りの README）は短くし、詳しい文書への一覧にとどめる。
- エージェントに常に読み込ませるもの（CLAUDE.md、rules プラグインが読み込ませるもの）は、守るべき前提と行き先
  だけにする。詳しいものはスキルや文書にし、必要なときに読ませる。

### 機械で確かめる（Docs as Code）

- 文書の種類や ADR の状態などは、本文ではなく frontmatter に機械で読める形で持たせ、CI で確かめる。
- 何を確かめるか（リンク、ADR の参照、ターゲットの CLAUDE.md の骨組み、target-template との食い違い、常に読み込ませる
  ものの量など）は、要るものから足す。

## Alternatives

- **今のまま関心で分け、全体の知識をこのリポジトリに置く**：control-plane のリポジトリを読めないエージェントに、
  ハーネスや用語が届かない。
- **ハーネスの知識を、ターゲットごとの CLAUDE.md に書く**：ターゲットの数だけ同じ説明がずれていき、control-plane を
  変えても行き渡らない。
- **ハーネスの契約を control-plane のリポジトリに置き、エージェントにそのリポジトリを読ませる**：ターゲットの
  エージェントに別のリポジトリへの認証を渡すことになり、要るのは契約だけなのにアプリの内部まで見せることになる。
- **用語集を区切りごとに持つ**：区切りをまたぐ言葉の意味が区切りの間でずれる。
- **文書の種類を分けず、話題ごとに一つの文書にする**：手順を探す人と理由を探す人が同じ文書を読むことになり、
  一つの文書が複数の理由で変わる。
- **チュートリアルも置く**：使う人が限られ、README の始め方と手順で足りる。

## Consequences

- overview の「全体の知識は control-plane に」は、全体の設計は control-plane に置き、エージェントに要る部分
  （契約と用語）は platform が持つ、に改める。
- 今ある文書は、この区切りと種類に合わせて順に置き直す。置き直すまでは、関心で分けた今のディレクトリが残る。
- platform に、ハーネスの契約と用語集が加わる。ハーネスのことは、書き方のルール（rules プラグイン）とは変わる理由が
  違うので、別のプラグインで届ける。
- control-plane を変えるときに、ハーネスの契約も変える必要がある。食い違いは control-plane の検査で見つける。
