# 依頼と知らせ

依頼が control-plane にどう入り、結果と知らせがどう依頼者に戻るか。使う人から見た依頼の仕方は
[依頼の仕方](../../reference/usage.md)に、エージェントから見た依頼と回答は
[ハーネスの契約](../../../platform/docs/reference/harness.md)にある。プロセスの中の構成要素は
[control-plane の構成](components.md)にある。

## 全体の構成

依頼の入口は二つあり、どちらも `Dispatcher.Execute` に依頼を渡して、それに答えるターンが終わるまで待つ。

```
Slack のメンション ─▶ slackbot.Bot ─▶ HandleMessage ─▶ Dispatcher ─▶ セッションのワーカー
                         ▲               │ 返事、リアクション
                         └───────────────┘
acp run / stop ─▶ httpapi ─▶ Dispatcher（応答の本文で結果を返す）

依頼を待つ人のいない知らせ：
  ワーカー ─▶ sessionObserver ─▶ slackbot.Bot（状態メッセージ、自分で始めたターンの回答、中断）
  SessionCleaner ─▶ sessionObserver ─▶ slackbot.Bot（片付け）
```

- **依頼への返事**は、依頼を受けた入口が返す。Slack では `HandleMessage` が結果に合わせてスレッドに返信し、
  依頼のメッセージにリアクションを付ける。HTTP API では応答の本文になる。
- **依頼を待つ人のいない知らせ**は、`serve.go` の `sessionObserver` が受け、セッションが Slack のスレッドから
  始まっていれば、そのエージェントの Bot に渡す。CLI から始めたセッションには知らせる場所がないので、
  自分で始めたターンの回答をログに書くほかは何もしない。

依頼のメッセージに付くリアクション：

| リアクション | 付くとき |
| --- | --- |
| `:eyes:` | 依頼を受け付けた |
| `:no_entry_sign:` | 依頼が停止で取り消された、ターンが中断された、再起動で中断された |
| `:white_check_mark:` | 前の依頼への返信が、この依頼の答えも兼ねている |

スレッドに投稿されるもの：

| 投稿 | 投稿するもの | きっかけ |
| --- | --- | --- |
| ターンの回答 | `HandleMessage` | 依頼に答えるターンが終わった |
| 状態メッセージ | `slackbot.Bot` | ターンが始まった。終わるまで書き換える |
| 自分で始めたターンの回答 | `slackbot.Bot` | バックグラウンドの処理が終わり、エージェントが自分で始めたターンが終わった |
| 失敗や取り消しの文面 | `HandleMessage` | 依頼者が許可されていない、ターンが失敗した、停止や再起動で取り消された |
| 中断の知らせ | `slackbot.Bot` | 待っている依頼がないのに進めていた処理を、control-plane が止まるときや起動したときに止めた |
| 片付けの知らせ | `SessionCleaner` | セッションを消した、または残す理由があって残した（[セッション](sessions.md)） |

## 構成要素

### `slackbot.Bot`（`bot.go`）

- **責務**：エージェントの Slack アプリとしてメンションを依頼に直して `HandleMessage` に渡し、返事をスレッドに
  書く。
- **置くもの / 置かないもの**：
  - メンションのスレッド（スレッドの外のメンションなら、そのメッセージ自身）を会話にする。会話からセッション ID が
    決まる（[セッション ID](sessions.md#session-id)）。
  - プロンプトには本文を入れず、依頼したユーザー、依頼のメッセージとスレッドの場所だけを書く。本文は、
    `:zap:` で始まるか（流し込み）を見るためだけに使う（[ADR 0020](../../adr/app/0020-slack-requests-by-reference.md)）。
  - Bot が書いたメッセージは依頼にしない。Slack が送り直した同じメッセージ（チャンネルと ts が同じ）は、
    1 時間のあいだ一度だけ扱う。
  - 依頼ごとにゴルーチンで `HandleMessage` を動かす。サーバーが止まるときも依頼の処理は取り消さず、
    `Dispatcher` が閉じて依頼が終わるのを待つ。
  - 返事は Slack の markdown ブロックの上限（12,000 文字）に収まるよう、11,000 文字で切り詰めて省いたことを書き添える。
- **関係**：`ChatResponder` を満たす。Bot のトークンは毎回 `slackauth.Source` から受け取る。
- **当てはめた原則・パターン**：[関心の分離](../../../platform/docs/reference/principles.md#soc)：Slack の受け方と書き方
  だけを持ち、依頼の扱いは `HandleMessage` に任せる。Slack に固有のこと（記号、ブロック、文字数の上限）はここに
  閉じる（[ADR 0016](../../adr/app/0016-chat-entry-point.md)）。

### `slackbot` の状態メッセージ（`status.go`）

- **責務**：ターンごとにスレッドへ状態メッセージを出し、ターンが終わるまで書き換え、そこへの
  `:no_entry_sign:` を停止の指示として受ける（[ADR 0019](../../adr/app/0019-chat-controls-and-status.md)）。
- **置くもの / 置かないもの**：状態（実行中、完了、中断、失敗）、経過時間、今の作業、待っている依頼と
  バックグラウンドの処理の数、セッション ID、止められる間は止め方。書き換えは 5 秒ごとと、変化から 1 秒
  まとめたあと。自分で始めたターンの回答と、中断の知らせの投稿もここにある。
- **関係**：`sessionObserver` から `SessionEvent` を受ける。どの状態メッセージがどのセッションのものかは
  メモリにだけ持つので、再起動の前に出した状態メッセージへのリアクションは効かない。停止は
  `HandleMessage.Stop` に渡し、依頼できる人の指示だけが効く。
- **当てはめた原則・パターン**：[高凝集・疎結合](../../../platform/docs/reference/principles.md#cohesion)：ワーカーは
  状態の値だけを伝え、どう見せるかと Slack の API の回数の抑え方はここで決める。

### `usecase.HandleMessage`（`handle_message.go`）

- **責務**：チャットから届いた依頼を、受信方式に関係なく、依頼者の確認、受付の合図、ターンの実行、返事の順に扱う。
- **置くもの / 置かないもの**：結果ごとの合図と文面。
  - 許可されていない依頼者には、受け付けないと返す。依頼できるのは、エージェントごとの `allowed_users` に
    載っている人だけ。
  - ターンの回答を返信する。回答が別の依頼への返信と同じなら、返信せずに `:white_check_mark:` を付ける。
  - 中断されたターンは、回答があればそれを、なければ中断したことを返す。
  - 停止と再起動で取り消された依頼には、そう返す。
  - 失敗には、セッションが使用中、待っている依頼が多すぎる、内容が空、それ以外の失敗（セッション ID と
    エラー）を書き分けて返す。
- **関係**：会話からセッション ID を決め、なければ作るよう `Dispatcher` に頼む。
- **当てはめた原則・パターン**：[依存の向き](../../../platform/docs/reference/principles.md#dependency-rule)：返事の手段は
  `ChatResponder` で、Slack 以外の受け方も同じユースケースを使える（[ADR 0016](../../adr/app/0016-chat-entry-point.md)）。

### 依頼の順番（`usecase.Dispatcher` のワーカー）

- **責務**：一つのセッションに届いた依頼を、待たせるか、実行中のターンに流し込むかに分け、ターンの結果を
  それを待つ依頼に返す（[ADR 0017](../../adr/app/0017-long-lived-session-process.md)）。
- **置くもの / 置かないもの**：
  - 依頼は受信箱（32 件まで）に入り、ターンがなければすぐに、あれば終わってから一つずつ送る。
    バックグラウンドの処理だけが残っているときは待たせない。
  - 流し込む依頼は、ターンの実行中ならすぐに送る。実行中のターンがなければ、普通の依頼と同じに扱う。
  - 送った依頼は、エージェントが取り込んだ時点（Claude Code が依頼を出力し直したとき）のターンに属する。
    一つのターンに複数の依頼が入ったら、最初の依頼が回答を受け取り、ほかは答えを兼ねたことを受け取る。
  - 停止では、待っている依頼とまだ取り込まれていない依頼を取り消し、バックグラウンドの処理を止め、実行中の
    ターンを中断する。何も動いていないセッションには何もしない。
- **関係**：進み具合を `SessionObserver` に順に伝える。ターンの始まりと終わり、今の作業、待っている依頼と
  バックグラウンドの処理の数の変化を伝える。
- **当てはめた原則・パターン**：[単一の情報源](../../../platform/docs/reference/principles.md#ssot)：セッションの状態は
  ワーカーだけが持ち、状態メッセージはそこから伝えられた値だけを見せる。

<a id="shutdown"></a>

### 停止と再起動の知らせ（`Dispatcher.Close`、`Dispatcher.Recover`）

- **責務**：control-plane が止まるときと起動したときに、動いていた処理を中断し、スレッドに知らせる
  （[ADR 0024](../../adr/app/0024-restart-abandons-running-work.md)）。
- **置くもの / 置かないもの**：
  - 止まるとき：ワーカーごとに実行中のターンを中断してからプロセスを閉じる。待っている依頼には再起動で中断した
    ことを返し、待っている依頼がないのに進めていた処理（自分で始めたターン、バックグラウンドの処理）があれば、
    スレッドに同じことを知らせる。知らせ終えるまで終了を待てるよう、compose の停止の猶予はプロセスを止める期限
    より長い（[コンテナ](containers.md)）。
    止まり始めたあとに届いた依頼は受け付けない。
  - 起動するとき：依頼を受け付ける前に、前の実行が残したエージェントのコンテナを runner に消させ
    （[コンテナ](containers.md#runner)の `RemoveLeftovers`）、そのセッションのスレッドに、再起動で止めたことを知らせる。
- **関係**：知らせは `SessionAbandoned` として `sessionObserver` に伝わる。

### `sessionObserver`（`cmd/acp/serve.go`）

- **責務**：セッションの出来事と知らせを、セッションのエージェントの Bot に渡す。
- **関係**：`SessionObserver` と `SessionNotifier` を満たす。Slack のスレッドから始まったセッションだけを Bot に
  渡し、それ以外は自分で始めたターンの回答をログに書くだけにする。
- **当てはめた原則・パターン**：[依存の向き](../../../platform/docs/reference/principles.md#dependency-rule)：ユースケースは
  知らせる先を知らず、組み立ての場所で入口と結ぶ。

<a id="http-api"></a>

### `httpapi` のサーバー（`server.go`）

- **責務**：HTTP API で依頼と停止を受け、ターンの結果を応答として返す。
- **置くもの / 置かないもの**：ルーティング、トークンの確認、JSON の形、エラーと HTTP の状態の対応。

  | エンドポイント | すること |
  | --- | --- |
  | `GET /healthz` | 動いていることを返す |
  | `POST /v1/turns` | 依頼する。`session_id` を省くとランダムな ID の新しいセッションを始め、付けるとそのセッションの続きにする（なければエラー）。ターンが終わるまで応答を返さない |
  | `POST /v1/sessions/{id}/stop` | セッションを停止する |

  - `/v1/` は `Authorization: Bearer <ACP_API_TOKEN>` を求める。依頼者の確認はこのトークンだけで、
    `allowed_users` は見ない。
  - エラーは HTTP の状態と `code`（`session_busy`、`inbox_full`、`unavailable` など）で返し、セッションが
    あればその ID と作業領域のパスを添える。
  - 会話を持たないセッションなので、状態メッセージは出ず、自分で始めたターンの回答は届かない。
- **関係**：`Dispatcher` を、自分で定めた `TurnRunner` として呼ぶ。クライアントは `httpapi.Client` で、`acp run` と
  `acp stop` が使う（[依頼の仕方](../../reference/usage.md)）。
- **当てはめた原則・パターン**：[スキーマを先に](../../../platform/docs/reference/principles.md#schema-first)：要求、応答、
  エラーの形を `types.go` に定め、サーバーとクライアントがそれを共有する。
