# 0013. まだマージされていない PR の中身を前提にする変更だけ PR を重ね、prctl create に向き先を渡せるようにする

## Context

#105 のセッションで #120 を #119 の上に重ね、このセッションでも #133 を #132 の上に、#135 を #133 の上に重ねた
（Issue #129）。どちらも、下の PR の中身（同じ `prctl` や決まりの文書）を上の PR が変えるためで、既定のブランチから
切ると、下がマージされるまで衝突を抱えるか、待つことになった。

- `prctl create` は向き先をいつも既定のブランチにしていた。重ねるたびに、作ったあと REST API で向き先を付け替えた。
  付け替える前は、上の PR の差分に下の PR の中身がすべて入って見えた。
- ハーネスの契約は、別の PR に分けるときは既定のブランチから切るとだけ書いていた。
- 重ねたあと下の PR に push したときの扱いも、マージの順も決まっていなかった。

## Decision

- conventions の変更の扱い方に、PR を重ねてよいときを決める。PR は既定のブランチから切る。まだマージされていない
  PR の中身を前提にする変更（同じ所を変える、その PR で足したものを使う）だけは、その PR のブランチから切って
  重ね、向き先をそのブランチにする。本文には、どの PR の上かとマージの順（下から）を書く。下の PR に push したら、
  上のブランチに取り込む（merge。履歴を書き換えないので、レビューの記録が残る）。下がマージされたら、上の向き先が
  既定のブランチに変わったことを確かめる。
- ハーネスの契約に、重ねるときは下の PR のブランチから `$ACP_SESSION_BRANCH-<内容>` を切ると書く。
- `prctl create --base <ブランチ>` を足す。ブランチが下のブランチの上にあり（`origin/<下>` を履歴に含む）、下に
  開いている PR があるときだけ作る。
- 重ねた PR で、下が先に進んで取り込んでいないときと、下の PR がもう開いていないときは、`prctl status` と hook
  （ADR 0002 の本文の古さと同じ所）が知らせる。下の PR を直す後のセッションは、上の PR の文脈を持たないので、
  決まりだけでは取り込みを忘れやすい。

## Alternatives

- **重ねずに、下がマージされるまで待つ**：エージェントは依頼者のマージを待てず、まとめて頼まれた作業が止まる。
- **重ねずに、既定のブランチから切って衝突を後で解く**：下と同じ所を変えると、上の差分に下の前の姿への変更が
  入り、レビューの範囲も合わない。
- **上を下に rebase し直す**：履歴を書き換えると、レビューの記録（`commit_id`）が今の履歴から外れ、ブランチ全体が
  まだレビューしていない範囲に戻る（ADR 0005）。
- **作ったあと API で向き先を付け替える（今までのやり方）**：付け替えるまでの間、差分が誤って見え、手順も
  `prctl` の外になる。

## Consequences

- 重ねた PR の差分は、下の PR の中身を含まない。レビューも上の PR の分だけになる。
- マージは下から順にする必要があり、依頼者に順を伝える。
- 下の PR がマージされたときに向き先が既定のブランチに変わるかは、GitHub の設定（マージでブランチを消すか）による。
  このリポジトリは消す設定。変わらなければ、hook が知らせ、エージェントか人が付け替える。
- hook は、重ねた PR のターンの終わりごとに、下のブランチの PR を GitHub に聞く。ただし、本文とレビューが済み CI が
  通った head は覚えて聞き直さない（ADR 0006）ので、そのあとに下が進んでも、上に新しい push があるまで hook は
  知らせない。`prctl status` は、いつでも見る。
