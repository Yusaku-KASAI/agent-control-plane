# 0037. コミットメッセージと PR のタイトルでも閉じるキーワードを使わず、prctl が PR のコミットとタイトルを読んで知らせる

## Context

ADR 0035 は、`prctl` の本文の検査で、文の中の閉じるキーワードを断ることにした。コミットメッセージはその検査の外に
置き、確かめるかを #344 に送った。

GitHub の文書（Linking a pull request to an issue）は、閉じるキーワードをコミットメッセージにも使え、そのコミットを既定の
ブランチに取り込んだときに Issue が閉じると書く。このリポジトリは merge commit で取り込むので、PR のコミットはそのまま
既定のブランチに入り、本文で `Refs #1` と書いて閉じないと決めた依頼の Issue も、コミットメッセージの「Closes #1」で閉じる。
GitHub が作る merge commit のメッセージは、このリポジトリの設定（`merge_commit_message` が `PR_TITLE`）では PR のタイトルを
含むので、タイトルの閉じるキーワードも同じに読まれうる。

実際に、PR #281 の 4 つのコミットのメッセージは「Closes #245」を持っていた。#245 はその PR の本文の `Closes` で閉じる
はずのものだったので害はなかったが、依頼の Issue を `Refs` で残す PR で同じ書き方をすれば、範囲の中の項目が済まないまま
Issue が閉じる。

## Decision

- conventions の書き方に、コミットメッセージと PR のタイトルでは閉じるキーワードの後ろに Issue を書かないことを足す。
  Issue を閉じるのは本文の `Closes` の行だけにする。
- `prctl` は、PR のコミット（GitHub の compare の API が、PR の向き先から push した head までとして挙げるもの）のメッセージを、本文の文の中と同じ正規表現
  （`closing_re`）で読み、閉じるキーワードと後ろの Issue があれば、本文とレビューとともに足りないもの（`pending_message`）
  として知らせる。push のあとの hook、ターンの終わりの hook、`prctl ready` が同じ判定を使う。
- PR の今のタイトルも、同じ判定で読んで知らせる（GitHub の画面で変えたものも読む）。書く前に断れるように、
  `prctl create` と `prctl update --title` も同じ正規表現で読んで断る。
- PR のコミットを読めないときは、閉じるかが分からないことを、ほかの足りないものといっしょに知らせる。黙ると、hook が
  ほかの足りないもの（レビュー、本文、CI）まで言わずにターンを終わらせる。

## Alternatives

- **ハーネスの commit-msg の hook で、コミットするときに断る**：一番早く、書き直しに履歴の書き換えが要らない。ただ、
  hook は control-plane が作業領域に入れるもので、devcontainer や人の手元では効かず、閉じるキーワードの正規表現を
  platform と control-plane の二か所に持つことになる。PR のコミットとして確かめるのは、どこでコミットしても通る
  `prctl` の方で、push のあとの hook がすぐ知らせるので、多くはレビューの前に直せる。commit-msg の hook は、早めたく
  なったときに足せる。
- **ハーネスの pre-push の hook で、push する前に断る**：commit-msg と同じく control-plane の作業領域でしか効かない。
- **`prctl ready` だけで確かめる**：一度で済むが、下書きを外す直前まで気づかず、レビューのあとで履歴を書き換えると、
  レビューした head が履歴から消えてレビューし直しになる。push のあとに知らせる方が、直すのが軽い。
- **手元の git で `origin/<向き先>..HEAD` を読む**：API を読まずに済むが、向き先の参照が古いと、既定のブランチにすでに
  入ったコミット（「Closes #245」を持つものもある）を PR のコミットと読み、直せないものを直すよう言う。GitHub の向き先の
  ブランチと比べる compare の API は向き先のコミットを含まないので、そちらを読む。
- **GitHub の PR のコミットの一覧（`pulls/<N>/commits`）を読む**：PR の番号だけで読めるが、GitHub は push の少しあとに
  一覧を更新するので、push の直後の hook が、直す前のコミットを知らせるか、閉じるキーワードを持つコミットを見落としうる。
  compare の API は push した head を渡して読める。
- **GitHub Actions のジョブで確かめる**：人の PR にも効くが、ターゲットごとにワークフローを足すことになり、エージェントは
  CI の結果を待つまで気づかない。
- **取り込み方の設定で、PR のコミットを既定のブランチに入れない**（squash merge だけにし、そのメッセージを PR の
  タイトルと本文にする）：本文はすでに検査しているので、コミットメッセージを読まずに済む。ただ、merge commit で
  取り込んで PR のコミットを残すのは conventions の変更の扱い方の決まりで、変えるとレビューを付けたコミットが既定の
  ブランチに残らない。設定はターゲットごとに人が変えるもので、`prctl` からは守れない。
- **GitHub の ruleset のコミットメッセージの制限で、push をサーバーで断る**：どこでコミットしても効き、人の PR にも
  効く。ただ、ターゲットごとに人が設定するもので `prctl` からは守れず、使えるプランが限られる（このリポジトリで
  使えるかは確かめていない）。
- **決まりだけにして、検査にしない**：PR #281 のように実際に書かれており、閉じたことはマージのあとまで表に出ない。
  仕組みで守る方を採る。
- **依頼の Issue を閉じるキーワードだけは通す**：本文の `Closes` と同じ Issue なら害はないが、ADR 0035 と同じく、比べる
  道具が要り、`Refs` のときの抜けが残る。コミットメッセージで閉じるキーワードを使う要はないので、どの Issue でも知らせる。

## Consequences

- PR のコミットのメッセージかタイトルに閉じるキーワードがあると、hook がターンを止め、`prctl ready` は下書きを外さない。直すには
  メッセージを書き直して force push する。force push のあとは、レビューした head が履歴から消えていれば、レビューし直しになる。
- コミットメッセージには書式がないので、バッククォートの中の閉じるキーワードも読む（本文と違う）。
- hook のたびに PR のコミットを API で読む。読めないと、一時的な失敗でも、閉じるかが分からないとしてターンを一度止め、
  `prctl ready` は下書きを外さない。
- 下書きを外し、ターンの終わりの hook が済んだと覚えた head では、次の push かレビューまでタイトルを読み直さない。その
  あとに GitHub の画面で変えたタイトルは、マージまで知らせないことがある。
- マージする人が書き換えた merge commit のメッセージは読まない。
- merge commit のメッセージに本文が入る設定（`PR_BODY`）のターゲットでは、本文のコードの中の閉じるキーワード（ADR 0035 で
  通すもの）も merge commit のメッセージに入り、Issue を閉じうるが、読まない。
- GitHub が merge commit のメッセージの中の PR のタイトルから Issue を閉じるかは、確かめていない（閉じうるとして断る）。
