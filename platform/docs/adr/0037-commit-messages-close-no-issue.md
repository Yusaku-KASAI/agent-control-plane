# 0037. コミットメッセージと PR のタイトルでも閉じるキーワードを使わず、prctl が PR のコミットを読んで知らせ、タイトルを断る

## Context

ADR 0035 は、`prctl` の本文の検査で、文の中の閉じるキーワードを断ることにした。コミットメッセージはその検査の外に
置き、確かめるかを #344 に送った。

GitHub の文書（Linking a pull request to an issue）は、閉じるキーワードをコミットメッセージにも使え、そのコミットを既定の
ブランチに取り込んだときに Issue が閉じると書く。このリポジトリは merge commit で取り込むので、PR のコミットはそのまま
既定のブランチに入り、本文で `Refs #1` と書いて閉じないと決めた依頼の Issue も、コミットメッセージの「Closes #1」で閉じる。
GitHub が作る merge commit のメッセージは PR のタイトルを含むので、タイトルの閉じるキーワードも同じに読まれうる。

実際に、PR #281 の 4 つのコミットのメッセージは「Closes #245」を持っていた。#245 はその PR の本文の `Closes` で閉じる
はずのものだったので害はなかったが、依頼の Issue を `Refs` で残す PR で同じ書き方をすれば、範囲の中の項目が済まないまま
Issue が閉じる。

## Decision

- conventions の書き方に、コミットメッセージと PR のタイトルでは閉じるキーワードの後ろに Issue を書かないことを足す。
  Issue を閉じるのは本文の `Closes` の行だけにする。
- `prctl` は、PR のコミット（GitHub の API が PR のコミットとして挙げるもの）のメッセージを、本文の文の中と同じ正規表現
  （`closing_re`）で読み、閉じるキーワードと後ろの Issue があれば、本文とレビューとともに足りないもの（`pending_message`）
  として知らせる。push のあとの hook、ターンの終わりの hook、`prctl ready` が同じ判定を使う。
- タイトルは、`prctl create` と `prctl update --title` が同じ正規表現で読んで断る。

## Alternatives

- **ハーネスの commit-msg の hook で、コミットするときに断る**：一番早く、書き直しに履歴の書き換えが要らない。ただ、
  hook は control-plane が作業領域に入れるもので、devcontainer や人の手元では効かず、閉じるキーワードの正規表現を
  platform と control-plane の二か所に持つことになる。PR のコミットとして確かめるのは、どこでコミットしても通る
  `prctl` の方で、push のあとの hook がすぐ知らせるので、多くはレビューの前に直せる。commit-msg の hook は、早めたく
  なったときに足せる。
- **ハーネスの pre-push の hook で、push する前に断る**：commit-msg と同じく control-plane の作業領域でしか効かない。
- **`prctl ready` だけで確かめる**：一度で済むが、下書きを外す直前まで気づかず、レビューのあとで履歴を書き換えると、
  レビューした head が履歴から消えてレビューし直しになる。push のあとに知らせる方が、直すのが軽い。
- **手元の git で `origin/<向き先>..HEAD` を読む**：API を読まずに済むが、向き先の参照が古いと、既定のブランチにすでに
  入ったコミット（「Closes #245」を持つものもある）を PR のコミットと読み、直せないものを直すよう言う。GitHub が挙げる
  PR のコミットは向き先のコミットを含まないので、そちらを読む。
- **GitHub Actions のジョブで確かめる**：人の PR にも効くが、ターゲットごとにワークフローを足すことになり、エージェントは
  CI の結果を待つまで気づかない。
- **決まりだけにして、検査にしない**：PR #281 のように実際に書かれており、閉じたことはマージのあとまで表に出ない。
  仕組みで守る方を採る。
- **依頼の Issue を閉じるキーワードだけは通す**：本文の `Closes` と同じ Issue なら害はないが、ADR 0035 と同じく、比べる
  道具が要り、`Refs` のときの抜けが残る。コミットメッセージで閉じるキーワードを使う要はないので、どの Issue でも知らせる。

## Consequences

- PR のコミットのメッセージに閉じるキーワードがあると、hook がターンを止め、`prctl ready` は下書きを外さない。直すには
  メッセージを書き直して force push する。force push のあとは、レビューした head が履歴から消えていれば、レビューし直しになる。
- コミットメッセージには書式がないので、バッククォートの中の閉じるキーワードも読む（本文と違う）。
- hook のたびに PR のコミットを API で読む。読めないときは、hook は何も言わず、`prctl ready` は失敗する。
- GitHub の画面で変えたタイトルと、マージする人が書き換えた merge commit のメッセージは読まない。
- GitHub が merge commit のメッセージの中の PR のタイトルから Issue を閉じるかは、確かめていない（閉じうるとして断る）。
