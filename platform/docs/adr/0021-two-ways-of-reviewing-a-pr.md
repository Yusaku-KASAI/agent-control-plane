# 0021. PR の差分のレビューを、通常と念入りの二つの回し方に分け、PR のラベルで見分ける

## Context

ADR 0005 で push のたびに前回からの差分を、ADR 0014 で終える前に PR 全体を、すべての観点でレビューすることにした。
ADR 0014 は、提案や必須を直したらもう一度 PR 全体をレビューし、5 回で終えられなければ依頼者に返すとした。

直近にマージした 11 件の PR（#172〜#189）では、レビューは 73 回で、すべて PR 全体だった（前回からの差分のレビューは
0 回）。1 件あたりは中央値 5 回、最多は 15 回（#183）で、上限は依頼者が続けるよう言って数え直していた。提案は 10 回目を
過ぎても 1 回に 1〜3 件出続け、必須は 73 回のうち 15 回で出た。必須が、必須のないレビューが何回か続いたあとに出た
PR もある（#187 の 7 回目、#189 の 9 回目と 10 回目）。

依頼者は、レビューで質を保ちつつ、ラリーの回数、時間、トークンを抑えたいと考えている。取り込める所まで来たら
マージして先に進み、残りは手の空いたときの全体のレビュー（監査）で拾う。そのうえで、次の二つの回し方を示した
（Slack）。

- PR のレビュー（明示的に頼まれたときを除く）：PR 全体のレビューだけ。読むエージェントは一つ。指摘を直すか、直したら
  もう一度見るかは今と同じ（必須は直す、範囲の中の提案は直す、直したらもう一度 PR 全体を見る、直しがないか細部だけなら
  終える）。今の決まりでは、範囲の中の提案は、直すか直さない理由を書く。依頼者はこれを「今と同じ」としたので、
  決まりはそのままにする。ただし、必須のないレビューが 3 回続いたら、そこで打ち切って終えてよい（残りは全体のレビューで拾う）。
- 全体のレビュー：全体のレビュー、PR 全体、前回からのレビューのすべてを含む。終える条件は回数のほかは今までどおりで、
  上限は 10 回。読むエージェントは観点ごとに並べる。

Issue #170 は、直したあとを前回からの差分で見て PR 全体を終える前にだけ回す案を、#171 は、観点「別の形」の指摘が
出にくいことを扱っていた。

## Decision

- conventions の `reviews.md` に「回し方」の節を足し、変更した人が頼む PR の差分のレビューを、通常（既定）と念入りに
  分ける。念入りは、依頼者が念入りに頼んだ PR と、全体のレビューの報告から作る PR に当てる。指摘を直すか、直したら
  もう一度見るか（レビューしない直しは細部への直しだけ）と、終える条件は、どちらも同じにする。
  - **通常**：PR を作ったあとのレビューも毎回 PR 全体にし、前回からの差分のレビューはしない。一人がすべての観点で読む。
    必須の指摘のない PR 全体のレビューが 3 回続いたら、そこで打ち切って終えてよい。そのレビューの提案は、範囲の中の
    直しでも、打ち切りを理由に直さずに終えてよい。
  - **念入り**：今までの回し方。push ごとに前回からの差分、終える前に PR 全体をレビューし、PR 全体のレビューの指摘を
    直したら、前回からの差分を挟まず PR 全体をもう一度レビューする。観点ごとに読む人を分けて並べ、頼んだ人が一つの
    結果にまとめる。打ち切りはない。
  - 依頼者に返すのは、どちらも PR 全体のレビューを 10 回しても終えられないとき（今までの 5 回から増やす）。依頼者が
    10 回と言ったのは念入りについてだが、通常は 3 回で打ち切れるので、上限に当たるのは必須が出続けるときだけになる。
    上限を一つにして、`prctl` の判定と数え直しを回し方によらず同じに保つ。
- 全体のレビュー（監査）は、回し方によらず、観点ごとに読む人を分けて並べる。
- 回し方は、PR のラベル `念入りのレビュー` で示す。`prctl mode` が付け外しし、`prctl` は、ラベルがあれば念入り、なければ
  通常と読む。通常の PR には、前回からの差分のレビュー（`"scope": "since"`）を残させない。push のあとの hook の案内と
  `prctl unreviewed` も、回し方に合わせて PR 全体のレビューか前回からの範囲のレビューを促す。
- 終えてよいかの判定（`lib/review.jq` の `final_errors`）は変えず、上限の既定（`PRCTL_FINAL_CAP`）を 10 にする。通常の
  打ち切りは `prctl` が数えない。打ち切った提案は「直さない」の答えになり、今の終える条件で終えられる。

## Alternatives

- **#170 の案（直したら前回からの差分、PR 全体は終える前だけ）**：PR 全体のレビューの回数は減るが、前回からの差分の
  レビューと PR 全体のレビューを交互に回すので、ラリーの数は減らない。依頼者は、前回からの差分のレビューはラリーを
  増やすだけと見ている。念入りでは、今までの回し方のまま前回からの差分も使う。
- **通常では、必須のない PR 全体のレビューを一度で取り込み、そのあとの提案への直しはもう一度見ない**：直近の 11 件に
  当てはめると 19 回まで減るが、直しを誰も見ないまま取り込み、#173 と #178 の 3 回目のような遅れて出る必須も拾えない。
  依頼者は、直したらもう一度見るのは今と同じにしたいと答えた。
- **打ち切りを `prctl` が数えて、ターンの終わりに知らせる**：打ち切っても、提案に「直さない」と答えれば今の終える条件で
  終えられるので、判定は変えなくてよい。数えるのはレビューを頼む人で足りる。数え間違いが続くなら足す。
- **通常の上限を 5 回のままにする**：上限を回し方ごとに持つことになる。通常で上限に当たるのは必須が出続けるときだけで、
  そのときに 5 回目で返すか 10 回目で返すかの違いは小さい。
- **回し方を `prctl ready` の引数で渡す**：ターンの終わりの hook が回し方を知れない。PR に持たせれば、依頼者も
  GitHub で付け外しでき、セッションをまたいで残る。
- **回し方を PR の本文の隠した印に持たせる**：本文は `prctl update` で書き換えるたびに印を保つ必要があり、人からも
  見えない。

## Consequences

- 直近の 11 件に通常の打ち切りを当てはめると、レビューは約 48 回（今は 73 回）になる。必須が遅れて出た #187 の 7 回目と
  #189 の 9 回目、10 回目は、打ち切りで拾えなくなる。それらは、あとの全体のレビューか、次の変更で見つける。
- 念入りでは、レビューのたびに観点の数（7）だけサブエージェントが動き、トークンが増える。
- 観点「別の形」だけを受け持つ人が読むのは、念入りと全体のレビューだけになる。通常の PR でそれが出にくいこと（#171）は
  残る。
- ラベルは、`prctl mode thorough` が初めて付けるときにリポジトリに作る。developer の App が Issue に書けることを前提にする。
- 打ち切りの数え方（3 回続いたか）は、レビューを頼む人の数えに任せていて、検査はない。
