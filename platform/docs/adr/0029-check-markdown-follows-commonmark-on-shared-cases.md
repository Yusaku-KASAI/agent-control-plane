# 0029. check-markdown は、パーサーにせず CommonMark に倣った走査で読み、例の一覧を slack プラグインが持つ

## Context

slack プラグインの `check-markdown` は、Slack で崩れる形を行ごとの手書きの走査で見つける（ADR 0028）。ADR 0028 は、
パーサーへの置き換えを、control-plane の直しを置き換えるか（#258）と一緒に考え、走査の誤りが続くなら置き換えると
書いた。control-plane の直しと同じに読むかを確かめる試験は「まだ置かない」とし、食い違いが続くなら、例の一覧を
両方の試験が読む形を考えると書いた。

そのあと、閉じを見つけられないフェンス（入れ子の引用の閉じ、引用やリストの項目の終わりで閉じるフェンス）のあとを
すべて読まない誤りと、引用の中の番号付きのリストの入れ子の見逃しが残っていた。依頼者は、一般的な Markdown ではなく
Slack に特有の読み方があるなら、ライブラリの実装の中身も参考にしつつ、個別に実装すればよい、と考えた（2026-10-25）。

## Decision

- `check-markdown` は、パーサーのライブラリにせず、行ごとの走査のまま、CommonMark の規則に倣って読む。
  - コードブロックは、閉じの行のほか、引用の中のものは引用が終わると（引用の印の少ない行）、リストの項目の中のものは
    その項目が終わると（項目の内容より浅く字下げした、別の項目の印の行）閉じる。字下げのタブは、次の 4 の倍数の桁まで進める。
  - リストの項目は、項目の印の行から内容の字下げを取って追う。字下げのない続きの行（遅延の続き）も項目の終わりと
    みなす。
  - 引用の中のリストは、引用ごとに読む。リストの項目の中の引用が終わると、その項目の読みに戻る。空行も引用を
    終える。
  - 項目の内容より浅く字下げした行は、CommonMark と違い、別の項目の印で始まるときだけ項目の終わりとみなし、ほかの
    行（閉じの行、ヒアドキュメントの `EOF` のような字下げできないコードの行）はコードの中とみなす。CommonMark
    どおりだと、そこで項目とともにブロックが閉じ、書き手の閉じの行が新しいフェンスを開いて、あとの本文をすべてコードと
    して読む。Slack はリストの項目の中のフェンスをコードブロックとして読まないので、CommonMark に合わせる理由は弱い。
  - 参照形式のリンク（`[…][…]`）は、インラインのリンクと同じく表示の文とみなし、中の URL を見つけない。
- 例を `tests/markdown-cases.json` に一つの一覧（名前、文、知らせる行）として置き、slackctl の試験はそれを読む。一覧の
  持ち主は slack プラグインで、ほかの道具（Slack に投稿する前に Markdown を直すものなど）の振る舞いは置かない。
  ほかの道具は、この一覧と `check-markdown` を前提にして、自分の試験で読み分けがそろっていることを確かめてよい。

## Alternatives

- **Markdown のパーサー（markdown-it-py など）で読む**：構文の見分けはライブラリが正しく持つが、`python3` に
  入っていないライブラリを入れていない環境では動かない（ADR 0028）。残っていた誤りは、規則を倣えば直せる種類だった。
- **一覧に、ほかの道具が直した文も置く**：両側の試験がそれぞれの言語の中で済むが、プラグインがほかの区切りの振る舞いを
  持ち、その道具を変えるたびにプラグインを直すことになる。
- **二つの読み分けを、同じ入力を作って比べる（差分のファジング）**：例にない食い違いも見つかるが、試験が重く、今の
  規模では例の一覧で足りる。

## Consequences

- リストの項目の中で閉じを書き忘れたフェンスは、次の項目の印の行か引用の終わりまで開いたままになる。そのあいだの
  字下げのない本文は、コードとして読む。
- 閉じを書き忘れたフェンスのあとも読み、崩れを黙って見逃さない。
- 見つける形を変えるときは、一覧に例を足す。一覧を読むほかの道具の試験も、その例で回る。
- 遅延の続きのあとの字下げしたフェンスは、CommonMark と違って読む。
