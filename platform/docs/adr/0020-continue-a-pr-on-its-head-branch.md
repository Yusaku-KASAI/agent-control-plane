# 0020. 既存の PR を続けるときは、新しいブランチを切らずその PR の head ブランチで作業する

## Context

control-plane 経由のエージェントには、作業するブランチとしてセッションのブランチ `ACP_SESSION_BRANCH` が渡される
（control-plane の ADR 0012）。Slack ではセッションがスレッドから決まるので、スレッドを替えて既存の PR を続けると、別の
セッションになり、別のセッションのブランチが渡される。

ハーネスの契約は、別の PR に分けるときと、ほかの PR に重ねるとき（ADR 0013）のブランチの切り方だけを書いていた。
既存の PR を続けるときの扱いは依頼文で毎回指示していた。指示がないと、新しいスレッドのセッションがその PR の
ブランチを rebase して force push したうえ、自分のセッションのブランチで別の PR を作ることがあった（PR #49 と #60）。

## Decision

- ハーネスの契約の「作業領域とブランチ」に、既存の PR を続けるとき（ほかのセッションや人が作った PR も含む）は
  新しいブランチを切らず、その PR の head ブランチを取ってきて作業し、push してその PR を更新すると書く。
  手元に同じ名前のブランチがもとからあれば、そのブランチに switch したあと `git pull --rebase origin <ブランチ>` で
  リモートの先頭に合わせてから作業する。
- control-plane 経由のセッションに毎回読み込ませる harness の要約（`scripts/context`）にも、この場面を足す。
  破られやすく検査で守れない決まりなので、契約を開かなくても届く形にする。
- ほかのセッションのブランチを扱うことと force push は、続ける作業に要ることがあるので止めない。

## Alternatives

- **いつもセッションのブランチで作業し、続ける PR とは別の PR にする**：一つの変更が二つの PR に分かれ、レビューと
  マージの単位が崩れる。
- **conventions の変更の扱い方に置き、どの動き方にも当てる**：この失敗は、作業するブランチが先に渡され、スレッドを
  替えると別のセッションになるという control-plane 経由の事情から起きる。devcontainer で人と対話するときは、人が
  ブランチを選ぶ。
- **依頼が PR を指すとき、control-plane がその PR の head ブランチを作業するブランチとして渡す**：仕組みで守れるが、
  依頼が既存の PR を続けるものかは自由な文面から機械では見分けにくく、同じスレッドの途中で別の PR に移ることもある。
  作業領域はセッションを作るときに一度だけ作るので、渡すブランチを依頼ごとに替えることもできない。
- **ほかのセッションのブランチへの push や force push を仕組みで断る**：既存の PR を続ける作業や、レビューの指摘に
  答えて履歴を直す作業まで止める。
- **手元のブランチを `merge --ff-only` で合わせるか、リモートの先頭から作り直してまだ push していないコミットを
  載せ直す**：リモートが書き換えられていると、前者は失敗し、後者は見分け方を誤ると書き換え前のコミットを戻す。
- **developer ロールにも同じ要約を置く**：要約は control-plane 経由のどのセッションにも読み込まれるので、二か所に
  重なる。ロールからは契約へ案内する。

## Consequences

- 依頼文でブランチを指示しなくても、既存の PR はその PR で更新される。
- 一つのブランチに複数のセッションが push する。片付けは push の記録でそのブランチを拾う（control-plane の ADR 0026）。
- `git pull --rebase` は、remote-tracking ブランチの reflog から分かれた所を求め、リモートで書き換えられる前に
  push したコミットを除く。作業領域はその reflog を消えないようにしている（control-plane の ADR 0026）。
