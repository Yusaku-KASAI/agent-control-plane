# 0006. CI は待たずに進み、今の head の CI が失敗していればターンの終わりに止める

## Context

push の前に手元で検査を通すことと、CI が失敗したらログを見て直すことは決まっていた（conventions の検査と履歴）。
push のあとに CI の結果を確かめることは、決まりにも仕組みにもなかった。CI が失敗したまま「終わった」と報告できた。

CI は devcontainer のイメージで手元と同じ検査を回す（target-template ADR 0005）が、1 回に数分かかる。結果を待つと、
そのぶん依頼者への答えが遅れる。control-plane 経由のエージェントは、バックグラウンドの処理が終わると自分でターンを
始め、その回答がスレッドに届く。

## Decision

- push の前に、手元で `make check` を通すことを必ずにする。CI は手元で通したことの確かめにする。
- push のあとは CI を待たずに進み、報告には CI の状態（通った、失敗した、実行中）を書く。
- CI の状態は `prctl` の一か所で判定する。各 check の最新の run（`filter=latest`）を、失敗（failure、
  timed_out）、実行中、人の操作待ち（action_required）、取り消し（cancelled、stale）、通った（success、neutral、
  skipped）、なしに分ける。
- control-plane 経由では、push のあと `prctl ci --wait` をバックグラウンドで実行してからターンを終える。check run が
  現れて終わるまで待つ。現れないまま 5 分たつか、1 時間たっても終わらなければ、そうと分かる形で
  終える。CI が終わると自分で始めるターンになり、失敗していれば直して報告する。
- ADR 0002 と 0005 の hook を広げる。ターンの終わりに、この作業ツリーから push した head の CI が失敗していれば止める。
  ほかの状態では止めない。通るか、head にワークフローがないと分かるまでは、その head を済んだとは覚えない。

## Alternatives

- **push のたびに CI が終わるまで待つ**：手元で通した検査を繰り返すだけのことが多いのに、毎回数分待つ。
- **CI のことは報告に書かせるだけにする**：失敗したまま終えることを止められない（仕組みで守る）。
- **実行中でも止めて、待たせる**：待つことが hook に強いられ、待たずに進む決まりと食い違う。
- **人の操作待ちや取り消しでも止める**：ログを読んで直せるものではなく、エージェントにできることがない。
- **`gh pr checks --watch` で待つ**：push の直後で check run がまだないと、待たずに終わることがある。commit status も
  含むので、hook の判定と見る範囲が食い違う。

## Consequences

- CI が実行中のあいだのターンの終わりには、GitHub に問い合わせ続ける（1 回のターンに数回の API の呼び出し）。
- 対話で使うときは、バックグラウンドで待つ仕組みがなく、次のターンの終わりに失敗を知る。
- 人の操作待ちや取り消しの head は済んだと覚えないので、その間はターンの終わりごとに問い合わせる。
- ワークフローはあっても、その head では動かない（`on:` の絞り込み）ときも、check run がないまま済んだと覚えず、
  ターンの終わりごとに問い合わせる。
- 再実行した run が前の run に置き換わることは、`filter=latest` の説明によるもので、実際の再実行では確かめていない。
