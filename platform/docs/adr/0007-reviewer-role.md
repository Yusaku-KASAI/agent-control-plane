# 0007. レビューは guide と分けた reviewer ロールが行い、COMMENT のレビューと Issue だけを書く

## Context

差分のレビューは、変更したエージェントがサブエージェントに頼んで回し、PR に残すようになった（ADR 0005）。同じ
エージェントの中の別の文脈なので、ロールの指示やモデル、前提の読み方は変更した側と同じになる。全体のレビュー
（監査）は、人が頼んで回していた。どちらも、変更した側とは別のエージェントに頼めると、別の目が強くなる。

guide はリポジトリについての質問に、読むだけで答えるロールで、GitHub App は読み取りの権限しか持たない。レビューの
結果を PR と Issue に残すには、書き込みの権限が要る。

## Decision

- レビューは reviewer ロールが行う。guide とは分け、エージェントも GitHub App も別にする。
- reviewer は、依頼が PR を指せば差分のレビューを、指さなければ全体のレビューをする。決まりと手順は conventions の
  レビューの扱い方と review スキルに従う。
- 差分のレビューは、PR 全体を見て、見た head に付けた COMMENT の PR のレビューとして残す（`prctl review --pr`）。
  変更した側のセルフレビューが済んでいても、全体を見る。承認も変更の要求もしない（マージを決めるのは人。
  app ADR 0025）。このレビューは、変更した側のレビュー済みの範囲にも数えられる（ADR 0005）。
- 全体のレビューの報告は Issue にする。
- reviewer はファイルを変更せず、push も PR の作成もしない。GitHub App の権限は、Contents は読み取り、Pull requests と
  Issues は書き込み、CI の結果は読み取り。
- 他人の PR と、全体のレビューで読む既定のブランチは、`prctl worktree` が作る一時的な worktree に head を
  detached で取り出して読む。置き場所は毎回同じなので、あとのシェルからも消せる。作業領域の HEAD を動かさないので、作者に
  向けた hook（ADR 0002、0005、0006）が働かず、セッションの片付けの判定（作業領域の状態）も変わらない。
- 自動のきっかけ（PR の作成や push、定期的な実行）は作らず、人が頼む（#59、#91）。

## Alternatives

- **guide にレビューも任せる**：質問に答えるだけの依頼にも書き込みの権限が付く。答えることと、決まりに照らして
  判定し残すことは、変わる理由が違う。
- **reviewer にも承認と変更の要求を許す**：エージェントの判定でマージが止まったり進んだりし、人が確かめる最後の
  防衛線と役割が重なる。
- **reviewer も、前のレビュー（セルフレビューを含む）のあとだけを見る**：変更した側が push のたびにセルフレビューを
  付けるので、reviewer の範囲がほとんど空になり、別の目にならない。
- **作業領域で PR のブランチや head を checkout して読む**：作者に向けた hook が自分のターンで働く。detached のまま
  残ると、どのブランチにもないコミットとして片付けがセッションを残す。
- **全体のレビューの報告を依頼への回答だけにする**：Slack のスレッドに埋もれ、直す作業（developer への依頼）から
  指せない。

## Consequences

- reviewer のエージェントごとに、GitHub App（と、使うなら Slack アプリ）を用意する。
- reviewer が PR に付けたレビューで、その head までがレビュー済みになるので、変更した側のセルフレビューは、そのあとの
  push の範囲だけになる。観点を絞って頼んだレビューでも同じに数える。
- reviewer の指摘に変更した側が答える仕組みはない。人が developer に頼んで答えさせる。
- COMMENT だけを付けることは、指示と `prctl review` で守る。GitHub App の Pull requests の書き込みの権限は、PR の
  編集やクローズも許すので、権限では守られない。
