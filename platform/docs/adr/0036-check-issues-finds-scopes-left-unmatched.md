# 0036. check-issues は、範囲の中と扱う PR の付け合わせの漏れも確かめ、範囲の項目の読み方を prctl と共有する

## Context

conventions の課題の扱い方は、範囲の中の項目を扱う PR を項目の末尾の番号で表し、その PR がマージされたらチェックを付け、
マージされずに閉じたら番号を外すことを、次にその Issue に手を入れる人が行うと決めている（範囲の項目と PR の付け合わせ）。
付け合わせで範囲の中がすべて済めば、Issue を閉じる。

ADR 0034 は、マージのときにこれを行う仕組みを作らず、`prctl ready` が、マージされた PR の番号で終わる項目をチェックが
なくても済んだと読むことで、付け合わせの遅れが `Closes` と `Refs` を誤らせないようにした。そのうえで、付け合わせの漏れを
`check-issues` で見つける形を、確かめるものを足す判断が要るとして #306 に送った（PR #335 のレビュー）。付け合わせが
遅れたままだと、Issue の本文は範囲の中のどれが済んだかを表さず、すべて済んだ Issue が開いたまま残る（整っている状態の
「開いているか」と「本文」）。

## Decision

- `check-issues` に五つ目を足す：開いている Issue（テーマ、ロードマップ、キャンバスのほか）の範囲の中が、扱う PR と
  付け合わせてあること。次をずれとして挙げる。
  - チェックがなく、末尾の番号の PR がマージされた項目。
  - チェックがなく、末尾の番号の PR がマージされずに閉じた項目（番号を外す）。
  - 範囲の中の項目がすべてチェックされたのに開いている Issue。
- ADR 0023 の三つの条件に照らす：番号とチェックと PR の状態だけで決まり、判断が要らない。付け合わせの漏れは実際に
  起きる（PR #331、#333、#335 のマージのあと、#306 の項目は手で付け合わせるまでチェックがなかった）。マージされた PR の
  番号は機械で読めるので、誤って落ちにくい。番号が PR でない（404）ものは数えない。
- 範囲の項目の読み方は `lib/markdown.jq` の `scope_items` にし、`prctl ready` と共有する。項目の PR は、末尾の `#N` の
  前が項目の始まりか `owner/repo` に使えない文字（空白、括弧など）のときだけと読む。閉じ括弧のすぐあとの番号
  （「…）#5」）を読み、`owner/repo#N` と `x#5` は読まない（PR #335 のレビュー 741bdc9 の提案 1）。
- 直すのは課題を整える手順とセッションを締める手順のまま。`check-issues` は Issue を書き換えない（ADR 0023）。

## Alternatives

- **`check-issues` が付け合わせを直す（チェックを付け、番号を外す）**：ADR 0023 は Issue を書き換えないと決めている。番号を
  外したときに積んだもののうち残るものを項目にするのは判断が要り、直す手順に任せる。
- **マージのときに GitHub Actions で付け合わせる**：ADR 0034 の理由のまま採らない。
- **項目の読み方を `prctl` と `check-issues` のそれぞれに持つ**：同じ項目を二つの道具が違って読むと、`ready` が通した
  PR を `check-issues` がずれと言うことになる。

## Consequences

- 課題を整えるときとセッションを締めるときに、付け合わせの漏れが `NG` の行で挙がる。範囲の中に PR の番号のある項目の
  数だけ、GitHub に PR を聞く。
- すべて済んだのに開いている Issue は、続けて範囲の中に足すものがなければ閉じる（課題の扱い方の付け合わせ）。足すかは
  `check-issues` では分からないので、直す手順が決める。
- `prctl ready` は、閉じ括弧のすぐあとの番号を項目の PR と読むようになり、このリポジトリの Issue を `owner/repo#N` で
  書いた行も `#N` と同じに確かめる。
