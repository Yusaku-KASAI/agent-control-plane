# 0035. prctl の本文の検査は、文の中の閉じるキーワードも読み、文の中で Issue を閉じる本文を断る

## Context

conventions の書き方は、PR が依頼の Issue を閉じるときは `Closes` の行に、閉じないときは `Refs` の行に依頼の Issue を
置き、ほかの Issue には文の中で触れると決めている（書き方：PR）。`prctl` の本文の検査（`body_check`）は、閉じるキーワードか
`Refs` と Issue で始まる行が挙げる Issue を、依頼の Issue 一つに限ってきた。

GitHub は、閉じるキーワード（close、fix、resolve とその活用。大文字小文字を問わない）を本文のどこにあっても読み、後ろの
`#N`、`owner/repo#N`、Issue の URL が指す Issue を、PR のマージで閉じる。行の始まりだけを見る検査では、「これは fixes #7
の続き」のように文の中で Issue に触れると、検査を通ったまま、その Issue がマージで閉じる。`Refs #1` と書いて閉じないと
決めた依頼の Issue も、文の中の「fixes #1」で閉じる。閉じたことはマージのあとに初めて表に出て、範囲の中の項目が済まない
まま Issue が閉じる（PR #331 のレビュー 81efbcd の提案 1 の案 2、#306）。

書き方の決まりのもとでは、閉じるのは `Closes` の行で、ほかの Issue には文の中で触れるので、文の中で閉じるキーワードを
使う要はない。

## Decision

- `body_check` は、文の中の閉じるキーワードと後ろの Issue を、どの Issue でも断る。`Refs` は含めない（GitHub は `Refs` で
  閉じない）。断る文は、文の中では閉じるキーワードを使わず、閉じるなら `Closes` の行に書くことを伝える。
- 文は、行の始まりの形（閉じるキーワードか `Refs` と Issue。`issue_start_re`）の行ではその始まりの部分を除いた残り、
  コードブロックとインラインのコード（バッククォートの数のそろう組）の外にあるもの。段落（空行かコードブロックまで）
  ごとに改行を空白にしてつなぎ、改行をまたぐキーワードと Issue も読む。
- キーワードの前は行の始まりか、英数字と `_` でない文字にする（`prefix #2` は読まない）。キーワードの後ろには `:` と空白が
  あってよい。Issue は `#N`、`owner/repo#N`、`https://github.com/owner/repo/issues/N` のどれか。
- 閉じるキーワードは `closing_words` の一か所に置き、行の始まりの形と文の中の形の両方がそれを使う。
- 行の始まりの形の確かめ（行が依頼の Issue 一つを挙げるか）は、そのまま残す。依頼の Issue を読むのは行の始まりの形で、
  `prctl worktree pr` と `prctl ready` もそれによる。

## Alternatives

- **行の始まりの形だけを見る今の形のまま**：書き方の決まりは行に置くことを決めていて、文の中のキーワードは決まりの
  外とも読める。ただ、GitHub が閉じるかは行に置いたかによらず、閉じてほしくない Issue がマージで閉じる失敗は、
  マージのあとまで気づけない。検査は書いたときに断れるので、決まりの狙い（閉じると決めた Issue だけを閉じる）を仕組みで
  守る方を採る。
- **文の中の閉じるキーワードが依頼の Issue を挙げるなら通す**（行の始まりの形が挙げる Issue と比べ、違えば断る）：
  比べるために、URL を `owner/repo#N` に読み替え、大文字小文字をそろえ、依頼の Issue の集まりを持つ道具が要る。その
  集まりは `Refs` の行の Issue も含むので、`Refs #1` と文の中の「fixes #1」が通り、閉じないと決めた #1 がマージで閉じる。
  書き方の決まりのもとでは文の中で閉じるキーワードを使う要がなく、どの Issue でも断れば比べる道具も抜けも要らないので、
  採らない。
- **GitHub の `closingIssuesReferences` で読む**（PR を作ったあとに、GitHub が閉じると読んだ Issue を API で取り、依頼の
  Issue と比べる）：GitHub の読み方とずれない。ただ、PR を作る前と本文を書き換える前には読めず、`prctl create` と
  `prctl update` は書いてから断ることになる。本文を書き換えるたびに API を読み、検査が手元の文字列だけで閉じなくなる。
  正規表現でのずれ（GitHub が読まない形を断るなど）は安全側に止まるので、書く前に手元で読む形を採る。
- **一行ずつ読む**：つなぐ手間はないが、折り返しでキーワードと Issue が別の行に分かれた文を読まない。GitHub が改行を
  またいで閉じるかは確かめておらず、安全側（断る側）に倒して段落ごとにつなぐ。

## Consequences

- 文の中で Issue に触れるときは、閉じるキーワードを使わずに書く（「#7 の続き」など）。依頼の Issue と同じ番号でも、文の
  中なら断る。
- キーワードの直後に空白も `:` もない形（`fix#3`）も、文の中の閉じるキーワードと読んで断る。段落をつなぐので、行の
  終わりのキーワードと次の行の始まりの Issue も断る。
- インラインのコードは、バッククォートの数のそろう組を外して読む。コードの中に閉じるキーワードを書けば、断らない。
  エスケープしたバッククォート（`` \` ``）は見分けず、インラインのコードの始まりか終わりとして読む。
- コミットメッセージの閉じるキーワードは、この検査の外にある。既定のブランチに入ったコミットのメッセージでも GitHub は
  Issue を閉じうるが、`body_check` は本文だけを読む。確かめるかは #344 で決める。
- Closes の行の Issue は `#N` か `owner/repo#N` で書く。URL で書いた Closes の行（`Closes https://github.com/o/r/issues/1`）は
  閉じるか触れる行と読まず、文の中の閉じるキーワードとして断る。断る文は、`Closes #N` を一行に書くよう言う。
- Markdown のリンク（`fixes [#2](URL)`）、山括弧の自動リンク（`fixes <URL>`）、`www.` の付く URL、`GH-2` の形は読まない。
  GitHub がこれらで閉じるかは確かめていない。
