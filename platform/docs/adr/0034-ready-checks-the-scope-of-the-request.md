# 0034. prctl ready は、依頼の Issue の範囲との付け合わせを確かめ、マージのときの付け合わせは仕組みにしない

## Context

conventions の課題の扱い方は、PR を終えるときに、その PR が扱う範囲の中の項目の末尾に PR の番号を添え、依頼の Issue に
残るものがあれば `Refs`、なければ `Closes` と書くと決めている（範囲の項目と PR の付け合わせ、依頼の範囲）。どちらも
読むことだけで守っていて、番号の添え忘れや、残したままの `Closes` が黙って通る（PR #297 のレビュー 622e718 の指摘 13）。

[conventions の ADR 0034](../../plugins/conventions/docs/adr/0034-scope-as-task-list-keeping-done-items.md) は、扱う PR を項目の末尾の番号だけで表すと決めながら、マージで項目に自動でチェックを
付ける形を、どの項目を済んだとするか（一部だけを扱った PR など）に判断が要るとして採らなかった。項目を PR ごとに分けて
末尾の番号で表すなら、マージされた PR の番号で終わる項目は済んだと機械で読め、その理由は崩れている。かわりに、
[conventions の ADR 0043](../../plugins/conventions/docs/adr/0043-issue-rules-by-form-and-one-triage.md) で、付け合わせを次にその Issue に手を入れる人が行うと決め、手で付け合わせる
決まりが積み上がっている（PR #297 のレビュー 19bd94a の指摘 1。#306）。

## Decision

- `prctl ready` は、本文の `Closes` か `Refs` の行が依頼の Issue（このリポジトリの `#N`）を挙げていれば、その Issue の
  本文の `## 範囲` の節のタスクリストを範囲の中の項目として読み、次のどれかなら下書きを外さない。
  - この PR の番号で終わる項目がない。
  - `Closes` なのに、残る項目（チェックがなく、この PR の番号で終わらず、末尾の番号の PR がマージされていない項目）がある。
  - `Refs` なのに、残る項目がない。
  - `## 範囲` の節がない。
- 末尾の番号の PR がマージされていれば、チェックがなくても済んだと読む（付け合わせの前でも誤らない）。開いている PR か、
  マージされずに閉じた PR の番号で終わる項目は、残ると読む。
- 末尾の番号が PR でない（GitHub が 404 を返す）項目は、残ると読む。PR を読めないときは、Issue を読めないときと同じく、
  下書きを外さずに失敗する。
- 確かめるのは `ready` だけにする。終える前の判定（`status` の `end:`、ターンの終わりの hook）には入れない。Issue は PR と
  関わりなく変わり、下書きを外したあとに依頼者やほかの PR が Issue を書き換えても、終えた PR のターンを止める理由にならない。
- 積んだ指摘（PR を進めるあいだに依頼の Issue のコメントに積んだもの）が項目になったかは見ない。コメントのどれが積んだ
  ものかは、書き方で決まらない。
- マージのときに項目にチェックを付け、閉じた PR の番号を外す仕組みは、今は作らない（下の Alternatives）。

## Alternatives

- **マージのときに GitHub Actions で付け合わせる**（`pull_request` の `closed` で、依頼の Issue の項目にチェックを付けるか
  番号を外し、すべて済めば閉じる）：判断はもう要らないが、どのターゲットにもワークフローと Issue に書ける権限
  （`issues: write`）が要り、エージェントはワークフローを push できない（ハーネスの契約の認証情報）。番号を外したときに
  積んだもののうち残るものを項目にするのは、書き方で決まらず仕組みにできない。`ready` の確かめで、マージされた PR の
  項目はチェックがなくても済んだと読むので、付け合わせが遅れても `Closes` と `Refs` は誤らない。手で付け合わせる決まりが
  また増えるか、付け合わせの遅れで実際に困ったら、ここを量り直す。
- **`prctl` に付け合わせのサブコマンドを足し、次に手を入れる人が回す**：チェックを付けることは機械でできるが、回す
  きっかけは手順のままで、`ready` の確かめが要ることは変わらない。付け合わせの遅れが困りごとになったら、上の仕組みと
  あわせて量る。
- **マージのあとの付け合わせの漏れを `check-issues` で見つける**（マージされた PR の番号で終わるのにチェックのない項目と、
  範囲の中がすべて済んだのに開いている Issue をずれとして挙げる）：ワークフローも Issue に書ける権限も要らず、付け合わせの
  遅れが課題を整えるときとセッションを締めるときに表に出る。ただ、開いている Issue ごとに範囲の項目の PR を読むので、
  確かめるものを足す判断（platform の ADR 0023 の三つの条件）が要る。この ADR では決めず、#306 で決める。
- **終える前の判定（hook）にも入れる**：Decision の理由で採らない。
- **積んだ指摘も確かめる**：Decision の理由で採らない。

## Consequences

- 範囲の中を何本かの PR に分けて並べて開くと、どの PR も `Refs` のまま `ready` を通り、最後の一本も、ほかの PR がまだ
  マージされていなければ `Refs` になる。そのときは、conventions の決まりどおり付け合わせで閉じる。
- ほかのリポジトリの Issue を依頼とする PR と、依頼の Issue のない PR は、これまでどおり確かめない。
- `ready` は、Issue と、項目の末尾の番号の PR を GitHub から読む。読めなければ、下書きを外さずに失敗する。
