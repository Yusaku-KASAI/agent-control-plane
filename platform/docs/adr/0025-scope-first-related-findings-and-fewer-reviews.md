# 0025. 変更の依頼では取りかかる前に範囲を書き、関わりの強い範囲の外の指摘は依頼の Issue に積み、通常のレビューの打ち切りを 2 回にする

## Context

トークンの消費を調べたキャンバス（Issue #240）で、次のことが分かった。

- 一つのスレッドで作業を続けるほど、コンテキストが増える。API の呼び出しのたびに全体を読むので、1 回の費用は
  コンテキストの大きさに比例する。調べたスレッドでは、メインの会話のコンテキストが 17 万から 97 万トークンまで増えた。
- そのスレッドから、関わりの強い Issue が次々にでき（9 件）、それを同じスレッドで順に片付けた。作業の途中で出た関わりの
  強い直しや指摘は、「今回扱うべき」として今の PR に足すか、範囲の外の指摘は Issue にする決まり（`reviews.md` の差分の
  レビュー）に沿って新しい Issue にして、同じスレッドで続けることになりがちだった。範囲の中と外を分ける基準は
  「依頼と Issue の目的」だけで、取りかかる前に書いてはいなかった。
- レビューのサブエージェントは費用の約 3 割を占め、1 回あたり 7〜8 万トークンかかる。通常の回し方は、必須のない PR 全体の
  レビューが 3 回続いたら打ち切ってよい（ADR 0021）。

依頼者とキャンバスで、決まり（conventions）の F1、F2、F5 を Issue #244 で、締めを促す仕組み（control-plane）の F3 を
Issue #245 で進めると決めた。#244 は、F5 の回数を 2 回に、F2 の「独立して取りかかれる」の線引きを「元の Issue を閉じたあと
も、それだけで依頼として成り立つか」にすることを勧めていた。

## Decision

- **範囲を先に書く（F1）**：変更を届けるの 2 段で、取りかかる前に、依頼の Issue の本文の `## 範囲` の節に、範囲の中と
  範囲の外を書く。依頼の Issue がなければ PR の本文に書く。作業の途中で範囲の中を広げず、途中で出た直しとレビューの
  指摘は、これに照らして振り分ける。定義は `issues.md` の「範囲」に置き、`reviews.md` の範囲（観点「依頼との一致」、
  差分のレビュー、終える前）はそれを指す。
- **関わりの強い指摘は依頼の Issue に積む（F2）**：範囲の外の直しや指摘のうち、依頼の Issue を閉じたあとも、それだけで
  依頼として成り立つものだけを新しい Issue にする。ほかは依頼の Issue のコメントに積む（依頼の Issue がなければ新しい
  Issue）。PR が範囲の中を終えても、積んだ指摘が残るなら、その PR では依頼の Issue を閉じず、残るものを Issue に
  コメントする。範囲は、次にその Issue の変更を依頼されたときに書き直す。積んだ指摘への答えは、今の答えの種類
  `Issue にした` に依頼の Issue の番号を渡して書き、`prctl` の答えの種類は増やさない。
- **通常の打ち切りを 2 回にする（F5）**：必須の指摘のない PR 全体の差分のレビューが 2 回続いたら、打ち切って終えてよい。
  ほかの回し方（上限 10 回、念入り）は変えない。

## Alternatives

- **積んだ指摘を、PR を終えるときに一つの「続き」の Issue にまとめる**：依頼の Issue を閉じられるが、成り立たないとした
  指摘のために結局 Issue を作り、前の文脈をその Issue に書き写すことになる。依頼の Issue に残せば、次に頼まれた人は同じ
  Issue の本文とコメントから文脈ごと読める。
- **積んだ指摘が残っても依頼の Issue を閉じ、あとの全体のレビューで拾う**：打ち切りの提案と同じ扱いになるが、積むのは
  直すと決めたものなので、閉じた Issue に埋もれると失われる。
- **範囲の中だけを書き、範囲の外は書かない**：途中で出たものを振り分けるときに、外と決めたことの在りか（ほかの Issue
  など）が分からず、範囲を広げるか迷う。
- **範囲の節を `check-issues` で検査する**：節があるかは機械で見られるが、取りかかっていない Issue には要らず、何を
  書くかは中身なので、検査にするものの条件（誤って落ちにくい）を満たさない（conventions ADR 0028）。
- **打ち切りを 1 回（必須のない PR 全体のレビューが一度出たら終えてよい）にする**：ADR 0021 で、直しを誰も見ないまま
  取り込むとして採らなかった形に近い。2 回なら、提案への直しをもう一度見てから終えられる。
- **打ち切りを `prctl` で数える**：ADR 0021 のとおり、打ち切った提案に「直さない」と答えれば今の終える条件で終えられる
  ので、判定は変えない。

## Consequences

- conventions の決まりなので、それを使うすべてのターゲットに効く。どのターゲットも、プラグインの更新で受け取り、
  ターゲットの側で直すファイルはない。
- 必須のない PR 全体のレビューの 2 回目のあとに出たはずの必須は、打ち切りで拾えなくなる。あとの全体のレビューか、次の
  変更で見つける。
- 積んだ指摘が残る Issue は、PR がマージされても開いたままになり、範囲の節は次の依頼まで、終えた範囲を書いたままになる。
  コメントに残るものを書くので、課題を整えるときは、それを読んで本文の今の姿を確かめる。
- 効き具合は、この変更をマージした日の前と後で、`usage_log` のターンの使用量（app ADR 0036）を比べる。締めを促す
  仕組み（Issue #245）の閾値を決める材料にする。
- 範囲の節があるか、打ち切りを何回で数えたかを確かめる検査はない。
