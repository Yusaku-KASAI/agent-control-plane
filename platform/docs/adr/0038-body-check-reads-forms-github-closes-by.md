# 0038. 本文の検査は GitHub が閉じる形に合わせて読み、改行をまたぐ形は今のまま断る

## Context

ADR 0035 は、`prctl` の本文の検査で文の中の閉じるキーワードを断ることにし、Markdown のリンク、山括弧の自動リンク、
`www.` の付く URL、`GH-N` の形は読まず、エスケープしたバッククォートと数のそろわないバッククォートはインラインのコードの
始まりか終わりとして読むとした。段落の改行をつないで読むので、行の終わりのキーワードと次の行の始まりの Issue も断る。
GitHub がこれらの形で閉じるかは確かめていなかった。

#351 で、形ごとに使い捨ての Issue を本文に書いた PR #381 を merge commit でマージして確かめた（2026-11-03）。GitHub は、
Markdown のリンク（`fixes [#N](URL)`）、山括弧の自動リンク（`fixes <URL>`）、`GH-N`、エスケープしたバッククォートで
囲んだ形、数のそろわないバッククォートの中の形で閉じた。`www.` の付く URL（スキームの有無によらず）、強調で囲んだ
キーワード（`**fixes** #N`）、改行をまたぐ形では閉じなかった。結果の表は #351 にある。閉じた五つの形は、今の検査を
通るのに、マージで Issue を閉じる。

## Decision

- 閉じるキーワードの後ろの Issue に `GH-N` を足し、Issue の前の `[` か `<` を許す（`closing_re`）。リンクの文字と自動
  リンクの中の Issue を、ほかの形と同じに断る。`closing_re` はコミットメッセージとタイトルの検査（ADR 0037）も使うので、
  そこでも同じ形を知らせる。
- インラインのコードを外すときは、GitHub の読み方（CommonMark）に合わせる：左から、エスケープ（バックスラッシュと
  後ろの一文字）か、バッククォートの並びから同じ数の次の並びまで（どちらも、より長い並びの一部でない）を読み、コードだけを
  外す。終わりのない並びとエスケープしたバッククォートは文として読む（`inline_code_re`）。左から読むのは、バックスラッシュ
  自身をエスケープしたときに、後ろのバッククォートをエスケープしたものと読み違えて、組をずらさないため。
- 文は、段落（空行かコードブロックまで）をつないだものと、一行ずつのものの両方で読み、どちらかで閉じるキーワードが
  あれば断る。GitHub はインラインのコードをブロックの中で読み、ブロックは段落のことも、リストの項目や見出しのように一行の
  こともある。つないだものだけで読むと、項目どうしのバッククォートを組にして閉じるキーワードを隠し、一行ずつだけで読むと、
  段落の中で行をまたぐコードの組をずらして隠す。両方で読めば、断る側にだけ倒れ、残るずれは Consequences の一つになる。
- 改行をまたぐ形は、GitHub は閉じないが、今のまま段落をつないだもので読んで断る。
- `www.` の付く URL と強調で囲んだキーワードは、GitHub が閉じないので、読まないままにする。

## Alternatives

- **改行をまたぐ形を断らないように、段落をつながずに一行ずつだけ読む**：GitHub の振る舞いに合い、断りすぎがなくなる。ただ、断りすぎは
  書き直せば済み、起きることもまれで、行の始まりの形との組み合わせ（折り返した次の行が閉じるキーワードで始まる文）の
  読み方も変わるので、見合わない。
- **インラインのコードを外さず、本文のすべての閉じるキーワードを断る**：読み方が単純になるが、コードの中に閉じる
  キーワードを書く説明（この ADR のような）が書けなくなる。GitHub はコードの中では閉じない。
- **CommonMark のパーサーで本文を読む**：読み方が GitHub とそろうが、`prctl` は bash と jq だけで動き、パーサーを足すと
  依存が増える。
- **段落を、CommonMark で段落の途中でもブロックを始める行で分けて、一通りで読む**：GitHub と同じ一通りの読み方になるが、
  字下げ、入れ子、見出しの下線、表などを正規表現で写しきれず、写し誤ると、分けすぎた所でも分け足りない所でも閉じる
  キーワードを隠す（PR #386 のレビューで、分けすぎて前は断っていた本文を通す形が出た）。両方で読む形は、断る側にだけ
  倒れる。
- **GitHub の Markdown の API（`gh api markdown`）で本文を描き、コードの外の文を読む**：依存を増やさずに GitHub と同じ
  ブロックとコードの読み方を得られ、正規表現で写すずれがなくなる。ただ、本文の検査のたびに（hook でも）ネットワークに
  頼り、読めないときの扱いと試験の替え玉が要る。描き方は閉じるかそのものでもない。両方で読む形で残るずれは
  Consequences の一つのまれな形に限られるので、今は選ばない。
- **GitHub に閉じる Issue を尋ねる（PR の `closingIssuesReferences`）**：#351 では、マージの前の結び付きが閉じた Issue と
  ちょうど合い、正規表現で写し続けずに済む。ただ、PR を作る前と本文を書く前（`prctl create` と `prctl update`）には
  読めず、書いてから結び付くまでに間がある。#344 では、タイトルはマージの前に結び付かないのに閉じたので、本文の外の
  所の代わりにはならない。書く前に断れる今の検査を残す。

## Consequences

- `fixes [#2](URL)`、`fixes <https://github.com/o/r/issues/2>`、`fixes GH-2`、`` \` fixes #2 \` ``、``` ` fixes #2 `` ``` を文の中の
  閉じるキーワードとして断る。コミットメッセージとタイトルでも、リンクと `GH-N` の形を知らせる。
- `www.` の付く URL と強調で囲んだキーワードは、GitHub が閉じないので、通しても Issue は閉じない。
- 段落の中で行をまたぐインラインのコードの中に閉じるキーワードを書くと、一行ずつ読んだもので断る（GitHub は閉じない）。
  コードの中に書くなら、一行の中に収める。
- 通してしまいうるのは、二つの読み方がともに閉じるキーワードをコードの中と読み、GitHub だけが文と読む形に限られる。
  一行の中で閉じたインラインのコードの組を、GitHub のブロックの中の前の行の終わりのないバッククォートがずらし、しかも
  段落をつないだものでは別の組になる形で、ブロックの境目が段落の途中にあるときにだけ起きうる。
