# 0010. CI を待つのは一つのブランチに一つだけにし、最後に push した head を追う

## Context

ADR 0006 で、control-plane 経由では、push のあと `prctl ci --wait` をバックグラウンドで実行してからターンを終える
ことになった。バックグラウンドの処理が終わると、エージェントに知らせが届き、自分で始めるターンになる。そのターンの
回答もスレッドに投稿される（ハーネスの契約）。

次のことが起きた（Issue #110 の 2、#125 の A6）。

- CI をバックグラウンドで待ちながら、同じものをフォアグラウンドでも待った。バックグラウンドの方が最後の報告の
  あとに終わり、ターンが一つ増えて、全文の報告がもう一度出た。
- push を重ねるたびに `prctl ci --wait` を始め、古い head を待つ処理と今の head を待つ処理が重なった。古い方の
  終わりも知らせになる。
- 待つためだけに ScheduleWakeup を入れた。知らせの来ない形（`&` と `disown`）で始めかけたこともあった。

`prctl ci --wait` は、始めたときの PR の head だけを待ち、ほかに待つ処理があるかを知らなかった。見張りや二重の待ちを
止める決まりもなかった。

## Decision

- `prctl ci --wait` は、一つのブランチに一つだけ動く。コンテナの `TMPDIR` の中のブランチごとのファイルを `flock` で
  取り、取り合いで取れなければ、動いている方の pid を示して、待たずにすぐ終わる。作業領域のマウント（Docker Desktop
  の fakeowner）の上では `flock` が取り合いにならないので、ファイルは作業領域に置かない。`flock` がないか、取り合い
  以外で失敗したときは守らずに待つ（誰も待たないよりは、二重に待つ方にする）。
- 待つ head は、このクローンの参照（`origin/<ブランチ>`）が指す head にする。ふつうはこのクローンから最後に push
  した head で、ターンの終わりの hook が見るもの（ADR 0005、0006）と同じになる。fetch で取り込んだほかからの push
  も、参照が指せば待つ。参照がないときだけ、PR の head にする。
- 待つ間に参照が動いたら（push で進めても、force push で戻しても、fetch でも）、それまでの結果を捨て、新しい head を
  初めから待つ。待ちが終わると決めたあと、抜ける直前にも確かめる。
- 待ちは push のたびに始める。動いている待ちがあれば、すぐ終わる。前の待ちが終わった知らせは、ツールの呼び出しの
  合間にしか届かないので、エージェントからは動いているように見えても、もう終わっていることがある。
- 決まりとして、ハーネスの契約に、バックグラウンドの処理の終わりは知らせで届くので、Monitor、ScheduleWakeup、
  `sleep` の繰り返し、同じ処理のフォアグラウンドでの実行で見張らないことを書く。github スキルにその要約を置く。

拠り所は[仕組みで守る](../../plugins/principles/docs/reference/principles.md#mechanisms)。待ちを一つにまとめる形は、
同じ呼び出しが重なったら一つだけを動かし、ほかはその結果を受け取る duplicate suppression（Go の `singleflight`）に
倣う。ただし二つ目は結果を受け取らずに終わり、結果は一つ目の知らせで届く。

## Alternatives

- **二つ目の待ちが、一つ目の終わりを待って同じ結果を出す**：知らせが二つになり、同じ報告が二度出る。
- **古い head を待つ処理を、新しい `--wait` が止める**：止められた処理の終わりも知らせになる。止めるには、処理を
  見分けて送る先（pid）を持つ必要がある。
- **pid のファイルだけで守る**：処理が異常に終わるとファイルが残り、別の処理が同じ pid を持ちうる。`flock` は
  プロセスとともに消える。
- **ScheduleWakeup や Monitor を hook で断る**：control-plane 経由でも、開発用サーバーの見張りなど、ほかの使い道が
  ある。今回は、二重の待ちの元になった `prctl ci --wait` を仕組みで一つにし、見張りは決まりで止める。
- **GitHub の PR の head だけを追う**：push の直後は、GitHub がまだ前の head を返すことがある。
- **PR の head と比べて、ほかからの push を見分ける**：PR の head がこのクローンの push より新しいとき、ほかから
  push されたのか、force push で戻したのに GitHub がまだ前の head を返しているのかを見分けられない。hook も
  ほかからの push は見ない。

## Consequences

- push を重ねても、CI の結果の知らせは、最後の head についての一つだけになる。push のたびに始めた待ちは、一つ目が
  動いていればすぐ終わる。その知らせは、ふつう動いているターンの中に入る。
- 待ち直すたびに、check run が現れるまでの 5 分と、全体の 1 時間を数え直す。push を続けると、待ちはその分長く続く。
- 一つ目の待ちが、抜ける直前の確かめのあと、終わるまでのごく短い間に push すると、どの待ちも新しい head を待たない
  ことがある（その間に始めた `--wait` は、まだロックを取れずに終わる）。そのときは、ターンの終わりの hook が新しい
  head の CI を見るが、実行中なら止めない。
- ほかから push された head の CI は、このクローンに fetch するまで待たない。fetch したあとは、作業ツリーの HEAD と
  違っても待つ（hook は、HEAD と同じ head だけを見る）。
- fetch で参照が動いたときも、待ち直して、5 分と 1 時間を数え直す。
- `flock` のない環境（macOS の手元など）では、二重の待ちは防がない。devcontainer のイメージには `flock` がある
  （util-linux）。
- ロックはコンテナの中にあるので、同じ作業領域を別のコンテナから使うと、待ちは一つにならない。
- 待ちの処理の子（`gh`、`sleep`）もロックのファイルを開いたままなので、待ちを止めても、子が終わるまで（`sleep` なら
  最長でポーリングの間隔）ロックが残る。
- Monitor や ScheduleWakeup で見張らないことは決まりだけで、仕組みでは守らない。
