# 0027. エージェントは、頼まれれば Slack に投稿してよい（最後の回答は control-plane が投稿する）

## Context

control-plane 経由で動くエージェントのターンの最後の回答は、control-plane が依頼のスレッドに投稿する。依頼の
プロンプトは「回答を自分で投稿しないでください」とだけ書いていた。そのため、依頼者が「このスレッドに投稿して」
「あのチャンネルに知らせて」と頼んでも、エージェントが投稿してよいかが決まっていなかった。一方で、slack プラグインの
`slackctl post` は、Bot のトークンがあれば投稿できる。

devcontainer で直接動くときは、最後の回答は端末に出るだけで Slack には届かない。動き方によって、最後の回答が
どこに届くかが違う。

Slack アプリに許す権限（Bot のトークンのスコープ）は、アプリを作るときに人が決め、エージェントが操作して困らない
範囲にしてある。

## Decision

- エージェントは、依頼者に頼まれたとき、slack スキルの `slackctl post` で Slack に投稿してよい。頼まれていない投稿は
  しない。投稿先は、依頼のスレッドに限らない。できることは、Slack アプリに許した権限の範囲だけ。
- control-plane 経由で動くときは、最後の回答を control-plane が依頼者に届ける（Slack からの依頼ならスレッドに投稿し、
  CLI からの依頼なら応答で返す）ので、最後の回答は自分で投稿しない（二重に届く）。devcontainer で直接動くときは、
  最後の回答は端末に出るだけなので、頼まれて Slack に届けるなら投稿する。
- この違いをハーネスの契約（依頼と回答、devcontainer で直接動くとき）と slack スキルに書き、依頼のプロンプトは
  「最後の回答は自分で投稿しない。ほかの投稿は頼まれればしてよい」と伝える。

## Alternatives

- **投稿先を依頼のスレッドに限る**：誤った投稿の広がりを抑えられる。ただ、Bot が投稿できるのは参加しているチャンネル
  だけで、権限も人が決めている。依頼者一人が使う環境で、ほかのチャンネルへの知らせを頼むこともあるので、限らない。
- **投稿させない（最後の回答だけにする）**：頼まれても投稿できず、別のチャンネルへの知らせや、最後の回答とは別の
  まとめを残せない。
- **control-plane が投稿を代わりに受け持つ（エージェントが投稿を頼む口を作る）**：認証情報をエージェントに渡さずに
  済むが、口を作る量が大きく、Bot のトークンはすでにエージェントに渡している。

## Consequences

- 依頼者が頼めば、エージェントは依頼のスレッドのほか、Bot が参加するチャンネルにも投稿する。
- 最後の回答を自分でも投稿してしまうと二重に届く。避けるのはスキルと契約とプロンプトの書き方による。
