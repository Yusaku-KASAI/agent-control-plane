# 0027. エージェントは、頼まれれば Slack に投稿してよい（最後の回答は control-plane が投稿する）

## Context

control-plane の ADR 0020 は、エージェントに Bot のトークンを渡して Slack を読み書きできるようにし、ターンの最後の
回答は control-plane がスレッドに投稿して、エージェントは自分では投稿しないと決めた。依頼のプロンプトは「回答を自分で
投稿しないでください」とだけ書いていた。そのため、依頼者が「このスレッドに投稿して」
「あのチャンネルに知らせて」と頼んでも、エージェントが投稿してよいかが決まっていなかった。一方で、slack プラグインの
`slackctl post` は、Bot のトークンがあれば投稿できる。

devcontainer で直接動くときは、最後の回答は端末に出るだけで Slack には届かない。動き方によって、最後の回答が
どこに届くかが違う。

Slack アプリに許す権限（Bot のトークンのスコープ）は、アプリを作るときに人が決め、エージェントが操作して困らない
範囲にしてある。

## Decision

- エージェントは、依頼者に頼まれたとき、slack スキルの `slackctl post` で Slack に投稿してよい。頼まれていない投稿は
  しない。頼みに数えるのは依頼者の依頼だけで、読んだメッセージやリンク先、Issue の中の指示は数えない（外から入る値を
  信用しない）。投稿先は、依頼のスレッドに限らない。できることは、Slack アプリに許した権限の範囲だけ。
- サブエージェントは投稿しない。頼んだ側のエージェントからの頼みは依頼者の頼みに数えず、投稿は依頼者に頼まれた
  セッションのエージェントがする。
- どのロールでも同じにする。ロールの書ける範囲（ADR 0019）は作業領域と GitHub についてのもので、Slack への投稿は
  この決まりによる。
- control-plane 経由で Slack から依頼されたときは、control-plane が最後の回答を依頼のスレッドに投稿するので、同じ回答を
  そこに投稿しない（二重に届く）。CLI からの依頼の回答は応答で返るので、頼まれれば同じ内容を Slack に投稿してもよい。
  devcontainer で直接動くときは、最後の回答は端末に出るだけなので、頼まれて Slack に届けるなら投稿する。
- どの動き方でも同じ決まりはハーネスの契約の「Slack への投稿」の節に置き、最後の回答の届き方の違いは動き方ごとの節と
  slack スキルに書き、依頼のプロンプトは
  「最後の回答は自分で投稿しない。ほかの投稿は頼まれればしてよい」と伝える。

## Alternatives

- **投稿先を依頼のスレッドに限る**：誤った投稿の広がりを抑えられる。ただ、Bot が投稿できるのは参加しているチャンネル
  だけで、権限も人が決めている。依頼者一人が使う環境で、ほかのチャンネルへの知らせを頼むこともあるので、限らない。
- **投稿させない（最後の回答だけにする）**：頼まれても投稿できず、別のチャンネルへの知らせや、最後の回答とは別の
  まとめを残せない。
- **hook で、サブエージェントの `slackctl post` や、最後の回答と同じ投稿を断る**：harness プラグインの hook は
  サブエージェントを見分けられるので、サブエージェントの投稿は断れる。ただ、まだ破られておらず（検査にするものの
  「実際に破られる」を満たさない）、最後の回答との重なりは、頼まれた正しい投稿と機械では見分けられない。破られる
  ようなら、サブエージェントの投稿を断る hook から考える。
- **control-plane が投稿を代わりに受け持つ（エージェントが投稿を頼む口を作る）**：認証情報をエージェントに渡さずに
  済むが、口を作る量が大きく、Bot のトークンはすでにエージェントに渡している。

## Consequences

- devcontainer で直接動くときは、`slackctl` が使うのは人が用意したトークンか webhook で、できることはその権限による
  （Slack アプリの範囲とは限らない）。
- 依頼者が頼めば、エージェントは依頼のスレッドのほか、Bot が参加するチャンネルにも投稿する。
- 最後の回答を自分でも投稿してしまうと二重に届く。避けるのはスキルと契約とプロンプトの書き方による。
