# 0011. レビューの結果と答えを決まった形の JSON で受け、表と機械で読む写しを作る

## Context

ADR 0005 で、差分のレビューの結果を PR のレビューとして残すことになった。指摘に持たせる項目は conventions の
`reviews.md` で決まっていたが、書き方は自由な文で、PR のレビューの本文の形は決まっていなかった。そのため、過去の
PR では形がばらばらだった。答え方も「直したならコミット、直さないなら理由」だけで、形がなく、答えは push の変更点の
コメントに混ざっていた。

依頼者は、レビューを終えてよいかを、レビューの結果から機械的に判定したいと考えている（Issue #134）。たとえば、
終えようとしたときに PR 全体の差分のレビューを強い、必須の指摘や答えていない指摘が残っていないかを見る。それには、
prctl がレビューの結果と答えを読めなければならない。#110 の 3 では、使った決まりを出力に出すことも求められていた。

## Decision

- 差分のレビューの結果の形を、conventions の `reviews.md` の「結果の形」に決める。範囲とその種類（前回からか、PR
  全体か）、見た観点と外した観点（理由）、指摘の表（番号、重さ、観点、場所、要約、拠り所）、表の下の詳しい中身。
  拠り所を表に出すことで、使った決まりが出力に出る。指摘への答えは、番号ごとに、直した、直さない、Issue にした、
  答えたのどれか。
- PR を作る前のレビューと、ほかの人の PR のレビューは、PR 全体の差分のレビューにし、すべての観点で見る。
- `prctl review` は、結果を JSON で受ける。`lib/review.jq` で形を検査し、足りなければ断る。Markdown の表と詳しい
  中身を作り、同じ JSON の写しを base64 にして隠した印に入れる。`scope` が `pr` なら、範囲は PR 全体（PR の向き先から
  分かれた所から）にする。
- 答えは `prctl answer` で、そのレビューへの答えの PR のコメントにする。prctl が残したレビューの印を読み、その指摘
  すべてに答えていなければ断る。PR を作る前のレビューの答えは、結果の JSON の `answers` に書く。push の変更点の
  コメントには、push で何をなぜ変えたかだけを書く。
- `--minor` の記録（ADR 0009）は、これまでどおり自由な文のメモで受ける。

## Alternatives

- **Markdown を人が書き、prctl がそれを読み取る**：表の書き方の揺れを読み取りで吸収することになり、壊れやすい。
  表と機械で読む写しを人が別々に書くと食い違う（依頼者の指摘）。
- **YAML で受ける**：手で書きやすいが、読み書きの道具が要る。prctl はすでに jq を使っていて、JSON ならそのまま検査
  できる。
- **写しを HTML のコメントに JSON のまま入れる**：JSON の中に `--` があると、HTML のコメントが途中で終わる。base64
  にすれば、どんな中身でも安全に入る。
- **答えを push の変更点のコメントに書き続ける**：変更点のコメントは自由な文で、答えを機械で読めない。push のない
  答え（直さない、Issue にした）の置き場所も別になっていた。

## Consequences

- レビューする人（サブエージェント）は、結果を決まった項目で返し、変更した人がそれを JSON にする。手間は増えるが、
  形が足りないものは記録できない。
- 重さと観点の名前は、`reviews.md` と `lib/review.jq` の二か所にある。`reviews.md` を変えたら、`lib/review.jq` も
  直す。
- これまでの自由な文のレビューも、本文のある PR のレビューとして数え方は変わらない。ただ、隠した印がないので、
  `prctl answer` で答えることはできない。
- 終えてよいかの判定（PR 全体の差分のレビューを hook で強いる）は、この形の上に、別の変更で足す（Issue #134）。
