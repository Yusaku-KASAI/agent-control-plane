# 0024. check-issues は今の焦点の PR もずれとして挙げ、締めるときに直す NG を締めの手順に合わせると github スキルに書く

## Context

ADR 0023 の `check-issues` は、ロードマップの今の焦点にある PR を数えなかった。最初のレビューで、マージした PR を
「閉じた Issue」と誤って挙げると指摘されたためで、そのときはまだ、今の焦点に何を並べるかの決まりがなかった。そのあと
conventions の ADR 0029 が、今の焦点には開いている Issue だけを `#<番号>` で並べると決めた。今の焦点にマージした PR が
残っていても（以前の #42 の #139）、検査は黙って通していた。

github スキルは、セッションを締めるときにも `check-issues` を回し、`NG` の行の判断を課題を整える手順に任せていた。
締めで直すのは今の焦点に残る閉じた Issue を外すことなどに限られるのに、締める人がほかの `NG`（Issue のラベルなど）まで
直しにいきうる（#234）。

## Decision

- 今の焦点の PR は、開いていても閉じていても、Issue でないものとしてずれに挙げる。
- 締めで何を直し、何を締めのまとめに書くかは、conventions の締めの手順に置く（conventions の ADR 0030）。github スキルは
  それを出典付きで `check-issues` の出力に当てはめる（`NG` の行のうち、締めの手順の 5 段で直すもの（今の焦点に残る閉じた
  Issue を外すこと）だけを直し、ほかの `NG` は締めのまとめに書く）。課題を
  整えるときは、すべての `NG` を課題を整える手順で判断する。
- PR と、このリポジトリにない番号は、直し方が違う（直し方は conventions の ADR 0030 と課題を整える手順にある）ので、
  別の `NG` の行に出す。

## Alternatives

- **閉じた PR だけをずれにし、開いている PR は今の焦点に並べてよいと決まりに書く**：今の焦点は取りかかる順の Issue の
  並びで、PR はその Issue から辿れる。PR を並べると、PR を閉じたあと Issue が残るかを読み手が見分けることになる。

## Consequences

- 今の焦点で PR に触れていたロードマップは、課題を整える手順で直す。直し方は課題を整える手順にある。
