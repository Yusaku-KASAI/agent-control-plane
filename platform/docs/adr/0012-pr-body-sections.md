# 0012. PR の本文に決まった節を持たせ、prctl が作るときと書き換えるときに確かめる

## Context

PR の本文に書くこと（何をなぜ変えるか、どう確かめたか、確かめていないこと、残っていること）は、conventions の
書き方で決まっていた。ただ、形は決まっておらず、PR ごとに見出しも並びも違った。

#96 では、決まりの文書を読んだのに、判断の軸として使わなかった。#105 で読ませ方を直したが、読んだものを使わせる
仕組みはなかった。#110 の 3 は、使った決まりを出力に出させ、出していなければ止める形（強制機能）を求めていた。
依頼者は、PR の本文とレビューのコメントを、共通の項目（形の決まったもの）と自由な項目に分けたいと考えていた。
レビューの側は ADR 0011 で、指摘の表に拠り所の列を持たせた。

## Decision

- PR の本文は、`## 何を変えるか`、`## 当てはめた決まり`、`## どう確かめたか`、`## 確かめていないこと` の節をこの
  順に一度ずつ持ち、どれも空にしない（conventions の書き方：PR）。節の中は自由に書く。ほかの節はどこに足しても
  よい。見出しのない `Closes #<番号>` などの行と署名の行は、節の中身に数えない（最後の節のあとにふつう書かれるので、
  数えると最後の節が空でも通る）。
- `## 当てはめた決まり` には、判断の軸にした原則、パターン、決まりの名前と、どこにどう当てはめたかを書く。使った
  決まりが PR に出る（#110 の 3）。
- `prctl create` と `prctl update` は、本文を出す前に節を確かめ、足りないか、重なるか、空か、並びが違えば断る。
  コードブロックの中の行は見出しに数えない（節の形を例として引ける）。

## Alternatives

- **本文も JSON で受けて組み立てる**：レビューと違い、本文の中身は機械で読まない。見出しの検査で足りる。
- **`## 当てはめた決まり` の中身を、決まりの名前の一覧と照らす**：名前の書き方の揺れを吸収することになり、壊れ
  やすい。中身が書いてあるかまでにとどめ、何を書いたかはレビューで見る。
- **hook で、本文の節を後から確かめる**：本文を出す道具は `prctl` だけなので、出す前に止める方が早い。

## Consequences

- 節の中身の質（本当に判断の軸にしたか）は、仕組みでは確かめない。レビューと、PR を確かめる人が見る。
- 節の名前は、conventions の書き方と `prctl` の二か所にある。二つが同じかは、`prctl-test.sh` が書き方を読んで
  確かめる。
- 中身のない節は空にできないので、確かめていないことがなければ「なし」と書くことになる。
