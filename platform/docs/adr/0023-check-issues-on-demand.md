# 0023. Issue の決まりのうち判断の要らないものを、github プラグインの check-issues で、整えるときと締めるときに確かめる

## Context

#111：Issue の決まり（conventions の課題の扱い方）が守られているかを、人の気づきのほかに確かめる仕組みがない。
2026-10-22 に数えると、ロードマップ（#42）の「今の焦点」が閉じた Issue を 15 件挙げたままで、ラベルのない Issue が
1 件、閉じた Issue に blocked by された Issue が 4 件あった。締めの手順（conventions の ADR 0024）と課題を整える手順
（conventions の ADR 0025）は、今の焦点を見直すと決めているが、見直すきっかけの外で古くなっていた。

conventions の ADR 0027 は、検査にするものを三つの条件（判断が要らない、実際に破られる、誤って落ちにくい）で選び、
置き場所を、確かめる決まりと状態を読む相手で決めるとした。Issue の状態を読むのは GitHub で、決まりは conventions に
ある。

## Decision

- github プラグインに `check-issues` を足す。確かめるのは、三つの条件を満たす三つ：テーマの Issue とロードマップのほかの
  開いている Issue が、どこを変えるかのラベルと `theme:<名前>` を持つこと。ピン留めした「ロードマップ」の
  `## 今の焦点` の節があり、そこにこのリポジトリの閉じた Issue がないこと（PR は数えない）。開いている Issue が閉じた Issue に blocked by されていないこと。
- 本文が今の姿か、重なり、順番、テーマの狙いは確かめない。判断が要り、課題を整える手順で人とエージェントが見る。
- 検査が知る形（ロードマップの `## 今の焦点` の節に開いている Issue を `#<番号>` で並べ、閉じた Issue に触れないこと、
  どこを変えるかに GitHub の既定のラベルを使わないこと）は、conventions の課題の扱い方に決まりとして書く。その判断は
  conventions の ADR 0029 にある。検査が知る形は、決まりにある形だけにする。
- CI では回さない。Issue は PR と関わりなく変わるので、PR を止める理由にならない。課題を整えるときとセッションを
  締めるときに回し、エージェントには github スキル（その場面を description に挙げる）と pm の指示で届ける。conventions の手順からは名前を出さない（conventions は
  platform を前提にしない）。定期実行（#91）ができたら、そこで回す。
- Issue を書き換えない。直すのは課題を整える手順。

## Alternatives

- **Issue を開いたときやラベルを変えたときに GitHub Actions で検査し、抜けをコメントする**（#111 の案）：ターゲット
  ごとにワークフローと、Issue に書ける権限が要る。ロードマップの古さは Issue を閉じたときに起きるので、全部の Issue の
  出来事を見ることになる。手で回す道具で足りるかを先に見る。
- **schedule の GitHub Actions で定期的に回す**：読む権限だけで足り、`check-protection` と同じく複合アクションで配れる。
  ただ、知らせが失敗した実行の通知のメールになり、直すのは結局、課題を整える手順を頼まれたときになる。直す人
  （エージェント）に届く定期実行は #91 で作るので、そこで回す。
- **github プラグインの hook（Bash のあと）で、`gh issue create`、`close`、`edit` のあとに回す**：人が画面で起こした
  Issue と、PR のマージで閉じた Issue には効かない。今の焦点の古さはマージで閉じたときに起きる。
- **全体のレビューの観点に入れる**（#111 の案）：全体のレビューの範囲は地図の項目（文書、設計、コード）で、Issue は
  その外。機械で決まるものを人の目に戻すことになる。
- **conventions の `check-docs` に入れる**：Issue の状態は GitHub にあり、conventions は外の道具を前提にしない（conventions の ADR 0027）。
- **Issue を起こすスキルやコマンドで、起こすときにラベルを求める**：ロードマップの古さと依存関係は起こすときの話では
  ない。ラベルの抜けは、人が GitHub の画面で起こした Issue でも起きる。

## Consequences

- 今のロードマップ（#42）は、今の焦点で閉じた Issue に経緯として触れていて、新しい決まりに合わない。この判断のあと、
  課題を整える手順で今の焦点を書き直し、経緯は各 Issue に任せる。順番の入れ替えは依頼者が決める。
- 今の焦点の `#N` のうち、このリポジトリの Issue でも PR でもないもの（消した Issue、打ち間違い）もずれとして挙げる。
  このリポジトリの Issue を URL や `<owner>/<repo>#N` で書いたものは数えない（今の焦点は `#<番号>` で書く。conventions の ADR 0029）。

- 課題を整える手順の「ずれを挙げる」と、締めの手順の「課題の今の姿を合わせる」で、機械で挙げられるずれが漏れにくく
  なる。どちらも、`NG` の行を直すか人に渡すかは手順の判断のまま。
- ターゲットのリポジトリでも、github プラグインを有効にしていれば回せる。どこを変えるかのラベルの名前は見ず、
  `theme`、`theme:*`、`canvas`、GitHub の既定のラベル（`isDefault` で読む。課題の扱い方が使わないと決めている）のほかの
  ラベルがあるかだけを見る。リポジトリが独自に作った
  関係のないラベルがあると、どこを変えるかのラベルの抜けを見逃しうる。
