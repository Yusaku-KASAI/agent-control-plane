# 0033. check-issues は、テーマの Issue の本文が三つの節をこの順に一度ずつ持つかも確かめる

## Context

ADR 0023 の `check-issues` は、整っている状態のうち判断の要らない三つ（ラベル、今の焦点、blocked by）を確かめる。
conventions の ADR 0035 は、Issue の本文の形を確かめる検査を、開いている Issue を形に合わせ終えたあとに、検査の三つの
条件（判断が要らない、実際に破られる、誤って落ちにくい）で決めるとして先に送った。

そのあと、テーマの本文の形（`## 狙い`、`## 目指す姿`、`## 進め方` をこの順に持つ。conventions の課題の扱い方の
「テーマ」）が決まり、PR #297 のレビューで、今あるテーマの Issue がすべてその形と違っていたこと、形が判断なしに確かめ
られるのに読む人の気づきに任されていることが挙がった（#306）。今の開いているテーマの Issue は、形に合わせ終えている。

## Decision

- `check-issues` に四つ目を足す：開いているテーマの Issue（ラベル `theme`）の本文が、三つの節をこの順に一度ずつ持つこと。
  同じ節が二度あると「この順に持つ」の順が決まらないので、一度ずつと読む（PR の本文の検査と同じ読み方）。ほかの節は
  あってよい。欠けていれば `NG` の行で、ある節とともに出す。
- 見るのは見出しの有無と順だけで、節の中身は見ない。中身（狙いと進め方が今のメンバーと合っているか、目指す姿が overview と
  食い違わないか）と、終えたときの状態やメンバーの番号を持たないことは、判断が要るので課題を整える手順に残す。
- 見出しとコードブロックの見分け方は、prctl の PR の本文の検査と同じ `lib/markdown.jq` の `body_lines` で読む。
  コードブロックの中の見出しは数えない。
- 節の名前は conventions の写しで、試験が課題の扱い方のテーマの箇条とアンカーで照らす。
- ふつうの Issue の本文の形（冒頭、`## 今の姿`、`## 範囲`）は、この判断では確かめない。冒頭の狙いは見出しで決まらず、
  検査の三つの条件をまだ量っていない。

## Alternatives

- **節の中身が空でないかも確かめる**：テーマの節の中身は判断が要るものが多く、空かどうかだけを見ても整っている状態の
  ずれを拾えるとは限らない。
- **三つの節がこの順に現れるかだけを見る（二度あってもよい）**：二度あるとどちらが今の姿か読む人が迷い、「この順に
  持つ」の読み方としても曖昧になる。
- **Issue のテンプレートで、作るときに形をそろえる**：画面での書き換えと、今ある Issue には効かない。
- **見出しの読み方を check-issues の中にだけ持つ**：prctl の本文の検査と二か所になり、片方だけ直るとずれる。

## Consequences

- テーマの Issue の本文を書き換えて節を消したり並べ替えたりすると、課題を整えるときと締めるときに `NG` として挙がる。
- conventions の課題の扱い方のテーマの節の名前を変えるときは、`check-issues` の名前も直す（試験が落ちて知らせる）。
- ターゲットのリポジトリでも、テーマの Issue があれば同じに確かめる。テーマの Issue のないリポジトリでは何も挙げない。
