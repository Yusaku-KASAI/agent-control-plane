# 0022. Issue にだけ書ける pm ロールを足し、課題を整えると相談に乗るを主に受け持たせる

## Context

依頼者は、ロールの権限を、エージェントのハーネスの外に残るもの（GitHub）への書き込みで分けると考えている。guide は
何にも書かず、pm は Issue だけ、reviewer は PR のレビューと Issue だけ、developer はすべてに書ける（#28、ADR 0019）。
conventions の ADR 0025 で、目的の手順「課題を整える」と「相談に乗る」（Issue をキャンバスにする壁打ち）ができた。
どちらも、書くのは Issue だけで終えられる。

今は、Issue を整えたり、相談の考えを Issue に残したりするには、すべてに書ける developer に頼むか、レビューのために
分けた reviewer に頼むしかない。developer に頼むと、コードを変えない依頼にも push と PR の権限が付く。guide は
Issue に書けないので、相談の考えと課題のずれを回答に書き、ほかのロールに回すよう案内している。

## Decision

- roles に pm ロール（`agents/pm.md`）を足す。書ける範囲は Issue だけ（作る、本文とコメント、ラベル、依存関係、閉じる）。
  ファイルを変えず、コミット、push、PR、PR のレビューもしない。
- 受け持つ手順は ADR 0019 の決め方で決める。課題を整えると相談に乗るを主に使う手順として受け持ち、その「始めに読む」の
  段の文書（課題の扱い方とリポジトリのラベルの決まり）を指示に直に並べる。セッションを締めるも受け持つ（持ち越すものを
  Issue に残せる）。変更を届けるは受け持たず、変えるべきことを Issue に書いて developer に回す。レビューするは受け持たない
  （PR のレビューを残せない）。
- guide が残せない相談の考えと課題のずれは、pm に回すよう案内する。
- GitHub App の権限は、Contents と Pull requests は読み取り、Issues は読み書き。CI の結果は読まない。Issues の書き込みは、
  GitHub の仕組みで PR の会話のコメントとラベルにも届く（推測。動かして確かめていない）ので、PR に書かないことは
  ロールの指示で守る（ADR 0007 と同じく、App の権限より細かい範囲は指示が守る）。
- ファイルを変えないロールなので、guide と reviewer と同じく `isolation: worktree` を持つ（ADR 0016）。モデルは、
  比べて選ぶ判断が多いので opus にする（ADR 0003）。
- 定期的に整えること（#91）や、Issue の決まりを機械で確かめること（#111）は、それぞれの Issue で作り、pm に頼む形にする。

## Alternatives

- **reviewer に課題の整理と相談を任せる**：reviewer は Issue に書けるので手順は終えられ、今もどちらも受け持つ（ADR 0019 の
  当てはめ）。ただ、reviewer は PR のレビューにも書け、別の目のために分けたロールで、指示の大半がレビューの決まりで
  占められている。課題の整理を主に使うロールとして、始めに読む文書を並べる余地がない（量の上限）。
- **pm を置かず、developer に頼む**：コードを変えない依頼にも、push と PR の書き込みが付く。
  最小権限に反する。
- **pm に Pull requests の読み書きも持たせる（PR の本文や Issue との結び付けを整える）**：PR は変更した人が持つもので、
  本文は prctl が head と合わせて保つ（ADR 0002）。pm が書くと、その仕組みと食い違う。
- **ロールの名前を `*-pm` のようにターゲット付きにする**：ターゲットの名前はエージェント（Slack の Bot）の側に付けていて
  （エージェントの用語集）、ロールの定義はターゲットをまたいで使う。

## Consequences

- control-plane では、pm ロールのエージェントを足すと、その GitHub App と Slack アプリを作ることになる（設定の例に
  control-plane-pm を足した）。
- 課題を整えると相談に乗るは、developer と reviewer も受け持ったまま。pm は、それを主に使い、最小の権限で受けるロール。
