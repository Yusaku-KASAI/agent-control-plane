# ドキュメントの設計

どのリポジトリでも、文書をどう分け、どこに何を書き、どう確かめるか。判断の理由は
[ADR 0005](adr/0005-documents-by-distribution-context.md) にある。一つひとつの文の書き方は、rules プラグインが
常に読み込ませる[共通のルール](../plugins/rules/rules/comments-and-docs.md)にある。言葉は[用語集](glossary.md)のとおり。

## 原則

それぞれの考え方が、どの問いに答えるか。

| 問い | 考え方 | ここでの形 |
| --- | --- | --- |
| 知識を何で分けるか | 関心の分離、Bounded Context、高凝集・疎結合 | 届く先（誰が読めるか）と持ち主が同じものを、一つの区切りにする |
| 区切りの間で何を約束するか | Published Language、Schema-First | 区切りをまたぐのは契約と用語集だけ。契約を先に書き、実装は検査で合わせる |
| 一つの文書に何を入れるか | 単一責任、Diátaxis | 1 つの文書は 1 つの話題の 1 つの種類だけ |
| 同じ事実をどう持つか | SSOT、DRY、Ubiquitous Language | 事実ごとに持ち主の文書を一つ決め、ほかはリンクで参照する。言葉は用語集で定める |
| 今と経緯をどう分けるか | ADR | 今の姿は文書、判断の理由は ADR、道筋は Issue、経緯はコミットと PR |
| 読み手にどう届けるか | Progressive Disclosure | 入口は短く、詳しいものは必要なときに読ませる |
| ずれをどう見つけるか | Docs as Code、メタデータ | 機械で読める形で書き、検査で確かめる |

## 区切りと契約

| 区切り | 置くもの | 届く先 |
| --- | --- | --- |
| platform | 共通のルール、ロール、スキル、ハーネスの契約、用語集、この文書 | すべてのエージェント（プラグインのマーケットプレイスと一緒に `docs/` が届く） |
| target-template | ターゲットの契約、devcontainer、CI | すべてのターゲット（テンプレートから作る） |
| control-plane | アプリの仕組み、設定、運用の手順、Go の書き方 | control-plane の開発者 |
| 各ターゲット | プロダクトの前提、そのリポジトリの仕組みと判断 | そのターゲットのエージェント |

- 区切りをまたいでよいのは、[ハーネスの契約](harness.md)、ターゲットの契約、[用語集](glossary.md)だけ。ほかの区切りの
  文書を前提にしない。届かない読み手がいる。
- 契約は、使う側に届く区切りに置く。作る側は契約に合わせて作り、食い違いは検査で見つける。

## 文書の種類

| 種類 | 書くもの | 書かないもの |
| --- | --- | --- |
| 手順 | 目的を果たすための手順（準備、追加、移行、復旧） | 仕組みの説明、理由 |
| 参照 | 事実の一覧（設定、契約、コマンド、用語） | 手順、理由 |
| 解説 | 今の姿と考え方。ADR をたどらなくても今が分かるようにまとめる | 手順の細部、選ばなかった案 |
| ADR | 判断、選ばなかった案、理由。その時点の記録で、後から本文を変えない | 今の姿のまとめ |

- 1 つの文書は 1 つの種類だけを持つ。変わる理由が 2 つあれば分ける。
- 種類ごとにディレクトリを分けるかは、文書の数で決める。少ないうちは、入口の一覧で種類を示す。
- チュートリアルは置かない。
- コード中のコメント、コミットメッセージ、PR に何を書くかは、共通のルールにある。

## 入口

- 入口（README、CLAUDE.md、各ディレクトリの README）は短くし、詳しい文書への一覧にとどめる。
- エージェントに常に読み込ませるもの（CLAUDE.md、rules プラグイン、ロールの定義）には、守るべき前提と行き先だけを
  書く。詳しいものはスキルや文書にし、必要なときに読ませる。
- ターゲットの CLAUDE.md の節は、ターゲットの契約にある。

## 置き場所の決め方

書く前に、次の順に決める。

1. **区切り**：誰が読む必要があるか。読む必要がある人すべてに届く区切りに置く。ほかの区切りの読み手にも要るなら、
   契約か用語集にする。
2. **種類**：手順、参照、解説、判断のどれか。混ざるなら分ける。
3. **持ち主**：その事実を持つ文書がすでにあるか。あればそこを書き換え、ほかからはリンクする。なければ、区切りと
   種類に合う文書に書くか、新しく作って入口の一覧に足す。

## ADR

判断の記録は `<文書のディレクトリ>/adr/NNNN-<slug>.md` に置く。番号はディレクトリごとの連番。

```markdown
---
status: accepted        # accepted か superseded
date: 2026-10-11
amends: [7]             # 一部を変えた ADR（なければ書かない）
amended_by: [12]        # この ADR の一部を変えた ADR
supersedes: [3]         # 全体を置き換えた ADR
superseded_by: [15]     # この ADR を置き換えた ADR（status: superseded と組み）
---

# NNNN. 決めたこと（一文）

## Context
## Decision
## Alternatives
## Consequences
```

- 判断を変えるときは新しい ADR を作り、両方の frontmatter に向き合う参照（`amends` と `amended_by`、`supersedes` と
  `superseded_by`）を書く。番号は同じディレクトリの ADR を指す。
- 検討中の設計は Issue に書き、決まったら ADR にする。

## 決まりの強さ

決まりは、強いものから次の 4 つで守らせる。守らせたいことは、できるだけ強い方に寄せる。

| 強さ | 仕組み | 中身 |
| --- | --- | --- |
| 検査 | `make check-docs`（`tools/check-docs.py`） | 相対リンクが実在するファイルを指すこと、ADR の frontmatter の形、見出しの番号、参照が向き合っていること |
| 常に読み込む決まり | rules プラグイン | 一つひとつの文の書き方 |
| 必要なときに読む指針 | この文書、review プラグインの観点 | 分け方と置き場所 |
| 判断の理由 | ADR | なぜそう決めたか |
