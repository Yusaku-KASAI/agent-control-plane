# prctl の判定

github プラグインの `bin/prctl` が何をどう判定するか。サブコマンドの一覧は `prctl` の usage に、エージェントが使う手順は
[github スキル](../../skills/github/SKILL.md "在りか")に、構成と理由は[全体像](../overview.md "在りか")と ADR にある。

<a id="body"></a>

## 本文

- PR は、今のブランチの名前で探す。
- 本文に、どの head コミットまで説明したかの印（`<!-- prctl: head=<コミット> -->`）を隠して入れる。書き換えは push 済みの
  HEAD に対してだけ行う。
- 本文は、決まった節（conventions の[書き方：PR](../../../conventions/docs/reference/writing.md#pull-requests)）がこの順に
  一度ずつあり、どれも空でないことを確かめてから作る・書き換える。節の名前はその写しで、コードブロックの中の行は見出しに
  数えない。
- Issue を閉じるか触れる行は、GitHub の閉じるキーワードか `Refs`（大文字小文字を問わず、後ろに `:` があってもよい。
  箇条書きの項目と引用の中でもよい）と Issue（`#N` か `owner/repo#N`）で始まる行。GitHub は後ろに何が続いても閉じるので、
  後ろの文によらず、その Issue を挙げた行として読む。後ろに何もない行と署名の行は、節の中身に数えない。
- コードブロックの外のその行が挙げる Issue は、依頼の Issue 一つに限る（`owner/repo` の大文字小文字は問わない）。
  ほかの Issue も挙げる行と、行どうしで違う Issue を挙げる本文は断る。
- GitHub は閉じるキーワードを本文のどこにあっても読み、後ろの Issue を閉じる。閉じるのは `Closes` の行だけなので、
  文の中の閉じるキーワード（`Refs` は含めない）と後ろの Issue は、どの Issue でも断る。文は、上の行の始まりの部分、
  コードブロック、インラインのコードの外で、段落（空行かコードブロックまで）ごとに改行を空白にして一つにつないで読む。
  キーワードの前は行の始まりか英数字と `_` でない文字で、後ろに `:` と空白があってよく、Issue は `#N`、`owner/repo#N`、
  `https://github.com/owner/repo/issues/N` のどれか。Closes の行の Issue を URL で書くと、閉じるか触れる行と読まず、文と
  して断る（Closes の行は `#N` か `owner/repo#N` で書く。[ADR 0035](../../../../docs/adr/0035-body-check-reads-closing-keywords-in-sentences.md)）。
- `worktree pr` は、同じ形で読んだ依頼の Issue（重ねたものは一つに）とタイトルを出す。レビューする人が、本文の意図を
  読む前にそれだけを見るため。
- 書き換えるとき、前の印から push があれば、その変更を説明するコメントを求め、なければ断る。push がなければコメントは
  付けない。

<a id="commits"></a>

## コミットメッセージとタイトル

GitHub は、既定のブランチに入ったコミットのメッセージの閉じるキーワードでも、本文によらず Issue を閉じる（[ADR 0037](../../../../docs/adr/0037-commit-messages-close-no-issue.md)）。

- PR のコミット（GitHub が PR のコミットとして挙げるもの。向き先のブランチのコミットは入らない）のメッセージに、
  閉じるキーワードと後ろの Issue があれば知らせる。読み方は本文の文の中と同じ正規表現（`closing_re`）で、メッセージ
  全体を一つとして読む。コミットメッセージには書式がないので、バッククォートの中も読む。
- タイトルは merge commit のメッセージに入るので、同じ正規表現で読む。閉じるキーワードと後ろの Issue があれば、
  `create` と `update --title` が断り、GitHub の画面で変えたものも、PR の今のタイトルとして下の所で知らせる。ただし、
  ターンの終わりの hook が済んだと覚えた head（[hook](#hooks)）では、次の push かレビューまでタイトルを読み直さず、
  下書きでない PR では `ready` も判定しない。
- 知らせるのは、本文とレビューとともに足りないものを言う所（push のあとの hook、ターンの終わりの hook、`ready`）。
  コミットを読めないときは、閉じるかが分からないと、ほかの足りないものといっしょに知らせ、`ready` は下書きを外さない。
- merge commit のメッセージにタイトルが入ることは、リポジトリの設定（`merge_commit_message` が `PR_TITLE`）を前提にする。
  本文が入る設定（`PR_BODY`）では、本文のコードの中の閉じるキーワードも merge commit のメッセージに入るが、読まない。

<a id="range"></a>

## まだレビューしていない範囲

- 範囲は、本文のある PR のレビュー（誰が付けたものでもよい）が付いたコミットのうち、今の head の履歴にある最後のものから、
  今の head まで。ないときは、ブランチが PR の向き先のブランチから分かれた所から。レビューしない直しの記録も PR の
  レビューなので、同じに数える。
- レビューしない直しの記録は、範囲の始まりがレビューでないとき（PR にレビューが一つもない、どれも今の head の履歴にない、
  レビューしない直しの記録のあと）は断る。
- レビューしない直しの記録を断るときと、`unreviewed` や hook がそれを案内するときは、同じ判定を使う。
- レビューを読めないときは、コマンドは失敗し、hook は何も言わない。

<a id="records"></a>

## 記録の形

- レビューの結果と答えは JSON で受け、`lib/review.jq` で形を検査して Markdown の表を作る。JSON の写しを base64 にして、
  本文の最後の行の隠した印（`<!-- prctl-review: … -->`、`<!-- prctl-answers: … -->`）に入れる。印は本文の最後の行からだけ
  読む（指摘の文が印を引いていてもよい）。
- レビューの写しは、範囲の種類、見た観点、指摘ごとの重さと観点と要約だけにする。本文は GitHub の上限の 65536 文字まで
  で、超えれば断る。
- head の履歴にまだレビューがなければ、PR 全体の差分のレビュー（`"scope": "pr"`）を求める。
- 答えは、`prctl` が残したレビューに対してだけ受け、その指摘すべてに、一つずつ答えることを求める。

<a id="ending"></a>

## 回し方と、終えてよいか

- 回し方は、PR のラベル `念入りのレビュー` があれば念入り、なければ通常と読む（`mode` が付け外しする）。通常の PR には
  前回からの差分のレビュー（`"scope": "since"`）を残させず、hook と `unreviewed` の案内も PR 全体のレビューを促す。
- 終えてよいかは、head の履歴にあるレビュー（コミット、レビューしない直しの記録か、写しの範囲の種類と指摘の重さ、
  写しと答えのコメントから分かる答えた番号）から判定する。最後の PR 全体の差分のレビューのあとに、次のどれかが欠ければ
  終えられない。
  - それより後のコミットの記録（レビューしない直しの記録は除く）と、まだ記録のない head がない（まだ記録のない push は、
    先に記録するよう言う）。
  - 必須の指摘がない。
  - すべての指摘に答えた（答えはレビューの id で突き合わせる）。
- 通常の打ち切りは数えない。終える条件は回し方によらない。
- 終えられないまま PR 全体の差分のレビューが上限（`PRCTL_FINAL_CAP`、既定は 10。conventions の
  [回し方](../../../conventions/docs/reference/reviews.md#ways)の「依頼者に返すとき」に合わせる）に達したら、依頼者に返すよう言う。
  最後に数えた PR 全体の差分のレビューのコミットを作業ツリーの `.git` に覚えて、そのあとから数え直す（そのコミットが
  head の履歴になければ、すべてを数える）。覚えるのは、ターンの終わりに上限に達していたとき（下書きでなければ返すよう言って
  止め、下書きのあいだは言わずに覚える）と、下書きでない PR で終えてよいと確かめたとき（ほかにターンを止めるものが
  ないとき）と、`ready` が下書きを外したとき。
- PR は下書きで作る（`create`）。`ready` は終えてよいときだけ下書きを外し、`draft` は下書きに戻す。
- `ready` は、本文の `Closes` か `Refs` の行が依頼の Issue を挙げていれば、その Issue の範囲との付け合わせ（conventions の
  [範囲の項目と PR の付け合わせ](../../../conventions/docs/reference/issues.md#scope-items)、[依頼の範囲](../../../conventions/docs/reference/issues.md#scope)）も確かめ、合わなければ
  下書きのままにする（[ADR 0034](../../../../docs/adr/0034-ready-checks-the-scope-of-the-request.md)）。
  - 範囲の中の項目は、Issue の本文の `## 範囲` の節のタスクリスト。項目を扱う PR は、項目の末尾の `#<番号>`（このリポジトリの番号だけ。
    `#` の前は項目の始まりか、`owner/repo` に使えない文字（空白、括弧、日本語の文字など）。`owner/repo#N` や `x#5` で終わる項目は、
    扱う PR のない項目と読む）。読み方は `lib/markdown.jq` の `scope_items` で、`check-issues` と同じ。コードブロックの中の行は項目に数えない。
  - この PR の番号で終わる項目が一つもなければ断る。
  - 残る項目は、チェックがなく、この PR の番号で終わらず、末尾の番号の PR がマージされていない項目。`Closes` なのに残る
    項目があるか、`Refs` なのに残る項目がなければ断る。コメントに積んだ指摘は見ない（PR を終えるときに項目にする）。
  - 末尾の番号が PR でない（404）項目は残ると読む。`## 範囲` の節がなければ断り、Issue か項目の PR を読めなければ失敗する。ほかのリポジトリの Issue（`owner/repo#N`）は読まない。このリポジトリの Issue を `owner/repo#N` で書いた行は、`#N` と
    同じに読む（大文字小文字を問わない）。
  - `status` の `end:` と、ターンの終わりの hook は、これを確かめない。

<a id="ci"></a>

## CI

- CI の状態は、失敗、実行中、人の操作待ち、取り消し、通った、なしに分け、各 check の最新の run だけを数える。同じ head に
  check suite が二つ以上あっても、同じ app の同じ名前の check run は一番新しいものだけを数える。CI を読めないときは、
  CI のことだけを言わない。
- CI を待つ（`ci --wait`）のは一つのブランチに一つだけで、コンテナの `TMPDIR`（なければ `/tmp`）の中のファイルの `flock` で
  守る（`flock` がないか、取り合い以外で失敗したら守らない）。ほかの待ちが動いていれば「already waiting」ですぐ終わる。
- 待つ head は、このクローンの参照（`origin/<ブランチ>`）が指す head。ふつうはこのクローンから最後に push した head で、
  fetch で取り込んだほかからの push も、参照が指せば待つ。待つ間にその参照が動けば（push で進めても戻しても、fetch でも）、
  終わる直前でも、新しい head を初めから待ち直す。1 時間で「timeout」、check run が現れなければ「none (...)」で終わる。
- 重ねた PR（向き先が既定のブランチ `origin/HEAD` でない）は、向き先のブランチの PR がマージされたか、マージされずに
  閉じたか、`origin/<向き先>` が head の履歴にないかを見て知らせる。`origin/HEAD` が手元にない、GitHub を読めない、head が
  手元にないときは何も言わない。

<a id="hooks"></a>

## hook

どちらも、自分のエラー（PR がない、`gh` やネットワークが使えない）でツールの呼び出しやターンを失敗させない。覚えた head は
作業ツリーの `.git` の中に置く。

- **Bash のあと（`hook post-tool-use`）**：今の HEAD が push 済みで、PR の本文がそれを説明していないか、レビューがそれに
  追いついていないか、PR のコミットのメッセージかタイトルが Issue を閉じる（[コミットメッセージとタイトル](#commits)）なら、足りないものを促す文脈を足す。一つの push には一度だけ促す。
- **ターンの終わり（`hook stop`）**：この作業ツリーから push した head について、本文が説明していないか、レビューが
  追いついていないか、PR のコミットのメッセージかタイトルが Issue を閉じるか、CI が失敗していれば、ターンを終わらせず、足りないものを済ませて依頼への回答全体をまとめ直すよう
  求める。CI の失敗は、PR で直せるものは直し、直せないもの（守りの検査が設定を読めないなど）は依頼者に報告するよう
  言う。CI の失敗のほかの状態では止めない。
  - 下書きでなければ、PR を終えてよいかも確かめ、ほかの足りないものといっしょに言って止める（hook は一つのターンで
    一度しか止めない）。下書きのあいだは、終えてよいかでは止めず、head を済んだとも覚えない。
  - まだ記録のない push は、先に記録するよう言うだけで、上限に数えない。
  - 本文とレビューが済み、終えてよく、CI が通った（またはワークフローがない）と確かめた head は、そのときのレビューの
    数といっしょに覚えて、同じ head とレビューのあいだは CI と答えのコメントを聞き直さない（PR とレビューの一覧は毎回
    読み、同じ head にレビューが足されれば確かめ直す）。
  - hook に促されて続けたターンでは、もう止めない。
