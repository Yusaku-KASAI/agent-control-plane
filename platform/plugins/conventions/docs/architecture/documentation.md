# 文書の体系

どのリポジトリでも、文書をどう分け、どこに何を書くか。判断の理由は
[ADR 0002](../adr/0002-documents-by-distribution-context.md)、[0003](../adr/0003-type-first-docs-and-platform-kernel.md)、[0005](../adr/0005-principles-and-conventions-plugins.md)、[0006](../adr/0006-nested-items-and-prerequisite-directions.md)、[0007](../adr/0007-navigation-links-marked-by-title.md)、[0008](../adr/0008-maps-per-level-and-the-whole.md)、[0009](../adr/0009-definitions-and-delivery.md)、[0010](../adr/0010-always-read-selection-and-size.md)、[0014](../adr/0014-prerequisites-by-change-and-whereabouts-links.md)、[0015](../adr/0015-starting-points-and-reading-scope.md)、[0016](../adr/0016-summaries-guides-and-common-rules.md)、[0017](../adr/0017-procedures-in-guides-and-skills-deliver-them.md)、[0018](../adr/0018-role-instructions-split-and-changing-definitions.md)、[0020](../adr/0020-scene-procedures-start-by-reading.md)、[0021](../adr/0021-purpose-procedures-and-triage.md)、[0022](../adr/0022-forms-of-procedures-and-role-instructions.md)、[0025](../adr/0025-consult-and-organize-issues.md)、[0027](../adr/0027-checks-by-rule-and-reader.md)、[0028](../adr/0028-document-checks-cover-structure.md) にある。
原則は[設計の原則](../../../principles/docs/reference/principles.md "在りか")、パターンは[設計のパターン](../../../principles/docs/reference/patterns.md "在りか")、形は[文書の形式](../reference/formats.md "在りか")、書くときの手順は
[文書を書く](../guides/write-docs.md "在りか")にある。

## 構成

文書の体系は、置き場所と関係（どこに何を置き、何が何を前提にするか）と、読み手への届け方（決まりを、どの文書に、
どう書いて読ませるか）の二つのまとまりと、その両方に関わる書き換えの方針からなる。

### 置き場所と関係

#### 設計を記述する 3 つの層

| 層 | 書くもの | 置き場所 |
| --- | --- | --- |
| 原則とパターン | 原則（何を大事にするか）と、それを特定の問題への形にしたパターン（どう組むか）。一般的な当てはめ方とよくある失敗まで書き、どこで使うかは書かない | principles プラグインの [principles.md](../../../principles/docs/reference/principles.md "在りか") と [patterns.md](../../../principles/docs/reference/patterns.md "在りか") |
| アーキテクチャ | その区切りで採った全体の構成と、部分の間の関係 | 文書の根の `overview.md` と、`architecture/` の各文書の冒頭 |
| 構成要素の説明 | 層、ディレクトリ、ファイルごとの責務と関係、当てはめた原則・パターン | `architecture/` の各文書。[形式](../reference/formats.md#component)に沿う |

構成要素の説明から原則やパターンへリンクし、それがそこでどう効いているかを書く。一つの原則やパターンは多くの
構成要素に、一つの構成要素は多くの原則やパターンに当てはまる。

<a id="contexts"></a>

#### 区切りと依存の向き

- 知識は、使う人（誰が読めるか）と持ち主が同じものを一つの区切りにまとめる（[境界づけられた文脈](../../../principles/docs/reference/principles.md#bounded-context)）。
  区切りは最上位の項目で、それぞれが自分の文書の根を持つ。
- 依存は一方向にだけ向ける（[依存の向き](../../../principles/docs/reference/principles.md#dependency-rule)）。principles は何も前提にせず、
  conventions は principles だけを前提にする。この二つは、ほかのすべての区切りが前提にしてよい
  [共有の核](../../../principles/docs/reference/patterns.md#shared-kernel)になる。
- 共有の核のほかに区切りをまたぐのは、契約だけ。契約は使う側から読める場所に置き、作る側はそれに合わせて作り
  （[使う側に届く契約](../../../principles/docs/reference/patterns.md#published-language)）、実装との一致は[契約の試験](../../../principles/docs/reference/patterns.md#contract-test)で確かめる。

<a id="map"></a>

#### 項目の階層と関係

- 区切りと、その中の部品（プラグイン、話題の文書など）は、入れ子の項目として表す（[階層的分解](../../../principles/docs/reference/principles.md#hierarchy)）。
  何段あってもよい。同じ親の下の項目は、同じ種類と粒度にし、重ならず親を尽くす（[兄弟をそろえる](../../../principles/docs/reference/principles.md#siblings)）。
- 含む関係（親子）は依存ではない。子を持つ項目が直接持つ文書（`overview.md`、索引、全体の解説）は、子と並ぶ「全体」として
  扱う。子は全体（全体の構成や共通の考え方）を前提にしてよく、全体は子を前提にしない（子への道は在りかのリンクにする）。全体には
  全体についての事実だけを書き、子の細部を書き写さず、子へは[案内](#summaries-and-guides)で書く（[安定依存](../../../principles/docs/reference/principles.md#stable-dependencies)、
  [依存関係の逆転](../../../principles/docs/reference/principles.md#dip)）。
- 区切りの間の契約は、作る側にも使う側にも属さない独立した項目として扱い、両側がそれを前提にする
  （[依存関係の逆転](../../../principles/docs/reference/principles.md#dip)）。置き場所は使う側から読める所にする。置き場所の親と、関係の上での親は
  違ってよい。
- 項目の間の関係は種類で分け、依存の向きの決まりは「前提にする」関係にだけ当てる
  （[関係を種類で分ける](../../../principles/docs/reference/patterns.md#relation-kinds)）。在りかを示すだけのリンク（在りかのリンク）を、どう見分けてどう書くかは
  [形式](../reference/formats.md#links "在りか")にある。
- 前提の向きは階層ごとに決め、循環させない（[非循環依存](../../../principles/docs/reference/principles.md#acyclic)）。多くから前提にされる項目ほど
  変わりにくく小さく保つ（[安定依存](../../../principles/docs/reference/principles.md#stable-dependencies)）。二つの文書の関係は、それらが初めて同じ親の
  下に入る階層で、その親の下の項目どうしの向きとして判断する。下の階層の向きは、上の階層の向きの範囲の中でだけ決める。
- 地図（どんな項目があり、どの項目がどれを前提にするか）は、階層ごとにその持ち主が書く。最上位の地図は全体の設計を
  持つリポジトリの `overview.md` に、各項目の中の地図はその項目の `overview.md` に置き、上の階層の地図は中の項目を書かずに
  委ねる。書き方は[形式](../reference/formats.md#map "在りか")にあり、`check-docs` がすべての地図を集めて文書のリンクと照らす。
  地図からは[設計構造行列](../../../principles/docs/reference/patterns.md#dsm)を出せる。

<a id="roots"></a>

#### 文書の根と器

区切りごとに一つ、`README.md` を持つ `docs/` ディレクトリ（文書の根）を置く。リポジトリ自身の文書の根はルートの
`docs/`、リポジトリの中のほかの区切り（プラグインなど）の文書の根は、その区切りのディレクトリの `docs/`。
入口（`README.md` と `CLAUDE.md`）はリポジトリのルートにだけ置く。

```
README.md
CLAUDE.md
docs/                 （区切りのディレクトリの中なら <区切り>/docs/）
  README.md
  overview.md
  architecture/
  guides/
  reference/
  adr/
```

- 要らないものは置かない。小さな区切り（プラグインなど）は、`README.md` と `overview.md`（構成と構成要素）だけでもよい。
- 手順は、エージェントが使うものも `guides/` に定義する。プラグインのスキル（`skills/`）は、その手順を要約か案内で載せ、
  そのプラグインの道具の使い方（道具を使う手順を含む）だけを自分で持つ。
- 文書の根の中で関心の違う部分は、`architecture/` と `adr/` を `<関心>/` に分ける。`guides/` と `reference/` は、
  文書が増えたら同じように分ける。

<a id="types"></a>

#### 文書の種類

[文書の種類で分ける](../../../principles/docs/reference/patterns.md#diataxis)のうち、解説、手順、参照を使い、チュートリアルは置かない（読み手が
限られ、手順で足りる）。かわりに判断（ADR）を 4 つ目の種類にする。

| 種類 | 置き場所 |
| --- | --- |
| 解説 | `overview.md`、`architecture/` |
| 手順 | `guides/` |
| 参照 | `reference/` |
| 判断 | `adr/` |

#### 文書の外

コード中のコメント、コミットメッセージ、PR に何を書くかは[書き方](../reference/writing.md "在りか")にある。道筋と
予定は Issue に置き、文書には書かない（[課題の扱い方](../reference/issues.md "在りか")）。

### 読み手への届け方

<a id="delivery"></a>

#### 定義と届け方

決まりは、一か所で定義し、効き方の違う形でエージェントや人に届ける（[一つの出典から届ける](../../../principles/docs/reference/patterns.md#single-source)）。

- **定義**：決まりそのもの。原則とパターン（principles）、このプロジェクト群の決まり（conventions の `docs/`：書き方、
  変更と課題の扱い方、レビューの扱い方、文書の体系、形式、用語集、手順）、区切りの間の契約。同じ決まりを二か所で定義しない。
- **届け方**：定義を、効く形にしたもの。新しい決まりを足さない。検査は定義を確かめ、文書の届け方（共通のルール、役割ごとの
  指示、スキル）は定義を要約か案内で載せる。定義を変えたら、それを確かめる検査と、それを載せた文書も直す。
  例外として、役割ごとの指示は役割に固有の振る舞いを、スキルはそのプラグインの道具の使い方を、自分で持ってよい。
- リポジトリの決まり（CLAUDE.md）が conventions の定義と食い違うときは、リポジトリの決まりに従う。

定義がエージェントや人に効く形は、強いものから次のとおり。最後の行のほかが届け方で、最後の行は届け方ではなく、
定義の文書を読みに行くこと。守らせたいことは、できるだけ強い形で届ける（[仕組みで守る](../../../principles/docs/reference/principles.md#mechanisms)）。

| 形 | 効き方 | 例 |
| --- | --- | --- |
| 検査 | 守らないと通らない | `check-docs`（何を確かめるかは[形式](../reference/formats.md "在りか")の各節の「検査」） |
| 共通のルール | 毎回の作業の前提になる。短くする | conventions の `rules/`（hook が読み込ませる） |
| 役割ごとの指示 | その役割で動くときの前提になる | プラグインの `agents/` の文書（受け持つ手順と、使う決まりとスキルの要約と案内と、役割に固有の振る舞い） |
| 必要なときに読む手順と観点 | 当てはまる作業のときだけ読む | 起点が最初に読むものとして指す目的の手順（変更を届ける、レビューする、相談に乗る、課題を整える）と、スキル（`guides/` の共通の手順と、ロールの外から入る目的の手順の要約か案内。write-docs、design、review、close-session、consult、organize-issues） |
| 定義の文書そのもの | 読みに行ったとき | principles と conventions の文書、契約 |

- **共通のルール**は、毎回すべての作業の前に読まれるので、載せるものを絞る。載せるのは、ほぼすべての作業に
  関わり、破られやすく、検査で守れない決まりだけ。特定の作業（文書を書く、変更を届ける）にだけ要る決まりは、その作業の
  手順（目的の手順か、共通の手順のスキル）や役割ごとの指示で届ける。ただし、どの作業でも読ませる文書は共通のルールの
  「始めに読む」の節に、目的の手順で読ませる文書は振り分けの節かロールの指示に、直に並べる（[起点](#starting-points)）。
- 文書の届け方は、定義を[要約か案内](#summaries-and-guides)で書く。

<a id="checks"></a>

#### 検査にするものと置き場所

検査は最も強い届け方だが、保つ手間がかかり、誤って落ちると作業を止める（[仕組みで守る](../../../principles/docs/reference/principles.md#mechanisms)）。

文書の検査（`check-docs`）は、まず範囲を文書の構造の決まりに限る（[ADR 0028](../adr/0028-document-checks-cover-structure.md)）。
文書の検査が守るのは文書の体系（ハーネスの設計を書いたもの）で、作業の安全（既定のブランチの守りなど）ではなく、崩れは
レビューでも見つけられる。中身を数えられる形に落とすと、書き方を検査に合わせることになり、誤って落ちるか、検査を
通すための書き方が増えるので、中身の検査は下の条件「誤って落ちにくい」を満たさないものとして扱う。

| 検査の候補（構造）。下の三つの条件で選ぶ | 検査にしない（中身）。レビューに任せる |
| --- | --- |
| 文書の体系そのものが決める置き場所、印、リンクの関係。形式（決まった節、見出し、印があるか、量の上限）、リンク（リンク先、在りかの印、どの文書も入口、索引、地図から届くか）、依存（地図と前提の向き）、メタデータ（ADR の frontmatter と参照） | ある文書が述べること（何をどこまで書くか、特定の節に何を並べるか（すべての目的の手順が並ぶかのような網羅を含む）、どの手順を誰が受け持つか、要約、例、説明）が、ほかの定義や今の姿と合っているか |

分け目は、どの文書にも届くか（到達）は構造、特定の節に何を名前や説明として並べるかは中身、とする。

どの検査も（文書の検査は構造の範囲の中で）、静的解析の道具の経験（直せる指摘だけを出し、誤検知を少なく保たないと
使われなくなる。Sadowski ほか「Lessons from Building Static Analysis Tools at Google」）に倣い、次の三つを満たす
決まりを検査にし、ほかはレビューの観点に任せる。

- 判断が要らない：リポジトリや、外の道具（GitHub など）の状態だけから機械で決まる。意味の食い違い（要約と出典など）は
  検査にせず、検査はその手がかり（出典へのリンクがあるか）までにする。
- 実際に破られる：レビューで繰り返し見つかる。または、既定のブランチの守りのように、黙って外れると気づく機会がなく、
  失うものが大きい。
- 誤って落ちにくい：誤検知が少なく、保つ手間が、見逃したときの手戻りより安い。

[仕組みで守る](../../../principles/docs/reference/principles.md#mechanisms)の「検査できる決まりを、文書に書くだけで済ませる」は、
このプロジェクト群では、この三つを満たす決まりについて言う。

検査の仕組み（コマンド、試験、CI のジョブ、hook）も、アーキテクチャの検査（Fitness Function、Ford ほか『Building
Evolutionary Architectures』）と同じく守る構造の中に置き、それを置く区切りが前提にしてよいものだけを知る
（[区切りと依存の向き](#contexts)）。置き場所は、確かめる決まりと、状態を読む相手で決める。検査を回すだけの器（CI の
複合アクション、ターンの終わりの hook）と、決まりを載せる器（Claude Code のプラグインやカスタムエージェントの並び）は、
置き場所を決めない。

| 確かめるもの | 置き場所 | 知ってよいもの |
| --- | --- | --- |
| 一つの区切りが定めた形（どの区切りのファイルに当てはめるかによらない） | その形を定義する区切り | その区切りが定めた形だけ。ほかの区切りの名前やパス（特定のプラグイン、ファイル）は知らず、形から見分ける |
| 外の道具（GitHub など）の状態 | その道具を扱う区切り | 確かめる決まりは、前提にしてよい区切り（conventions、契約）に合わせる。値をコマンドに直に持つときは、どの決まりに合わせたかを書く |
| 区切りの間で値が合っていること | 契約の試験として、両側を前提にしてよい区切り | 両側と、その間の契約 |

- ほかの区切りのファイルを確かめても、形から見分けて形を確かめるなら 1 行目に当たる（`check-docs` の地図とロールの
  形の検査）。値が合っているかを、特定の区切りの名前やパスを知って確かめるなら 3 行目に当たる。
- 置き場所の区切りが前提にしてよくないものを確かめたくなったら、確かめる値を契約に置き、検査はその契約に合わせる
  （[使う側に届く契約](../../../principles/docs/reference/patterns.md#published-language)、[契約の試験](../../../principles/docs/reference/patterns.md#contract-test)）。
- 検査は、それを置く区切りの文書に、何を確かめるかを書く（conventions の形の検査は[形式](../reference/formats.md "在りか")の
  各節の「検査」）。

<a id="summaries-and-guides"></a>

#### 要約と案内

文書がほかの文書の中身に触れるときは、次のどちらかで書く。

| 書き方 | 書くもの |
| --- | --- |
| 要約 | リンク先の中身を短く言い直したもの。開かなくても分かり、守れるようにする |
| 案内 | 中身を言い直さず、どの場面で、どこを読むかだけ |

- リンクの種類（前提のリンクか在りかのリンクか）は、これとは別に[形式](../reference/formats.md#links "在りか")の決め方で
  決める。要約には、項目ごとに、要約が拠る文書（出典）へのリンクを付ける。出典が変わると要約の見直しが要るので、このリンクは前提のリンクになる。案内のリンクは、
  ふつう在りかのリンクになる。
- 全体（`overview.md`、索引）から子へは案内で書き、子の細部を要約しない（[項目の階層と関係](#map)）。全体が自分の事実として
  持つ子の責務や一行の説明（構成要素の説明、索引の説明の列）は、子の要約ではない。
- 一般的な原則と、それをこのプロジェクト群で具体化した決まりがあるときは、具体化した決まりを要約にし、原則はその
  理由として添える。

<a id="starting-points"></a>

#### 起点

起点は、エージェントがリンクをたどって選ぶのではなく、丸ごと読み込む文書。エージェントの入口（CLAUDE.md）、共通の
ルール、役割ごとの指示は作業の始めに、スキルは使うと決めたときに読み込まれる。人の入口（`README.md`）、索引、
全体は、読み手が選んでたどる文書で、起点ではない。

書いてあっても読まれない、読まれても使われないことを避けるため、起点には載せるものを選ぶ。

- principles と conventions の定義を載せるときは、上の共通のルールに載せる基準を、その起点の範囲（すべての作業、
  その役割の作業、その作業）に当てはめて、要約にするか案内にするかを選ぶ。起点が自分で持つもの（CLAUDE.md の
  リポジトリの決まり、役割に固有の振る舞い、スキルの道具の使い方）は、この選び方に限らない。
- 起点が自分で持つものと、ほかの定義の要約と案内が一つの文書に混ざるときは、節で分ける。役割ごとの指示は、
  振り分けの目的の手順をその役割がどう扱うか（「受け持つ手順」の節）と、役割に固有の振る舞い（「固有の振る舞い」の節）と、
  ほかの定義の要約と案内（「使う決まり」の節）に分ける。どの行がその役割だけの定義で、どの行が定義を変えたら直すものかを、
  節で見分けられるようにする。判断の軸になる「受け持つ手順」と「使う決まり」を先に置く。形は
  [形式](../reference/formats.md#role "在りか")にある。
- 判断の軸になる決まりを、細かい作法より先に載せる。読み手は先に書かれたものから読むためで、並び順で大事さを
  表すためではない。大事さは、起点に要約として書くことで表し、「大事」の印は付けない。
- 起点は、項目を作業の場面や関心ごと（始めに読む、決めるとき、書くときなど）の節に分け、一続きの段落や長い一つの
  リストにしない。読み手が、今の作業に当たる所を見つけ、途中で立ち返れるようにする。読み込ませる起点（共通のルール）
  は、読み込ませるときに自分の在りかも示す。
- 作業の始めに読み込まれる起点は、[形式](../reference/formats.md#size "在りか")の量の上限の中に収める
  （[必要十分](../../../principles/docs/reference/principles.md#sufficiency)）。
- 全体まで読ませたい文書は、次のどれかで示す。
  - どの作業でも読ませる文書（今は文書の体系だけ）：共通のルールの「始めに読む」の節に、条件を付けずに
    直に並べる。「変更するときは」のような前置きを付けると、読み手が自分の作業は当てはまらないと読み、飛ばしうる。
  - 目的の手順がある作業で読ませる文書：その手順の「始めに読む」の段に置き、起点にはその段の文書を直に並べる
    （[目的の手順と共通の手順](#procedures)）。
  - 目的の手順がまだない作業で読ませる文書：起点のリンクに[「（全体を読む）」](#reading-scope)を付ける。

<a id="reading-scope"></a>

#### 読む範囲

どの文書でも、リンク（役割ごとの指示では、パス）の直後に「（全体を読む）」を付けると、その場面ではリンク先の文書を
全体まで読む。

- 付けないリンクは、要るときに、リンク先の節を読む。
- 読んだ文書や節の中に、場面が当てはまる「（全体を読む）」があれば、それもたどる。
- 「（全体を読む）」は、場面を限って付ける（例：ほかの人の差分をレビューするとき、全体のレビューをするとき）。いつも要るものは要約にするか、共通の
  ルールに載せる（全体まで読ませるものをどこに並べるかは[起点](#starting-points)にある）。
- 読む範囲は、どれだけ読むかだけを表す。大事さは表さない。

<a id="procedures"></a>

#### 目的の手順と共通の手順

手順（`guides/`）は、最大 2 層の階層にする（[階層的分解](../../../principles/docs/reference/principles.md#hierarchy)）。
読み手が深い所までたどらなくて済むよう、3 層目は作らない。プラグインの `docs/guides/`（エージェントに届ける手順）に置く
手順は、どれもどちらかの層に入る。人が読む運用や準備の手順（リポジトリの `docs/guides/` など）は、この層の外に置いてよい。
それぞれの形は[形式](../reference/formats.md#procedure "在りか")にある。

| 層 | 何の手順か | 例 |
| --- | --- | --- |
| 目的の手順 | 依頼者が何をしてほしいかの単位。依頼を受けてから終えるまでの全体で、いくつものターンやセッションにわたることがある | 変更を届ける、レビューする、セッションを締める |
| 共通の手順 | 目的の手順の段の中で使う、作業の一部分。いくつもの目的の手順から使いうる | 文書を書く、パターンを当てはめる、レビューを頼んで答える |

- 手順は依頼の目的で切り、ロール（役割）では切らない。ロールは、権限と隔離の境界（書けるもの、残せる所）で、使うモデルも持つ。
  手順とロールは多対多になる。ロールの指示の「受け持つ手順」の節は、頭にそのロールの書ける範囲（作業領域、PR、
  PR のレビュー、Issue のうち、どれを書けるか）を置き、振り分けの目的の手順ごとに、受け持つか、受け持たないか（受け持たないなら、
  どのロールに回すか）を並べ、目的の手順のない依頼は、書ける範囲の中で依頼に沿って試す、と書く。受け持つ手順のうち、
  そのロールが主に使うものは「始めに読む」の段の文書を直に並べ、ほかはスキルへの案内でよい。振り分けとロールの指示が
  食い違うときは、ロールの指示の「受け持つ手順」に従う。
- 目的の手順を足したり、ロールの受け持ちを変えたりしたら、それを並べた所を直す。共通のルールの振り分け、各ロールの
  「受け持つ手順」と description、ロールの全体像（roles などのプラグインの `docs/overview.md`）、この文書の届け方の表と
  起点の説明の例、conventions の索引と全体像、用語集の例。どの文書も索引から届くことは検査が確かめる（構造）。
  ほかは特定の節に何を並べるかで中身なので、検査にせず、変える人とレビューする人がここから直す所を挙げる（[ADR 0028](../adr/0028-document-checks-cover-structure.md)）。
- 目的の手順は、段の中で、その段で使う共通の手順を案内する。共通の手順は、目的の手順を前提にせず、ほかの手順を案内しない。
- 依頼を受けたら、まずどの目的の手順に当たるかを決める（振り分け）。目的の手順がまだない依頼（事実を聞く質問
  など）は、依頼に沿って進める。作業の途中で目的が変わったら（相談から変更へなど）、その目的の
  手順に入り直す。
- 目的の手順は一つのターンで終わるとは限らない（追加の依頼、レビューの指摘への答え、CI の失敗）。
  どこからを新しい依頼として振り分けから入るかは、各目的の手順に書く。
  続きのターンでは、今どの段にいるかを確かめてそこから進める。会話の記録がない新しいセッションで続きから入るときと、
  ほかの作業の途中からその目的の手順に入るときは、「始めに読む」から始める。
- 目的の手順の最初の段は「始めに読む」にし、その手順で全体まで読む文書を並べる。並べるのは、その手順の多くの段で
  判断の軸になる文書だけにし、一つの段でだけ使う文書は、その段で案内する。「（全体を読む）」のリンクは、読み手が
  そのリンクに目を向けないと飛ばされるので、その手順で必ず要る文書は、文中の印ではなく、省かない段として書く。
- 起点（共通のルール、役割ごとの指示）は、目的の手順と、その「始めに読む」の段の文書を、最初に全体まで読むものとして、
  出典（その段）付きの要約で直に並べる。手順を指すだけにすると、読む文書が一段たどった先になり、読まれにくい。
  共通のルールの振り分けの節には、すべての目的の手順を並べる。そのうち「始めに読む」の段の文書まで直に並べるのは、
  ロールの指示を通らずに入ることが多い手順（変更を届ける）だけにし、ほかは、主に使うロールの指示に直に並べ、振り分け
  からはスキルへの案内で届ける。どのロールも主に使わない手順（セッションを締める）は、ロールの指示からもスキルへの
  案内で届ける。目的の手順によらず読む文書の置き方は[起点](#starting-points)にある。「始めに読む」の段を変えたら、それを
  並べた起点も直す。スキルは、共通の手順への入口として、使うと決めたときに読み込まれる。そのロールで動いていない人が
  目的の手順に入るとき（たとえば役割を持たないセッションがレビューを頼まれたとき）の入口にもなる。
- 決まりとして守る順序も手順に置く。参照の文書は、手順の段が使う決まり（条件、表、形）を持ち、順序は持たない。

<a id="rewrite"></a>

### 書き換え

決まりを守るためなら、文書とコメントは破壊的に変えてよい。散らばった説明をまとめ直す、置き場所を移す、
ディレクトリ構成を変えることも含む。

## 構成要素

各文書の根の器の構成要素。体系を作る部品（conventions の定義と届け方、`check-docs`）は
[conventions の全体像](../overview.md "在りか")にある。

### `README.md`

- **責務**：人の入口。何のリポジトリかと、索引（`docs/README.md`）と全体の解説（`docs/overview.md`、あれば）への道を示す。
- **置くもの / 置かないもの**：数行の説明、索引と全体の解説へのリンク、よく使う手順へのリンク（1〜2 本まで）。文書の
  一覧は置かない。
- **当てはめた原則・パターン**：[段階的な開示](../../../principles/docs/reference/principles.md#progressive-disclosure)：最初に要るものだけ。
  [入口と唯一の一覧](../../../principles/docs/reference/patterns.md#single-index)：一覧は `docs/README.md` にだけ置く。

### `CLAUDE.md`

- **責務**：エージェントの入口。常に読み込まれる。
- **置くもの / 置かないもの**：エージェントがいつも知っておくべき前提（プロダクトの前提、完了条件、言語など）と、索引
  （`docs/README.md`）と全体の解説（`docs/overview.md`、あれば）への道。詳細は置かず、文書へのリンクにする。
- **関係**：どの節を持つかは、リポジトリが従う契約で決める。
- **当てはめた原則・パターン**：[段階的な開示](../../../principles/docs/reference/principles.md#progressive-disclosure)：常に読み込まれるので前提と行き先
  だけ。[スキーマを先に](../../../principles/docs/reference/principles.md#schema-first)：節を決めて揃える。

### `docs/README.md`

- **責務**：そのリポジトリの文書の唯一の一覧。
- **置くもの / 置かないもの**：文書ごとに、種類と 1 行の説明。中身は置かない。
- **当てはめた原則・パターン**：[入口と唯一の一覧](../../../principles/docs/reference/patterns.md#single-index)。

### `docs/overview.md`

- **責務**：そのリポジトリの全体の解説。狙い、全体の構成と部分の間の関係、目指す姿。
- **置くもの / 置かないもの**：部分の細部は置かず、`architecture/` の各文書へリンクする。目指す姿は今の方針として
  書き、そこへの道筋（何をどの順でやるか）は Issue に置く。
- **当てはめた原則・パターン**：[関心の分離](../../../principles/docs/reference/principles.md#soc)：全体と部分を分ける。
  [判断の記録](../../../principles/docs/reference/patterns.md#adr)：道筋と理由はここに置かない。

### `docs/architecture/`

- **責務**：今の姿の解説。部分ごとに、その構成と、構成要素の説明。
- **置くもの / 置かないもの**：文書ごとに一つの部分（例：セッション、コードの層、devcontainer）。冒頭にその部分の
  構成と関係、続けて構成要素の説明を[形式](../reference/formats.md#component)で書く。選ばなかった案は置かず ADR に。
- **関係**：構成要素の説明から原則、パターン、ADR へリンクする。
- **当てはめた原則・パターン**：[文書の種類](../../../principles/docs/reference/patterns.md#diataxis)の解説。
  [判断の記録](../../../principles/docs/reference/patterns.md#adr)：ADR の連鎖をたどらなくても今の姿が分かるようにする。

### `docs/guides/`

- **責務**：手順。目的を果たすために何をどの順で行うか（準備、追加、移行、復旧）。決まりとして守る順序も含む。
  プラグインの手順は目的の手順と共通の手順に分け、人が読む運用や準備の手順は層の外に置いてよい
  （[目的の手順と共通の手順](#procedures)）。
- **置くもの / 置かないもの**：手順と、その場で要る最小の説明。仕組みの説明は `architecture/` へリンクする。目的の手順と
  共通の手順の形は[形式](../reference/formats.md#procedure "在りか")にある。
  プラグインでは、目的の手順は起点（共通のルール、役割ごとの指示）が、共通の手順とロールの外から入る目的の手順は
  スキルが、要約か案内で載せてエージェントに届ける。
- **当てはめた原則・パターン**：[文書の種類](../../../principles/docs/reference/patterns.md#diataxis)の手順。

### `docs/reference/`

- **責務**：引くための事実。契約、設定、コマンド、形式、用語、決まり、原則の一覧。
- **置くもの / 置かないもの**：一覧や表。手順の段が使う決まり（条件、表、形）。手順（守る順序を含む）と、理由は置かない。設定の既定値は、例の設定ファイルを正にする。
- **当てはめた原則・パターン**：[文書の種類](../../../principles/docs/reference/patterns.md#diataxis)の参照。
  [スキーマを先に](../../../principles/docs/reference/principles.md#schema-first)：契約と形式はここに先に書く。

### `docs/adr/`

- **責務**：判断の記録。
- **置くもの / 置かないもの**：[形式](../reference/formats.md#adr)に沿う。今の姿のまとめは置かない。
- **当てはめた原則・パターン**：[判断の記録](../../../principles/docs/reference/patterns.md#adr)、[メタデータ](../../../principles/docs/reference/patterns.md#metadata)：
  状態と参照を frontmatter に持たせて検査する。
