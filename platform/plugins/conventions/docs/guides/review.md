# レビューする

レビューを頼まれた人（人でもエージェントでも）が、頼まれてから結果を返すか残す（PR のレビューか、報告の Issue）までの手順。目的の手順で、段の中で共通の
手順を使う（[手順と役割](../architecture/documentation.md#procedures)）。決まりは
[レビューの扱い方](../reference/reviews.md "在りか")にある。自分の変更のレビューを頼んで答える手順は、
[レビューを頼んで答える](request-review.md "在りか")にある。

結果を返すか残したら（全体のレビューなら、報告の Issue を作ったら）終わる。そのあとに頼まれたレビュー（push で進んだ
head のレビューなど）は、新しい依頼として振り分けから入る。

1. **始めに読む**：次の二つを全体まで読む。この段は省かない。このセッションですでに全体まで読んだ文書は、読み直さなくて
   よい。
   - [文書の体系](../architecture/documentation.md)：どこに何を置き、決まりをどう定義して届けるか。観点「文書とコメント」
     で、変更が置き場所に合っているかと、直すべき所（定義を変えたら直す届け方など）に漏れがないかを見る入口に使う。
   - [レビューの扱い方](../reference/reviews.md)：種類、観点、指摘、結果の形、差分のレビューと全体のレビューの決まり。
2. **種類を決める**：頼まれたものが差分（PR の差分か、コミットの範囲）なら、下の「差分のレビュー」に進む。範囲（地図の
   項目か、リポジトリ全体）なら、下の「全体のレビュー」に進む（[種類](../reference/reviews.md#kinds)）。

## 差分のレビュー

1. **自分の変更でないかを確かめる**：自分（同じセッション）が変えた差分なら、自分ではレビューせず、共通の手順の
   [レビューを頼んで答える](request-review.md "在りか")の「頼む」の 1〜3 段（回し方を決める、いつ頼むか、頼む相手と渡すもの）に沿って別の目に頼み、返った結果で下の 6 段に進む
   （[差分のレビュー](../reference/reviews.md#diff)）。指摘を直すなら、[変更を届ける](deliver-change.md "在りか")に入り直す。
2. **依頼と範囲を集める**：依頼の内容、依頼の Issue（閉じるか触れる Issue）、差分の範囲を、頼む文か、PR のタイトルと依頼の Issue から読む。変更の
   意図と検討した別の形（頼む文の最後の見出しか、PR の本文。本文は最初の節が意図なので丸ごと）は、まだ読まず、在りかだけを
   確かめる。
3. **範囲のファイルを確かめる**：`git diff --stat <範囲>` で確かめる。変えたと聞いたファイルのほかに入っているものも、
   範囲に数える。レビューするリポジトリのファイル、index、HEAD は変えず、試すときは作業領域の外（隔離して動くときの
   自分の worktree か、`mktemp -d` で作った場所）を使う（[手順と役割](../architecture/documentation.md#procedures)）。
4. **読む**：差分と、それが前提にする所、それを前提にする所を読み、関わる観点を選んで、その拠り所に照らして読む
   （[観点](../reference/reviews.md#perspectives)）。PR 全体の差分のレビューでは、すべての観点で読む。ただし、観点を分けて
   頼まれたら（[回し方](../reference/reviews.md#ways)の念入り）、頼まれた観点で読む。観点「別の形」は、変更した人の枠組みに
   寄らないよう、差分と変更の意図を読む前に、依頼と Issue の目的だけから別の形を挙げる。そのあとで、変更の意図と
   検討した別の形を読み、差分と照らす。当てはめるパターンは、[変更とパターン](../reference/changes.md#patterns)の表で選ぶ。
5. **指摘を書く**：指摘は、元の文書とコードを開いて確かめてから出す。確かめていない推測は、推測と書く。決まった形で
   書き、[結果の形](../reference/reviews.md#record)にまとめる（[指摘](../reference/reviews.md#findings)）。
6. **返すか残す**：結果を返すよう頼まれたら、PR が書かれていても GitHub には残さず返す。そうでなく PR を指す依頼なら、
   PR 全体の差分のレビューにして、見た head に付けた PR のレビューとして残す（[差分のレビュー](../reference/reviews.md#diff)）。

## 全体のレビュー

各段の決まり（重点の足し方、指摘の確かめ方、分類と判断が要る点、報告に書くもの）は[全体のレビュー](../reference/reviews.md#audit)に
ある。この手順は、報告の Issue を作るまで。直しと検査の追加は、変更する人が目的の手順の[変更を届ける](deliver-change.md "在りか")で進める。

1. **範囲と観点を決める**：範囲は地図の項目で分け、観点は[観点](../reference/reviews.md#perspectives)の表から選ぶ。
   - 地図は `check-docs --map` で一覧できる。各項目の置き場所（範囲にするファイル）は、その項目を宣言する地図の表にある。
   - 文書ごとの区分、更新日、項目、前提にする文書は `check-docs --catalog` で一覧できる（長く変わっていない文書や、
     変わった文書を前提にする文書を探すのに使う）。
   - 前回の報告は `gh issue list --state all --search '"の全体のレビュー" in:title'` で探し、報告であることと範囲を本文で
     確かめる（タイトルの言葉を含む、報告ではない Issue も出る）。
   - 前回の報告から変えた決まりは、principles と conventions の履歴が前回の報告の head と同じリポジトリにあれば、
     その head からの `git log` で見る。
   - 打ち切りで直さなかった提案は、前回の報告のあとにマージした PR のうち、答えのコメントに「打ち切り」を含むものを
     `gh pr list --state merged --search '打ち切り in:comments'` で探し、そのコメントと、答えたレビューで読む。
2. **検査を回す**：先に、そのリポジトリの、CI と同じ検査と、`check-docs` を回す。
3. **範囲ごとに読む**：範囲ごとに、別の目で読む。範囲は重ならないように分け、観点ごとに読む人（エージェントなら
   サブエージェント）を分けて並べ（[全体のレビュー](../reference/reviews.md#audit)）、それぞれに、範囲、観点、指摘の形
   （[指摘](../reference/reviews.md#findings)）を渡し、ファイルを変えないよう頼む。
4. **指摘を確かめる**：戻ってきた指摘を、自分で元の文書とコードを開いて確かめる。
5. **まとめる**：同じ原因の指摘を分類にまとめ、判断が要る点を分ける。
6. **報告する**：報告を `gh issue create` で Issue にし、その Issue へのリンクを依頼への回答に添える。判断が要る点の
   答えを受けてからの直しと検査の追加は、直す人が[変更を届ける](deliver-change.md "在りか")で進める。
