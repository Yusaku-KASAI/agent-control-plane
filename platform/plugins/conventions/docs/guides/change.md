# 変更する

変更する人（人でもエージェントでも）が、依頼を受けてから変更（PR）を終えるまでの手順。作業の場面の手順で、段の中で
部品の手順を使う（[場面の手順と部品の手順](../architecture/documentation.md#procedures)）。決まりは[変更の扱い方](../reference/changes.md "在りか")、
[レビューの扱い方](../reference/reviews.md "在りか")、[書き方](../reference/writing.md "在りか")にある。

変更は一つのターンで終わるとは限らない（追加の依頼、レビューの指摘への答え、CI の失敗、マージのあとの確かめ）。
続きのターンでは、今どの段にいるかを確かめてそこから進める。会話の記録がない新しいセッションで続きから入るときと、
質問などほかの作業の途中から変更に入るときは、1 段から始める。

1. **始めに読む**：次の二つを全体まで読む。この段は省かない。
   - [文書の体系](../architecture/documentation.md)：どこに何を書き、決まりをどう定義して届けるか。文書を変えない
     変更でも、変更をどこに置き、変えたらほかに何を直すかを決めるのに使う。
   - [変更の扱い方](../reference/changes.md)：PR の流れ、変更とパターン、検査と履歴。
2. **依頼を読む**：依頼が Issue を指していれば、本文とコメントを読む。依頼文が短くても、Issue とリポジトリから読み取れる
   ことは前提にする。
3. **今の姿を確かめる**：変更が関わる仕組みの今の姿と前提を、文書、ADR、コードで確かめる。
4. **壊れうる場面を挙げる**：変更で壊れうる場面を挙げて確かめる。たとえば、同じものを作り直すとき、再起動や失敗の途中、
   同時に動くとき、すでにあるデータや設定との組み合わせ。変更の種類に応じて[変更とパターン](../reference/changes.md#patterns)の
   パターンを当てはめる。選び方と使い方は、部品の手順の[パターンを当てはめる](design.md "在りか")にある。
5. **作る**：文書を足したり書き換えたりするときは、部品の手順の[文書を書く](write-docs.md "在りか")に沿う。コミットの前と
   push の前は[検査と履歴](../reference/changes.md#checks)に、コミットメッセージと PR の本文は[書き方](../reference/writing.md "在りか")に
   沿う。
6. **レビューを頼んで答える**：変更した人とは別の目（サブエージェントや別の人）に差分をレビューさせ、指摘に答える。
   [レビューする](review.md "在りか")の「差分のレビュー」と、指摘への答え方に沿う。いつ、何を渡すか、観点、指摘の書き方と答え方、
   終える前に満たすことは[レビューの扱い方](../reference/reviews.md "在りか")にある。
7. **確かめていないことを書く**：確かめられなかったことは、確かめていないと PR に書く。依頼に答えるときは、その答えにも
   書く。
