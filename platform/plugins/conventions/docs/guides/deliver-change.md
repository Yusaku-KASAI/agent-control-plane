# 変更を届ける

変更する人（人でもエージェントでも）が、依頼を受けてから、変更をマージできる PR にして終えるまでの手順。目的の手順で、
段の中で共通の手順を使う（[手順と役割](../architecture/documentation.md#procedures)）。決まりは[変更の扱い方](../reference/changes.md "在りか")、
[レビューの扱い方](../reference/reviews.md "在りか")、[書き方](../reference/writing.md "在りか")にある。

マージされたあとの依頼（既定のブランチでの確かめなど）は、新しい依頼として振り分けから入る。マージの前の同じ PR への
依頼（追加の依頼、レビューの指摘への答え、CI の失敗）は続きで、続きのターンの扱いは
[手順と役割](../architecture/documentation.md#procedures)にある。

1. **始めに読む**：次の二つを全体まで読む。この段は省かない。このセッションですでに全体まで読んだ文書は、読み直さなくて
   よい。
   - [文書の体系](../architecture/documentation.md)：どこに何を置き、決まりをどう定義して届けるか。文書を変えない
     変更でも、変更をどこに置き、変えたらほかに何を直すかを決めるのに使う。
   - [変更の扱い方](../reference/changes.md)：PR の流れ、変更とパターン、検査と履歴。
2. **依頼を読む**：依頼が Issue を指していれば、本文とコメントを読む。依頼文が短くても、Issue とリポジトリから読み取れる
   ことは前提にする。依頼の狙いを Issue の文言だけで決めず、食い違いがありそうなら、どう読んだかを最初の回答に書いて
   確かめる（聞いて待てないときは、妥当な読み方で進める）。会話で決まったことは、依頼の Issue があれば
   そこに残してから進め、なければ PR を作るときに本文に書く（[どの Issue にも当たること](../reference/issues.md#general)）。
3. **範囲を決める**：取りかかる前に、範囲の中の項目と PR を付け合わせ（[範囲の項目と PR の付け合わせ](../reference/issues.md#scope-items)）、
   依頼の範囲（範囲の中と範囲の外）を今の依頼に合わせて、依頼の Issue の本文に書く（[依頼の範囲](../reference/issues.md#scope)）。
   作業の途中で出た直しとレビューの指摘は、それに照らして振り分ける（[済んでいないものの置き場所](../reference/issues.md#append)）。
4. **今の姿を確かめる**：変更が関わる仕組みの今の姿と前提を、文書、ADR、コードで確かめる。
5. **形を選び、壊れうる場面を挙げる**：形を決める前に、ほかの形（目的に立ち返った別の手段、より単純な形、一つ上の
   枠組みでの解き方）を挙げ、選ぶ理由を決める（[前提を問い直す](../../../principles/docs/reference/principles.md#double-loop)）。
   挙げた形と選ばなかった理由は、PR の本文に書く（[書き方：PR](../reference/writing.md#pull-requests)）。[変更とパターン](../reference/changes.md#patterns)の
   判断の記録に当たるなら、ADR にも書き、本文からはそれを指す。
   そのうえで、選んだ形で壊れうる場面を挙げて確かめる。たとえば、同じものを作り直すとき、再起動や失敗の途中、同時に
   動くとき、すでにあるデータや設定との組み合わせ。変更の種類に応じて[変更とパターン](../reference/changes.md#patterns)の
   表からパターンを選んで当てはめる。
6. **作る**：案を練り直すたびに範囲を見直し、最初の PR は小さく保つ。広がったら、一つの目的ごとに分ける。依頼の範囲の中を何本かの PR に
   分けるときの依頼の Issue の扱いは[依頼の範囲](../reference/issues.md#scope)にある（[小さく試して確かめる](../../../principles/docs/reference/principles.md#small-experiments)、[変更とパターン](../reference/changes.md#patterns)）。
   文書を足したり書き換えたりするときは、共通の手順の[文書を書く](write-docs.md "在りか")に沿う。コミットの前と
   push の前は[検査と履歴](../reference/changes.md#checks)に、コミットメッセージと PR の本文は[書き方](../reference/writing.md "在りか")に
   沿う。
7. **レビューを頼んで答える**：変更した人とは別の目（サブエージェントや別の人）に差分をレビューさせ、指摘に答え、
   [終える前](../reference/reviews.md#ending)を満たす。共通の手順の[レビューを頼んで答える](request-review.md "在りか")に沿う。
   レビューする人が沿う手順は[レビューする](review.md "在りか")で、頼む文にその在りかを書く。
   満たせないまま上限の回数に達したら、9 段の返し方に進む。
8. **確かめていないことを書く**：確かめられなかったことは、確かめていないと PR に書く。依頼に答えるときは、その答えにも
   書く。
9. **終える**：
   - 依頼の Issue の範囲の中のうち、この PR が扱う項目に PR の番号を添え、残る積んだ指摘を項目にする
     （[範囲の項目と PR の付け合わせ](../reference/issues.md#scope-items)）。PR の本文の `Closes` と `Refs` を、依頼の Issue を閉じるか
     どうかに合わせる（[依頼の範囲](../reference/issues.md#scope)）。
   - PR の下書きを外し、そのときに終える前を満たしていることを確かめる。外したあとに変更したら、もう一度満たす。
   - 満たせないまま上限の回数（[回し方](../reference/reviews.md#ways)）に達したら、そこで止め、残っていることを添えて依頼者に
     返す。依頼者が続けるよう言ったら、回数を数え直して 7 段から進める。
   - 下書きを外したあとに、同じ PR で追加の依頼を受けて作業を続けるときは、回数を数え直し、下書きに戻して、2 段から進める。
