# 0032. 変更の依頼では取りかかる前に依頼の範囲を書き、それだけで依頼として成り立たない範囲の外の指摘は依頼の Issue に積む

## Context

トークンの消費を調べたキャンバス（control-plane の Issue #240）で、次のことが分かった。

- 一つのスレッドで作業を続けるほど、コンテキストが増える。API の呼び出しのたびに全体を読むので、1 回の費用は
  コンテキストの大きさに比例する。調べたスレッドでは、メインの会話のコンテキストが 17 万から 97 万トークンまで増えた。
- そのスレッドから、関わりの強い Issue が次々にでき（9 件）、それを同じスレッドで順に片付けた。作業の途中で出た関わりの
  強い直しや指摘は、「今回扱うべき」として今の PR に足すか、範囲の外の指摘は Issue にする決まり（`reviews.md` の差分の
  レビュー）に沿って新しい Issue にして、同じスレッドで続けることになりがちだった。範囲の中と外を分ける基準は
  「依頼と Issue の目的」だけで、取りかかる前に書いてはいなかった。

依頼者とキャンバスで、範囲を先に決めること（F1）と、関わりの強い指摘の受け皿（F2）を、レビューの回数を抑えること
（F5）とともに Issue #244 で進めると決めた。#244 は、F2 で新しい Issue にするものの線引きを「元の Issue を閉じたあとも、
それだけで依頼として成り立つか」にすることを勧めていた。

## Decision

- **依頼の範囲を先に書く（F1）**：変更を届けるの 2 段で、取りかかる前に、依頼の Issue の本文の `## 範囲` の節に、範囲の
  中と範囲の外を書く。依頼の Issue がなければ決めておき、PR を作るときに本文に書き、レビューを頼むときに依頼の
  内容として渡す。作業の途中で範囲の中を広げず、途中で出た直しとレビューの
  指摘は、これに照らして振り分ける。定義は `issues.md` の「依頼の範囲」に置き、用語集に言葉を足して、差分の範囲や
  全体のレビューの範囲と分ける。`reviews.md` の範囲（観点「依頼との一致」、差分のレビュー、終える前）はそれを指す。
- **それだけで成り立たない指摘は依頼の Issue に積む（F2）**：範囲の外の直しや指摘のうち、依頼の Issue を閉じたあとも、
  それだけで依頼として成り立つものだけを新しい Issue にする。ほかは依頼の Issue のコメントに積む（依頼の Issue がなければ
  新しい Issue）。
- **済んでいないものが残る PR**：範囲の中を何本かの PR に分けるときは、依頼の Issue のまま PR ごとに一部を扱い、分けた一部を
  新しい Issue にするのは、それだけで依頼として成り立つときだけにする（F2 と同じ線引き。sub-issues は大きな作業を手順に
  分けるときだけ使い、ADR 0001 で親子でテーマを表すことは採っていない）。PR を終えても範囲の中の残りか積んだ指摘が
  残るなら、その PR では依頼の Issue を閉じず、本文には `Closes` のかわりに `Refs` を書き、最後の PR で `Closes` を書く。
  そのときに Issue の本文の範囲の中のうちその PR が扱うものに PR を添え、残る積んだ指摘を同じ節の
  「残るもの」に並べて、コメントする。マージのあと、済んだ範囲の中を消すのは、締めの 5 段か次の依頼の 2 段にする。
  これを、レビューを頼んで答えるの「終える」の段（下書きを外す前）に置く。PR から依頼の Issue を読む所（レビューする
  の 2 段、github スキル）は、`Refs` の行も読む。
- 積んだ指摘への答えは、今の答えの種類「Issue にした」に依頼の Issue の番号を渡して書く。`prctl` の答えの種類は増やさない。

## Alternatives

- **積んだ指摘を、PR を終えるときに一つの「続き」の Issue にまとめる**：依頼の Issue を閉じられるが、成り立たないとした
  指摘のために結局 Issue を作り、前の文脈をその Issue に書き写すことになる。依頼の Issue に残せば、次に頼まれた人は同じ
  Issue の本文とコメントから文脈ごと読める。
- **範囲の中を分けるときは、いつも Issue（sub-issues）に分ける**：段階ごとの Issue と PR が一対一になりきれいだが、
  それだけでは成り立たない段階のために Issue を作り、文脈を書き写すことになる。それだけで成り立つ段階だけを分ければ、
  積むものと同じ線引きで決められる。
- **積んだ指摘が残っても依頼の Issue を閉じ、あとの全体のレビューで拾う**：打ち切りの提案と同じ扱いになるが、積むのは
  直すと決めたものなので、閉じた Issue に埋もれると失われる。
- **範囲の節を、次の依頼まで書き換えない**：PR を終えてから次の依頼までのあいだ、本文に残るものが書かれず、
  整っている状態（本文が今の姿）と締めの 5 段（古い本文を書き直す）に食い違う。
- **PR を終えるときに、範囲の中を残る積んだ指摘に書き直す**：マージの前に本文からこの PR の範囲が消えるので、その PR を
  続けるとき、ほかの人がレビューするとき、マージされずに閉じたときに、Issue から範囲を読めなくなる。
- **積むたびに本文の範囲の節にも一覧（済んだかの印付き）で足す**：積むのはこの PR の範囲の外なので、この PR のあいだに
  済むことはなく、一覧は PR を終えるときに一度作れば足りる。積むたびに本文も書き換えると、手間とコメントとの重なりが増える。
- **範囲の中だけを書き、範囲の外は書かない**：途中で出たものを振り分けるときに、外と決めたことの在りか（ほかの Issue
  など）が分からず、範囲を広げるか迷う。
- **範囲の節を `check-issues` で検査する**：節があるかは機械で見られるが、取りかかっていない Issue には要らず、何を
  書くかは中身なので、検査にするものの条件（誤って落ちにくい）を満たさない（ADR 0028）。

## Consequences

- conventions の決まりなので、それを使うすべてのターゲットに効く。どのターゲットも、プラグインの更新で受け取り、
  ターゲットの側で直すファイルはない。
- 範囲の中の残りか積んだ指摘が残る Issue は、PR がマージされても開いたままになり、次の依頼は本文の範囲の節から始められる。
- 範囲の節があるか、積んだ指摘が残るときに `Refs` にしたかを確かめる検査はない。
