# 0022. 目的の手順、共通の手順、役割ごとの指示に形を持たせ、決まった枠を検査する

## Context

ADR 0020 と 0021 で、手順を目的の手順と共通の手順に分け、役割ごとの指示に「受け持つ手順」の節を置いた。決まりは文書の
体系にあるが、それぞれの文書が何をどの順に持つかの形はなかった。そのため、手順ごとに冒頭の書き方、段の名前の付け方、
始めに読む段や新しい依頼になる境の有無がまちまちになり、guide の定義だけ節の分け方が違っていた。レビューのたびに、
こうしたそろえ漏れが指摘として出た。

依頼者からは、conventions の文書の体系が前提にできる文書には、決まった枠と柔軟な部分を示した形を用意し、一貫させたい、
という指摘があった。

## Decision

- 形式（`reference/formats.md`）に、目的の手順、共通の手順、役割ごとの指示、スキルの形を置き、決まった枠と柔軟な部分を
  書き分ける。
- 決まった枠のうち機械で確かめられるもの（プラグインの手順が層を名乗ること、目的の手順の 1 段が始めに読むで、新しい
  依頼の境を書くこと、共通の手順が始めに読む段を持たないこと、段に番号と太字の名前を付けること、役割ごとの指示の
  最初と最後の節）を `check-docs` で確かめる。スキルは数が少ないので検査せず、レビューで見る。
- 役割ごとの指示の形は、節の分け方が conventions の起点の決まりなので、roles プラグインではなく conventions の形式に
  置き、roles の全体像から指す。

## Alternatives

- **形を roles や各プラグインの文書に置く**：役割ごとの指示は、プラグインの `agents/` にもリポジトリの `.claude/agents/`
  にも置く。どこでも同じ形にするには、決まりの持ち主の conventions に置く方がよい。
- **形だけを書き、検査しない**：そろえ漏れはレビューで見つけるしかなく、今回のように何度も指摘として出る。

## Consequences

- 人が読む運用や準備の手順（目的の手順と共通の手順の層に入らないもの）は、この形と検査の外に置く。プラグインの
  `docs/guides/` の手順はどれも層を名乗る。ほかの置き場所では、層を名乗った文書だけを検査する。
