# 0054. 差分のレビューを頼むとき、変更の意図と検討した別の形は、頼む文に書かず在りかで渡す

## Context

[ADR 0023](0023-alternatives-before-building.md) は、レビューする人が観点「別の形」で、変更の意図を読む前に依頼と
Issue の目的だけから別の形を挙げるとし、頼む人は意図と検討した別の形を頼む文の最後の見出しの下にまとめるとした。

#201 の確かめ（2026-10-26）で、この順が守られていないと分かった。reviewer のサブエージェント 221 件のうち 181 件で、
頼む文に変更の意図そのものが書かれていた。サブエージェントは頼む文を一度に読むので、最後の見出しに置いても、依頼と
同時に意図を読む。レビューする人が書いた「意図を読む前に挙げた」は、記録と食い違う例があった。

#279 は、頼みを 2 段に分ける（1 通目で依頼だけを渡して別の形を挙げてもらい、2 通目で同じサブエージェントに意図を渡す）
ことを、原因に直接効く候補としていた。しかし control-plane 経由では、`SendMessage` は harness の hook が宛先によらず断る
（platform の [ADR 0008](../../../../docs/adr/0008-subagents-in-foreground-under-control-plane.md)）。同じサブエージェントに
2 通目は送れない。

## Decision

- 変更の意図と検討した別の形は、頼む文に書かず、在りかで渡す。在りかは PR の本文で、PR を作る前のレビューでは、
  作るときに使う本文のファイル。頼む文には、依頼から別の形を挙げたあとで開くよう書く（レビューを頼んで答えるの
  「頼む」の 3 段、レビューの扱い方の「差分のレビュー」）。
- レビューする人は、依頼から挙げた別の形を、在りかを開く前に見える文に書き出す（レビューするの 4 段）。考え
  （thinking）の中身は会話の記録に残らないので、文に書き出さないと、挙げてから開いたかを確かめられない。開くのは
  道具の呼び出しになるので、書き出した文と開いた呼び出しの前後が記録に残る。
- 道具での在りかの書き方（本文のファイルの絶対パスか、`gh pr view`）は github スキルに置く。

## Alternatives

- **頼みを 2 段に分け、同じサブエージェントに 2 通目を送る**：control-plane 経由では `SendMessage` が断られる。
  断る理由（続きがバックグラウンドで動き、依頼への回答が 2 回出る）は今も当たる。
- **1 段目に別のサブエージェントを立て、依頼だけから別の形を挙げさせる**（作る前でも、レビューの前でも）：
  順は仕組みで守れるが、PR ごとか、レビューごとにサブエージェントが一つ増える。reviewer はすでに費用の約 3 割を
  占める（#280 の結果）。#247 は 1 回あたりの費用を下げようとしており、向きが逆になる。在りかで渡す形で順が
  守られないと分かったときの次の手にする。
- **通常の回し方でも、観点「別の形」だけのレビュアーを分ける**：同じく、レビューごとにサブエージェントが一つ増える
  （ADR 0023 の Alternatives と同じ理由）。
- **頼む文に意図の中身（PR の本文の決まった見出し）が入っていたら、Agent の呼び出しを hook で断る**：頼む人が
  決まりを守ることまで仕組みで守れる。ただ、新しい渡し方がまだ破られると分かっていない（[検査の扱い方](../reference/checks.md)
  は、実際に破られる決まりを検査にする）。#279 の確かめで、頼む文に中身が入ると分かったときに入れる。
- **今のまま（最後の見出しの下にまとめる）**：#201 で効いていないと分かった。

## Consequences

- PR を作る前のレビューでも、本文のファイルを先に書いておくことになる。`prctl create` に渡す本文を、レビューを
  頼む前に書く。
- レビューする人が開く呼び出しが一つ増える。
- 頼む文だけを見ても意図は分からない。レビューの結果に意図を書き写さないので、意図は PR の本文で読む。
- 効き目（別の形を挙げてから意図を開いているか）は、入れたあとに会話の記録で確かめる（#279 の範囲の中）。
