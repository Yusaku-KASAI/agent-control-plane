# 0025. 相談に乗ると課題を整えるを目的の手順にし、相談の考えは Issue をキャンバスにして残す

## Context

ADR 0021 は、相談や壁打ち、課題の整理を、目的の手順のない依頼として扱い、中身は #28（pm ロール）、#102（ロードマップの
今の焦点をいつ誰が書き直すか）、#111（Issue の決まりが守られているかを確かめる）で作るとした。

依頼者は、pm ロールと、それが主に使う課題を整える手順と、Issue をキャンバスにする壁打ちを進めたいと考えている
（Slack、#28 のコメント）。研究のように数式や図を使う考察は Slack では表示できないので、Issue と Markdown をキャンバスに
して残したい。

今は、課題の整理を誰も頼まれたときの手順として持たない。ロードマップの今の焦点が閉じた Issue を並べたまま残ったり
（#102）、テーマのラベルの抜けに人が気づくまで誰も見なかったり（#111）した。相談は、そのつど依頼文で何をするかを
伝えていて、考えが会話の中にだけ残る。

## Decision

- 目的の手順「相談に乗る」（`guides/consult.md`）を足す。相談は、依頼者が決めたいこと、整理したいことについて考えを
  求める依頼で、事実を聞くだけの質問は含まない。段は、始めに読む（課題の扱い方）、問いを読む、調べる、広げて絞る、
  キャンバスに残す、答える。壁打ちの次の回は続きとして 2 段から繰り返す。
- 考えを残す先は Issue にし、課題の扱い方に「キャンバス」の節を置く。本文に今の姿（問い、前提、選択肢と比べ、決まった
  こと、決めていないこと、次にやること）を、コメントに回ごとの考察を書く。数式は GitHub の Markdown の数式、図は Mermaid
  で書き、チャットの答えには要約と Issue へのリンクを書く。決まったことは、やることを Issue に分け、決まりや設計の判断は
  ADR にする変更の Issue にする。今ある「検討中の設計は Issue に書き、決まったら ADR にする」を、相談の場面に広げた形。
- 目的の手順「課題を整える」（`guides/organize-issues.md`）を足す。段は、始めに読む（課題の扱い方とリポジトリのラベルの
  決まり）、範囲を決める、今の姿を確かめる、ずれを挙げる、整える、まとめを答える。照らす基準は、課題の扱い方に
  「整っている状態」の表として置く（ラベル、開いているか、本文、重なり、依存関係、ロードマップ、テーマ）。範囲や狙いの
  変更、根拠のない閉じ、依頼者が示した方針にない順番の入れ替えは、直さずに人が決めるものとしてまとめに書く。この手順では
  文書やコードを直さない。
- ロードマップの今の焦点を書き直すきっかけ（#102）は、課題を整えるを頼まれたとき（ロードマップを範囲に含む）と、
  セッションを締めるとき（ADR 0024）にする。誰がするかは、その手順を受け持つロール（書ける範囲に Issue を含むロール）に
  する。定期的に整えるのは、エージェントの定期実行（#91）で、この手順を頼むことで行う。
- 届け方は、セッションを締めると同じく、consult、organize-issues スキルにし、共通のルールの振り分けに並べる。今は
  どのロールも主に使わないので、ロールの指示からもスキルへの案内で届ける。pm ロール（#28）を足すときに、主に使う
  ロールとして、その指示に「始めに読む」の段の文書を直に並べる。
- 受け持つロールは、書ける範囲で決める（platform の ADR 0019）。developer と reviewer は Issue に書けるので両方を受け持つ。
  guide は相談に乗るを受け持ち、書けないキャンバスの中身は回答に書く。課題を整えるは受け持たず、ずれを挙げて回答に
  書く。

## Alternatives

- **相談と課題の整理を一つの目的の手順にする**：相談の終わりは考えを返すことで、課題の整理の終わりは Issue が決まりに
  合うことで、終わりの状態が違う。一つにすると、どちらの段も「当てはまれば」が増える。
- **質問（事実を聞く）も相談に乗るに含める**：質問の多くは調べて答えるだけで、選択肢を広げたりキャンバスに残したりする
  段が要らない。手順を読ませる手間が勝つ。
- **キャンバスを Issue でなく、リポジトリの Markdown のファイルや GitHub の Discussions にする**：ファイルは変更（PR）を
  通さないと残せず、壁打ちの回ごとに PR になる。文書には今の姿だけを置く決まり（課題の扱い方）とも合わない。Discussions
  は、やること（Issue）への分け方とラベル、依存関係の仕組みを持たず、課題の扱い方の分類の外になる。どちらも GitHub の
  Markdown の数式と Mermaid は同じく書ける。
- **Issue の決まりを仕組みで確かめる（#111 の検査のコマンドや GitHub Actions）を、ここで一緒に作る**：手順と、それが
  使う検査は別に決められる。手順の 4 段は、検査ができたらそれを使える。#111 に残す。
- **課題を整えるを pm ロールと一緒に作る**：手順はロールと多対多で（ADR 0021）、pm がなくても developer と reviewer が
  使える。ロールの権限と GitHub App の用意は別の変更にする。

## Consequences

- 「相談や壁打ち、課題の整理」は振り分けで目的の手順に当たる。目的の手順のない依頼の例は、事実を聞く質問などになる。
- 共通のルールの量は上限（40 行）に当たったので、振り分けの節で、締めとレビューの行を相談と整理と一つの項目にまとめた。
- 課題を整える手順の 4 段は、人の判断と GitHub の読み取りに頼る。ずれを機械で見つける仕組みは #111 に残る。
