# 0013. レビューを変更の扱い方から分けて定義し、差分のレビューと全体のレビューを観点と指摘の形で揃える

## Context

レビューの決まりは、変更の扱い方（`changes.md`）の一節にあった。中身は、PR の差分のレビューで何を渡すか、指摘の
仕方、指摘への答え方だけだった。

全体のレビュー（文書や設計の監査）は、人が頼んで 3 回回したが、範囲の分け方、観点、指摘の確かめ方、報告と直し方は
どこにも書いていなかった。全体のレビューは変更に結び付かないので、変更の扱い方には収まらない。

#59 で、レビューを決まったきっかけで機械的に回すことを目指している。その前に、何をどう見るかの定義が要る。

## Decision

- レビューの定義を conventions の `reference/reviews.md` に置く。差分のレビューと全体のレビューの二つの種類が、
  共通の観点と指摘の形を使う。
- 観点は、別の形、依頼との一致、正しさ、設計、セキュリティ、文書とコメント、検査に分け、それぞれに拠り所を書く
  （観点を分けて読む）。
- 指摘は、重さ（必須、提案、質問、細部）を頭に付けた決まった形で書く（指摘に重さを付ける）。
- 全体のレビューは、地図の項目で範囲を分けて読み、指摘を元の文書とコードで確かめてから、分類と判断の要る点に
  まとめて報告する。直すのは報告への答えを受けてから。
- 手順は conventions の review スキルで届ける。拠り所のパターン（別の目で見る、観点を分けて読む、指摘に重さを
  付ける）は principles に足す。

## Alternatives

- **差分のレビューは `changes.md` に残し、全体のレビューだけ別に書く**：観点と指摘の形が二か所に分かれ、片方だけ
  直されてずれる。
- **観点ごとにスキルを分ける**：観点ごとの中身はまだ短く、定義の表の 1 行で足りる。スキルが増えると、どれを読むかの
  判断が増える。観点の中身が育ったら、そのときに分ける。
- **全体のレビューの手順を書かず、毎回頼む人が指示する**：やり方が回ごとに変わり、機械的に回す（#59）ときの
  拠り所がない。

## Consequences

- レビューを機械的に回す仕組み（きっかけ、reviewer の役割、結果の出し方）は、この定義を前提にして #59 で決める。
