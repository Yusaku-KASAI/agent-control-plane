# 0009. 決まりの定義と、それをエージェントに届ける形を分け、届ける形は出典を示す写しにする

## Context

共通のルール（`rules/`）は、コメント、コミット、PR の書き方をそこだけで定義しつつ、文書の決まりの要約も持っていた。
developer ロールの定義は、変更の進め方（前提を確かめる、壊れうる場面を挙げる、PR の前にレビューさせる、確かめて
いないことを書く）を持っていたが、これは developer に固有のことではなく、このプロジェクト群での変更の進め方だった。
github スキルは、PR の本文とコメントに何を書くかを定義していた。決まりの定義と、それを効く形で届けることが混ざり、
同じ決まりがどこにあるのかが分からなくなっていた。

## Decision

- 決まりは一か所で定義する。このプロジェクト群の決まりは conventions の `docs/` に置き、書き方（コメント、コミット、
  PR）と変更の進め方を足す。
- 共通のルール、役割ごとの指示（ロールの定義）、スキル、検査は、定義を効く形で届けるものとして扱う。新しい決まりを
  足さず、要約や選び出しだけをし、どの定義によるかを示す。
- conventions の中の地図を、定義と届け方の二つの集まりに分け、届け方が定義を前提にする向きにする。

## Alternatives

- **共通のルールを、コメント、コミット、PR の定義の置き場所のままにする**：いつも読み込む短い要約と、定義の詳しさが
  一つのファイルで競い、どちらにも寄せられない。
- **変更の進め方を developer ロールに置いたままにする**：人が変えるときや、ほかのロールが変えるときに同じ決まりを
  書き直すことになる。
- **届ける形の側に出典を書かない**：二か所に定義があるように見え、どちらを直せばよいか分からない。

## Consequences

- 決まりを変えるときは、定義を直し、それを写している届け方（共通のルール、ロール、スキル）も直す。
- 届け方の各項目に出典があるかは、いまは検査していない。
