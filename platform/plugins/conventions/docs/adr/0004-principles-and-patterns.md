# 0004. 設計の拠り所を、原則（何を大事にするか）とパターン（どう組むか）の二つの一覧に分ける

## Context

ADR 0003 で、設計の拠り所を platform の原則の一覧（`reference/principles.md`）に置いた。一覧には、単一責任や SSOT の
ような原則と、Clean Architecture、ADR、Diátaxis、Docs as Code のような特定の問題への解き方が混ざっていた。また、
状態を軸で洗い出す、事実と判定を分けるといった設計の観点は、review プラグインのスキルの中にだけあり、文書から
リンクできず、構成要素の説明から指せなかった。

## Decision

- 拠り所を二つの一覧に分ける。原則（`reference/principles.md`）は何を大事にするかを、原則・何のため・一般的な
  当てはめ方・よくある違反で書く。パターン（`reference/patterns.md`）は特定の問題への形を、解く問題・形・使いどころ・
  よくある失敗・拠り所の原則で書く。
- 構成要素の説明は「当てはめた原則・パターン」として、パターンを採ったときはパターンを、拠り所にしただけのときは
  原則を指す。
- review プラグインのスキルは、パターンの定義を持たず、どの変更にどのパターンを当てはめるかと指摘の仕方だけを持つ。

## Alternatives

- **一つの一覧のままにする**：原則とパターンで書く項目が違い（パターンには解く問題と形がある）、どちらにも合わない。
- **パターンの定義をスキルに残す**：文書から指せず、スキルとアーキテクチャの文書で同じ定義が二か所になる。

## Consequences

- 原則の一覧から、ADR、Diátaxis、Docs as Code、メタデータはパターンの一覧に移る。判断の記録の拠り所として、
  原則に「今と経緯を分ける」を足す。
