# 0020. 手順を場面の手順と部品の手順に分け、場面の手順の最初の段で全体まで読む文書を示す

## Context

ADR 0017 で手順を `guides/` に移したが、手順の範囲と階層は見直していなかった。手順は部品（文書を書く、パターンを
当てはめる、レビューする）だけで、依頼を受けてから終えるまでの作業の場面の手順はなかった。変更の進め方は、決まりとして
守る順序として参照の文書（`reference/changes.md`）に置かれていた。

ADR 0015 では、その場面で全体まで読ませたい文書を、起点のリンクの「（全体を読む）」で示した。Alternatives では、起点の
冒頭に「先に読む」の節を置く案と、`documentation.md` を hook で読み込ませる案を退け、効くかは記録で確かめるとした。

#130 で、#122 のあとのトランスクリプトを数えた。

- スキルを読んだサブエージェントが、スキルの「（全体を読む）」から手順を全体まで読んだのは、review で 88 件のうち 58 件、
  design で 22 件のうち 15 件だった。レビューを頼む文に手順の在りかが書かれていれば、スキルを読まなくても 36 件のうち
  28 件が読んだ。
- 文書を書き換えた本体のセッション 7 件のうち、共通のルールの「（全体を読む）」から文書の体系を全体まで読んだのは 1 件、
  write-docs スキルを読んだのも 1 件だった。本体のセッションは、conventions のスキルをほとんど呼んでいなかった。

依頼者からは、「（全体を読む）」のリンクは、読んだときにそのリンクに関心が向いていなければ、文ごと飛ばされる、という
見方があった。人に対しても、場面ごとの印より「まずこれを読む」と書く方が効く。

## Decision

- 手順を、場面の手順（依頼を受けてから終えるまでの、一つの作業の場面の全体。いくつものターンやセッションにわたる
  ことがある）と、部品の手順（場面の手順の段の中で使う、
  作業の一部分）の二つの層に分ける。場面の手順は、段の中で部品の手順を案内する。部品の手順は、場面の手順を前提に
  しない。
- 場面の手順の最初の段を「始めに読む」にし、その場面で全体まで読む文書を、省かない段として並べる。
- 起点（共通のルール、役割ごとの指示）は、場面の手順と、その「始めに読む」の段の文書を、最初に全体まで読むものとして、
  出典付きの要約で直に並べる。手順を指すだけでは、読む文書が一段たどった先になり、#130 で読まれなかった形に戻る。
  役割を問わず行う場面（変更する）は共通のルールに、役割に固有の場面はその役割ごとの指示に並べる。
- これは、ADR 0015 が退けた「起点の冒頭に『先に読む』の節を置き、いつも読む文書を並べる」を、場面を限って採り直す
  ことになる。0015 が退けた理由は、いつも読むなら読み込ませるのと同じコストで、読まれるかが確かでなくなるだけ、という
  ものだった。変更する手順と変更の扱い方は、場面（変更する）を限って並べるので、すべての作業のコストにはならない。
  文書の体系は、どの作業でも読ませるので、0015 が退けたコストをそのまま受け入れる。#130 では、場面を限った
  「（全体を読む）」は読まれず、直に書かれた在りかは読まれていた。読まれないことの方が、読む量より高くつくと判断した。
- スキルは部品の手順への入口にする。
- 決まりとして守る順序も手順に置く。参照の文書は、手順の段が使う決まり（条件、表、形）を持ち、順序は持たない。
- 最初の場面の手順として「変更する」（`guides/change.md`）を作り、変更の進め方をそこへ移す。その「始めに読む」には、
  文書の体系と変更の扱い方を置く。
- 文書の体系は、場面によらず、どの作業でも始めに全体まで読む。共通のルールの冒頭（「始めに読む」の節）に、条件を
  付けずに並べる。文書の体系は、文書と決まりの置き場所のほか、共通のルール、ロール、スキルが読み手に何をどう届けて
  いるかも説明する。どの作業でも、プロジェクトと自分の受け取っているものを知るのに要る。「変更するときは」のような
  前置きを付けると、読み手が自分の作業を当てはまらないと読み、飛ばしうる。
- 場面の手順は、一つのターンで終わるとは限らない。続きのターンでは今どの段にいるかを確かめてそこから進め、会話の
  記録がない新しいセッションで続きから入るときは「始めに読む」からやり直す。
- 起点は、項目を作業の場面や関心ごとの節に分ける。共通のルールは、読み込ませるときに自分の在りかも示し、作業の途中で
  立ち返れるようにする。

## Alternatives

- **手順を作業の場面だけで切る（部品の手順を持たない）**：文書を書く、パターンを当てはめる、は複数の場面で使うので、
  場面ごとに同じ段を書くことになる。
- **手順を部品だけで切る（今のまま）**：どの部品をいつ使うかを、スキルの description と、読み手の判断に任せることになる。
  #130 では、本体のセッションはスキルをほとんど呼ばず、部品の手順に届いていなかった。
- **`documentation.md` を hook で毎回読み込ませる**：確実に読ませられるが、約 22KB を、サブエージェントを含むすべての
  始めに足すことになる。本文を丸ごと注入すると、起点の量の上限（`formats.md` の量の上限）の考え方の外で、文書の体系の
  要らない小さな作業（検索だけのサブエージェントなど）の文脈にも常に入る。読むように書く形は、まず効くかを数え直す
  ための判断で、共通のルールの始めに読むものとして読ませて数え直す。それでも読まれなければ、場面を限って hook で
  読み込ませる（ADR 0015 の Alternatives の判断はそこで見直す）。
- **変更の進め方を参照に残し、手順はその段ごとの操作だけを持つ**：同じ段の並びが参照と手順の二か所に書かれ、ずれる。

## Consequences

- 「始めに読む」の段で本当に全体が読まれるかは、確かめていない。いくつかの依頼のあと、#130 と同じ数え方で数え直す。
- レビューの手順は、まだ部品と場面に分けていない。`guides/review.md` は、変更する人の段（レビューを頼んで答える）と、
  reviewer の場面（差分のレビュー、全体のレビュー）を一つに持ち、全体のレビューの順序は参照（`reference/reviews.md`）にも
  ある。次の変更で、reviewer の場面の手順と、変更する人の部品の手順に分け、順序を手順へ移す。
- スキルの description と、design の手順の置き場所は、まだ見直していない。
- 文書の体系（約 22KB）を、どの作業でも、サブエージェントも含めて読むことになる。使用量にどれだけ効くかは確かめて
  いない。
- 役割ごとの指示は、developer の「使う決まり」だけを節に分けた。reviewer と guide は、それぞれの場面の手順を作るときに
  分ける。
