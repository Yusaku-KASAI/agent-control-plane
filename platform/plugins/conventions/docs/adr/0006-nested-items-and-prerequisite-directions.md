# 0006. 文書の関係を、入れ子の項目と、階層ごとの前提の向きで表し、契約を独立した項目にする

## Context

ADR 0002 で文書を届く先で区切り、区切りの間を契約と共有の核でつなぐことにした。依存の向きは区切りの間でしか決めて
おらず、区切りの中の部品どうし（プラグイン、話題の文書）の関係は決めていなかった。リンクを数えると、一覧から各文書への
リンクのような依存でない参照と、本当の依存が区別されず、問題のない指し合いまで違反に見えた。契約は platform と
target-template の文書の中にあり、契約を作る側の区切りに属しているように見えた。

## Decision

- 区切りとその中の部品を、入れ子の項目として表す。同じ親の下の項目は、同じ種類と粒度にそろえる。
- 前提の向きは階層ごとに決め、循環させない。二つの文書の関係は、それらが初めて同じ親の下に入る階層の向きで判断し、
  下の階層の向きは上の階層の向きの範囲の中でだけ決める。
- 関係を種類で分け、依存の向きの決まりは「前提にする」関係にだけ当てる。索引から各文書へのリンクと、ADR へのリンクは
  案内として扱う。
- 区切りの間の契約（用語集、ハーネスの契約、ターゲットの契約）は、作る側にも使う側にも属さない一つの項目にし、両側が
  それを前提にする。置き場所は使う側から読める所のままにする。
- 地図（項目と前提の向き）は階層ごとに書く。最上位は全体の設計を持つリポジトリの overview に、設計構造行列で書く。

## Alternatives

- **区切りの間の向きだけを決める**：区切りの中で循環しても気づけず、中の部品が増えるほど関係が読めなくなる。
- **すべてのリンクを依存として扱う**：索引や判断の理由へのリンクまで違反になり、決まりが守れない。
- **契約を作る側の区切りに置いたまま、その区切りの一部とする**：使う側が作る側を前提にすることになり、作る側の中身の
  変更が使う側に波及する。
- **契約を一つずつ最上位の項目にする**：用語集を二つの契約が共有するので、どちらかに置くと契約の間に依存ができる。
  契約を一つの項目にまとめ、その中で用語集を前提にする方が向きが単純になる。

## Consequences

- 文書の中で、より一般的な項目から個別の項目への在りかの案内は、リンクにせず文章で書く。
- 地図に合っているかは、いまは一度きりの確かめで、`check-docs` で確かめるには項目と向きを機械で読める形で宣言する
  必要がある。
