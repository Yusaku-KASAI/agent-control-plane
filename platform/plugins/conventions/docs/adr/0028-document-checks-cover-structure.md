# 0028. 文書の検査は文書の構造（形式、リンク、依存、メタデータ）に限り、中身と網羅はレビューに任せる

## Context

ADR 0027 で、何を検査にするかの三つの条件（判断が要らない、実際に破られる、誤って落ちにくい）を決めた。そのうえで
#212（目的の手順が共通のルールの振り分けと、各ロールの「受け持つ手順」に並んでいるかを確かめる）を作る前に、依頼者が
次のように考えを示した（Slack）。

- 文書の検査は、エージェントの動きを仕組みで強いるものではなく、ハーネスの設計（文書の体系）を守るためのもので、
  レビューでも対応できる。
- 形式、依存関係、リンク切れ、メタデータのようなものは、機械の検査が効く。

#212 を見直すと、根拠に挙げたレビューの指摘（roles の全体像の受け持ちの説明、guide の締めの回し先、文書の体系の
届け方の表の例、guide が課題を整える手順の始めに読むを飛ばす段の指定）は、どれも「どの手順を誰が受け持つか」の
説明が古くなったもので、#212 の検査（名前が並んでいるか）では
見つからない。並べ忘れそのものは起きていない。今の `check-docs` の検査は、どれも形式、リンク、依存、メタデータの
どれかに当たる。

## Decision

- 文書の検査（`check-docs`）は、文書の構造の決まりに限る。形式（決まった節、見出し、印、量の上限）、リンク（リンク先、
  在りかの印、入口と索引からの道）、依存（地図と前提の向き）、メタデータ（ADR の frontmatter と参照）。
- 何をどこまで書くか、どの手順を誰が受け持つか、要約が出典と合うか、説明が今の姿と合うかは、中身としてレビューに
  任せる。名前やリンクの有無で数えられても、網羅や対応（すべての目的の手順が並んでいるか、など）は中身として扱う。
  数えられる形に落とすと、書き方（同じ行にまとめる、パスで書くなど）を検査に合わせることになり、誤って落ちるか、
  検査を通すための書き方が増える。
- #212 は検査にせず閉じる。目的の手順を足したときに直す所は、レビューの観点（文書とコメント、依頼との一致）で見る。
- ADR 0027 の三つの条件は変えない。文書の検査では、そのうち「判断が要らない」を、構造の決まりに当たることと読む。

## Alternatives

- **#212 を作る（名前やパスが並んでいるかを数える）**：並べ忘れは起きておらず、条件「実際に破られる」を満たさない。
  ロールの行はまとめて書くことがあり、数え方を決めると書き方を縛る。
- **中身も、数えられるものは検査にする**：ADR 0027 の条件だけで判断すると、数えられる中身の検査が増える。文書の
  検査はレビューで補えるので、誤って落ちる損の方が大きい。
- **#212 を、落とさずに知らせるだけの一覧にする**：並べ忘れは起きておらず、知らせを読む手間が増えるだけになる。
  かわりに、変更とパターンに、目的の手順を足すときに直す所の在りかを案内する行を置く。
- **線を引かず、ADR 0027 の条件で一つずつ判断する**：毎回同じ議論になる（今回がそうだった）。文書の検査では、構造か
  中身かで先に分けられる。

## Consequences

- 今の `check-docs` の検査は、どれも構造に当たり、外すものはない。`--catalog` は検査ではなく一覧。
- #212 で積んだ文言の直し（検査にした決まりは検査に任せる、変更とパターンからの案内）は、この線に合わせて入れる。
- `check-docs --catalog`（ADR 0026）で前提の末尾に `?` を付ける行を、役割ごとの指示からスキルにも広げる。契約の在りかを
  パスで指すスキル（harness）があり、リンクから導けない前提があることを示すため。一覧のメタデータの正しさの話で、
  検査ではない。
