# 0050. check-docs は、コードブロックとコードスパンを、依存を持たず CommonMark に倣う行ごとの走査で見分ける

## Context

check-docs は、リンク、見出しのアンカー、地図、行の表示幅を読むときに、コードブロックとコードスパンの中を除く。
前は、囲みを一つの正規表現（字下げ 3 までの ``` か ~~~ から、同じ印の次の行まで）で、コードスパンを ` 一つの組で
見分けていた。全体のレビュー #283 と PR #301 のレビューは、閉じない囲み、深い字下げ、4 個の ` の囲み、情報文字列
付きの行で CommonMark と食い違い、コードの中のリンクを検査したり、囲みのあとを検査しなかったりすることを挙げた
（#305）。見分けの誤りは、文書の誤りを黙って通すか、誤りのない文書を落とす。

## Decision

- 標準のライブラリだけで、行ごとに一度読む走査で見分ける。CommonMark の次の規則に倣う。
  - 囲みは、同じ印の同じ長さ以上の行で閉じ、閉じなければ末尾まで続く。` の囲みの情報文字列に ` があれば開かない。
  - 囲みを開き閉じる字下げは、そこにあるリストの項目の文の始まりから 3 まで（印のすぐ後も含む）。項目より浅い行で、
    項目と囲みが終わる。項目の文の始まりは、開いている項目ごとに印の行から取る。
  - 文の始まりから 4 先の字下げは、空行、閉じた囲み、同じ字下げのコードの行のあとなら、字下げのコードとする。
  - コードスパンは、` の並びで開き、同じ長さの並びで閉じる（一行の中に限る）。
- 怠けた続きの行、引用の中、タブの字下げ、行をまたぐコードスパンは見分けない。見分ける形と見分けない形は、
  check-docs の試験（`tests/check-docs-test.sh`）の場合で押さえる。

## Alternatives

- **Markdown の解析ライブラリ（markdown-it-py など）を使う**：CommonMark に正しく沿うが、check-docs は依存を持たない
  一つのファイルで、ターゲットの CI とハーネスのイメージに入れるものが増える。
- **slack プラグインの check-markdown の走査を使う（platform の ADR 0029）、またはそれを conventions に移して共有する**：
  conventions は principles だけを前提にする区切りで、slack を前提にできない。逆に conventions に置いて slack が使う形は、
  プラグインが実行時にほかのプラグインのコマンドに頼ることになり、Slack に特有の閉じの読み（引用やリストの項目の
  終わりで閉じる囲みの扱い）も分けられない。
- **正規表現を直さず、ずれる形を試験で押さえるだけにする**：ずれたままだと、コードの中のリンクを検査し、囲みのあとを
  検査しない形が残る。
- **読めない形（閉じない囲みなど）を文書の誤りとして落とす**：走査は小さく済むが、文書の形の決まりを足すことになる。
  #305 の範囲の外。

## Consequences

- 手書きの走査は、レビューで CommonMark とのずれが続けて見つかった（#305 の PR のレビュー）。ずれが見つかるたびに、
  試験の場合を足して直す。続くなら、解析ライブラリへの置き換えを、依存を持たせるかと一緒に考え直す。
- このリポジトリの Markdown では、前の見分け方とリンク、アンカー、行の表示幅の結果が同じだった。ほかのターゲットでは、
  コードの中だったリンクが検査から外れるか、囲みのあとのリンクが検査に入るかで、結果が変わりうる。
