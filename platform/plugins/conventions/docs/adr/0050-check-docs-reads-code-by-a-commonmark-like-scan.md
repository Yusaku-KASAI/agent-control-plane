# 0050. check-docs は、コードブロックとコードスパンを、依存を持たず CommonMark に倣う行ごとの走査で見分ける

## Context

check-docs は、リンク、見出しのアンカー、地図、手順の段、ロールの節を読むときに、コードブロックとコードスパンの中を
除く。行の表示幅は、コードの中ではリンクの括弧も数える。前は、フェンス（囲みのコード）を一つの正規表現（字下げ 3
までの ``` か ~~~ から、同じ文字の次の行まで）で、コードスパンを `` ` `` 一つの組で見分けていた。全体のレビュー #283 と
PR #301 のレビューは、閉じないフェンス、深い字下げ、4 個の `` ` `` のフェンス、情報文字列付きの行で CommonMark と食い違い、
コードの中のリンクを検査したり、フェンスのあとを検査しなかったりすることを挙げた（#305）。見分けの誤りは、文書の
誤りを黙って通すか、誤りのない文書を落とす。

## Decision

- 標準のライブラリだけで、行ごとに読む走査で見分ける。CommonMark の次の規則に倣う。
  - フェンスは、同じ文字の同じ長さ以上の並びだけの行で閉じる。`` ` `` のフェンスの情報文字列に `` ` `` があれば開かない。
  - フェンスを開き閉じる字下げは、そこにあるリストの項目の文の始まりから 3 まで（項目の印のすぐ後も含む）。項目の
    文の始まりは、開いている項目ごとに印の行から取り、それより浅い行で項目が終わる。
  - 文の始まりから 4 先の字下げは、空行、閉じたフェンスかコメント、字下げのコードの行のあとなら、字下げのコードと
    する。
  - 行の始めの HTML のコメントは、`<!--` の行から `-->` を含む行の終わりまでをコードとして読む（中の ``` の行は
    フェンスを開かない）。
  - コードスパンは、`` ` `` の並びで開き、同じ長さの並びで閉じる（一行の中に限る）。
- 閉じの行があとのどこかにあるフェンスは、項目より浅い行（ヒアドキュメントの終わりや、その中のリストの行など）も
  コードとして閉じの行まで続く。書き手の閉じの行が新しいフェンスを開いて、あとの本文をすべてコードとして読まない
  ようにするため。閉じの行がどこにもなければ、リストの項目の中では項目が終わると閉じ、項目の外では末尾まで続く。
  `-->` のないコメントも同じ。
- 遅延の続きの行、引用の中、行の途中の HTML のコメント、コメントのほかの HTML ブロック、タブの字下げ、バックスラッシュの escape、行をまたぐ
  コードスパンは見分けない。見分ける形と見分けない形は、check-docs の試験（`tests/check-docs-test.sh`）の場合で
  押さえる。

## Alternatives

- **Markdown の解析ライブラリ（markdown-it-py など）を使う**：CommonMark に正しく沿うが、check-docs は依存を持たない
  一つのファイルで、ターゲットの CI とハーネスのイメージに入れるものが増える。
- **純 Python の解析ライブラリをプラグインに同梱する**：ターゲットの CI とイメージに足すものはないが、ほかの人の
  コードの版とライセンスの表示を追い続けることになる。閉じの行のあるフェンスを閉じの行まで読む形も、ライブラリの
  結果に重ねて補う必要がある。
- **参照の実装（commonmark.js など）を試験の答えにだけ使い、場合ごとに突き合わせる**：本体は依存を持たないまま
  ずれを見つけられるが、`make check` が node とパッケージの取得に頼る。場合ごとの答えを試験に書く形にした。
- **例の一覧（入力と、コードと読む行）を conventions に置き、check-markdown の試験も読む**：片方で見つけたずれが
  もう片方の試験にも入るが、二つの走査は閉じの行のないフェンスの終わり方を意図して違えていて、走査ごとの答えが要る。
  この PR では決めず、#327 で比べる。
- **slack プラグインの check-markdown の走査を使う、またはそれを conventions に移して共有する**：conventions は
  principles だけを前提にする区切りで、slack を前提にできない。逆に conventions に置いて slack が使う形は、プラグインが
  実行時にほかのプラグインのコマンドに頼ることになる。閉じの行があとにあるフェンスを閉じの行まで読む形は、
  platform の ADR 0029 と同じ考えによる（閉じの行のないフェンスの終わり方は違う）。
- **CommonMark どおり、項目より浅い行で、閉じの行のあるフェンスも閉じる**：書き手の閉じの行が新しいフェンスを開き、
  あとの本文をすべてコードとして読んで、文書の誤りを黙って通す（platform の ADR 0029 が退けた理由と同じ）。
- **#305 が挙げたずれ（閉じないフェンス、深い字下げ、4 個以上の `` ` `` のフェンス、情報文字列付きの行）だけを直し、
  リストの項目、字下げのコード、HTML のコメントは見分けない形として試験で押さえる**：走査は小さい。このリポジトリの
  文書には深い字下げのフェンスも行の始めのコメントもないが、check-docs はほかのターゲットの文書も検査し、入れ子の
  リストの中のフェンスは項目の文の始まりを取らないと開けない。#305 の項目が求める深い字下げを見分けるには要る。
- **閉じの行を探すのを、次の項目の印の行までにする**：閉じ忘れたフェンスが、あとのほかのフェンスの閉じの行と組に
  なることは避けられるが、ヒアドキュメントの中のリストの行で探すのが止まり、書き手の閉じの行が新しいフェンスを開く。
- **正規表現を直さず、ずれる形を試験で押さえるだけにする**：ずれたままだと、コードの中のリンクを検査し、フェンスの
  あとを検査しない形が残る。
- **読めない形（閉じないフェンスなど）を文書の誤りとして落とす**：走査は小さく済むが、文書の形の決まりを足すことに
  なる。#305 の範囲の外。

## Consequences

- リストの項目の中で開き、項目より浅い閉じの行があとにあるフェンスは、CommonMark では項目の終わりで閉じるが、
  check-docs は閉じの行までをコードとして読む。フェンスを閉じ忘れ、あとにほかのフェンスがあると、その開きの行を
  閉じの行と読み、そこまでの本文を検査せず、そのフェンスの中を本文として読み、その閉じの行から先を検査しない
  （前の正規表現と platform の ADR 0029 の check-markdown も同じ）。
- 手書きの走査は、この判断の PR のレビューで CommonMark とのずれが続けて見つかった。ずれが見つかるたびに、試験の場合を
  足して直す。手書きのまま続けるか、解析ライブラリか例の一覧の共有に替えるかは、#327 で決める。
- このリポジトリの Markdown では、前の見分け方とリンク、アンカー、行の表示幅の結果が同じだった。ほかのターゲットでは、
  コードの中だったリンクが検査から外れるか、フェンスのあとのリンクが検査に入るかで、結果が変わりうる。
