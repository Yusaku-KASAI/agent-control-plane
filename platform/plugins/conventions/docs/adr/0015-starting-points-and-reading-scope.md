# 0015. 起点には定義を要約か案内で書き、読ませる範囲はリンクの後ろの「（全体を読む）」で示す

## Context

#96 のやりとりで、文書の置き場所の決まり（定義と届け方）が、判断の軸として使われなかった。いつも読み込む要約には、
その決まりへのリンクがあった。ただ、CLAUDE.md と食い違ったときの決まりの出典として置かれていた。「同じ事実は一か所に」
の項目は principles の SSOT にだけつながり、それを決まりの置き場所に具体化した定義には届いていなかった。対話の
Claude は `documentation.md` を読んでいたが、要約の書き方どおりに SSOT の一般論で考えた。

いつも読み込む要約の項目には、どれを判断の軸にし、どこを深く読むかの区別がなかった。決まりの中身を書くことと、
読みに行かせることも、書き分けられていなかった。

## Decision

- 読み手が読み始める文書を起点（いつも読み込む要約、役割ごとの指示、スキル、CLAUDE.md）と呼ぶ。起点には、定義を
  要約（中身を短く言い直し、出典を付ける）か、案内（要約を持たず、どの場面でどこを読むかだけ）で書く。どちらにするかは、
  ADR 0010 の基準（ほぼすべての作業に関わり、破られやすく、検査で守れない）を、その起点の範囲に当てはめて選ぶ。
- 一般的な原則と、それを具体化した決まりがあるときは、具体化した決まりを要約にし、原則は理由として添える。
- 読む範囲は、リンクの直後の「（全体を読む）」で示す。付けたリンクは、その場面ではリンク先を全体まで読み、その中の
  「（全体を読む）」もたどる。付けないリンクは、要るときにリンク先の節を読む。場面を限って付け、いつも要るものは要約に
  するか、いつも読み込む要約に載せる。
- 量の上限に当たったら、言い回しを詰めずに、要約を案内に下げる。

## Alternatives

- **決まりの間に優先順位を付ける（プロジェクトの決まりを原則より先に引く）**：問題は食い違いではなく、書いてあるのに
  読まれない・使われないことにある。一般的な原則の上に具体的な決まりを組む向きは自然で、変えなくてよい。
- **項目を重要度で並べ替える、「大事」の印を付ける**：並び順は優先として伝わらず、印は増えるほど平らになる。
- **起点の冒頭に「先に読む」の節を置き、いつも読む文書を並べる**：いつも読むなら、読み込ませるのと同じコストで、
  読まれるかが確かでなくなるだけ。
- **読む範囲に段を増やす（ある程度読む、前提までたどって読む）**：まず二つで効くかを確かめる。
- **principles と `documentation.md` を hook で読み込ませる**：合わせて約 740 行あり、毎回のセッションとサブエージェントの
  コストが大きい。

## Consequences

- 「（全体を読む）」で本当に全体が読まれるか、読んだ決まりが判断に使われるかは確かめていない。何回かの依頼のあと、
  セッションの記録で数える。足りなければ、読み込ませるか、仕組みで守る形を考える。
- 使った決まりを出力（PR の本文、レビューの指摘）に書かせる仕組みは、ここでは決めていない。
- 起点の各項目が要約か案内かは検査していない。「写し」と「いつも読み込む要約」の言葉の整理、ロールとスキルの整理も
  まだしていない。
