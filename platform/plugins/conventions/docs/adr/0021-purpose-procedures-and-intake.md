# 0021. 手順を依頼の目的で切って最大 2 層にし、ロールと切り離し、受け付けで目的の手順を決める

## Context

ADR 0020 で、手順を場面の手順と部品の手順に分けた。続く変更で、レビューの手順を reviewer の場面の手順と、変更する人の
部品の手順に分けた。依頼者から、次の問い直しがあった（#123 のコメント）。

- 手順ごとの範囲と切り分けを吟味したい。「変更する」という名前も、何が終わりかが分かりにくい。
- 「場面」と「部品」の二分類は、一般的な階層に比べて据わりが悪い。ただ、深い所まで読まれないおそれがあるので、層は
  2 つまでに限りたい。
- 実際の依頼は相談から入ることが多い。手順とロールが 1 対 1 になるのは、責務として違う。
- セッションの締め、ロードマップや Issue の整理、壁打ちなど、ほかにも依頼の種類がある。将来は、Issue だけに書ける pm
  ロールを置くことも考えている（#28）。

## Decision

- 手順（how-to）は、依頼者が何をしてほしいか（依頼の目的）で切る（[文書の種類で分ける](../../../principles/docs/reference/patterns.md#diataxis)の手順）。
  ロール（役割）では切らない。
- 手順は最大 2 層にする（[階層的分解](../../../principles/docs/reference/principles.md#hierarchy)）。
  - 目的の手順：依頼を受けてから終えるまで。いくつものターンやセッションにわたることがある。例：変更を届ける、レビューする。
  - 共通の手順：目的の手順の段の中で使う、作業の一部分。いくつもの目的の手順から使う。ほかの手順は案内しない（3 層目を
    作らない）。例：文書を書く、パターンを当てはめる、レビューを頼んで答える。
- ロールは、権限と隔離の境界（書けるもの、残せる所、モデル）にする。手順とロールは多対多で、ロールの指示は、そのロールが
  使う目的の手順を指す。
- 依頼を受けたら、まずどの目的の手順に当たるかを決める（受け付け）。共通のルールに受け付けの節を置き、今ある目的の手順へ
  振り分ける。目的の手順がまだない依頼（相談や壁打ち、課題の整理、セッションの締め）は、依頼に沿って進める。作業の
  途中で目的が変わったら、その手順に入り直す。
- 「場面の手順」「部品の手順」を「目的の手順」「共通の手順」と呼び直し、「変更する」の手順を「変更を届ける」
  （`guides/deliver-change.md`）と呼び直す。終わりの状態（マージできる PR）が名前から分かるようにする。
- ADR 0020 のほかの決定（目的の手順の最初の段を「始めに読む」にすること、起点に直に並べること、文書の体系をどの作業
  でも始めに読むこと）は変えない。

## Alternatives

- **層の数を限らない一般の階層にする**：目的が細かく分かれるほど、読み手が深い所までたどらず、手順が読まれない。
- **手順をロールごとに持つ（ADR 0020 の形）**：相談のようにどのロールでも入る依頼や、pm のように新しいロールを足すとき
  に、手順を複製するか、どのロールの手順かを決め直すことになる。
- **相談、課題の整理、締めの目的の手順を、ここで一緒に作る**：それぞれ決めることが多く（pm ロールの権限、引き継ぎの
  形）、一つの変更が大きくなる。体系の中の置き場所だけを決め、中身はそれぞれの Issue（#28、#62、#102、#111）で作る。

## Consequences

- 相談に乗る、課題を整える、セッションを締める、の目的の手順はまだない。それぞれの Issue で作り、受け付けの節に足す。
- レビューの回し方（#170、#171）は、この体系の中の「レビューする」と「レビューを頼んで答える」を書き換える形で扱う。
