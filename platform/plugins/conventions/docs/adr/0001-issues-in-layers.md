# 0001. Issue の分類は木にせず、関心・テーマ・依存・焦点を別々の仕組みで持つ

## Context

やることを GitHub の Issue で管理している。1つの項目は複数の関心やテーマにまたがり（たとえばリモートからの
取得は「複数ターゲット」と「実行基盤の拡張」の両方に関わる）、順序は木ではなく依存の網になる。
マイルストーンは Issue を1つにしか属させられず、説明も短い文しか置けない。

## Decision

- 関心（どこを変えるか）とテーマ（何のためか）は、どちらも多対多のラベルで表す。
- テーマの説明（狙い、終えたときの状態、進め方とその理由）は、テーマごとの Issue の本文に Markdown で書く。
  テーマに属する Issue は本文に並べず、ラベルで決める。
- 順序は GitHub の Issue の依存関係（blocked by）で表す。
- 今の焦点と取りかかる順は、ピン留めした「ロードマップ」の Issue 1枚に書く。
- マイルストーンと GitHub Projects は使わない。

## Alternatives

- **マイルストーンで段階を分ける**：Issue が1つの段階にしか入らず、テーマとして使うと重なりを表せない。
- **親 Issue と sub-issues、またはチェックリストでテーマを表す**：親が1つに限られるか、メンバーを本文に
  手で書くことになり、ラベルと二重になる。
- **GitHub Projects**：期限、担当者、状態のボードが強みで、今ほしい説明と整理には要らない。置き場所が増える。
- **本文に「前提：#N」と書く**：依存が文章に埋もれ、相手側の Issue からは見えない。

## Consequences

- テーマの一覧はラベルの検索で見る。テーマ Issue の本文は、メンバーが変わっても書き換えなくてよい。
- 時期で区切りたくなったら、そのときにマイルストーンを改めて使う。
