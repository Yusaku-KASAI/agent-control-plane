# 0039. 文書の体系は仕組みの解説に絞り、決まりを形式、届け方、検査の扱い方の参照に移し、地図で決まりを一つの項目にまとめる

## Context

ADR 0020 で、文書の体系（`architecture/documentation.md`）を、どの作業でも始めに全体まで読む文書にした。そのときの量は
約 22KB だった。その後、届け方、起点、手順の層、検査の置き場所の決まりが足され、全体のレビュー #283 の時点で 36.6KB に
なっていた。

#283 は次を挙げた。

- 決まりの定義の多くを、解説の場所（`architecture/`）に置いている。文書の体系の `docs/reference/` の構成要素の説明（決まりは参照に置く）と合わない。
- ほぼすべての作業に要るわけではないもの（検査の条件と置き場所、手順の層の細則、器の構成要素）が、毎回読まれている。
- 同じ決まり（全体の扱い、地図の置き場所、全体まで読ませる文書の並べ方、役割ごとの指示の決まり）を、文書の体系と形式の
  いくつもの所で定義している。
- 検査の置き場所は、コードだけを変える人にも要る決まりなのに、「文書の体系」の名前の下にあって見つけにくい。
- conventions の地図で、「定義」の子が、関心で切った 4 つ（用語集、文書、変更と課題、レビュー）と、層で切った手順で
  並んでいる（兄弟をそろえる）。

依頼者は、判断 1 と 8 をおすすめの形（判断 1 は (a)、判断 8 は (b)：定義の子を用語集、決まり、手順にし、決まりの下に
文書、変更と課題、レビューを置く）で進め、配置は試しながら整えると決めた（#284）。下の Decision の地図は (b) を基に、
判断 1 で分けた検査の扱い方を決まりの子に足し、文書の体系を定義の子の「体系」にしたもので、(b) の字面とは違う。
違えた理由は Alternatives にある。

## Decision

- 文書の体系は、仕組みの解説だけにする：3 つの層、区切りと依存の向き、項目の階層と地図、文書の根と種類、定義と届け方
  （届け方を構成要素として、効き方の強い順に）、手順と役割（2 層の定義）。どの作業でも始めに全体まで読むのは、この解説だけにする
  （ADR 0020 の、どの作業でも文書の体系を全体まで読むことは変えない）。
- 決まりは参照の文書に移す。
  - 文書の検査の範囲（構造に限ること）、文書の根と器（各器に置くもの / 置かないもの）、全体の扱い、地図、手順の層の
    形、役割ごとの指示の節と受け持つ手順の書き方：形式（`reference/formats.md`）。それぞれ、ここだけで定義する。
  - 要約と案内、起点に何をどう載せるか、全体まで読ませる文書の示し方、目的の手順の読ませ方（「始めに読む」の段、起点
    への並べ方）：届け方の決まり（`reference/delivery.md`）。ADR 0028 が文書の体系に置いた、目的の手順を足したときに
    直す所の一覧も、ここに移す。振り分けと続きのターンは、手順と役割の仕組みとして文書の体系に残す。
  - 何を検査にし、どこに置くか：検査の扱い方（`reference/checks.md`）。ADR 0027 が文書の体系に置いた決まりを移す。
    文書にもコードにも当てはまり、コードだけを変える人も読む。
  - 決まりを守るための破壊的な書き換え：変更の扱い方。
- conventions の地図の「定義」の子を、用語集、体系（文書の体系）、決まり、手順にし、決まりの下に、検査、文書、変更と
  課題、レビューを置く。体系は用語集だけを、決まりと手順は体系を前提にする。決まりの中では、文書は検査を、変更と
  課題は文書を、レビューは検査、文書、変更と課題を前提にする。
- 索引の説明の列は一行の要旨にし、手順は目的の手順と共通の手順に分けて並べる。用語集は意味だけを持ち、話題で節に
  分ける。

## Alternatives

- **全体を参照に移し、`changes.md` などとそろえる（#283 の判断 1 の (b)）**：どの作業でも全体まで読む文書が、決まりの
  細部まで持つことになり、量は変わらない。仕組みを理解するための解説が、置き場所の上でなくなる。
- **今のまま、毎回読む文書にも量の上限を当てる（同じく (c)）**：上限で量は抑えられても、決まりの細部と仕組みの解説が
  一つの文書に混ざったままになる。分けたうえで上限を当てることは、この判断と両立する。
- **文書の体系を「決まり」の下の「文書」の項目に置く**：文書の体系は区切り、定義と届け方、手順と役割まで解説し、検査の
  扱い方もそれを前提にする。文書の項目に置くと、検査の扱い方が形式と届け方の決まりまで含む項目を前提にすることになり、
  文書の検査の範囲を形式に置くと循環する。
- **文書の体系をどの項目にも入れず、conventions の全体にする**：循環は避けられるが、全体の解説は `overview.md` で、
  `architecture/` は部分の文書とする形式と合わない。文書の体系は区切りや定義と届け方の決まりも持つ定義なので、定義の
  子として、決まりと手順が前提にする項目にした。
- **手順の層の決まりを届け方の決まりに置く**：層の決まり（2 層、3 層目を作らない、共通の手順は目的の手順を前提に
  しない）は手順の形で、検査も形式が持つ。届け方の決まりには、起点から目的の手順に入る決まりだけを置いた。
- **地図を今のまま、理由を書く（判断 8 の (a)）**：関心で切った項目と層で切った項目が並び、兄弟がそろわない。
- **変更と課題も分ける（判断 8 の (c)）**：変更と課題は互いを前提にし合う（依頼の範囲は PR の本文を、PR は依頼の範囲を
  指す）ので、分けると循環する。

## Consequences

- どの作業でも読む量が、約 37KB から約 12KB に減る。決まりの細部は、手順の段と起点の要約から、要るときに読まれる。
- 文書の体系の量は、まだ検査で守らない。量の上限を当てるかは、起点の量の検査を見直す変更で扱う。
- 決まりの細部を毎回読まなくなるので、それが要る作業で読まれるかは、手順の段とスキルの案内に頼る。変更を届ける手順の
  「始めに読む」の段は、文書の体系と変更の扱い方のまま変えない。
