# 0034. 依頼の範囲の中はタスクリストで書き、済んだ項目は消さずに扱った PR とチェックを付けて残す

## Context

ADR 0032 は、範囲の中を何本かの PR に分けるとき、PR を終えるときに範囲の中のその PR が扱うものに PR を添え、残る
積んだ指摘を同じ節の「残るもの」に並べ、マージのあと（締めの 5 段か次の依頼の 2 段）に済んだ範囲の中を消して、
残るものを範囲の中にすると決めた。Issue の本文を今の姿にする決まり（整っている状態の「本文」）に合わせ、済んだものは
経緯として扱った。

control-plane の Issue #245 の締めで、この決まりどおりに PR #253 が扱った 2 つを範囲から消したところ、依頼者から指摘が
あった：すでに着手した内容を Issue から消すと、PR との関係と、それをやって終えたことが Issue に残らない（#255）。
どの項目が済み、どの PR で入ったかは、その Issue を次に読む人（続きを頼まれたエージェントを含む）が今の状態として
知りたいことで、経緯（なぜそう決めたか、どう進んだか）とは違う。

## Decision

- **範囲の中をタスクリストで書く**：Issue の範囲の中は項目ごとに `- [ ]` で書く。扱う PR の番号を項目の末尾に
  `#<番号>` で添え、その PR がマージされて項目が済んだら `- [x]` にする。扱う PR を表すのは末尾の番号だけで、積んだ
  指摘がどこで出たかなど、ほかの PR には文の中で触れる（出た元の PR がマージされても、積んだ項目は済んでいない）。済んだ項目は消さない。どれが済み、どの PR で
  入ったか、どれが残るかを本文の今の姿に含める。項目は範囲の節に並べ、中身はほかの節を指してよい。範囲の中を
  何本かの PR に分けると決めたときに、PR ごとに扱う単位へ項目を分ける（PR を終えるときには分けない）。PR がマージされずに
  閉じたら番号を外す。
- **番号は PR を終えるときに、チェックはマージのあとに付ける**：番号は、レビューを頼んで答えるの「終える」の 2 段で、
  `Refs` でも `Closes` でも添える。チェックは、締めの 5 段か次の依頼の 2 段で、マージされた PR の番号を添えた項目に
  付ける。最後の PR（`Closes`）で閉じた Issue も、締めの 5 段で付ける。締め直しがなくチェックが付かないまま閉じた
  Issue では、番号を添えた項目を済んだものとして読む（閉じたことが済んだ印になる）。
- **残る積んだ指摘は、PR を終えるときに範囲の中の項目にする**：「残るもの」の節は作らず、どこで出たかを添えて
  チェックのない項目として範囲の中に足す。#255 の「決めること」の一つ目（残るものの節もタスクリストにするか）への答え。
  二つ目（PR の番号を項目の末尾に `#<番号>` で添えるか）は、添えると決めた。GitHub は `#<番号>` を PR へのリンクにし、
  PR の側にもその Issue からの参照が出る。

ADR 0032 のほかの決定（範囲を先に書く、積む線引き、`Refs` と `Closes`、PR を終えるときに範囲を書き直さない）は変えない。

## Alternatives

- **済んだものを消したまま、PR の `Refs` と GitHub のタイムラインで関係をたどる**：タイムラインは経緯で、どの項目が
  どの PR で済んだかは読み手が PR を開いて照らさないと分からない。依頼者の指摘（終えたことが残らない）に応えない。
- **済んだものを本文の別の節（「済んだもの」）に移す**：今の姿として残るが、マージのたびに項目を節の間で動かすことになり、
  範囲の中の全体（何を扱う依頼か）が二つの節に割れる。タスクリストなら項目を動かさず、印を変えるだけで済む。
- **PR を終えるときにチェックも付ける**：マージの前に済んだと書くことになり、PR がマージされずに閉じたときに本文が
  誤る。ADR 0032 の「PR を終えるときに範囲の中を書き直す」を採らなかった理由と同じ。
- **積んだ指摘を「残るもの」の節に並べ、マージのあとに範囲の中へ移す（ADR 0032 のまま）**：移す手間が一つ増え、
  そのあいだ範囲の中と「残るもの」が別の節に分かれる。積んだ指摘は、依頼の Issue で扱うと決めた時点で範囲の中に
  入るものなので、PR を終えるときに項目にすれば足りる。PR がマージされずに閉じても、積んだ指摘は依頼の Issue の
  やることとして残る。
- **PR のマージで、`Refs` や `Closes` の先の Issue の項目に自動でチェックを付ける（GitHub Actions など）**：取りこぼしは
  なくなるが、仕組みを作って保つ手間がかかり、どの項目を済んだとするか（一部だけを扱った PR など）は判断が要る。締めの
  5 段と次の依頼の 2 段で付け、閉じた Issue は閉じたことを済んだ印として読めば、読み手が誤ることはない。
- **項目ごとに Issue（sub-issues）に分ける**：ADR 0032 で採らなかった理由と同じ（それだけで成り立たない項目のために
  Issue を作り、文脈を書き写す）。

## Consequences

- conventions の決まりなので、それを使うすべてのターゲットに効く。どのターゲットも、プラグインの更新で受け取り、
  ターゲットの側で直すファイルはない。範囲の節をすでに箇条書きで持つ開いている Issue は、次にその Issue の変更を
  依頼されたときの 2 段で、タスクリストに書き直す（課題の扱い方の「決め方」）。
- 最後の PR のあと締め直さなければ、閉じた Issue に番号付きでチェックのない項目が残る。GitHub の Issue の一覧が見せる
  タスクの数は実際より少なくなるが、閉じたことで済んだと読める。
- 範囲の中が、済んだ項目の分だけ長くなる。済んだ項目は短い 1 行とチェックと番号なので、読む妨げは小さいとみる。
- タスクリストの形やチェックを確かめる検査はない（ADR 0032 と同じく、何を書くかは中身で、ADR 0028 の条件を満たさない）。
