# 0035. ふつうの Issue の本文は、冒頭の狙い、今の姿、範囲を順に持つ基本の形にし、形は扱いの決まりのそばに置く

## Context

課題の扱い方は、Issue の分類、ロードマップ、テーマの Issue、キャンバス、依頼の範囲（`## 範囲` の節。ADR 0032、0034）の
形を決めていたが、ふつうの Issue（変更の依頼、決めること、確かめること）の本文全体の形は決めていなかった。control-plane の
開いている Issue（2026-10-25 に 36 件）は、見出しが「狙い」「終えたときの状態」「今の姿」「やること」「考えること」「範囲」
「方針」「背景」などとばらばらで、見出しのない 1〜2 行のものもあった。整っている状態の「本文が今の姿を表す」を照らすにも、
読む人が狙いや残りを探すにも、どこを見ればよいかが Issue ごとに違った。#245 は `## やること` と `## 範囲` に同じ項目を
二重に持ち、範囲の項目が「上のやることの 1 つ目」と指していた。

また、形の決まりは何についての決まりかで分けて置かれ（文書は形式、コミットと PR は書き方、Issue は課題の扱い方、レビューの
結果はレビューの扱い方）、形の在りかを探す入口がなかった。依頼者は相談（control-plane の #261）で、本文の形と、決まりや形を
述べる文書の置き場所の整理を求めた。

## Decision

- **基本の形を一つにする**：テーマとキャンバスの Issue、ロードマップ、全体のレビューの報告のほかの Issue の本文は、冒頭（最初の見出しの前の
  1〜2 行）に狙い、`## 今の姿`、`## 範囲` を、この順に一度ずつ持つ。節の中は自由に書く。PR の本文（決まった節を順に一度
  ずつ持ち、中は自由。書き方の「PR」）と同じ作りにする。
- **任意の節は名前だけそろえる**：要るときだけ、どこに足してもよい。気をつけること、確かめていないこと、関係、保留に
  当たるものは、その名前にする。
- **やることは範囲の中に一本化する**：別の節に同じ項目を並べない。中身が長い項目は、ほかの節に書いて項目から指す。
- **決める Issue と確かめる Issue も同じ形で書く**：範囲の中の項目を、決めること（問い）か確かめることにする。依頼の
  範囲の形を当て、PR で済ませない項目は、答えか結果を `## 今の姿` に書いたらチェックを付ける。すべて済み、続く作業を
  ほかの Issue に移したら閉じる（整っている状態の「開いているか」にも足す）。考えを何回も積む相談はキャンバスにする。
- **テーマ、ロードマップ、キャンバス、全体のレビューの報告は今の形のまま**：役目が違い、形はすでに決まっている（全体の
  レビューの報告はレビューの扱い方）。
- **答えで済んだことも終えた根拠にする**：決める Issue と確かめる Issue では、答えか結果を `## 今の姿` に書いてチェックした
  範囲の中の項目を、終えた根拠（PR、まとめた先の Issue と並ぶ）にする。相談で決める Issue に答えが出たら、その Issue に
  答えを書いてチェックを付ける（ADR 0025 の、依頼がふつうの Issue を指すときは本文の形を保ちキャンバスへのリンクをコメント
  するだけ、を決める Issue では改める。本文の形は保ったまま `## 今の姿` と範囲を書き直す）。依頼の範囲を決める Issue と
  確かめる Issue に広げ（ADR 0032）、PR のない項目のチェックを足す（ADR 0034）。
- **形は扱いの決まりのそばに置き、入口を一つ足す**：Issue の本文の形は課題の扱い方に置く。文書の体系の「文書の外」の節に、
  文書の外の書きもの（コメント、コミット、PR、Issue、レビューの指摘と結果、依頼への答え）の形と書き方の在りかを案内する
  （定義は写さない）。

## Alternatives

- **形を決めない**：手間はないが、読む人ごとに探す所が違い、整っている状態の「本文」を照らす枠がないまま残る。
- **種類ごとのひな形（変更の依頼、決める、確かめる）**：種類ごとには合うが、種類の見分けが要り、決まりが増える。
  決める Issue とキャンバスの境もあいまいになる。基本の形の範囲の中の書き方で、種類の違いは表せる。
- **テーマ、ロードマップ、キャンバスも基本の形にそろえる**：冒頭の狙いを共通にし、違いを種類ごとの節で持つ形。今ある形を
  書き換える手間に見合う得が見えない。
- **文書の外の書きものの形を書き方（`writing.md`）に集める**：文書（形式）と文書の外（書き方）の分け目は分かりやすいが、
  Issue の扱い（ラベル、範囲の振り分け）と形が別の文書に分かれ、課題を整える・締めの手順が両方を読む必要が出る。
- **形をすべて形式（`formats.md`）に集める**：入口は一つになるが、扱いの決まりと形が離れ、形式の検査の節（文書の構造）と
  混ざる。
- **GitHub の Issue のテンプレート（`.github/ISSUE_TEMPLATE`）を置く**：人が GitHub の画面から作るときにしか効かず、
  エージェントが `gh` で作る Issue には効かない。リポジトリごとに置くことになり、conventions の決まりとして届かない。

## Consequences

- conventions の決まりなので、それを使うすべてのターゲットに効く。どのターゲットも、プラグインの更新で受け取り、
  ターゲットの側で直すファイルはない。
- 今ある開いている Issue は、課題を整える手順で形に合わせる（control-plane では #263）。狙いや範囲が本文とコメントから
  読み取れない Issue は、人が決めるもの（整っている状態）になる。
- 持ち越すもの（セッションを締めるとき）の置き場所は変えない（ADR 0024 のまま、依頼の Issue のコメントか新しい Issue）。
  締めるときは依頼の Issue が PR のマージで閉じていることがあり、閉じた Issue の範囲の中に残りを足すと、閉じたことが
  済んだ印として読まれる（ADR 0034）。ただ、コメントに置いたものが本文に届くのは、開いている Issue のコメントにある
  決まったことだけ（整っている状態の「本文」）。閉じた Issue のコメントと、確かめていないこと、保留にした提案は、課題を
  整えるときに拾われない。これは control-plane の #265 で扱う。
- 本文の形を確かめる検査は、今は足さない。決まった節が順にあるかは判断なしで決まり、置き場所は外の道具の状態を確かめる
  github プラグインの `check-issues` になる（文書の体系の「検査にするものと置き場所」）。ただ、開いている Issue を形に
  合わせ終えるまでは、ほとんどがずれと出て役に立たず、実際に破られるかもまだ分からない。合わせ終えたあとに、検査の
  三つの条件で決める（#263 に積んだ）。
