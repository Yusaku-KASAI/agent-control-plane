# 0008. 地図は階層ごとに持ち主が表で書いて検査し、子を持つ項目が直接持つ文書は子と並ぶ「全体」として扱う

## Context

ADR 0006 で、文書の関係を入れ子の項目と階層ごとの前提の向きで表し、最上位の地図を設計構造行列で書くことにした。
書いてみると、次のことが分かった。

- 行列を手で書くと、項目の宣言と二重になり、検査もできない。地図の表を機械で読める形にすれば、宣言と検査の入力と
  行列の出力を一つにできる。
- 最上位の地図にすべての階層を書くと、上の階層が下の細部を知ることになる。
- 親と子の間のリンクを「含む関係」として検査から外すと、依存が漏れる。親の overview が子の細部を前提にし、子が親の
  overview を前提にすれば循環になるが、気づけない。
- 置き場所をリポジトリのルートからのパスで書くと、その項目を別のリポジトリに切り出したときに地図が使えない。
- 案内かどうかを書き手が決めるので、逆向きの依存を通す抜け道になりうる。
- ADR 0005 は、移した ADR が番号のまま移ると書いたが、形式の決まり（移した先で番号を振る）に合わせて振り直した。

## Decision

- 地図は「項目、親、置き場所、前提にする」の表で書き、`map-` で始まる id で示す。階層ごとに分け、最上位の地図は全体の
  設計を持つリポジトリに一つ、各項目の中の地図はその項目の overview に置く。置き場所を持たない集まりの中は、集まりを
  宣言した地図に書く。置き場所は、地図を書いた文書からの相対パスで書く。`check-docs` はすべての地図を集めて確かめ、
  設計構造行列は地図から出す。
- 含む関係（親子）は依存ではない。子を持つ項目が直接持つ文書は、子と並ぶ「全体」として扱い、子は全体を前提にしてよく、
  全体は子を前提にしない。親と子の間のリンクも、この向きで確かめる。
- 案内かどうかは、リンク先を読まなくてもリンクを含む文がそれだけで分かり、正しいかで決める。
- ADR から出るリンクは、向きの確かめから外す（ADR は書き換えないので、地図を変えても直せない）。
- ADR を別の `adr/` に移したときは、移した先で番号を振る。ADR 0005 の「番号のまま」はこれで置き換える。

## Alternatives

- **行列を手で書き、別に宣言を持つ**：同じことを二か所に書き、ずれる。
- **最上位の地図にすべての階層を書く**：上の階層が下の細部を知り、項目の中を変えるたびに最上位の文書を変える。
- **親と子の間を検査から外す**：依存が漏れ、循環に気づけない。
- **親が子を前提にし、子は親を前提にしない（親を子のまとめとする）**：全体の文書が子の細部を書き写すことになり、
  変わりやすい細部に変わりにくい全体が依存する。

## Consequences

- 全体の文書から子への道は、すべて案内のリンクになる。
- 全体の文書が子の細部を要約の形で書き写していないかは、検査では分からないので、レビューで見る。
