# 検査の扱い方

どのリポジトリでも同じにする、何を検査（コマンド、試験、CI のジョブ、hook など、機械で確かめて落とすもの）にし、
検査をどこに置くかの決まり。文書でもコードでも同じに従う。検査は最も強い届け方だが、保つ手間がかかり、誤って
落ちると作業を止める（[仕組みで守る](../../../principles/docs/reference/principles.md#mechanisms)、[ADR 0027](../adr/0027-checks-by-rule-and-reader.md)）。

<a id="conditions"></a>

## 検査にするもの

静的解析の道具の経験（直せる指摘だけを出し、誤検知を少なく保たないと使われなくなる。Sadowski ほか「Lessons from
Building Static Analysis Tools at Google」）に倣い、次の三つを満たす決まりを検査にし、ほかはレビューの観点に任せる。

- 判断が要らない：リポジトリや、外の道具（GitHub など）の状態だけから機械で決まる。意味の食い違い（要約と出典など）は
  検査にせず、検査はその手がかり（出典へのリンクがあるか）までにする。
- 実際に破られる：レビューで繰り返し見つかる。または、既定のブランチの守りのように、黙って外れると気づく機会がなく、
  失うものが大きい。
- 誤って落ちにくい：誤検知が少なく、保つ手間が、見逃したときの手戻りより安い。

[仕組みで守る](../../../principles/docs/reference/principles.md#mechanisms)の「検査できる決まりを、文書に書くだけで済ませる」は、
このプロジェクト群では、この三つを満たす決まりについて言う。

<a id="documents"></a>

### 文書の検査

文書の検査（conventions の `check-docs`）は、範囲を文書の構造の決まりに限る。中身（文書が述べること）の検査は、
「誤って落ちにくい」を満たさないものとして扱う（[ADR 0028](../adr/0028-document-checks-cover-structure.md)）。

| 検査の候補（構造）。上の三つの条件で選ぶ | 検査にしない（中身）。レビューに任せる |
| --- | --- |
| 体系が決めた変わらない語と置き場所、印、入口・索引・地図からの到達。形式（決まった節、見出し、印があるか、量の上限）、リンク（リンク先、在りかの印、どの文書も入口、索引、地図から届くか）、依存（地図と前提の向き）、メタデータ（ADR の frontmatter と参照） | ある文書が述べること（何をどこまで書くか、特定の節に何を並べるか（すべての目的の手順が並ぶかのような網羅を含む）、どの手順を誰が受け持つか、要約、例、説明）が、ほかの定義や今の姿と合っているか |

- 分け目は、体系が決めた変わらない語と置き場所（決まった節、見出し、決まった段の名前（始めに読む）、印）と、どの
  文書にも届くか（到達）は構造、ほかの文書の決まった節に何を並べるか（網羅）と述べることは中身、とする。到達は、
  入口（`README.md` と `CLAUDE.md`）、索引、地図からの道で、そこに並ぶかも含む。決まった枠（形式の各節が挙げるもの）の
  うち、あるか、名前、位置、印は構造で、そこに何を述べるかは中身。
- 何を確かめるかは、[形式](formats.md "在りか")の各節の「検査」に書く。

<a id="placement"></a>

## 置き場所

検査の仕組みも、アーキテクチャの検査（Fitness Function、Ford ほか『Building Evolutionary Architectures』）と同じく守る
構造の中に置き、それを置く区切りが前提にしてよいものだけを知る（[区切りと依存の向き](../architecture/documentation.md#contexts)）。
置き場所は、確かめる決まりと、状態を読む相手で決める。検査を回すだけの器（CI の複合アクション、ターンの終わりの
hook）と、決まりを載せる器（Claude Code のプラグインやカスタムエージェントの並び）は、置き場所を決めない。

| 確かめるもの | 置き場所 | 知ってよいもの |
| --- | --- | --- |
| 一つの区切りが定めた形（どの区切りのファイルに当てはめるかによらない） | その形を定義する区切り | その区切りが定めた形だけ。ほかの区切りの名前やパス（特定のプラグイン、ファイル）は知らず、形から見分ける |
| 外の道具（GitHub など）の状態 | その道具を扱う区切り | 確かめる決まりは、前提にしてよい区切り（conventions、契約）に合わせる。値をコマンドに直に持つときは、どの決まりに合わせたかを書く |
| 区切りの間で値が合っていること | 契約の試験として、両側を前提にしてよい区切り | 両側と、その間の契約 |

- ほかの区切りのファイルを確かめても、形から見分けて形を確かめるなら 1 行目に当たる（`check-docs` の地図とロールの
  形の検査）。値が合っているかを、特定の区切りの名前やパスを知って確かめるなら 3 行目に当たる。
- 置き場所の区切りが前提にしてよくないものを確かめたくなったら、確かめる値を契約に置き、検査はその契約に合わせる
  （[使う側に届く契約](../../../principles/docs/reference/patterns.md#published-language)、[契約の試験](../../../principles/docs/reference/patterns.md#contract-test)）。
- 検査は、それを置く区切りの文書に、何を確かめるかを書く。
