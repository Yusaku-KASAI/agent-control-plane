# 課題の扱い方

どのリポジトリでも同じにする、やること（課題）の扱い方。

やることは GitHub の Issue で管理する。文書には今の姿だけを書くので、予定や残りの作業は置かない。分類は木にせず、
性質ごとに分けて持つ（[ADR 0001](../adr/0001-issues-in-layers.md)、[0029](../adr/0029-issue-labels-and-roadmap-focus-form.md)）。

| 表すもの | 置き場所 |
| --- | --- |
| やること 1 件 | Issue |
| どこを変えるか | 文書の区切りや関心ごとのラベル（名前と意味はリポジトリの参照の文書に置く）。複数付けてよい。GitHub が最初から用意するラベル（`bug`、`documentation` など）は使わない |
| 何のためか | ラベル `theme:<名前>`。複数付けてよい |
| テーマの狙い、終えたときの状態、進め方 | ラベル `theme` の Issue。メンバーは本文に並べず、ラベルで決まる |
| 何が先か | Issue の依存関係（blocked by） |
| 今の焦点と順番 | ピン留めした「ロードマップ」の Issue。本文の `## 今の焦点` の節に、取りかかる順に開いている Issue を `#<番号>` で並べ、閉じた Issue には触れない（経緯はその Issue に書く。[今と経緯を分ける](../../../principles/docs/reference/principles.md#present-state)）。順番を変えるときは本文を書き換える |
| 相談の考え（問い、選択肢、決まったこと） | ラベル `canvas` の Issue（[キャンバス](#canvas)） |

- sub-issues は、大きな作業を手順に分けるときだけ使う。
- 検討中の設計は Issue に書き、決まったら ADR にする。
- 会話で決まったこと（方針、範囲、分け方）は、依頼の Issue があればそこに、なければ [PR の本文](writing.md#pull-requests)に書く。PR の外に続く
  作業が残るなら Issue を作る。書いた先（Issue か PR）の本文の見出しや今の姿が古くなったら、その本文も書き直す。
- 気づいているリスクや、壊してはいけない前提は、会話や依頼文だけでなく Issue の本文に書く。作業するエージェントは
  Issue とリポジトリから読み取れることしか知らない。

<a id="scope"></a>

## 依頼の範囲

変更の依頼で、取りかかる前に決める、この依頼で扱うもの（範囲の中）と扱わないもの（範囲の外）。作業の途中で出た直しと
レビューの指摘を、これに照らして振り分け、一つの PR と一つの依頼が膨らみ続けないようにする
（[一つの目的の小さな変更](../../../principles/docs/reference/patterns.md#small-change)、[ADR 0032](../adr/0032-scope-first-and-related-findings-on-the-issue.md)）。
決める順は手順の[変更を届ける](../guides/deliver-change.md "在りか")の 2 段に、PR を終えるときの扱いは
[レビューを頼んで答える](../guides/request-review.md "在りか")の「終える」にある。

- 置き場所：依頼の Issue の本文の `## 範囲` の節に、範囲の中と範囲の外（扱う所があればその在りか）を書く。範囲の中は、
  本文のほかの節（やることなど）を指してよい。依頼の Issue がなければ、PR の本文の「何を変えるか」に書く（PR を作るまでは決めておき、レビューを頼むときに依頼の内容として渡す）。
- 決め方：依頼と Issue の本文から読み取る。節がすでにあり、今の依頼と合っていればそれに従う。作業の途中で範囲の中を
  広げない。広げたくなったものは、範囲の外として下の表で振り分ける。
- 振り分け：

  | 直しや指摘 | 扱い |
  | --- | --- |
  | 範囲の中 | この PR で直すか、直さない理由を書く（[レビューの扱い方：差分のレビュー](reviews.md#diff "在りか")） |
  | 範囲の外で、依頼の Issue を閉じたあとも、それだけで依頼として成り立つ | 新しい Issue にする |
  | 範囲の外で、それだけでは依頼として成り立たない（依頼の Issue と関わりが強い） | 依頼の Issue のコメントに積む。依頼の Issue がなければ、新しい Issue にする |

- 積むコメントには、どこで出たか（PR とレビューの指摘の番号、または作業）と、何をどう直すかを書く。
- 範囲の中を何本かの PR に分けるときは、依頼の Issue のまま、PR ごとに範囲の中の一部を扱う。分けた一部を新しい Issue に
  するのは、上の表と同じく、依頼の Issue を閉じたあとも、それだけで依頼として成り立つときだけにする。
- PR を終えても依頼の Issue に済んでいないもの（その PR が扱わない範囲の中の残りか、積んだ指摘）が残るなら、その PR では
  依頼の Issue を閉じず、本文には `Closes #<番号>` のかわりに `Refs #<番号>` と書く。そのときに、本文の `## 範囲` の範囲の
  中のうちその PR が扱うものに PR の番号を添え、積んだ指摘のうち残るものを同じ節の「残るもの」に並べて、そのことを
  Issue にコメントする。済んでいないものが残らない PR（最後の PR）は `Closes #<番号>` と書く。PR がマージされたあと、
  済んだものを消して残るものを範囲の中にするのは、締めの 5 段か、次にその Issue の変更を依頼されたときの 2 段で行う。

<a id="tidy"></a>

## 整っている状態

開いている Issue とロードマップが満たしていること。課題を整えるとき（[課題を整える](../guides/organize-issues.md "在りか")）に、
これと照らしてずれを挙げる。

| 見るもの | 整っている状態 |
| --- | --- |
| ラベル | テーマの Issue とロードマップのほかは、どこを変えるかのラベルと `theme:<名前>` を一つ以上ずつ持つ |
| 開いているか | 終えた Issue（PR のマージで終えたもの、範囲がほかの Issue にすべて移ったもの）は閉じている |
| 本文 | 本文が今の姿（狙い、決まったこと、残る範囲。キャンバスの Issue はキャンバスの本文の形）を表す。コメントで決まったことや、ほかに分けた範囲が本文に入っている |
| 重なり | 同じことを扱う Issue が二つない |
| 依存関係 | blocked by が閉じた Issue を指していない。本文やコメントで先に要ると書いた Issue が blocked by に入っている |
| ロードマップ | 今の焦点に開いている Issue だけがある（閉じた Issue、PR、このリポジトリにない番号がない）。順番が依存関係と、依頼者が示した方針に合っている |
| テーマ | テーマの Issue の狙いと終えたときの状態が、今のメンバー（そのラベルの Issue）と合っている |

ずれのうち、次のものは直さず、人が決めるものとして案を添えて渡す。ほかは直す。

- 範囲や狙いを変えること。
- 終えたかを根拠（PR、まとめた先の Issue）から判断できないこと。
- 依頼者が示した方針にない、今の焦点の順番の入れ替え。blocked by に合わせる入れ替えは直す。
- 今の焦点の開いている PR が、開いている Issue を閉じないときの扱い（外すと、取りかかり中の作業が今の焦点から消える）。
- 依頼者とエージェントのほかの人が書いたコメントだけに拠る直し。公開のリポジトリでは誰でもコメントを書ける。

<a id="canvas"></a>

## キャンバス

相談や壁打ち（[相談に乗る](../guides/consult.md "在りか")）で、考えを会話の外に置いて積み上げる Issue。チャット（Slack など）は
数式、図、長い表を表示できず、流れて残らないので、残す考えは Issue に書く。

- 置き場所：依頼が指す Issue がラベル `canvas` を持てば、それ。ほかは、ラベル `canvas` の開いている Issue から同じ問いの
  ものを探し、あればそれ。なければ、相談の問いを題にした新しい Issue を作り、`canvas` と、ほかの Issue と同じラベル
  （どこを変えるか、何のためか）を付ける。リポジトリにラベル `canvas` がなければ、分類の表の行を説明にして作る。依頼が
  ふつうの Issue を指すときは、その本文の形を保ち、キャンバスへのリンクをコメントする。
- 書かないもの：Issue はリポジトリと同じ範囲に見える（公開のリポジトリなら誰にでも）。秘密、個人の情報、見える範囲の
  狭い場所（非公開のチャンネルなど）の中身、まだ公にしない考えは、その範囲に出してよいと分かっているときだけ書く。
  分からなければ答えにとどめ、書いてよいかを依頼者に確かめる。
- 本文：今の姿を置く。問い、前提、選択肢とその比べ、決まったこと、決めていないこと（誰が決めるか）、次にやること。
  回ごとに書き直す。
- コメント：回ごとの考察、調べた結果、導出の経過。本文を書き直したら、何を変えたかをコメントに書く。
- 数式は GitHub の Markdown の数式（`$...$`、`$$...$$`）、図は Mermaid のコードブロックで書く。
- 決まったことのうち、やることは Issue に分け、決まりや設計の判断は ADR にする変更の Issue にする。問いに答えが出て、
  続く作業がほかの Issue に移ったら、キャンバスの Issue は閉じる。

<a id="carry-over"></a>

## 持ち越すもの

セッションを締めるとき（[セッションを締める](../guides/close-session.md "在りか")）に、会話や作業領域にしかなく、そのままでは
失われるものと、その置き場所。締めるときには、このセッションの PR はマージされたか閉じているので、置き場所は Issue に
する。

| 持ち越すもの | 置き場所 |
| --- | --- |
| 終えていない作業、次に回したもの、手を付けていないもの、会話で出て保留にした提案 | 依頼の Issue があれば、そのコメント。なければ新しい Issue |
| レビューの指摘のうち、直さなかったもの（打ち切り、範囲の外） | [レビューの扱い方](reviews.md#diff "在りか")の答える場所（打ち切りは「打ち切り」で始めた答え、範囲の外は Issue にするか依頼の Issue に積んで、その番号を書いた答え）。答えてあれば、ほかに置かない。答えがなければ、依頼の Issue のコメントか新しい Issue |
| 確かめていないこと | 依頼の Issue があれば、そのコメント。なければ新しい Issue |
| 会話で決まったことのうち、まだどこにも書いていないもの | 相談のキャンバスがあれば、その本文（今の姿）。ほかは、依頼の Issue があれば、そのコメント。なければ新しい Issue。決まりや設計の判断として残すなら、ADR にする変更を Issue にする |
| 手順、決まり、ハーネスへの気づき（つまずいたこと、抜けや食い違い） | それを持つリポジトリ（ターゲット、プラグインを配るリポジトリ、control-plane）の Issue |

- 置き場所に書けないもの（書ける範囲の外、ほかのリポジトリ）は、締めのまとめに置き場所とともに書いて、人に渡す。
- 引き継ぎのための文書やファイルは作らない。続きは、Issue と、締めのまとめを書いたスレッドから読む。
