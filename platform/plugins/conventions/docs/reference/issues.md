# 課題の扱い方

どのリポジトリでも同じにする、やること（課題）の扱い方。やることは GitHub の Issue で管理し、文書には予定や残りの
作業を置かない（[ADR 0001](../adr/0001-issues-in-layers.md)、[0029](../adr/0029-issue-labels-and-roadmap-focus-form.md)、[0033](../adr/0033-repositories-without-label-rules-and-others-comments.md)、[0035](../adr/0035-issue-body-base-form.md)、[0036](../adr/0036-append-to-issues-by-scope-triage.md)、[0037](../adr/0037-themes-as-standing-axes.md)、[0038](../adr/0038-themes-keep-their-vision.md)、[0043](../adr/0043-issue-rules-by-form-and-one-triage.md)）。

<a id="kinds"></a>

## 分類

分類は木にせず、性質ごとに分けて持つ。

| 表すもの | 置き場所 |
| --- | --- |
| やること 1 件 | Issue（形は[ふつうの Issue](#body)） |
| どこを変えるか | 文書の区切りや関心ごとのラベル。名前と意味はリポジトリの参照の文書に置く。複数付けてよい |
| 何のためか | ラベル `theme:<名前>`。複数付けてよい |
| テーマの狙い、目指す姿、進め方 | ラベル `theme` の Issue（[テーマ](#theme)） |
| 何が先か | Issue の依存関係（blocked by） |
| 今の焦点と順番 | ピン留めした「ロードマップ」の Issue（[ロードマップ](#roadmap)） |
| 相談の考え（問い、選択肢、決まったこと） | ラベル `canvas` の Issue（[キャンバス](#canvas)） |

- GitHub が最初から用意するラベル（`bug`、`documentation` など）は、どこを変えるかのラベルに使わない。
- リポジトリの参照の文書にラベルの決まり（どこを変えるかのラベルの名前と意味）がなければ、どこを変えるかのラベルは
  付けない。当たるテーマの Issue がなければ、`theme:<名前>` は付けない。決まりやテーマを作るかは人が決める（決まりを
  作るなら変更にする）。
- 区切りのある目標（終えたときの状態を持つもの）は、テーマにせず、ふつうの Issue（[依頼の範囲](#scope)で終わりを持つ）にする。
- sub-issues は、大きな作業を、それだけで依頼として成り立つ手順に分けるときだけ使う。
- 検討中の設計は Issue に書き、決まったら ADR にする。
- 会話で決まったこと（方針、範囲、分け方）は、相談では[キャンバス](#canvas)の本文に、ほかは依頼の Issue があればそこに、
  なければ [PR の本文](writing.md#pull-requests)に書く。PR の外に続く作業が残るなら Issue を作る。書いた先（Issue か PR）の
  本文の見出しや中身が古くなったら、その本文も書き直す。
- 気づいているリスクや、壊してはいけない前提は、会話や依頼文だけでなく Issue の本文に書く。作業するエージェントは
  Issue とリポジトリから読み取れることしか知らない。

## Issue の形

<a id="body"></a>

### ふつうの Issue

下の形の Issue（テーマ、ロードマップ、キャンバス、全体のレビューの報告）のほかの Issue（変更の依頼、決めること、確かめる
ことなど）の本文の形。読む人（作業するエージェントを含む）が、どの Issue でも同じ所で、狙い、今の姿、範囲を見つけられる
ようにする（[スキーマを先に](../../../principles/docs/reference/principles.md#schema-first)）。

- 本文は、次をこの順に一度ずつ持つ。中は自由に書く。

  | 置く所 | 書くこと |
  | --- | --- |
  | 冒頭（最初の見出しの前の 1〜2 行） | 何をなぜするか（狙い） |
  | `## 今の姿` | 関わる仕組みの今の姿、背景、前提と、コメントや会話で決まったこと |
  | `## 範囲` | 範囲の中（タスクリスト）と範囲の外。形と決め方は[依頼の範囲](#scope) |

- ほかの節は、要るときだけ、どこに足してもよい。次に当たるものは、この名前にする。
  - `## 気をつけること`：気づいているリスクと、壊してはいけない前提。
  - `## 確かめていないこと`：確かめていない前提や推測。
  - `## 関係`：関わる Issue と、その関わり（依存は blocked by にも入れる）。
  - `## 保留`：扱いを決めて待たせているものの、待つ理由（待たせているものは範囲の中の項目にし、その項目からこの節の理由を指す）。
- やることは、範囲の中の項目として書き、別の節（`## やること` など）に同じ項目を並べない。中身が長い項目は、ほかの
  節に書いて項目から指す。
- 決める Issue は、範囲の中の項目を決めること（問い）にする。選択肢と比べは、ほかの節に書く。考えを何回にもわたって
  積むなら、[キャンバス](#canvas)を別に作り、決める Issue にそのリンクをコメントする。
- 確かめる Issue は、範囲の中の項目を確かめること（何を、どこで見るか）にし、結果で何を決めるかを書く。
- 決める Issue と確かめる Issue で PR で済ませない項目は、答えか結果を `## 今の姿` に書いたらチェックを付ける（PR の番号は
  添えない）。すべての項目が済み、続く作業をほかの Issue に移したら（続く作業がなければそのまま）閉じる。
- 本文はいつも今を表すようにする。範囲の中の済んだ項目のほかの経緯（どう進んだか、前の案）は、コメントに書く
  （[今と経緯を分ける](../../../principles/docs/reference/principles.md#present-state)）。

<a id="theme"></a>

### テーマ

ラベル `theme` の Issue。テーマは閉じずに続く軸で、やめるか（閉じるか）は人が決める。

- 本文は、冒頭（最初の見出しの前の 1〜2 行）の狙い（何のためか）、`## 目指す姿`（そのテーマの切り口での理想の状態。
  届いたら終わる条件ではない）、`## 進め方`（取りかかる方針とその理由）を、この順に持つ。終えたときの状態は持たない。
- メンバーは本文に並べず、ラベルで決まる。目指す姿と進め方にも、メンバーの番号と順を並べない。何が先かは blocked by が、
  今の焦点と順番はロードマップが持ち、個々の Issue に取りかかる条件や依存の理由はその Issue の本文（待つ条件は `## 保留`、
  依存の理由は `## 関係`）に書く。方針の理由として、決めた Issue を指すのはよい。
- リポジトリ全体の目指す姿は、そのリポジトリの `overview.md` に置く（[形式：文書の根](formats.md#layout "在りか")）。テーマの
  目指す姿は、それをテーマの切り口で細かくしたものにする。

<a id="roadmap"></a>

### ロードマップ

ピン留めした「ロードマップ」の Issue。本文の `## 今の焦点` の節に、取りかかる順に開いている Issue を `#<番号>` で並べ、
閉じた Issue には触れない（経緯はその Issue に書く）。順番を変えるときは本文を書き換える。

<a id="canvas"></a>

### キャンバス

相談や壁打ち（[相談に乗る](../guides/consult.md "在りか")）で、考えを会話の外に置いて積み上げる Issue。チャット（Slack など）は
数式、図、長い表を表示できず、流れて残らないので、残す考えは Issue に書く。

- 置き場所：依頼が指す Issue がラベル `canvas` を持てば、それ。ほかは、ラベル `canvas` の開いている Issue から同じ問いの
  ものを探し、あればそれ。なければ、相談の問いを題にした新しい Issue を作り、`canvas` と、ほかの Issue と同じラベル
  （どこを変えるか、何のためか。ラベルの決まりや当たるテーマの Issue がなければ、そのラベルは付けない）を付ける。
  リポジトリにラベル `canvas` がなければ、分類の表の行を説明にして作る。依頼がふつうの Issue を指すときは、その本文の形を
  保ち、キャンバスへのリンクをコメントする。
- 書かないもの：Issue はリポジトリと同じ範囲に見える（公開のリポジトリなら誰にでも）。秘密、個人の情報、見える範囲の
  狭い場所（非公開のチャンネルなど）の中身、まだ公にしない考えは、その範囲に出してよいと分かっているときだけ書く。
  分からなければ答えにとどめ、書いてよいかを依頼者に確かめる。
- 本文：今の姿を置く。問い、前提、選択肢とその比べ、決まったこと、決めていないこと（誰が決めるか）、次にやること。
  回ごとに書き直す。
- コメント：回ごとの考察、調べた結果、導出の経過。本文を書き直したら、何を変えたかをコメントに書く。
- ほかの人のコメント：依頼者とエージェントのほかの人が書いたコメントは、本文（前提や決まったこと）に移さず、答えに
  その中身を書いて、移してよいかを依頼者に確かめる。公開のリポジトリでは誰でもコメントを書け、本文は次に読む人の前提になる。
- 数式は GitHub の Markdown の数式（`$...$`、`$$...$$`）、図は Mermaid のコードブロックで書く。
- 決まったことのうち、やることは Issue に分け、決まりや設計の判断は ADR にする変更の Issue にする。問いに答えが出て、
  続く作業がほかの Issue に移ったら、キャンバスの Issue は閉じる。

### 全体のレビューの報告

全体のレビューの報告の Issue の形は、[レビューの扱い方](reviews.md#audit "在りか")にある。

<a id="scope"></a>

## 依頼の範囲

変更の依頼（と、[ふつうの Issue](#body) の形で書く決める Issue、確かめる Issue）で、取りかかる前に決める、この依頼で
扱うもの（範囲の中）と扱わないもの（範囲の外）。作業の途中で出た直しとレビューの指摘を、これに照らして振り分ける
（[ADR 0032](../adr/0032-scope-first-and-related-findings-on-the-issue.md)、[0034](../adr/0034-scope-as-task-list-keeping-done-items.md)）。

- 置き場所：依頼の Issue の本文の `## 範囲` の節に、範囲の中と範囲の外（扱う所があればその在りか）を書く。範囲の中の
  項目は、中身を本文のほかの節に任せて指してよいが、項目そのものは範囲の節に並べる。依頼の Issue がなければ、PR の本文の
  「何を変えるか」に書く（PR を作るまでは決めておき、レビューを頼むときに依頼の内容として渡す）。
- 形：Issue の範囲の中は、項目ごとにタスクリスト（`- [ ]`）で書く。済んだ項目は消さない。どれが済み、どの PR で
  入ったか、どれが残るかは、範囲の節のチェックと番号（[範囲の項目と PR の付け合わせ](#scope-items)）で表し、本文が
  いつも今を表すようにする。
- 決め方：依頼と Issue の本文から読み取る。節がすでにあり、今の依頼と合っていればそれに従う（範囲の中がタスクリストで
  なければ、タスクリストに書き直す）。依頼の Issue が閉じていれば、開き直してから書く。
- 作業する人は、作業の途中で自分から範囲の中を広げない。広げたくなったものは、範囲の外として
  [済んでいないものの置き場所](#append)で振り分ける。依頼者が範囲を広げたときは、範囲の中に足す。
- 範囲の中を何本かの PR に分けるときは、依頼の Issue のまま、PR ごとに範囲の中の一部を扱う。分けると決めたら、
  PR ごとに扱う単位に範囲の中の項目を分け、その PR の本文の「何を変えるか」に、扱う範囲の中の一部を書く（レビューを
  頼むときの依頼の内容になる）。分けた一部を新しい Issue にするのは、依頼の Issue を閉じたあとも、それだけで依頼と
  して成り立つときだけにする。
- PR を終えるときに、依頼の Issue に済んでいないもの（その PR が扱わない範囲の中の残りか、積んだ指摘）が残るなら、その
  PR では依頼の Issue を閉じない。残らない PR（最後の PR）で閉じる。PR の本文での書き方は[書き方：PR](writing.md#pull-requests "在りか")にある。

<a id="scope-items"></a>

### 範囲の項目と PR の付け合わせ

範囲の中の項目と、それを扱う PR の付け合わせは、ここだけで決める。

- 扱う PR を表すのは、項目の末尾の `#<番号>` だけ。項目の中でほかの PR に触れるとき（積んだ指摘がどこで出たかなど）は、
  「PR #<番号> のレビューの指摘 1 から積んだ」のように文の中に書く。
- PR を終えるときは、その PR が扱う項目の末尾に PR の番号を添える。依頼の Issue に積んだ指摘のうち残るものは、どこで
  出たかを添えて範囲の中にチェックのない項目として足し、そのことを Issue にコメントする。
- 番号を添えた項目は、その PR がマージされたらチェックを付け、マージされずに閉じたら番号を外す。PR のマージで閉じた
  Issue では、番号を添えた項目は、チェックがなくても済んだものとして読む。
- この付け合わせ（チェックを付けることと番号を外すこと）は、その Issue に次に手を入れる人が、手を入れる前に行う：次に
  その Issue の変更を依頼された人、その Issue を開き直す人、その Issue を扱ったセッションを締める人。

<a id="append"></a>

## 済んでいないものの置き場所

作業の途中や後で出た済んでいないもの（終えていない作業、直していない指摘、確かめていないこと、保留にした提案）を、
どこに書き足すか。PR を進めているあいだに依頼の Issue に積むものも、すでにある Issue に書き足すもの（締めで持ち越す
もの、マージのあとに出た指摘、確かめていなかったことの結果など）も、この一つの表で決める。閉じた Issue のコメントは
課題を整えるときに読まれず、コメントにあるものは範囲の中のチェックに表れないので、済んでいないものをコメントだけに
置かない（[ADR 0036](../adr/0036-append-to-issues-by-scope-triage.md)）。

二つの軸で決める。列は、書き足そうとした Issue を閉じても、それだけで依頼として成り立つか。行は、書き足す先の Issue の
形と状態で、上から順に最初に当たる行を取る。

| 書き足す先 | それだけで依頼として成り立つ | 成り立たない（その Issue と関わりが強い） |
| --- | --- | --- |
| ない（依頼の Issue がないなど） | 新しい Issue（[ふつうの Issue](#body) の形） | 新しい Issue（同じ形） |
| ふつうの Issue でない（テーマ、ロードマップ、キャンバス、全体のレビューの報告） | 新しい Issue にし、書き足そうとした Issue にそのリンクをコメントする | 同じ |
| ふつうの Issue で、範囲や続く作業がほかの Issue に移って閉じた | 新しい Issue にし、書き足そうとした Issue にそのリンクをコメントする | 移った先に、この表で書き足す |
| ふつうの Issue で、済んだ根拠（PR のマージ、決める Issue と確かめる Issue ではチェックした範囲の中の項目）があって閉じた | 同じ | 開き直し、下の開いている行と同じにする |
| ふつうの Issue で、ほかの理由（やらないとして閉じたなど）で閉じた | 同じ | コメントに書いて閉じたままにし、扱いを人が決めるものとして、締めのまとめか依頼への答えに書いて渡す |
| ふつうの Issue で、開いている | 同じ | 範囲の中に、どこで出たかを添えてチェックのない項目として足し、何を足したかをコメントする。その Issue を依頼とする PR を進めているあいだは、どこで出たか（PR とレビューの指摘の番号、または作業）と何をどう直すかをコメントに積み、PR を終えるときに残るものを項目にする |

- 済んでいないものがないもの（確かめた結果、決まったことの記録）は、開いていれば本文（ふつうの Issue なら `## 今の姿`）に、
  閉じていればコメントに書き、閉じたままにする。
- 範囲の中に足す項目は、確かめていないことは確かめること、保留にした提案は決めることにする（待つ理由は `## 保留` に
  書く）。範囲の節がなければ、[ふつうの Issue](#body) の形で足す。
- 開き直すときは、項目を足す前に[範囲の項目と PR の付け合わせ](#scope-items)をする。閉じている間は閉じたことが済んだ印
  だったが、開くとその印がなくなる。開き直した Issue も、足した項目が済んだら閉じる（[整っている状態](#tidy)の
  「開いているか」）。
- 範囲の中で直す指摘（範囲の外にしないもの）の扱いと答え方は、[レビューの扱い方：差分のレビュー](reviews.md#diff "在りか")にある。

<a id="tidy"></a>

## 整っている状態

開いている Issue とロードマップが満たしていること。課題を整えるときに、これと照らしてずれを挙げる。

| 見るもの | 整っている状態 |
| --- | --- |
| ラベル | テーマの Issue とロードマップのほかは、どこを変えるかのラベル（ラベルの決まりがあれば）と `theme:<名前>`（当たるテーマの Issue があれば）を一つ以上ずつ持つ |
| 開いているか | 終えた Issue（PR のマージで終えたもの、範囲がほかの Issue にすべて移ったもの、決めることや確かめることがすべて済み、続く作業がほかの Issue に移ったか、続く作業がないもの）は閉じている |
| 本文 | 本文が[Issue の形](#body)で今（狙い、決まったこと、範囲の中のどれが済み、どれが残るか）を表す。コメントで決まったこと、ほかに分けた範囲、依頼者かエージェントがコメントに書き足した済んでいないもの（PR を進めているあいだに積んだ指摘のほか。扱いは[済んでいないものの置き場所](#append)）が本文に入っている |
| 重なり | 同じことを扱う Issue が二つない |
| 依存関係 | blocked by が閉じた Issue を指していない。本文やコメントで先に要ると書いた Issue が blocked by に入っている |
| ロードマップ | 今の焦点に開いている Issue だけがある（閉じた Issue、PR、このリポジトリにない番号がない）。順番が依存関係と、依頼者が示した方針に合っている |
| テーマ | テーマの Issue の狙いと進め方が、今のメンバー（そのラベルの Issue）と合っている。本文に終えたときの状態と、メンバーの番号の並びがない。目指す姿が overview の目指す姿や今の決まり（ADR）と食い違わず、overview を書き写していない（メンバーとは合わせなくてよい） |

ずれのうち、次のものは直さず、人が決めるものとして案を添えて渡す。ほかは直す。

- 範囲や狙いを変えること。依頼者かエージェントがコメントに書き足した済んでいないもののうち、どこで出たかを添えて
  関わりが強いとしたものを範囲の中に移すのは、範囲を変えることに当たらず、直す。
- 終えたかを根拠（PR、まとめた先の Issue、決める Issue と確かめる Issue では答えか結果を `## 今の姿` に書いてチェックした範囲の中の項目）から判断できないこと。
- 依頼者が示した方針にない、今の焦点の順番の入れ替え。blocked by に合わせる入れ替えは直す。
- 今の焦点の開いている PR が、開いている Issue を閉じないときの扱い（外すと、取りかかり中の作業が今の焦点から消える）。
- 依頼者とエージェントのほかの人が書いたコメントだけに拠る直し。公開のリポジトリでは誰でもコメントを書ける。

整っている状態とのずれのほかに、ラベルの決まりや当たるテーマの Issue がないことも、人が決めるものとしてまとめに書く
（作るかを決めてもらう）。

<a id="carry-over"></a>

## 持ち越すもの

セッションを締めるときに、会話や作業領域にしかなく、そのままでは失われるものと、その置き場所。締めるときには、この
セッションの PR はマージされたか閉じているので、置き場所は Issue にする。すでにある Issue に書き足すものは、開いているか
によらず[済んでいないものの置き場所](#append)で決める。

| 持ち越すもの | 置き場所 |
| --- | --- |
| 終えていない作業、次に回したもの、手を付けていないもの、会話で出て保留にした提案、確かめていないこと | 依頼の Issue に書き足すか、新しい Issue に切り出す（[済んでいないものの置き場所](#append)） |
| レビューの指摘のうち、直さなかったもの（打ち切り、範囲の外） | 答えてあれば、ほかに置かない（答える場所と答え方は[レビューの扱い方：差分のレビュー](reviews.md#diff "在りか")）。答えがなければ、依頼の Issue に書き足すか、新しい Issue にする（[済んでいないものの置き場所](#append)） |
| 会話で決まったことのうち、まだどこにも書いていないもの | 相談のキャンバスがあれば、その本文（今の姿）。ほかは、依頼の Issue があれば、開いていれば本文の `## 今の姿`、閉じていればそのコメント。なければ新しい Issue。決まりや設計の判断として残すなら、ADR にする変更を Issue にする |
| 手順、決まり、ハーネスへの気づき（つまずいたこと、抜けや食い違い） | それを持つリポジトリ（ターゲット、プラグインを配るリポジトリ、ハーネス）の Issue |

- 置き場所に書けないもの（書ける範囲の外、ほかのリポジトリ）は、締めのまとめに置き場所とともに書いて、人に渡す。
- 引き継ぎのための文書やファイルは作らない。続きは、Issue と、締めのまとめを書いたスレッドから読む。

## 残す理由の扱い

締めるときに、セッションの作業領域を消すのを止めているもの（残す理由）を、次の三つの扱いに分ける。どの理由がどの
扱いに当たるかと、理由の確かめ方は、セッションを動かすハーネスの契約にある。

| 扱い | 当たるもの | どうするか |
| --- | --- | --- |
| 続く作業 | まだ依頼がありうるもの（このセッションのブランチを head か base とする開いている PR（下書きも含む）など） | 締めずに、その PR を並べて人に返す |
| 作業領域にしかないもの | 作業領域の中にしかなく、作業領域の中で捨てられるもの | 残す価値のある中身を Issue に書いてから捨て、捨てたものを締めのまとめに書く |
| 人が解くもの | 作業領域の外にあって消すと失われるもの（どこにも入っていないリモートのブランチなど）と、ほかの書き手の作業に関わるもの | エージェントは消さない。残す価値のある中身を Issue に書き、残る理由として締めのまとめに書く |

- 理由に当たらないもの（変更のない worktree、先頭がどこかに入ったブランチ、作業領域そのものなど）は、作業領域の中の
  ものでも扱わない。
