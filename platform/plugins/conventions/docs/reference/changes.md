# 変更の扱い方

どのリポジトリでも同じにする、変更（PR）の扱い方と進め方。課題の扱い方は[課題](issues.md "案内")にある。

<a id="changes"></a>

## 変更

- 既定のブランチへの変更は PR 経由で行い、merge commit でマージする。PR のコミットがそのまま残る。
- PR とコミットに何を書くかは[書き方](writing.md)にある。

<a id="how-to-change"></a>

## 変更の進め方

変更する人（人でもエージェントでも）は、次の順に進める。

1. 依頼が Issue を指していれば、本文とコメントを読む。依頼文が短くても、Issue とリポジトリから読み取れることは
   前提にする。
2. 変更が関わる仕組みの今の姿と前提を、文書、ADR、コードで確かめる。
3. 変更で壊れうる場面を挙げて確かめる。たとえば、同じものを作り直すとき、再起動や失敗の途中、同時に動くとき、
   すでにあるデータや設定との組み合わせ。当てはまる変更には、設計のパターン（[状態を軸で洗い出す](../../../principles/docs/reference/patterns.md#state-axes)、
   [事実と判定を分ける](../../../principles/docs/reference/patterns.md#facts-and-judgement)、[失われうるものを先に挙げる](../../../principles/docs/reference/patterns.md#loss-first)、
   [手順を実装と突き合わせる](../../../principles/docs/reference/patterns.md#verify-procedures)）を当てはめる。
4. PR を作る前に、変更した人とは別の目（サブエージェントや別の人）に差分をレビューさせる。依頼の内容、変更の意図、
   差分を渡し、前提との矛盾や壊れる場面を探させる。指摘は直すか、直さない理由を PR に書く。
5. 確かめられなかったことは、確かめていないと PR に書く。
