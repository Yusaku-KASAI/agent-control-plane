# 変更の扱い方

どのリポジトリでも同じにする、変更（PR）の扱い方と進め方。課題の扱い方は[課題](issues.md "案内")にある。

<a id="changes"></a>

## 変更

- 既定のブランチへの変更は PR 経由で行い、merge commit でマージする。PR のコミットがそのまま残る。
- PR とコミットに何を書くかは[書き方](writing.md "案内")にある。

<a id="how-to-change"></a>

## 変更の進め方

変更する人（人でもエージェントでも）は、次の順に進める。

1. 依頼が Issue を指していれば、本文とコメントを読む。依頼文が短くても、Issue とリポジトリから読み取れることは
   前提にする。
2. 変更が関わる仕組みの今の姿と前提を、文書、ADR、コードで確かめる。
3. 変更で壊れうる場面を挙げて確かめる。たとえば、同じものを作り直すとき、再起動や失敗の途中、同時に動くとき、
   すでにあるデータや設定との組み合わせ。変更の種類に応じて、次の設計のパターンを当てはめる（[変更とパターン](#patterns)）。
4. PR を作る前と、push で PR の head が進んだときに、変更した人とは別の目（サブエージェントや別の人）に差分をレビューさせる。レビューの観点、指摘の
   書き方と答え方は[レビューの扱い方](reviews.md "案内")にある。
5. 確かめられなかったことは、確かめていないと PR に書く。依頼に答えるときは、その答えにも書く。

<a id="patterns"></a>

## 変更とパターン

| 当てはまる変更 | 当てはめるパターン |
| --- | --- |
| どの変更も | [一つの目的の小さな変更](../../../principles/docs/reference/patterns.md#small-change) |
| 状態によって振る舞いが変わる | [状態を軸で洗い出す](../../../principles/docs/reference/patterns.md#state-axes)、[事実と判定を分ける](../../../principles/docs/reference/patterns.md#facts-and-judgement) |
| 消す、上書きする、作り直す | [失われうるものを先に挙げる](../../../principles/docs/reference/patterns.md#loss-first) |
| 人が実行する移行や運用の手順を含む | [手順を実装と突き合わせる](../../../principles/docs/reference/patterns.md#verify-procedures) |

<a id="checks"></a>

## 検査と履歴

- CI が失敗したら、ログで原因を確かめてから直す。手元で同じ検査を実行できるなら、push の前に通す。
- 履歴を書き換えて force push したら、PR の本文を今の中身に合わせ、何をなぜ書き換えたかをコメントに書く。
