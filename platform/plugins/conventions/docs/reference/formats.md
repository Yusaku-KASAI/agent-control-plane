# 文書の形式

どのリポジトリでも同じにする文書の形。形のうち、各節の「検査」に挙げたものは、conventions のコマンド
`check-docs` が確かめる。

<a id="check-scope"></a>

## 検査の範囲

文書の検査（`check-docs`）は、範囲を文書の構造の決まりに限る。中身（文書が述べること）の検査は、
[検査にするもの](checks.md#conditions)の「誤って落ちにくい」を満たさないものとして扱う（[ADR 0028](../adr/0028-document-checks-cover-structure.md)）。

| 検査の候補（構造）。検査にするものの三つの条件で選ぶ | 検査にしない（中身）。レビューに任せる |
| --- | --- |
| 決まりが定めた変わらない語と置き場所、印、入口・索引・地図からの到達。形式（決まった節、見出し、印があるか、量の上限）、リンク（リンク先、在りかの印、どの文書も入口、索引、地図から届くか）、依存（地図と前提の向き）、メタデータ（ADR の frontmatter と参照） | ある文書が述べること（何をどこまで書くか、特定の節に何を並べるか（すべての目的の手順が並ぶかのような網羅を含む）、どの手順を誰が受け持つか、要約、例、説明）が、ほかの定義や今の姿と合っているか |

- 分け目は、決まりが定めた変わらない語と置き場所（決まった節、見出し、決まった段の名前（始めに読む）、印）と、どの
  文書にも届くか（到達）は構造、ほかの文書の決まった節に何を並べるか（網羅）と述べることは中身、とする。到達は、
  入口（`README.md` と `CLAUDE.md`）、索引、地図からの道で、そこに並ぶかも含む。決まった枠（下の各節が挙げるもの）の
  うち、あるか、名前、位置、印は構造で、そこに何を述べるかは中身。
- 何を確かめるかは、下の各節の「検査」に書く。

<a id="layout"></a>

## 文書の根

`README.md` を持つ `docs/` を文書の根とする（一つのリポジトリにいくつあってもよい）。区切りごとに一つ置き、リポジトリ
自身の文書の根はルートの `docs/`、リポジトリの中のほかの区切り（プラグインなど）の文書の根は、その区切りの
ディレクトリの `docs/` にする。

```
README.md             （入口。リポジトリのルートにだけ置く）
CLAUDE.md             （入口。同じ）
docs/                 （区切りのディレクトリの中なら <区切り>/docs/）
  README.md
  overview.md
  architecture/
  guides/
  reference/
  adr/
```

| 器 | 置くもの | 置かないもの |
| --- | --- | --- |
| `README.md`（人の入口） | 何のリポジトリかの数行の説明、索引と全体の解説（あれば）へのリンク、よく使う手順へのリンク（1〜2 本まで） | 文書の一覧 |
| `CLAUDE.md`（エージェントの入口。常に読み込まれる） | エージェントがいつも知っておくべき前提（プロダクトの前提、完了条件、言語など）と、索引と全体の解説（あれば）への道。どの節を持つかは、リポジトリが従う契約で決める | 詳細（文書へのリンクにする） |
| `docs/README.md`（索引） | その文書の根の唯一の一覧。文書ごとに、種類と一行の要旨 | 中身 |
| `docs/overview.md`（全体の解説） | 狙い、全体の構成と部分の間の関係、地図、目指す姿（今の方針として） | 部分の細部（`architecture/` へリンクする）、目指す姿への道筋（Issue に置く） |
| `architecture/` | 部分ごとに一つの文書で、その部分の構成と関係と、[構成要素の説明](#component) | 手順と、決まりの細部（条件、表、形。`guides/` と `reference/` へリンクする） |
| `guides/` | 手順（決まりとして守る順序を含む）と、その場で要る最小の説明。エージェントに届ける手順もここに定義する（スキルが自分で持ってよいものは[定義と届け方](../architecture/documentation.md#delivery "在りか")） | 仕組みの説明（`architecture/` へリンクする）、決まり（条件、表、形。`reference/` へリンクする） |
| `reference/` | 引くための事実と決まり：契約、設定、コマンド、形式、用語、条件、表 | 手順と守る順序、設定の既定値（例の設定ファイルを正にする） |
| `adr/` | [ADR](#adr) | 今の姿のまとめ |

- 理由をどこに置くかは[文書の体系：今の姿と理由の置き場所](../architecture/documentation.md#reasons "在りか")にある。
- 根の直下に置くのは `README.md`（索引）、`overview.md`、`architecture/`、`guides/`、`reference/`、`adr/` だけ。要らないものは
  置かない。小さな区切り（プラグインなど）は、`README.md` と `overview.md` だけでもよい。
- 文書の根の中で関心の違う部分は、`architecture/` と `adr/` を `<関心>/` に分ける。`guides/` と `reference/` は、
  文書が増えたら同じように分ける。
- 根の下の文書は、`adr/` の中を除いて、どれも索引からリンクする。
- 検査：根の直下に上のほかのもの（OS が置く `.DS_Store` は除く）がないこと。`adr/` の外の文書がどれも索引から
  リンクされていること。

<a id="reach"></a>

## 入口からの道

人はリポジトリのルートの `README.md` から、エージェントは `CLAUDE.md` から読み始める。リポジトリのすべての
Markdown（プラグインのルール、スキル、役割ごとの指示を含む）は、その両方からリンクをたどって行き着けるようにする。

- たどるリンクには在りかのリンクも含む。ディレクトリへのリンクは、その中のすべての文書に行き着く（`adr/` など）。
- 検査：`README.md` と `CLAUDE.md` のそれぞれから行き着けない文書がないこと（二つの入口どうしは除く）。

<a id="component"></a>

## 構成要素の説明

アーキテクチャの文書（`docs/architecture/`）で、層、ディレクトリ、ファイル、パッケージなどの構成要素を説明する
ときの形。文書にもコードにも同じ形を使う。

アーキテクチャの文書は、`## 構成`（その部分の構成と関係）と `## 構成要素` の節を持ち、構成要素の節の中に、
構成要素ごとに次の形の `###` を置く。

```markdown
### <構成要素の名前（パスなど）>

- **責務**：1 文。
- **置くもの / 置かないもの**：
- **関係**：依存してよい先、契約、参照する先。
- **当てはめた原則・パターン**：[<原則かパターン>](<principles.md か patterns.md へのパス>#<id>)：ここでどう効いているか。いくつでも。
```

- [設計の原則](../../../principles/docs/reference/principles.md)か[設計のパターン](../../../principles/docs/reference/patterns.md)を指す。パターンを採ったときはパターンを、形にせず
  拠り所にしただけのときは原則を指す。一つの原則やパターンは、いくつの構成要素に当てはめてもよい。原則とパターンの
  側には、どこで使っているかを書かない。
- 自明な項目は省いてよい。責務だけは必ず書く。
- 検査：アーキテクチャの文書が `## 構成要素` を持ち、その中の `###` がどれも「責務」を持つこと。

## 手順

手順（`guides/`）のうち、目的の手順と共通の手順（[手順と役割](../architecture/documentation.md#procedures)）の形。

- 手順は最大 2 層にし、3 層目は作らない。プラグインの `docs/guides/`（エージェントに届ける手順）に置く手順は、どれも
  どちらかの層に入れる。人が読む運用や準備の手順（リポジトリの `docs/guides/` など）は、層の外に置いてよく、この形に
  限らない。
- 目的の手順は、段の中で、その段で使う共通の手順を案内する。共通の手順がほかの手順を指さないことは、下の箇条にある。

目的の手順：

```markdown
# <目的の名前（何をしてほしいかの動詞句。終わりの状態が分かる名前）>

<誰が>、<何を受けて>から、<終わりの状態>までの手順。目的の手順で、段の中で共通の手順を使う（[手順と役割](<documentation.md>#procedures)）。
決まりは<参照の文書>にある。

<どこからを新しい依頼として振り分けから入るか。続きのターンの扱いが文書の体系と違うときだけ、それも書く。>

1. **始めに読む**：次を全体まで読む。この段は省かない。このセッションですでに全体まで読んだ文書は、読み直さなくてよい。
   - [<文書>](<パス>)：<その手順でなぜ要るか>
2. **<段の名前>**：<その段ですること。使う共通の手順と決まりへの案内>
```

共通の手順：

```markdown
# <名前（作業の一部分の動詞句）>

<何をする手順か>。共通の手順で、目的の手順の段の中で使う（[手順と役割](<documentation.md>#procedures)）。
決まりは<参照の文書>にある。

1. **<段の名前>**：<その段ですること>
```

- 決まった枠：見出し（手順の名前）、冒頭の段落（目的の手順なら、誰が、何を受けてから、何で終えるまでか。共通の手順なら、
  何をするか。どちらも層と決まりの在りか）、目的の手順の境の段落と 1 段の「始めに読む」、段に番号と太字の名前を付けること。
- 柔軟な部分：段の数と名前、段の中身、小見出しで場面を分けること（例：レビューするの差分のレビューと全体のレビュー、
  レビューを頼んで答えるの頼む、答える、終える前を満たす）。小見出しで分けた中の段も、番号と太字の名前を付ける。
- 共通の手順は、始めに読む段と境の段落を持たない（それは使う側の目的の手順が持つ）。同じ `docs/guides/` のほかの手順
  （使う側の目的の手順も、ほかの共通の手順も）を指さない。どの手順をどの段で使うかは、使う側の目的の手順が決める。
- 決まり（条件、表、形）と守る順序の分け方は[文書の根](#layout)の器の表に、理由の置き場所は[文書の体系](../architecture/documentation.md#reasons "在りか")にある。
- 検査：プラグインの `docs/guides/`（その下のディレクトリを含む）の文書は、冒頭の段落に「目的の手順で」か「共通の
  手順で」のどちらか一つを持つこと（ほかの手順の置き場所では、持つ文書だけを確かめる）。目的の手順は、最初の番号付きの
  段が `1. **始めに読む**` で、冒頭に「新しい依頼」に触れる段落を持つこと。共通の手順は、「始めに読む」の段を持たず、
  同じ `docs/guides/` のほかの手順へのリンクを持たないこと。どちらも、番号付きの段が太字の名前を持つこと。

## 役割ごとの指示

役割ごとの指示（プラグインの `agents/` と、リポジトリの `.claude/agents/` の文書）の形。何を載せるかは
[起点](delivery.md#starting-points "在りか")、手順と役割の関係は[手順と役割](../architecture/documentation.md#procedures)にある
（[ADR 0018](../adr/0018-role-instructions-split-and-changing-definitions.md)、[0022](../adr/0022-forms-of-procedures-and-role-instructions.md)）。

```markdown
---
name: <役割>
description: <受け持つ目的の手順と書ける範囲を一文で>
---

あなたはターゲットのリポジトリの <役割> ロールとして、<一文>。

<前置き：どの節がその役割だけの定義で、どの節がほかの定義の要約と案内か。定義の在りかの示し方>

## 受け持つ手順

書ける範囲：<作業領域、PR、PR のレビュー、Issue のうち、何を書けるか>。共通のルールの振り分けで決めた目的の手順ごとに、
次のとおりにする。

- <主に使う目的の手順>：受け持つ。始めに、<手順の在りか>と、その 1 段の文書（<在りか>）を全体まで読み、その段に沿う。
- <ほかに受け持つ目的の手順>：受け持つ。<スキル>を使い、<手順の在りか>に沿う。
- <受け持たない目的の手順>：受け持たない。<回す先の役割>に依頼するよう案内する。
- そのほか（<例>）：目的の手順のない依頼は、書ける範囲の中で依頼に沿って試す。

## 使う決まり

### 進め方（<目的の手順>の要約）

- <段の要約>（<出典の段>）

### 場面ごとに読むもの

- <場面>：<在りか>

## 固有の振る舞い

### <何をするか、しないこと、報告など>
```

- 決まった枠：frontmatter の `name` と `description`、冒頭の一文、前置き、`## 受け持つ手順`（最初の節。頭に書ける範囲を
  置き、最後に「そのほか」を置く）、`## 固有の振る舞い`（最後の節）。
- 各節に置くもの：`## 受け持つ手順` は、書ける範囲（作業領域、PR、PR のレビュー、Issue のうち、どれを書けるか。ほかの
  書き先の扱いは[手順と役割](../architecture/documentation.md#procedures "在りか")にある）と、
  振り分けの目的の手順をすべて、受け持つか、受け持たないか（受け持たないなら、どの役割に回すか）で並べたもの。
  `## 使う決まり` は、ほかの定義の要約と案内。`## 固有の振る舞い` は、その役割だけの定義。受け持つ
  手順のどれに「始めに読む」の段の文書を直に並べるかは[届け方の決まり](delivery.md#procedures "在りか")にある。何を並べるかは
  中身で、検査にしない（[検査の範囲](#check-scope)）。
- 柔軟な部分：`## 使う決まり`（ほかの定義の要約と案内がなければ省く）、各節の中の `###` の見出しと中身、frontmatter の
  ほかの項目（`model`、`isolation` など）。
- 定義の在りかは、リンクではなくパスで書く。conventions の外の在りかは、プラグインか区切りの名前を添える（例：roles の
  `docs/overview.md`、platform の ADR 0019）。
- 検査：プラグインの `agents/` の文書（どれもロール）と、`.claude/agents/` の文書のうち冒頭（最初の `##` より前）で
  「ロールとして」と名乗る文書の、最初の `##` が `## 受け持つ手順` で、その節に「書ける範囲：」があり、最後の `##` が
  `## 固有の振る舞い` であること。`.claude/agents/` のロールでないカスタムエージェント（補助のサブエージェントなど）は、
  この形に限らない。

<a id="skill"></a>

## スキル

プラグインのスキル（`skills/<名前>/SKILL.md`）の形。スキルが何を持ってよいかは[定義と届け方](../architecture/documentation.md#delivery)に、
何を載せるかは[起点](delivery.md#starting-points "在りか")にある。

```markdown
---
name: <名前>
description: <使う場面>ときに使う。<何の手順か、何の道具か>。
---

# <届ける手順の名前（道具のスキルなら、道具の名前）>

<どの場面で、どの手順を全体まで読んで沿うか。>

要約すると：

- <破られやすい数項目の要約>（<出典>）

## <道具の使い方（そのプラグインの道具を持つときだけ）>
```

- 決まった枠：frontmatter の `name` と `description`（「〜ときに使う」で使う場面を書く）、見出し。手順を届けるスキルは、
  見出しを届ける手順の名前にし、その手順を全体まで読んで沿うという案内を持つ。道具や一覧を持つスキル（github、harness、slack、principles など）は、
  見出しを道具か作業の名前にし、道具の使い方か在りかの案内を持つ。
- 柔軟な部分：要約の項目、道具の使い方の節。いくつかの手順への入口になるスキルは、見出しをまとめた名前にし、案内を
  手順ごとに並べる（例：review）。
- 検査：しない（レビューで見る）。

## ADR

判断の記録は、文書の根の `adr/NNNN-<slug>.md` に置く。決まりを変える判断は、その決まりを持つ区切りの `adr/` に、道具の
振る舞いの判断は、その道具を持つ区切りの `adr/` に置き、決まりの判断を指す（[ADR 0045](../adr/0045-review-rules-decided-in-conventions.md)）。
番号は `adr/` ごとに 1 から振る連番。ADR をほかの `adr/` に移したときは、移した先で次の番号を振り、元の番号は空きのまま使わない。文書の根に関心の違う
ADR があるときは、`adr/<関心>/NNNN-<slug>.md` に分ける。

```markdown
---
status: accepted        # accepted か superseded
date: 2026-10-11
amends: [7]             # 一部を変えた ADR（なければ書かない）
amended_by: [12]        # この ADR の一部を変えた ADR
supersedes: [3]         # 全体を置き換えた ADR
superseded_by: [15]     # この ADR を置き換えた ADR（status: superseded と組み）
---

# NNNN. 決めたこと（一文）

## Context
## Decision
## Alternatives
## Consequences
```

- 手で書く frontmatter は ADR と、Claude Code が読む定義（`agents/` のエージェントと `skills/` のスキル）だけに置く。ほかの文書の属性
  （区分、更新日、持ち主、前提など）は書かず、`check-docs --catalog` で一次の情報から導く
  （[ADR 0026](../adr/0026-derive-document-catalog.md)）。
- ADR はその時点の判断の記録なので、後から本文を書き換えない（文書を移したときのリンクの付け替えは除く）。判断を
  変えるときは新しい ADR を作り、両方の frontmatter に向き合う参照（`amends` と `amended_by`、`supersedes` と
  `superseded_by`）を書く。参照は、同じ `adr/` の ADR なら番号、ほかの `adr/` の ADR なら相対パス（`"../../x/adr/0004-y.md"`）で書く。
- 検査：frontmatter の形と値、`superseded` と `superseded_by` の組、日付の形、見出しの番号とファイル名の一致、
  参照先があることと向き合っていること。

<a id="links"></a>

## リンク

リンクの種類の判断の理由は [ADR 0007](../adr/0007-navigation-links-marked-by-title.md)、[0014](../adr/0014-prerequisites-by-change-and-whereabouts-links.md) にある。

- 文書の間は相対パスでリンクする（`/` で始まる絶対パスは使わない）。見出しに日本語を含む節を指すときは、節の前に `<a id="<英字の id>"></a>` を置いて
  その id を指す。
- リンクは、前提のリンクか在りかのリンクのどちらか。リンク先の中身が変わったときに、リンクを含む文を見直す要が
  あれば前提のリンク、在りかが変わらない限り直さなくてよいなら在りかのリンク。前提にしているのに在りかのリンクに
  して向きの確かめから外したり、確かめを避けるためにリンクそのものを消したりしない。
- 在りかのリンクには、タイトル `"在りか"` を付ける：`[設計のパターン](patterns.md "在りか")`。タイトルのないリンクは
  前提として扱う。付け忘れても、依存の向きの確かめが厳しい側に倒れる（[拒否を既定にする](../../../principles/docs/reference/principles.md#fail-safe-defaults)の考え方）。
  索引（文書の根の `README.md`）からのリンクと ADR へのリンクは、タイトルがなくても在りかのリンクとして扱う。
- 検査：絶対パスのリンクがないこと。リポジトリの中へのリンクのタイトルが、ないか `"在りか"` であること。相対リンクが実在するファイルを指していること（在りかのリンクも含む）。節を指すリンクは、指す先に同じ `<a id>` が
  あるか、英字だけの見出しから GitHub と同じ規則で作った id と一致すること。

<a id="size"></a>

## 量の上限

いつも読み込まれる文書は、空行と frontmatter を除いて、次の行数までにする。frontmatter のほかの行は、どの行も
表示幅（全角を 2、ほかを 1 として数え、リンクの括弧の中（行き先とタイトル）は数えない）を 130 までにする
（[ADR 0049](../adr/0049-starting-points-limit-line-width.md)）。

| 文書 | 上限 |
| --- | --- |
| リポジトリのルートの `CLAUDE.md` | 60 行 |
| プラグインの `rules/` の文書（共通のルール。ディレクトリの合計） | 40 行 |
| 役割ごとの指示（プラグインの `agents/` と、リポジトリの `.claude/agents/` の文書。一つずつ） | 50 行 |

- 上限に当たったら、行を伸ばしたり言い回しを詰めたりして収めるのではなく、載せるものを減らすか、ほかの場所へ移すか、
  要約を案内に下げる（[起点](delivery.md#starting-points "在りか")）。
- 検査：上の行数と、frontmatter のほかの行の表示幅を超えていないこと。

## 地図

項目と前提の向きは、文書の中の表（地図）で宣言する。地図は階層ごとに分けて、その階層の持ち主が書く。

- 最上位の地図（親が空の項目）は、リポジトリに一つだけ、`docs/overview.md` に置く。地図を持たないリポジトリでは、
  地図の検査をしない。
- 項目 P の中の項目（親が P の項目）は、P に属する文書（P の `overview.md`）の地図に書く。上の階層の地図は、中の項目を
  書かない。
- 置き場所を持たない項目には、ほかの項目の集まり（契約など）と、リポジトリの外の項目がある。集まりの中の項目は、
  その集まりを宣言した地図に書く。
- 地図は、`map-` で始まる id の `<a id>` の後の最初の表。間に見出しを一つと文を挟んでよい。

```markdown
<a id="map-docs"></a>

## 地図

| 項目 | 親 | 置き場所 | 前提にする |
| --- | --- | --- | --- |
| 参照 | docs | `reference/` | |
| 解説 | docs | `architecture/` | 参照 |
```

- 列：最初の 4 列は、項目、親、置き場所、前提にする。説明の列を後ろに足してよい。
- 項目：名前はリポジトリの中で一つ。
- 親：一つ上の項目。最上位なら空にする。
- 置き場所：その項目の文書のパスを、地図を書いた文書からの相対パスでバッククォートで囲み、カンマで並べる。`/` で
  終わればディレクトリ。文書は、置き場所がいちばん長く一致する項目に属する。
- 前提にする：同じ親の下の項目（兄弟）だけを、カンマで並べる。前提の前提は、書かなくても前提にしてよい。
- 子を持つ項目の置き場所のうち、子に属さない文書（`overview.md`、索引、全体の解説）は、子と並ぶ「全体」という項目として
  扱う。どの子も全体を前提にしてよく、全体はどの子も前提にしない（子への道は在りかのリンクにする）。
- 検査：
  - すべての地図を集めて一つの木にする。項目の名前が重ならないこと、親と前提にする項目があること、親が循環しないこと、
    前提が兄弟であること、前提が循環しないこと、最上位の地図が一つであること、各地図が上の決まりどおりの文書にあること、
    置き場所が実在すること。
  - リポジトリのすべての Markdown がどれかの項目に属すること。
  - 文書から文書へのリンクが、二つの項目が初めて同じ親の下に入る階層で、前提の向きに沿っていること。索引からのリンク、
    ADR へのリンク、ADR からのリンク（ADR は書き換えない）、在りかのリンクは除く。
- `check-docs --map` は、すべての地図から設計構造行列を出す。
