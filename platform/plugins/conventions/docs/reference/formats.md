# 文書の形式

どのリポジトリでも同じにする文書の形。形が合っていることは `make check-docs`（`tools/check-docs.py`）が確かめる
（確かめるものは各節に書く）。

<a id="component"></a>

## 構成要素の説明

アーキテクチャの文書（`docs/architecture/`）で、層、ディレクトリ、ファイル、パッケージなどの構成要素を説明する
ときの形。文書にもコードにも同じ形を使う。

アーキテクチャの文書は、`## 構成`（その部分の構成と関係）と `## 構成要素` の節を持ち、構成要素の節の中に、
構成要素ごとに次の形の `###` を置く。

```markdown
### <構成要素の名前（パスなど）>

- **責務**：1 文。
- **置くもの / 置かないもの**：
- **関係**：依存してよい先、契約、参照する先。
- **当てはめた原則・パターン**：[<原則かパターン>](<principles.md か patterns.md へのパス>#<id>)：ここでどう効いているか。いくつでも。
```

- [設計の原則](../../../principles/docs/reference/principles.md)か[設計のパターン](../../../principles/docs/reference/patterns.md)を指す。パターンを採ったときはパターンを、形にせず
  拠り所にしただけのときは原則を指す。一つの原則やパターンは、いくつの構成要素に当てはめてもよい。原則とパターンの
  側には、どこで使っているかを書かない。
- 自明な項目は省いてよい。責務だけは必ず書く。
- 検査：アーキテクチャの文書が `## 構成要素` を持ち、その中の `###` がどれも「責務」を持つこと。

<a id="adr"></a>

## ADR

判断の記録は、文書の根の `adr/NNNN-<slug>.md` に置く。番号は `adr/` ごとに 1 から振る連番。ADR をほかの `adr/` に
移したときは、移した先で次の番号を振り、元の番号は空きのまま使わない。文書の根に関心の違う
ADR があるときは、`adr/<関心>/NNNN-<slug>.md` に分ける。

```markdown
---
status: accepted        # accepted か superseded
date: 2026-10-11
amends: [7]             # 一部を変えた ADR（なければ書かない）
amended_by: [12]        # この ADR の一部を変えた ADR
supersedes: [3]         # 全体を置き換えた ADR
superseded_by: [15]     # この ADR を置き換えた ADR（status: superseded と組み）
---

# NNNN. 決めたこと（一文）

## Context
## Decision
## Alternatives
## Consequences
```

- ADR はその時点の判断の記録なので、後から本文を書き換えない（文書を移したときのリンクの付け替えは除く）。判断を
  変えるときは新しい ADR を作り、両方の frontmatter に向き合う参照（`amends` と `amended_by`、`supersedes` と
  `superseded_by`）を書く。参照は、同じ `adr/` の ADR なら番号、ほかの `adr/` の ADR なら相対パス（`"../../x/adr/0004-y.md"`）で書く。
- 検査：frontmatter の形と値、`superseded` と `superseded_by` の組、日付の形、見出しの番号とファイル名の一致、
  参照先があることと向き合っていること。

<a id="links"></a>

## リンク

- 文書の間は相対パスでリンクする。見出しに日本語を含む節を指すときは、節の前に `<a id="<英字の id>"></a>` を置いて
  その id を指す。
- 在りかを示すだけで前提にしないリンク（案内）には、タイトル `"案内"` を付ける：`[設計のパターン](patterns.md "案内")`。
  案内かどうかは、リンク先を読まなくても、リンクを含む文がそれだけで分かり、正しいかで決める。分かるなら案内、
  リンク先の中身を知らないと分からない・正しいと言えないなら前提。
  索引（文書の根の `README.md`）からのリンクと ADR へのリンクは、タイトルがなくても案内として扱う。
- 検査：相対リンクが実在するファイルを指していること（案内のリンクも含む）。節を指すリンクは、指す先に同じ `<a id>` が
  あるか、英字だけの見出しから GitHub と同じ規則で作った id と一致すること。

<a id="size"></a>

## 量の上限

いつも読み込まれる文書は、空行と frontmatter を除いて、次の行数までにする。

| 文書 | 上限 |
| --- | --- |
| リポジトリのルートの `CLAUDE.md` | 60 行 |
| プラグインの `rules/` の文書（いつも読み込む要約。ディレクトリの合計） | 40 行 |
| 役割ごとの指示（プラグインの `agents/` の文書。一つずつ） | 50 行 |

- 上限に当たったら、言い回しを詰めて収めるのではなく、載せるものを減らすか、ほかの場所へ移す。
- 検査：上の行数を超えていないこと。

<a id="map"></a>

## 地図

項目と前提の向きは、文書の中の表（地図）で宣言する。地図は階層ごとに分けて、その階層の持ち主が書く。

- 最上位の地図（親が空の項目）は一つだけ、全体の設計を持つリポジトリの文書に置く。
- 項目 P の中の項目（親が P の項目）は、P に属する文書（P の `overview.md`）の地図に書く。上の階層の地図は、中の項目を
  書かない。
- 置き場所を持たない項目には、ほかの項目の集まり（契約など）と、リポジトリの外の項目がある。集まりの中の項目は、
  その集まりを宣言した地図に書く。
- 地図は、`map-` で始まる id の `<a id>` の後の最初の表。間に見出しを一つと文を挟んでよい。

```markdown
<a id="map-docs"></a>

## 地図

| 項目 | 親 | 置き場所 | 前提にする |
| --- | --- | --- | --- |
| 参照 | docs | `reference/` | |
| 解説 | docs | `architecture/` | 参照 |
```

- 列：最初の 4 列は、項目、親、置き場所、前提にする。説明の列を後ろに足してよい。
- 項目：名前はリポジトリの中で一つ。
- 親：一つ上の項目。最上位なら空にする。
- 置き場所：その項目の文書のパスを、地図を書いた文書からの相対パスでバッククォートで囲み、カンマで並べる。`/` で
  終わればディレクトリ。文書は、置き場所がいちばん長く一致する項目に属する。
- 前提にする：同じ親の下の項目（兄弟）だけを、カンマで並べる。前提の前提は、書かなくても前提にしてよい。
- 子を持つ項目の置き場所のうち、子に属さない文書（`overview.md`、索引、全体の解説）は、子と並ぶ「全体」という項目として
  扱う。どの子も全体を前提にしてよく、全体はどの子も前提にしない（子への道は案内のリンクにする）。
- 検査：
  - すべての地図を集めて一つの木にする。項目の名前が重ならないこと、親と前提にする項目があること、親が循環しないこと、
    前提が兄弟であること、前提が循環しないこと、最上位の地図が一つであること、各地図が上の決まりどおりの文書にあること、
    置き場所が実在すること。
  - リポジトリのすべての Markdown がどれかの項目に属すること。
  - 文書から文書へのリンクが、二つの項目が初めて同じ親の下に入る階層で、前提の向きに沿っていること。索引からのリンク、
    ADR へのリンク、ADR からのリンク（ADR は書き換えない）、案内のリンクは除く。
- `python3 tools/check-docs.py --map` は、すべての地図から設計構造行列を出す。
