# 作業の進め方

どのリポジトリでも同じにする、変更と課題の扱い方。

## 変更

- 既定のブランチへの変更は PR 経由で行い、merge commit でマージする。PR のコミットがそのまま残る。
- PR の作成と更新は github スキル（`prctl`）に従う。PR が Issue を片付けるときは、本文に `Closes #<番号>` と書く。

## 課題

やることは GitHub の Issue で管理する。文書には今の姿だけを書くので、予定や残りの作業は置かない。分類は木にせず、
性質ごとに分けて持つ（[ADR 0006](../adr/0006-issues-in-layers.md)）。

| 表すもの | 置き場所 |
| --- | --- |
| やること 1 件 | Issue |
| どこを変えるか | 文書の区切りや関心ごとのラベル（名前はリポジトリの `docs/README.md` にある）。複数付けてよい |
| 何のためか | ラベル `theme:<名前>`。複数付けてよい |
| テーマの狙い、終えたときの状態、進め方 | ラベル `theme` の Issue。メンバーは本文に並べず、ラベルで決まる |
| 何が先か | Issue の依存関係（blocked by） |
| 今の焦点と順番 | ピン留めした「ロードマップ」の Issue。順番を変えるときは本文を書き換える |

- sub-issues は、大きな作業を手順に分けるときだけ使う。
- 検討中の設計は Issue に書き、決まったら ADR にする。
- 気づいているリスクや、壊してはいけない前提は、会話や依頼文だけでなく Issue の本文に書く。作業するエージェントは
  Issue とリポジトリから読み取れることしか知らない。
