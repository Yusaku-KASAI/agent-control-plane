# レビューの扱い方

どのリポジトリでも同じにする、レビューの種類、観点、指摘の書き方と答え方、回し方、差分のレビューと全体のレビューの決まり。
人でもエージェントでも同じに従う。進める順は、手順の[レビューする](../guides/review.md "在りか")と
[レビューを頼んで答える](../guides/request-review.md "在りか")にある。

<a id="kinds"></a>

## 種類

| 種類 | 何を見るか | いつ | 結果の置き場所 |
| --- | --- | --- | --- |
| 差分のレビュー | 一つの変更（PR の差分）と、それが前提にする所、それを前提にする所 | 変更した人が頼むとき：PR を作る前（PR 全体）と、push で PR の head が進んだとき（PR 全体か前回のレビューからの差分かは[回し方](#ways)に、頼まなくてよいときは[差分のレビュー](#diff)にある）。ほかの人の PR を頼まれたとき：PR 全体 | PR のレビュー（[差分のレビュー](#diff)） |
| 全体のレビュー（監査） | 地図の項目を範囲にした、今の姿全体（文書、設計、コード） | 頼まれたとき | 報告の Issue（依頼への回答にはそのリンク）と、そこから作る PR と Issue（[全体のレビュー](#audit)） |

<a id="perspectives"></a>

## 観点

[観点を分けて読む](../../../principles/docs/reference/patterns.md#perspective-based)に倣い、観点ごとに探すものと拠り所を
決めて読む。ここでの観点は、読む人の立場ではなく、関心で分ける。変更の種類や範囲に関わる観点を選び、どれを選んだかを
結果に書く。

| 観点 | 探すもの | 拠り所 |
| --- | --- | --- |
| 別の形 | そもそも別の形の方がよくないか。目的に立ち返った別の手段、より単純な形、一つ上の層や大きな枠組みでの別の解き方 | [前提を問い直す](../../../principles/docs/reference/principles.md#double-loop) |
| 依頼との一致 | 依頼や Issue の目的を満たしているか。目的の外の変更が混ざっていないか | [一つの目的の小さな変更](../../../principles/docs/reference/patterns.md#small-change) |
| 正しさ | 壊れる場面（状態の組み合わせ、失敗や再起動の途中、同時に動くとき、すでにあるデータや設定） | [変更とパターン](changes.md#patterns) |
| 設計 | 今の形の中での、構成要素の責務の分け方、依存の向き | [設計の原則](../../../principles/docs/reference/principles.md)と[設計のパターン](../../../principles/docs/reference/patterns.md) |
| セキュリティ | 秘密の扱い、渡す権限の広さ、許可の既定、守りの重ね方、外から入る値（エージェントが読む内容を含む）の確かめ方 | [守り方の原則](../../../principles/docs/reference/principles.md#security)と、そのリポジトリの契約と ADR |
| 文書とコメント | 今の姿だけか、一か所か、言葉が用語集どおりか、文書の置き場所、文書（地図や構成要素の説明を含む）が実装と食い違っていないか | [書き方](writing.md)、[文書の体系](../architecture/documentation.md)、[文書の形式](formats.md) |
| 検査 | 変更を確かめる検査があるか。機械で確かめられるのに、人が読むことに頼っていないか。足したり変えたりした検査が、守りたい性質を壊した版で落ちるか | [仕組みで守る](../../../principles/docs/reference/principles.md#mechanisms)、[壊した版で検査が落ちることを確かめる](../../../principles/docs/reference/patterns.md#mutation-testing) |

- 機械で確かめられることは、そのリポジトリの検査（CI と同じもの）と文書の検査（`check-docs`）に任せる。読む人は、検査では見つからないものを探す。
- 検査で見つけられたはずの指摘は、検査を足す案も一緒に出す。

<a id="findings"></a>

## 指摘

指摘は次の形で書く。重さの分け方は[指摘に重さを付ける](../../../principles/docs/reference/patterns.md#labeled-comments)に
倣い、ラベルを次の四つにそろえる（必須は blocking の issue、提案は suggestion、質問は question、細部は nitpick に当たる）。

| 持つもの | 書くこと |
| --- | --- |
| 重さ | 必須（壊れる、決まりに反する、依頼を満たさない。差分のレビューでは、直さないと取り込めない）、提案（直すとよくなるが、直すかは変更した人か、全体のレビューを頼んだ人が決める）、質問（意図や前提を確かめたい。答えによっては必須になる。全体のレビューでは、判断が要る点として書く）、細部（言い回しや並びなど、意味の変わらない直し。直したあとはもう一度見ないので、意味が変わりうるなら提案にする。[差分のレビュー](#diff)）のどれか |
| 観点 | 見つけた観点（[観点](#perspectives)の表のどれか） |
| 場所 | ファイルと行、文書の節 |
| 要約 | 何が問題かの一行 |
| 何が問題か | 何が起きるか。抜けている状態や失われうるものは、具体的な組み合わせ（どの軸のどの値か）で示す |
| 拠り所 | 原則、パターン、決まりの名前 |
| 直し方の案 | どう直すか。選択肢があれば並べる |
| 確かめ方 | レビューした人が、指摘をどう確かめたか（読んだだけか、動かしたか）。確かめていない推測は、推測と書く |
| 補足 | ほかに伝えること（任意） |

<a id="record"></a>

## 結果の形

差分のレビューの結果は、次の順に書く。指摘が一つもなければ、表のかわりに「指摘なし」と書く。

1. 範囲（コミットからコミットまで）と、その種類（前回のレビューからの差分か、PR 全体か）。
2. 見た観点と、外した観点（それぞれの理由）。PR 全体の差分のレビューは、すべての観点で見る。
3. 指摘の表：番号、重さ、観点、場所、要約、拠り所。
4. 表の下に、指摘ごとの詳しい中身：何が問題か、直し方の案、確かめ方、補足。

指摘への答えは、指摘の番号ごとに、次のどれかで書く。

| 答え | 添えるもの |
| --- | --- |
| 直した | 直したコミット |
| 直さない | 理由 |
| Issue にした | Issue の番号 |
| 答えた | 質問への答え |

<a id="ways"></a>

## 回し方

変更した人が頼む PR の差分のレビューは、通常か念入りのどちらかで回す。既定は通常で、レビューの回数と時間を抑え、
取り込める所まで来たら打ち切る。打ち切りで残った提案は、あとの全体のレビューで拾う。念入りは、依頼者が頼んだ PR と、
全体のレビューの報告から作る PR に当てる。どちらで回すかは、PR に印を付けて示す（印の付け方は、PR を扱う道具の
決まりにある）。指摘を直すか、直したあとにもう一度見るかは、どちらも[差分のレビュー](#diff)と[終える前](#ending)に従う。

| | 通常 | 念入り |
| --- | --- | --- |
| 当てる PR | 念入りに当てる PR のほか | 依頼者が念入りに頼んだ PR、全体のレビューの報告から作る PR |
| PR を作ったあとの差分のレビュー | 毎回 PR 全体。前回のレビューからの差分のレビューはしない | push で head が進んだら、前回のレビューからの差分。終える前に PR 全体。PR 全体のレビューの指摘を直したら、前回からの差分を挟まず、PR 全体をもう一度 |
| 打ち切り | 必須の指摘のない PR 全体の差分のレビューが 3 回続いたら、そこで打ち切って終えてよい。そのレビューの提案は、範囲の中の直しでも、直さずに終えてよい | なし |
| 読む人 | 一人が、すべての観点で読む | 観点ごとに別の人が、並べて読む（[観点を分けて読む](../../../principles/docs/reference/patterns.md#perspective-based)）。頼んだ人が一つの結果にまとめる |
| 依頼者に返すとき | PR 全体の差分のレビューを 10 回しても終えられないとき | 同じ |

- 打ち切りと上限の回数は、前に数え直したあと（[終える前](#ending)）の PR 全体の差分のレビューで数える。
- 観点ごとに分けた結果をまとめるときは、結果の見た観点に並べた観点をすべて書く。同じ所の同じ問題の指摘は一つにし、
  その観点は見つけた観点の一つにして、ほかに見つけた観点は補足に書く。
- 打ち切りで直さなかった提案には、理由を「打ち切り」で始めて答える。あとの全体のレビューが、それを集めて拾う。
- 全体のレビューは、回し方によらず、観点ごとに分けて読む（[全体のレビュー](#audit)）。

<a id="diff"></a>

## 差分のレビュー

- 変更した人とは別の人か、別の文脈のエージェント（サブエージェントなど）が見る（[別の目で見る](../../../principles/docs/reference/patterns.md#four-eyes)）。
- レビューする人には、依頼の内容、変更の意図、差分を渡す。変更した人がたどった考えは、同じ前提の抜けを引き継がない
  よう渡さない。
- レビューは、コミットしたものに対して行う。結果は、[結果の形](#record)で、見た最後のコミットに付けた PR のレビュー
  （コメントだけのもの）として残す。PR を作る前のレビューは、PR 全体の差分のレビューにし、作ったあとに残す。
- 一回のレビューの指摘への直しは、すべての指摘に答えを決めてから、まとめて push する。指摘ごとに push しない。
- レビューのあとに直したコミットは、まだレビューしていない範囲になる。それを次のレビューに回すかは、次のとおり
  （[直しを任せて見直しを終える](../../../principles/docs/reference/patterns.md#lgtm-with-comments)）。
  細部の指摘は、レビューした人が意味の変わらない直しで済むと判断したもので、その直しはもう一度見なくてよい。
  - 範囲が細部の指摘への直しだけで、直しがその指摘の中に収まる（意味が変わらない）なら、次のレビューに回さない。
    かわりに、その範囲をレビューしない直しとして、範囲の最後のコミットに付けた PR のレビューに残す。指摘への
    答えは、下の答える場所に書く。PR の最初のレビューは省かない。
  - 必須、提案、質問への直しや、指摘への答えではない直しが一つでもあるか、直しで意味（振る舞い、決まり、文書が
    述べること）が変わったら、次のレビューに回す。
- 必須の指摘は直す。提案と細部の指摘は、直さない理由を書いて終えてよい。この PR の範囲（依頼と Issue の目的）の中の
  直しは、この PR で直すか直さない理由を書く。通常の回し方で打ち切ったときは、打ち切りを理由にしてよい。Issue に
  して先に送ってよいのは、範囲の外の直しになるものだけ。
- 指摘には、すべてに[結果の形](#record)の答えを書く。答える場所は次のとおり。直したら、PR の本文も今の中身に
  合わせる。

  | レビュー | 答える場所 |
  | --- | --- |
  | 変更した人が頼み、PR を作る前に行ったもの | そのレビューを残すときに、指摘ごとに書く |
  | 変更した人が頼み、PR を作ったあとに行ったもの | そのレビューへの答えの PR のコメント |
  | ほかの人が PR に付けたもの | その指摘への返信 |

<a id="ending"></a>

### 終える前

変更した人が PR を終えようとする（依頼者に終えたと報告する）前に、PR 全体の差分のレビューをすべての観点で行う。
次のすべてを満たせば終えてよい。

- 最後の PR 全体の差分のレビューのあとに、細部の指摘への直し（レビューしない直し）のほかの変更がない。
- そのレビューに必須の指摘がない。
- そのレビューのすべての指摘に答えている。提案は、直さない理由（通常の打ち切りを含む）を書くか、範囲の外の直しなら
  Issue にして終えてよい。細部は、直さないか、細部の範囲で直して終えてよい。提案や必須を直したら、もう一度 PR 全体の
  差分のレビューを行う。

PR は下書き（draft）で作り、途中のあいだは下書きのままにする（終える前のレビューを求めない）。終えるときに下書きを
外し（ready にし）、そのときに上を満たしていることを確かめる。下書きを外したあとに変更したら、もう一度満たす。
下書きを外したあとに、同じ PR で追加の依頼を受けて作業を続けるときは、下書きに戻す。

終えられないまま、[回し方](#ways)の表の「依頼者に返すとき」に当たったら、そこで止め、残っていることを添えて
依頼者に返す。依頼者が続けるよう言ったら、そこから数え直す。終えてよいと確かめられたときも、そこから数え直す
（追加の依頼で続けるとき）。

<a id="audit"></a>

## 全体のレビュー

進める順は手順の[レビューする](../guides/review.md "在りか")の「全体のレビュー」にある。

- 範囲は地図の項目で分け、選んだ観点で、いつも今の決まりのすべてに照らして読む。その範囲を含む前回の報告に書いた
  見た head より後に変えた決まり（principles と conventions）が分かれば、それに沿っているかを、関わる観点の中の重点として
  足す（その観点を選んでいなければ選ぶ）。変えた決まりが分からなければ、重点を足さないだけで、読み方は変わらない。
- 同じく前回の報告の head より後にマージした PR で、打ち切りで直さなかった提案（[回し方](#ways)）があれば、範囲に
  入るものを、今も当てはまるかを見る重点として足す。
- 落ちた検査は、それぞれ一つの指摘にする（読んで探すものから外す）。
- 指摘は、元の文書とコードで、本当にそうなっているか、ほかの所ですでに決まっていないかを確かめてから報告に入れる。
- 同じ原因の指摘は一つの分類にまとめ、分類ごとに直し方の案を書く。決まりを変えるもの、どちらにも理由がある選択、
  答えによって直し方が変わる質問は、判断が要る点として分け、選択肢（質問なら答えごとの直し方）とおすすめを書く。
- 報告は Issue にする。タイトルは「<範囲>の全体のレビュー」で始め、本文には範囲、観点（前回からの決まりの変更を
  重点として足したか、足せなかったならそのことを含む）、見た既定のブランチの head、検査の結果、分類ごとの指摘と
  直し方の案、判断が要る点を書く。直す人は、この Issue とリポジトリから読み取れることだけで直せるようにする
  （[課題](issues.md "在りか")）。
- 範囲ごとに、観点ごとに分けて読む人を並べる（[観点を分けて読む](../../../principles/docs/reference/patterns.md#perspective-based)）。
- 判断が要る点の答えを受けてから直す。直しは一つの目的ごとの PR にし、本文に全体のレビューによる直しであることを
  書き、念入りに回す（[回し方](#ways)）。今は直さないものは Issue に積む。
- 検査で見つけられたはずの指摘には、検査を足す。同じ種類の指摘が続く決まりは、決まりの書き方か届け方を見直す
  （[前提を問い直す](../../../principles/docs/reference/principles.md#double-loop)）。
