# レビューの扱い方

どのリポジトリでも同じにする、レビューの種類、観点、指摘の書き方と答え方、進め方。人でもエージェントでも同じに
従う。

<a id="kinds"></a>

## 種類

| 種類 | 何を見るか | いつ | 結果の置き場所 |
| --- | --- | --- | --- |
| 差分のレビュー | 一つの変更（PR の差分）と、それが前提にする所、それを前提にする所 | 変更した人が頼むとき：PR を作る前と、push で PR の head が進んだとき（前回のレビューからの差分）。ほかの人の PR を頼まれたとき：PR 全体 | PR のレビュー（[差分のレビュー](#diff)） |
| 全体のレビュー（監査） | 地図の項目を範囲にした、今の姿全体（文書、設計、コード） | 頼まれたとき | 報告の Issue（依頼への回答にはそのリンク）と、そこから作る PR と Issue（[全体のレビュー](#audit)） |

<a id="perspectives"></a>

## 観点

[観点を分けて読む](../../../principles/docs/reference/patterns.md#perspective-based)に倣い、観点ごとに探すものと拠り所を
決めて読む。ここでの観点は、読む人の立場ではなく、関心で分ける。変更の種類や範囲に関わる観点を選び、どれを選んだかを
結果に書く。

| 観点 | 探すもの | 拠り所 |
| --- | --- | --- |
| 別の形 | そもそも別の形の方がよくないか。目的に立ち返った別の手段、より単純な形、一つ上の層や大きな枠組みでの別の解き方 | [前提を問い直す](../../../principles/docs/reference/principles.md#double-loop) |
| 依頼との一致 | 依頼や Issue の目的を満たしているか。目的の外の変更が混ざっていないか | [一つの目的の小さな変更](../../../principles/docs/reference/patterns.md#small-change) |
| 正しさ | 壊れる場面（状態の組み合わせ、失敗や再起動の途中、同時に動くとき、すでにあるデータや設定） | [変更とパターン](changes.md#patterns) |
| 設計 | 今の形の中での、構成要素の責務の分け方、依存の向き | [設計の原則](../../../principles/docs/reference/principles.md)と[設計のパターン](../../../principles/docs/reference/patterns.md) |
| セキュリティ | 秘密の扱い、渡す権限の広さ、許可の既定、守りの重ね方、外から入る値（エージェントが読む内容を含む）の確かめ方 | [守り方の原則](../../../principles/docs/reference/principles.md#security)と、そのリポジトリの契約と ADR |
| 文書とコメント | 今の姿だけか、一か所か、言葉が用語集どおりか、文書の置き場所、文書（地図や構成要素の説明を含む）が実装と食い違っていないか | [書き方](writing.md)、[文書の体系](../architecture/documentation.md)、[文書の形式](formats.md) |
| 検査 | 変更を確かめる検査があるか。機械で確かめられるのに、人が読むことに頼っていないか | [仕組みで守る](../../../principles/docs/reference/principles.md#mechanisms) |

- 機械で確かめられることは、そのリポジトリの検査（CI と同じもの）に任せる。読む人は、検査では見つからないものを探す。
- 検査で見つけられたはずの指摘は、検査を足す案も一緒に出す。

<a id="findings"></a>

## 指摘

指摘は次の形で書く。重さの分け方は[指摘に重さを付ける](../../../principles/docs/reference/patterns.md#labeled-comments)に
倣い、ラベルを次の四つにそろえる（必須は blocking の issue、提案は suggestion、質問は question、細部は nitpick に当たる）。

| 持つもの | 書くこと |
| --- | --- |
| 重さ | 必須（壊れる、決まりに反する、依頼を満たさない。差分のレビューでは、直さないと取り込めない）、提案（直すとよくなるが、直すかは変更した人か、全体のレビューを頼んだ人が決める）、質問（意図や前提を確かめたい。答えによっては必須になる。全体のレビューでは、判断が要る点として書く）、細部（言い回しや並びなど、意味の変わらない直し）のどれか |
| 場所 | ファイルと行、文書の節 |
| 何が問題か | 何が起きるか。抜けている状態や失われうるものは、具体的な組み合わせ（どの軸のどの値か）で示す |
| 拠り所 | 原則、パターン、決まりの名前 |
| 直し方の案 | どう直すか。選択肢があれば並べる |
| 確かめ方 | レビューした人が、指摘をどう確かめたか（読んだだけか、動かしたか）。確かめていない推測は、推測と書く |

<a id="diff"></a>

## 差分のレビュー

- 変更した人とは別の人か、別の文脈のエージェント（サブエージェントなど）が見る（[別の目で見る](../../../principles/docs/reference/patterns.md#four-eyes)）。
- レビューする人には、依頼の内容、変更の意図、差分を渡す。変更した人がたどった考えは、同じ前提の抜けを引き継がない
  よう渡さない。
- レビューは、コミットしたものに対して行う。結果は、見た範囲（コミットからコミットまで）と指摘を、見た最後のコミットに
  付けた PR のレビュー（コメントだけのもの）として残す。PR を作る前のレビューは、作ったあとに残す。
- レビューのあとに直したコミットは、次のレビューの範囲になる。
- 指摘には、直したならどのコミットで直したかを、直さないなら理由を書いて答える。答える場所は次のとおり。直したら、
  PR の本文も今の中身に合わせる。

  | レビュー | 答える場所 |
  | --- | --- |
  | 変更した人が頼み、PR を作る前に行ったもの | そのレビューを残すときに、指摘の後ろに書く |
  | 変更した人が頼み、PR を作ったあとに行ったもの | 直した push の変更点のコメント。直しがなければ PR のコメント |
  | ほかの人が PR に付けたもの | その指摘への返信 |

<a id="audit"></a>

## 全体のレビュー

1. **範囲と観点を決める**：範囲は地図の項目で分ける。観点は上の表から選ぶ。範囲は、選んだ観点で、いつも今の
   決まりのすべてに照らして読む。その範囲を含む前回の報告があり、そこに書いた見た head より後に変えた決まり
   （principles と conventions）が分かれば、それに沿っているかを、関わる観点の中の重点として足す（その観点を選んで
   いなければ選ぶ）。変えた決まりが分からなければ、重点を足さないだけで、読み方は変わらない。
2. **検査を回す**：先に、そのリポジトリの検査を回す。落ちた検査は、それぞれ一つの指摘にする（読んで探すものから外す）。
3. **範囲ごとに読む**：範囲ごとに、別の目で読む。手分けするときは、範囲が重ならないように分ける。
4. **指摘を確かめる**：指摘ごとに、本当にそうなっているか、ほかの所ですでに決まっていないかを、元の文書とコードで
   確かめ、誤りを除く。
5. **まとめる**：同じ原因の指摘を一つの分類にまとめ、分類ごとに直し方の案を書く。決まりを変えるもの、どちらにも
   理由がある選択、答えによって直し方が変わる質問は、判断が要る点として分け、選択肢（質問なら答えごとの直し方）と
   おすすめを書く。
6. **報告して直す**：報告を Issue にし、判断が要る点の答えを受けてから直す。報告のタイトルは「<範囲>の全体の
   レビュー」で始め、本文には範囲、観点（前回からの決まりの変更を重点として足したか、足せなかったならそのことを
   含む）、見た既定のブランチの head、検査の結果、分類ごとの指摘と直し方の案、判断が要る点を書く。直す人は、
   この Issue とリポジトリから読み取れることだけで直せるようにする（[課題](issues.md "在りか")）。
   全体のレビューの中でファイルを変えるのはこの段だけ。直しは一つの目的ごとの PR にし、本文に全体のレビューに
   よる直しであることを書く。今は直さないものは Issue に積む。
7. **仕組みに戻す**：検査で見つけられたはずの指摘には、検査を足す。同じ種類の指摘が続く決まりは、決まりの書き方か
   届け方を見直す（[前提を問い直す](../../../principles/docs/reference/principles.md#double-loop)）。
