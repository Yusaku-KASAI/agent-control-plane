# 書き方

コード中のコメント、コミットメッセージ、PR に何を書くかと、どの書きものにも書かないもの。
理由をどこに置くかは[文書の体系](../architecture/documentation.md#reasons)に、文書の形は[形式](formats.md "在りか")にある。どの言語で書くかは、リポジトリの CLAUDE.md が決める。

<a id="comments"></a>

## コード中のコメント

- 書かないものは、[書かないもの](#not-to-write)にある。
- コードは自己説明的に書き、コメントはできる限り削る。コードから読み取れることは書かない。
- コメントに残すのは、コードで表しきれない制約や、その理由だけ。
- 構成、方針、使い方はコメントではなく文書に書く。コメントが大きくなるようなら、文書か ADR に移す。
- 変更の履歴や以前の姿は書かない。

<a id="commits"></a>

## コミットメッセージ

- 1 行目に、何をしたかを一文で書く。
- 本文に、なぜそうしたか（変更の理由と経緯）を書く。
- 書かないものは、[書かないもの](#not-to-write)にある。

<a id="pull-requests"></a>

## PR

| | 答えること | 読み手 |
|---|---|---|
| タイトルと本文 | この PR は今何か：何をなぜ変えるか、検討した別の形、当てはめた決まり、どう確かめたか、確かめていないこと、残っていること | 初めて開く人 |
| コメント | 前回からの変更：この push で何をなぜ変えたか | 前回までを読んだ人 |

- 書かないものは、[書かないもの](#not-to-write)にある。
- 本文は、次の節をこの順に一度ずつ持ち、どれも空にしない。節の中は自由に書く。ほかの節（残っていることなど）は、
  どこに足してもよい。見出しのない `Closes #<番号>` などの行と署名の行は、節の中身に数えない。

  | 節 | 書くこと |
  | --- | --- |
  | `## 何を変えるか` | 何をなぜ変えるか |
  | `## 検討した別の形` | 選んだ形のほかに考えた形（目的に立ち返った別の手段、より単純な形、一つ上の枠組みでの解き方）と、選ばなかった理由。挙がらなければ、別の形がない理由。ADR があれば、その Alternatives へのリンクと一行の要約でよい |
  | `## 当てはめた決まり` | 判断の軸にした原則、パターン、決まりの名前と、それぞれをどこにどう当てはめたか |
  | `## どう確かめたか` | 検査、レビュー、手で試したこと |
  | `## 確かめていないこと` | 確かめていないこと。なければ「なし」と書く |

- 本文は、ブランチの今の中身を説明し続ける。追記せず、今のブランチの姿に合わせて書き換える。経緯はコメントと
  コミットメッセージに任せる。
- タイトルも本文と同じく今の PR 全体を表す。範囲が広がったり変わったりしたら直す。
- push で中身が変わったら、本文を書き換え、コメントを書く。コメントには理由を書く。
- PR が依頼の Issue を閉じるときは、本文に `Closes #<番号>` と書き、閉じないとき（[依頼の範囲](issues.md#scope)）は
  `Refs #<番号>` と書く。`Closes` と `Refs` の行には依頼の Issue だけを置き、ほかの Issue には文の中で触れる。
- ほかの PR に重ねた PR（[変更](changes.md#changes)）は、本文に、どの PR の上かと、マージの順（下から）を書く。

<a id="not-to-write"></a>

## 書かないもの

Issue（本文とコメント）、PR（本文、コメント、レビュー）、コミットメッセージ、コード中のコメント、リポジトリの文書
（ADR を含む）は、リポジトリと同じ範囲に見える（公開のリポジトリなら誰にでも）。そのどれにも、秘密、個人の情報、
見える範囲の狭い場所（非公開のチャンネルなど）の中身、まだ公にしない考えは、その範囲に出してよいと分かっているとき
だけ書く。分からなければ答えにとどめ、書いてよいかを依頼者に確かめる。認証情報（トークン、鍵、パスワード）の値は、
答えも含めてどこにも書かず、在りか（環境変数の名前やファイルのパス）で指す。
