# 設計の原則

設計で拠り所にする原則の一覧。文書にもコードにも、リポジトリ、ディレクトリ、ファイル、関数のどの粒度にも
当てはまる。載せるのは、名前と出典があり、広く良いとされている原則だけ。原則を特定の問題への形にしたものは、[設計のパターン](patterns.md "在りか")にある。ここには原則そのものと一般的な
当てはめ方だけを書く。どこでどう使っているかは、使う側が書き、ここを指す。

## 決め方

<a id="established"></a>

### 確立した考え方に拠る（Stand on Established Practice）

- **原則**：設計、文書、手順、進め方を決めるときは、まず一般に良いとされる確立した考え方（名前と出典のある原則、
  パターン、標準）を探し、それに沿って決め、その名前を挙げる。
- **何のため**：多くの場面で確かめられた解を使える。名前が共有の語彙になり、なぜそう決めたかを短く伝えられる。
- **当てはめ方**：この一覧と[設計のパターン](patterns.md "在りか")から探す。なければ外の確立した考え方を探し、使ったら一覧に
  足す。当てはまらないときは、どこが合わないかを書いて外す。
- **よくある違反**：その場の思いつきで決める。名前だけを挙げて、中身はそれに沿っていない。

<a id="double-loop"></a>

### 前提を問い直す（Double-Loop Learning）

- **原則**：今の枠組みの中で誤りを直す（シングルループ）だけでなく、枠組みと前提そのものを問い直し、より良い形が
  ないかを探す（ダブルループ）。
- **何のため**：枠組みの中の直しを重ねても、枠組みそのものが合っていなければ良くならない。前提を変えると、直しが
  まとめて要らなくなることがある。
- **当てはめ方**：決める前と見直すときに、次の問いを通す。目的に立ち返ると、別の手段の方がよくないか。より単純な
  形で足りないか（KISS）。一つ上の層や、より大きな枠組みから見ると、別の置き場所や分け方の方がよくないか。
  別の形が見つかったら、今の形と並べて比べ、選ばなかった方も理由とともに残す（ADR の Alternatives など）。
- **よくある違反**：指摘を一つずつ直し続け、同じ種類の指摘が続く原因（決まりや構成）を見ない。頼まれた手段を、
  目的を確かめずにそのまま作る。

## 分け方

<a id="soc"></a>

### 関心の分離（Separation of Concerns）

- **原則**：変わる理由や知識の種類が違うものを、別の単位に分ける。
- **何のため**：一つを変えるとき、ほかを読まず、壊さずに済む。
- **当てはめ方**：単位（リポジトリ、ディレクトリ、文書、パッケージ）ごとに「何の関心か」を一つ言えるようにする。
  言えないなら分ける。
- **よくある違反**：一つの文書に、手順、仕組みの説明、判断の理由が同居する。

<a id="srp"></a>

### 単一責任（Single Responsibility）

- **原則**：一つの単位は、変わる理由を一つだけ持つ。
- **何のため**：単位の名前と中身が一致し、どこを直せばよいかが一つに決まる。
- **当てはめ方**：単位の責務を 1 文で書く。書けないか、「と」でつながるなら分ける。
- **よくある違反**：「その他」「共通」「utils」のような、何でも入る単位。

<a id="cqs"></a>

### コマンドとクエリの分離（Command–Query Separation）

- **原則**：一つの操作は、状態を変えるコマンドか、答えを返すクエリのどちらかにする。答えを返す操作は状態を変えない。
  出典は Bertrand Meyer, *Object-Oriented Software Construction*（1988）。
- **何のため**：問い合わせは何度呼んでも答えも状態も変わらないので、確かめるために呼び直しても壊れない。状態が
  変わる所が、コマンドを呼んだ所に限られる。
- **当てはめ方**：判定や問い合わせの関数は、記録、印、数などを書かない。答えによって状態を変えるときは、呼ぶ側が
  答えを見てから、別のコマンドを呼ぶ。ただし、確かめることと変えることが不可分でないと壊れる操作（取り出す、
  比べて入れ替える、ロックを取る）は、同時に動くとその間に状態が変わるので、一つのコマンドにまとめ、その結果を
  返す。
- **よくある違反**：答えを返す関数が、ついでに記録やキャッシュや既読の印を書き、呼び直すたびに答えや状態が変わる。
  逆に、不可分であるべき「確かめて変える」を、クエリとコマンドに分ける。

<a id="cohesion"></a>

### 高凝集・疎結合（High Cohesion, Low Coupling）

- **原則**：一緒に変わるものは近くに集め、別々に変わるものの間のつながりは少なく、決まった形（インターフェース、
  契約）にする。
- **何のため**：変更が一か所に収まり、つながりの先に波及しない。
- **当てはめ方**：同時に直すことが多いものを同じ単位に置く。単位の間は、相手の内部ではなく公開された形にだけ
  依存する。
- **よくある違反**：ほかの単位の内部の細部（型、節の書き方）を前提にする。

<a id="bounded-context"></a>

### 境界づけられた文脈（Bounded Context）

- **原則**：言葉と模型が一貫して通じる範囲を区切りとして決め、区切りの中では一つの意味で使う。区切りの間の
  関係（Context Map）は明示する。
  区切りの間の関係の形は、パターンの[使う側に届く契約](patterns.md#published-language "在りか")や[共有の核](patterns.md#shared-kernel "在りか")にある。
- **何のため**：区切りごとに独立して考え、変えられる。区切りをまたぐところだけを注意深く扱えばよい。
- **当てはめ方**：誰がその知識を使い、誰が持つかで区切る。区切りの間の約束は、使う側から読める場所に置く。
- **よくある違反**：読めない読み手がいる場所に、その読み手に要る知識を置く。

<a id="dependency-rule"></a>

### 依存の向き（Dependency Rule）

- **原則**：依存は一方向にだけ向ける。中心（変わりにくく、多くから使われるもの）は外側（変わりやすく、個別のもの）
  を知らない。外側は中心が決めた形に合わせる。
- **何のため**：外側を差し替えても中心が変わらない。中心を外側なしで確かめられる。
- **当てはめ方**：単位の間の依存の向きを決め、逆向きの依存を検査で禁じる。事実を集める外側と、判定する内側を分ける。
  入れ子の構成では、向きを階層ごとに決める（[階層的分解](#hierarchy)）。A が B に依存するかは、B を変えたときに A の
  見直しが要るかで決め、参照しているだけでは依存にしない（コナーセンス。Meilir Page-Jones, *What Every Programmer Should
  Know About Object-Oriented Design*, 1995）。
- **よくある違反**：中心が特定の技術や個別の事情を知っている。外側が判定を持つ。

<a id="acyclic"></a>

### 非循環依存（Acyclic Dependencies Principle）

- **原則**：単位の間の依存に循環を作らない。依存をたどって自分に戻ってこない。
- **何のため**：循環した単位は、一つだけを取り出して理解することも、変えることも、試すこともできず、事実上一つの塊になる。
- **当てはめ方**：依存を向きのあるグラフとして書き、循環があれば、共通部分を切り出して両方がそれに依存するか、
  片方の依存を契約に置き換える（[依存関係の逆転](#dip)）。
- **よくある違反**：二つの文書が互いを前提にして説明し合い、どちらから読んでも分からない。

<a id="stable-dependencies"></a>

### 安定依存（Stable Dependencies Principle）

- **原則**：変わりにくいものに依存する。依存の向きは、変わりやすいものから変わりにくいものへ向ける。
- **何のため**：変わりやすいものが変わっても、それに依存する単位がないので波及しない。
- **当てはめ方**：多くから前提にされるもの（原則、決まり、契約、用語）ほど、変わりにくく小さく保つ。個別の事情は
  依存の末端に置く。
- **よくある違反**：多くの単位が前提にする文書に、よく変わる個別の事情が書かれている。

<a id="dip"></a>

### 依存関係の逆転（Dependency Inversion Principle）

- **原則**：作る側と使う側は、互いの中身ではなく、間に置いた抽象（インターフェース、契約）に依存する。
- **何のため**：作る側の中身が変わっても、契約が変わらなければ使う側は影響を受けない。依存の向きを、実行の向きと
  関係なく決められる。
- **当てはめ方**：区切りの間の受け渡しを契約として独立した項目にし、両側がそれを前提にする。契約は作る側と使う側の
  どちらにも属さない項目として扱い、置き場所は使う側から読める所にする。
- **よくある違反**：使う側が、作る側の実装の説明を読まないと何が渡されるか分からない。

<a id="hierarchy"></a>

### 階層的分解（Hierarchical Decomposition）

- **原則**：全体を項目に分け、各項目をさらに項目に分ける、という入れ子で構成を表す。関係（依存など）は階層ごとに
  決め、下の階層の関係は、上の階層で決めた関係の範囲の中でだけ決める。二つのものの関係は、それらが初めて同じ親の
  下に入る階層（共通の祖先）で、その親の下の項目どうしの関係として判断する。
- **何のため**：上の階層を見れば、下の階層の関係の大枠が分かる。細部を変えても、上の階層の関係を崩さない限り全体は
  崩れない。
- **当てはめ方**：各階層に、その中の項目と、項目どうしの依存の向きを書く。細かい単位どうしの関係が上の階層の向きに
  反していないかを、共通の祖先の階層で確かめる。
- **よくある違反**：下の階層の細部が、上の階層で決めた向きと逆の項目を前提にしている。

<a id="siblings"></a>

### 兄弟をそろえる（MECE、ピラミッド原則）

- **原則**：同じ親の下に並ぶ項目は、同じ種類で同じ粒度にし、互いに重ならず、合わせて親を尽くすようにする。出典は
  Barbara Minto, *The Pyramid Principle*（1987）の MECE と、要点を束ねる階層の組み方。
- **何のため**：並べたこと自体が「これらは同列の部分だ」という主張になる。そろっていれば、並びを見るだけで全体が分かり、
  抜けや紛れ込みに気づける。
- **当てはめ方**：項目を並べるたびに、種類と粒度がそろっているか、重なりや抜けがないかを確かめる。そろわないものは、
  別の階層か別の親に移す。
- **よくある違反**：同じ階層に、区切りと個々の文書が並ぶ。置き場所が同じだけで、関係の上では別の階層のものが並ぶ。

## 一意さ

<a id="ssot"></a>

### 単一の情報源（Single Source of Truth）と DRY

- **原則**：一つの事実は一か所にだけ書き、ほかはそこを参照する。
- **何のため**：直すときに一か所で済み、食い違いが生まれない。
- **当てはめ方**：事実ごとに持ち主を一つ決める。二か所に書きたくなったら、片方をリンクにする。
- **よくある違反**：同じ一覧を複数の入口に置く。

<a id="glossary"></a>

### ユビキタス言語と用語集（Ubiquitous Language, Glossary）

- **原則**：言葉の意味を一か所で定め、文書、コード、会話で同じ意味で使う。一つの言葉は一つの意味。
- **何のため**：読み手によって解釈が分かれない。
- **当てはめ方**：区切りの中で使う言葉は、その区切りで定める。複数の意味に取れる言葉は、使う前に定める。
- **よくある違反**：一つの言葉が、文脈によって別のものを指す。

## 約束

<a id="schema-first"></a>

### スキーマを先に（Schema-First, Contract-First）

- **原則**：中身を作る前に、形（スキーマ、契約、型）を決めて書き、中身はその形に合わせる。合っていることは
  検査で確かめる。
- **何のため**：作る側と使う側が、相手の中身を知らずに独立して進められる。食い違いが機械で見つかる。
- **当てはめ方**：受け渡すもの（入出力、文書の節、記録の項目）の形を先に書く。実装と形を照らす検査を置く。
- **よくある違反**：実装を読まないと何が渡されるか分からない。

## 時間

<a id="present-state"></a>

### 今と経緯を分ける

- **原則**：今の姿、判断の理由、これからの道筋、これまでの経緯を、それぞれ別の場所に書く。今の姿を書く場所には
  今だけを書く。
- **何のため**：今の姿を知りたい人が、経緯や予定を読み分けずに済む。理由や経緯は、要るときにだけたどれる。
- **当てはめ方**：書こうとしていることが、今・理由・道筋・経緯のどれかを決めてから置き場所を選ぶ。今の姿の説明を
  直すときは、追記せず書き換える。
- **よくある違反**：今の姿の説明に「以前は」「今後は」が混ざる。

## 見せ方

<a id="progressive-disclosure"></a>

### 段階的な開示（Progressive Disclosure）

- **原則**：最初に要るものだけを見せ、詳しいものは必要になったときにたどれるようにする。
- **何のため**：読み手（人もエージェントも）の注意と文脈の量は限られる。
- **当てはめ方**：入口は短い一覧と行き先にする。いつも読まれるものほど短くする。読み手が先に要るもの（結論や判断の
  軸）を先に書く（BLUF、Bottom Line Up Front。米陸軍の文書の規則 AR 25-50）。
- **よくある違反**：いつも読まれる文書に詳細を書き込む。

<a id="information-scent"></a>

### 情報の匂い（Information Scent）

- **原則**：読み手は、リンクや見出しの周りの書き方から、その先に何があり、今それが要るかを判断してたどる。たどって
  ほしい先には、それが分かる手がかり（匂い）を付ける。出典は Pirolli と Card の情報採餌理論（*Information Foraging*,
  Psychological Review, 1999）。
- **何のため**：[段階的な開示](#progressive-disclosure)で詳しいものを先に置いても、読み手がそこへたどらなければ届かない。
  人もエージェントも、手がかりの弱いリンクはたどらない。
- **当てはめ方**：リンクや見出しには、たどる先に何があり、いつ要るかが分かる語を添える。一つのリンクに、置いた目的と
  別の目的での読みを期待しない。
- **よくある違反**：リンクの文字が「こちら」「詳しくは」だけで、行き先が分からない。見出しが中身を表していない。

<a id="sufficiency"></a>

### 必要十分（Necessary and Sufficient）

- **原則**：持つのは、その単位の目的に要るものだけにする。要らないもの、ほかに持ち主があるもの、古くなったものは、
  消すか持ち主へ移す。表し方は短くするが、明確さを優先する。意味が一通りに読めて正確であることを、短さや小ささより
  優先し、そのために要る構成、定義、前提、条件や範囲は削らない。
- **何のため**：量が減るほど、読み手（人もエージェントも）は要ることに集中できる。一方で、意図や前提まで削ると、
  読み手が推測で補うことになり、かえって分かりにくく、誤解を生む。
- **当てはめ方**：減らすのは、重複、経緯、置き場所違い、要らないものだけにする。表し方を短くするのは、意味、条件、
  範囲が変わらず、別の読み方ができないときだけで、迷ったら明確な方を取る。
  - 文書：言い回しは短く、ただし明確に。見出し、表、言葉の定義、前提は削らない。
  - コード：要るまで作らず、使われていないものは消す（YAGNI）。名前や処理を縮めて意図を分からなくしない。
  - 指示や設定：いつも効くものほど絞る。上限に当たったら、表し方を詰めるのではなく、載せるものを減らすか移す。
- **よくある違反**：念のために同じことを何か所にも持つ。逆に、短く小さくしようとして主語や条件や前提を省き、文脈を
  知らないと分からないものや、二通りに読めるものにする。

## 確かめ方

<a id="mechanisms"></a>

### 仕組みで守る（Mechanisms over Prompts）

- **原則**：守らせたいことは、頼むより、検査や hook などの仕組みで確かめる。仕組みにできないものだけを指示で頼む。
- **何のため**：人もエージェントも、頼まれたことを忘れる。
- **当てはめ方**：決まりごとに、検査にできないかをまず考える。できなければ、その決まりが要る場面で必ず目に入る形で
  短く書く（すべての場面で要るならいつも読まれる場所に、特定の作業で要るならその作業の手順に）。読ませるだけで
  使われないときは、使ったことを出力に出させ、出ていなければ先へ進めない形にする（強制機能、Forcing Function。
  Donald Norman, *The Design of Everyday Things*。初版は 1988 年の *The Psychology of Everyday Things*）。
- **よくある違反**：検査できる決まりを、文書に書くだけで済ませる。

<a id="small-experiments"></a>

### 小さく試して確かめる（PDCA、Build–Measure–Learn）

- **原則**：効くかどうかが分からない変更は、小さく試し、結果を測ってから広げたり仕組みにしたりする。守ると決まった
  決まりの守らせ方は[仕組みで守る](#mechanisms)による。出典は Shewhart と Deming のサイクル（PDCA。
  W. Edwards Deming, *Out of the Crisis*, 1986）と、Eric Ries の Build–Measure–Learn（*The Lean Startup*, 2011）。
- **何のため**：確かめていない仮説の上に検査や構成を積むと、仮説が外れたときにまとめて作り直すことになる。
- **当てはめ方**：変えることが効くかを、何で測るか（記録、数、観察）を先に決める。最初の変更は、仮説を試せる最小の
  範囲にする。測った結果を見てから、範囲を広げるか、検査や仕組みにするかを決める。
- **よくある違反**：確かめていない仮説の上に、仕組みや大きな構成を先に作る。測らずに、入れたことで効いたとみなす。

<a id="security"></a>

## 守り方

<a id="least-privilege"></a>

### 最小権限（Principle of Least Privilege）

- **原則**：主体（人、プロセス、エージェント）には、その仕事に要る最小の権限だけを渡す。出典は Saltzer と Schroeder の
  設計原則（The Protection of Information in Computer Systems、1975）。
- **何のため**：主体が誤ったり乗っ取られたりしたときに起きうることが、渡した権限の範囲に収まる。
- **当てはめ方**：主体ごとに、何に対して何をするかを書き出し、それだけを渡す。権限は対象と操作で絞り、期限を短くする。
  渡した権限でできることは、すべて行われうる前提で範囲を決める。
- **よくある違反**：手間を省くために、広い権限や期限のない認証情報を一つ作って使い回す。

<a id="fail-safe-defaults"></a>

### 拒否を既定にする（Fail-Safe Defaults）

- **原則**：許可したものだけを通し、ほかはすべて拒む。出典は Saltzer と Schroeder の設計原則（The Protection of
  Information in Computer Systems、1975）。
- **何のため**：考え漏らしたものは拒まれる側に倒れる。漏れは使えないことで気づけるが、許しすぎは気づかれにくい。
- **当てはめ方**：拒否の一覧（denylist）ではなく、許可の一覧（allowlist）で書く。設定がないとき、確かめに失敗した
  ときも、拒む側に倒す。
- **よくある違反**：危ないものを並べて拒み、ほかを通す。設定が空のときに、すべてを許す。

<a id="defense-in-depth"></a>

### 多層の防御（Defense in Depth）

- **原則**：一つの守りに頼らず、同じ脅威に対して性質の違う守りを重ね、一つが破られても次で止める。出典は NIST の
  用語集（SP 800-53 など）。
- **何のため**：どの守りにも抜けがある。重ねておけば、一つの抜けがそのまま被害にならない。
- **当てはめ方**：守りたいものごとに、どの層（入口での確認、権限、隔離、人の確認など）で止めるかを並べる。層は互いを
  前提にしない（一つの層が破られた前提で、次の層を決める）。どの層でも止まらない影響があれば、それを書いておく。
- **よくある違反**：「中は安全」として、境界の内側では何も確かめない。同じ仕組みを二度重ねて、層を重ねたつもりになる。

<a id="untrusted-input"></a>

### 外から入る値を信用しない（Treat Input as Untrusted）

- **原則**：信頼の境界の外から入る値（利用者の入力、外部の API の応答、読んだ文書やメッセージ）は、確かめるまで
  信用しない。LLM のエージェントでは、読んだ内容に紛れた指示（プロンプトの注入、Prompt Injection）も外から入る値に
  含める。出典は OWASP の Input Validation Cheat Sheet と、OWASP Top 10 for LLM Applications の Prompt Injection と
  Improper Output Handling。
- **何のため**：外から入る値は、書いた人の意図どおりに処理を動かせる。確かめずに使うと、その人に処理の権限を渡すことに
  なる。
- **当てはめ方**：信頼の境界を決め、境界をまたぐ値は、許した形かを確かめてから使う。命令やクエリは、値をつなげて
  組み立てない。エージェントに外の内容を読ませるときは、内容に紛れた指示で動かされうる前提で、渡す権限を決め
  （[最小権限](#least-privilege)）、エージェントの出力も外から入る値として扱う。
- **よくある違反**：受け取った値をそのままコマンドやクエリに埋め込む。エージェントが読む内容を、依頼した人の指示と
  同じ重みで扱う。
