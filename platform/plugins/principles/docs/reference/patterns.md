# 設計のパターン

よくある問題への、名前の付いた解き方の一覧。[設計の原則](principles.md "在りか")が「何を大事にするか」なのに対し、
パターンは「この問題にはこう組む」という形で、原則を具体的な形にしたもの。載せるのは、名前と出典があり、広く使われているパターンだけ。ここにはパターンそのものと一般的な
使いどころだけを書く。どこでどう当てはめたかは、使う側が書き、ここを指す。

各パターンは、解く問題、形、使いどころ、よくある失敗、拠り所の原則で書く。組み合わせて使うパターンがあれば、
それも書く。

## 構造

<a id="layered-architecture"></a>

### 層に分けた構成（Clean Architecture、Hexagonal）

- **解く問題**：技術の詳細（DB、外部 API、入出力）に中心の判断が引きずられ、差し替えも試験もしにくい。
- **形**：中心（ドメイン、ユースケース）と外側（アダプター、入口）を層に分ける。中心は外側に要るもの（ポート）を
  インターフェースとして決め、外側がそれを実装する。部品を組み立てる場所（main）だけが全部を知る。
- **使いどころ**：外部とのやり取りが多く、中心の判断をそれと分けて確かめたいとき。
- **よくある失敗**：中心がライブラリの型を使う。アダプターが判定を持つ。層を飛ばして依存する。
- **拠り所の原則**：[依存の向き](principles.md#dependency-rule)、[関心の分離](principles.md#soc)。

<a id="facts-and-judgement"></a>

### 事実と判定を分ける（Functional Core, Imperative Shell）

- **解く問題**：外部を読みながら判定すると、判定が散らばり、試験に外部が要り、抜けている場合に気づけない。
- **形**：外部を読む部分は事実だけを集めて返し、意味づけをしない。判定は事実だけを受け取る一か所の関数にし、
  振る舞いも人への知らせの文面も、その判定の結果から作る。
- **使いどころ**：状態によって振る舞いが変わる処理、消すか残すかを決める処理。
- **よくある失敗**：アダプターの中に「これは片付いた」のような判定が入る。同じ判定を、振る舞いと文面で別々の
  条件式に書く。判定の関数が状態を書き、呼び直すと答えが変わる。
- **拠り所の原則**：[依存の向き](principles.md#dependency-rule)、[SSOT](principles.md#ssot)、
  [コマンドとクエリの分離](principles.md#cqs)。

<a id="state-axes"></a>

### 状態を軸で洗い出す

- **解く問題**：状態の組み合わせを思いつくままに扱うと、抜けた組み合わせ（多くは失われる作業や誤った削除）に
  気づけない。
- **形**：書く前に、状態を軸に分ける。軸は、その対象の上で値が互いに重ならず、すべての場合を尽くす。
  - 同時に成り立ちうる性質は、「ある / ない」の別の軸にする。
  - 一つの値に絞るものは、優先順位を決めて「上から順に最初に当たるもの」と定義する。
  - 軸が定義される範囲（「注文がある」「支払い済みである」など、その軸が意味を持つ条件）を書く。

  判定は軸の値だけで書く。軸と判定は表にし、試験もその表の組み合わせで書く。
- **使いどころ**：状態によって振る舞いが変わる処理全般。特に、消す、残す、知らせるを決める処理。
- **よくある失敗**：値が重なる軸（同時に成り立ちうる「支払い済み / 発送済み」を一つの軸の値にする）。どれにも当たらない
  場合が残る軸。
- **拠り所の原則**：[スキーマを先に](principles.md#schema-first)、[関心の分離](principles.md#soc)。

## 区切りの間

<a id="published-language"></a>

### 使う側に届く契約（Published Language）

- **解く問題**：作る側の内部を読まないと何が渡されるか分からず、読めない使い手は推測で動く。
- **形**：区切りの間で受け渡すもの（入出力、環境、ファイル、言葉）を契約として書き、使う側から読める場所に置く。
  作る側は契約に合わせて作る。
- **使いどころ**：作る側と使う側が別の区切りにあり、使う側が作る側の内部を読めないとき。
- **よくある失敗**：契約を作る側のリポジトリにだけ置く。契約と実装がずれる。
- **拠り所の原則**：[境界づけられた文脈](principles.md#bounded-context)、[スキーマを先に](principles.md#schema-first)。

<a id="shared-kernel"></a>

### 共有の核（Shared Kernel）

- **解く問題**：複数の区切りが同じもの（言葉、決まり、形式）を要るのに、それぞれが持つとずれていく。
- **形**：共有するものだけを小さな核として一か所に置き、すべての区切りがそれを前提にする。核はほかの区切りを
  前提にしない。核を変えるときは、使う全員に合わせる。
- **使いどころ**：用語、共通の決まり、形式など、区切りをまたいで同じであるべきもの。
- **よくある失敗**：核が大きくなり、個別の事情が入り込む。核がほかの区切りを参照する。
- **拠り所の原則**：[境界づけられた文脈](principles.md#bounded-context)、[依存の向き](principles.md#dependency-rule)、
  [SSOT](principles.md#ssot)。

<a id="contract-test"></a>

### 契約の試験（Contract Test）

- **解く問題**：契約を書いても、実装が変わると気づかないうちにずれる。
- **形**：実装の試験の中で、実装が渡すもの（名前、パス、形）が契約に書かれているかを照らす。試験で本物の代わりに
  使うもの（テストダブル。スタブ、モック、フェイクなどの総称。Gerard Meszaros, *xUnit Test Patterns*, 2007）も
  契約の片側として扱う。テストダブルにする問い合わせを本物にも流し、同じに答えるかを照らす試験を持つ。本物に
  流す試験は、毎回の試験とは別に、間をおいて流してよい（Martin Fowler, "ContractTest", 2011）。
- **使いどころ**：契約を文書として持つすべての場所。外部（API、コマンド）をテストダブルに置き換えて試験する所。
- **よくある失敗**：契約の文書だけを直し、照らす試験がない。テストダブルが本物と違う振る舞い（返す項目、付ける
  id、答えない問い合わせ）をし、本物では壊れる振る舞いを試験が通す。テストダブルを足したり変えたりしたのに、
  本物で一度も照らさない。
- **拠り所の原則**：[スキーマを先に](principles.md#schema-first)、[仕組みで守る](principles.md#mechanisms)。

## 構造の表し方

<a id="dsm"></a>

### 設計構造行列（Design Structure Matrix）

- **解く問題**：項目が多く入れ子になると、どれがどれに依存しているか、循環や上の階層への違反がないかを、文章や図
  からは読み取れない。
- **形**：項目を行と列に同じ順で並べ、行の項目が列の項目に依存するところに印を付けた行列にする。入れ子の項目は、
  親の行と列の中に子の行と列を入れて並べる。依存の向きが守られていれば、印は対角線の片側（下三角）だけに集まる。
  反対側の印は、循環か向きの違反を表す。
- **使いどころ**：項目が多いとき、入れ子の構成を確かめたいとき。依存を宣言から機械で組み立てて出すと、人が全体を
  見る道具にもなる。
- **よくある失敗**：図だけで済ませ、項目が増えて読めなくなる。印の意味（前提のリンクか在りかのリンクか）を混ぜる。
- **拠り所の原則**：[階層的分解](principles.md#hierarchy)、[非循環依存](principles.md#acyclic)。

<a id="relation-kinds"></a>

### 関係を種類で分ける（前提と在りか）

- **解く問題**：あらゆる参照を依存として数えると、一覧から各項目へのリンクのような問題のない参照まで、循環や違反に
  見える。逆に、本当の依存が参照の多さに埋もれる。
- **形**：項目の間の関係を種類で分けて扱う。少なくとも、含む（親子）、並ぶ（兄弟）、前提にする（依存：相手が
  変わると、こちらの見直しが要る。[依存の向き](principles.md#dependency-rule)）、満たす・作る（契約との関係）、
  在りかを示す（場所や、判断の理由の記録を指すだけで、相手の中身が変わっても直さなくてよい）を区別する。依存の向きの決まりは
  「前提にする」にだけ当てる。
- **使いどころ**：文書のリンク、モジュールの参照、設定の参照など、参照の意味が混ざりやすいところ。
- **よくある失敗**：索引から各文書へのリンクを依存として数える。逆に、前提にしているのに在りかを示すだけのように扱って、
  向きの確かめから外す。在りかを示すだけであることを参照に書かず、参照そのもの（リンク）を消して確かめを避ける。
- **拠り所の原則**：[関心の分離](principles.md#soc)、[依存の向き](principles.md#dependency-rule)。

## 文書

<a id="diataxis"></a>

### 文書の種類で分ける（Diátaxis）

- **解く問題**：一つの文書に手順、事実、説明が混ざり、手順を探す人も理解したい人も読みにくい。
- **形**：文書を、読み手の目的で 4 つの種類に分ける。チュートリアル（学ぶ）、手順（目的を果たす）、参照（事実を
  引く）、解説（理解する）。文書ごとに種類を一つ決め、混ざったら分ける。
- **使いどころ**：文書が複数あるすべてのリポジトリ。
- **よくある失敗**：README に何でも書く。解説の途中に手順を挟む。
- **拠り所の原則**：[関心の分離](principles.md#soc)、[単一責任](principles.md#srp)。

<a id="adr"></a>

### 判断の記録（Architecture Decision Record）

- **解く問題**：なぜ今の形なのかが後から分からず、同じ議論を繰り返す。今の姿の説明に経緯や却下した案が混ざる。
- **形**：判断ごとに、文脈、決めたこと、選ばなかった案、結果を一つの記録にし、後から本文を書き換えない。判断を
  変えるときは新しい記録を作り、新旧の両方から互いを参照する。今の姿は解説の文書に、道筋は課題の管理に、経緯は
  コミットに置く。
- **使いどころ**：後から理由を知りたくなる判断、また間違えそうな判断。
- **よくある失敗**：今の姿を知るのに記録の連鎖をたどる必要がある。記録の本文を書き換える。
- **拠り所の原則**：[今と経緯を分ける](principles.md#present-state)、[SSOT](principles.md#ssot)。

<a id="metadata"></a>

### 機械で読める属性（Frontmatter のメタデータ）

- **解く問題**：種類、状態、参照が本文の文章の中にあり、食い違っても気づけず、一覧も作れない。
- **形**：検査や一覧に使う属性を、文書の先頭の決まった形（YAML の frontmatter など）に書く。
- **使いどころ**：状態や参照を持つ記録（判断の記録など）。
- **よくある失敗**：同じ属性を frontmatter と本文の両方に書く。
- **拠り所の原則**：[スキーマを先に](principles.md#schema-first)、[仕組みで守る](principles.md#mechanisms)。

<a id="docs-as-code"></a>

### Docs as Code

- **解く問題**：実装を変えても文書が古いまま残る。
- **形**：文書をコードと同じリポジトリに置き、同じ変更の単位（PR）で変え、リンクや形式を CI で検査する。
- **使いどころ**：実装と一緒に変わる文書すべて。
- **よくある失敗**：文書を別の場所（wiki など）に置き、実装の変更と結びつかない。
- **拠り所の原則**：[仕組みで守る](principles.md#mechanisms)、[SSOT](principles.md#ssot)。

<a id="single-source"></a>

### 一つの出典から届ける（Single-Source Publishing）

- **解く問題**：同じ決まりを、いつも読ませる指示、必要なときの手順、検査など、効き方の違う形で届けたい。それぞれに
  書くと、どれが正しいかが分からなくなり、ずれていく。
- **形**：決まりは一か所（出典）で定義する。ほかの形は出典から作る出力として扱い、出典の要約か、出典への案内だけを
  書いて新しい決まりを足さず、どの出典によるかを示す。出典を変えたら出力も直す。出力は出典を前提にし、出典は出力を知らない。
- **使いどころ**：常に読み込ませる指示、役割ごとの指示、手順、検査など、同じ決まりを複数の場所で効かせたいとき。
- **よくある失敗**：出力の側にだけ決まりを書き足す。出力が出典を示さず、二か所に定義があるように見える。
- **拠り所の原則**：[SSOT](principles.md#ssot)、[段階的な開示](principles.md#progressive-disclosure)。

<a id="single-index"></a>

### 入口と唯一の一覧

- **解く問題**：入口ごとに文書の一覧を持つと、どれかが古くなる。入口が長いと、要るものにたどり着けない。
- **形**：一覧は一か所（索引）にだけ置く。入口（README、エージェントが常に読むもの）は短い説明と索引への道にする。
- **使いどころ**：入口が複数ある（人向けとエージェント向けなど）リポジトリ。
- **よくある失敗**：README と CLAUDE.md と索引に同じ一覧を書く。
- **拠り所の原則**：[SSOT](principles.md#ssot)、[段階的な開示](principles.md#progressive-disclosure)。

## 変更の組み立て

<a id="loss-first"></a>

### 失われうるものを先に挙げる

- **解く問題**：消す、上書きする、作り直す処理で、ほかに写しのないものが黙って失われる。
- **形**：作る前に、その処理で失われうるもの（ほかに写しがないもの、人が確かめる前のもの、あとで要りうるもの）を
  挙げる。あれば、残すか、確かめてから消す。安全側に倒して残り続ける場合も書いておく。
- **使いどころ**：消す、上書きする、作り直す処理すべて。
- **よくある失敗**：正常な場合だけを考え、途中の状態（保存していない変更、まだ送っていないもの）を見落とす。
- **拠り所の原則**：[関心の分離](principles.md#soc)：消す処理と、残すべきものを見分ける判断を分けて考える。
- **組み合わせるパターン**：[状態を軸で洗い出す](#state-axes)。

<a id="verify-procedures"></a>

### 手順を実装と突き合わせる

- **解く問題**：人が実行する手順（移行、運用）が実装と食い違い、実行して初めて間違いが分かる。
- **形**：手順は、実装と突き合わせるか、実際に実行して確かめる。パスの深さ、名前の付け方、権限など、食い違い
  やすいところを特に見る。確かめていなければ、そう書く。
- **使いどころ**：移行の手順、運用の手順、復旧の手順。
- **よくある失敗**：手順を書いただけで、一度も実行していない。
- **拠り所の原則**：[仕組みで守る](principles.md#mechanisms)。

<a id="extract-after-use"></a>

### 使ってから共通にする（Rule of Three）

- **解く問題**：使う前に共通部分を決めると、実際には共通でないものまで共通にし、個別の事情を無理に一つの形に押し込む。
- **形**：最初は写して使い、実際に二つ三つの場所で同じだったものだけを切り出して共通にする。規約も、要るようになって
  から一つずつ決める。
- **使いどころ**：ひな形、共通の部品、規約を作るとき。
- **よくある失敗**：一つ目の使い道だけを見て、汎用の仕組みを先に作る。
- **拠り所の原則**：[高凝集・疎結合](principles.md#cohesion)：本当に一緒に変わるものだけを一つにする。
  [小さく試して確かめる](principles.md#small-experiments)：使い道が確かめられてから共通にする。

<a id="small-change"></a>

### 一つの目的の小さな変更

- **解く問題**：大きな変更はレビューしきれず、問題が混ざり、戻しにくい。
- **形**：一つの PR は一つの目的にする。差分が大きくなったら、独立して確かめられる単位に分ける。
- **使いどころ**：すべての変更。
- **よくある失敗**：見つけた別の直しを同じ PR に足していく。
- **拠り所の原則**：[単一責任](principles.md#srp)。

## 見直し

<a id="four-eyes"></a>

### 別の目で見る（Four-Eyes Principle）

- **解く問題**：作った人は、自分の前提の抜けや誤りに気づきにくい。
- **形**：作った人とは別の人が、作ったものを確かめてから取り込む。
- **使いどころ**：取り込むと戻しにくいもの、多くの人が前提にするもの。
- **よくある失敗**：作った人の説明をなぞって確かめ、同じ前提の抜けを引き継ぐ。
- **拠り所の原則**：[仕組みで守る](principles.md#mechanisms)。

<a id="perspective-based"></a>

### 観点を分けて読む（Perspective-Based Reading）

- **解く問題**：「全部見る」レビューは、読む人が気づきやすいものに偏り、どこを見落としたかもわからない。
- **形**：読む人ごとに観点（元の形では、使う人、設計する人、試験する人などの立場）を割り当て、その観点で何を探すかを
  決めた手順に沿って読む。観点の和で全体を覆い、観点どうしは重ねない。
- **使いどころ**：仕様、設計、コード、文書のレビュー。
- **よくある失敗**：観点を増やしすぎて、どれも浅くなる。機械で確かめられることを人が読んで探す。
- **拠り所の原則**：[関心の分離](principles.md#soc)、[兄弟をそろえる](principles.md#siblings)。

<a id="labeled-comments"></a>

### 指摘に重さを付ける（Conventional Comments）

- **解く問題**：指摘が、直さないと取り込めないものか、提案か、質問かわからず、受け手が意図と重さを推測する。
- **形**：指摘の頭に、種類のラベル（issue、suggestion、question、nitpick など）と、取り込みを止めるかどうかの飾り
  （blocking、non-blocking）を付ける。
- **使いどころ**：レビューの指摘、監査の報告。
- **よくある失敗**：すべてを同じ重さで並べ、大事な指摘が細部に埋もれる。ラベルを付けても本文が曖昧なまま。
- **拠り所の原則**：[必要十分](principles.md#sufficiency)。

<a id="lgtm-with-comments"></a>

### 直しを任せて見直しを終える（LGTM with comments）

- **解く問題**：取り込みを止めない細部の直しのたびに見直しを頼み直し、見直しが終わらない。直しが細部の食い違いを
  生み、それを見るためにまた見直す。
- **形**：見直す人が、残る指摘は意味の変わらない直しで済むと判断したら、直したあとにもう一度見ないことを示して
  見直しを終える。変更した人はそれを直して、直したことを記録する。示されなかった指摘への直しや、直しで意味が
  変わったときは、もう一度見直してもらう。
- **使いどころ**：見直しの指摘への直し。
- **よくある失敗**：見直しを省くかを、変更した人が自分で決める。意味の変わる直しまで、見直さずに取り込む。逆に、
  言い回しの直しのたびに見直しを頼み直す。
- **拠り所の原則**：[必要十分](principles.md#sufficiency)。[別の目で見る](#four-eyes)と組む。

## 検査

<a id="mutation-testing"></a>

### 壊した版で検査が落ちることを確かめる（Mutation Testing）

- **解く問題**：検査（試験、hook、検査のスクリプトなど、機械で確かめるもの）が通るだけでは、守りたい性質を
  確かめているかは分からない。出力が空でも通る、直す前の版でも通る、実装が書くはずの値を検査が前もって書いて
  おくので実装が書かなくても通る、といった検査は、何も守らない。
- **形**：実装を小さく壊した版（変異）を作って検査を流し、それぞれの版で検査が落ちるかを見る。落ちない変異が
  あれば、検査はそこを確かめていない。道具で多くの変異（演算子や条件の置き換え）を機械的に作り、落ちた割合を測る
  形と、守りたい性質ごとに手で壊した版（直す前の版、守りたい行を外した版）を作る形がある。出典は
  Richard DeMillo、Richard Lipton、Frederick Sayward, "Hints on Test Data Selection"（1978）。
- **使いどころ**：直した不具合を防ぐ検査、決まりを守らせる検査、テストダブルを使う試験。
- **よくある失敗**：検査が通ったことで、性質が守られたとみなす。どの出力でも成り立つ条件（空の文字列を含むか
  など）で比べる。実装が書くはずの値を、検査が前もって書いておく。
- **拠り所の原則**：[仕組みで守る](principles.md#mechanisms)。
