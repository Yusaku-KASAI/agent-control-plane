# 設計の観点

作るときはこの順に当てはめ、レビューでは当てはまっていないところを指摘する。

## 状態を軸で洗い出す

状態によって振る舞いが変わる処理は、書く前に状態を軸で洗い出す。

- 軸は、その対象の上で値が互いに重ならず、すべての場合を尽くす。
  - 同時に成り立ちうる性質は、「ある / ない」の別の軸にする。
  - 一つの値に絞るものは、優先順位を決めて「上から順に最初に当たるもの」と定義する。
  - 軸が定義される範囲（「記録がある」「リポジトリである」など）を書く。どれにも当たらない場合が残っていないかを確かめる。
- 判定は軸の値だけで書く。軸と判定は ADR などに表で書き、テストもその表の組み合わせで書く。

## 事実を集めることと判定を分ける

- 外部（ファイル、git、API）を読む層は事実だけを返し、何を意味するかを決めない。
- 判定は一か所に置く。同じ判定の結果から、振る舞いも、人への知らせの文面も作る。判定を条件式としてあちこちに
  書き直さない。

## 失われうるものを先に挙げる

消す、上書きする、作り直す処理は、作る前に、それで失われうるものを挙げる（ほかに写しがないもの、人が確かめる前の
もの、あとで要りうるもの）。

- 失われうるものがある場合は、残すか、確かめてから消す。
- 安全側に倒した結果、残り続ける場合も書く。そうでないと、残った理由が後から分からない。

## 手順は実装と突き合わせる

移行や運用の手順（人が実行するコマンド）は、実装と突き合わせるか、実際に実行して確かめる。パスの深さ、名前の
付け方、権限など、実装と食い違いやすいところを特に見る。確かめていなければ、そう書く。

## 大きさ

一つの PR は一つの目的にする。差分が大きくなったら、独立して確かめられる単位に分ける。
