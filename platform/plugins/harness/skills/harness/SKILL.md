# ハーネスの問題を切り分ける

渡されるものとその制約は、ハーネスの契約（SessionStart で示されたパスの `harness.md`）にある。まずそれを読み、
起きていることが契約どおりかを確かめる。

## 手順

1. 動き方を確かめる：`ACP_SESSION_BRANCH` があれば control-plane 経由。
2. エラーの全文を残す。出力を `tail` などで切らない。
3. 契約にあるものが、契約どおりかを確かめる。値（トークン）は表示しない。
   - 環境変数があるか（`env | grep -E '^(ACP_|GH_CONFIG_DIR|SLACK_BOT_TOKEN_FILE|GIT_AUTHOR_)' | cut -d= -f1`）。
   - ファイルがあるか（`ls -la "$GH_CONFIG_DIR"`）。
   - 道具が動くか（`gh --version`、`gh api rate_limit --jq .rate.remaining`、`git push --dry-run --no-verify origin HEAD`）。
     `--dry-run` でも pre-push のフックは働くので、認証と push の道だけを見るここでは `--no-verify` で避ける。
   - ファイルの振る舞い（ロック、権限、所有者）が説明と合わないときは、そのファイルがどのファイルシステムの上かを
     確かめる（`df -T "$PWD" "${TMPDIR:-/tmp}"`。作業領域が `fakeowner` なら Docker Desktop のマウント）。作業領域の
     マウントの制約は、契約の「作業領域とブランチ」にある。
   - 道具がエラーの文面と合わない失敗をするとき（`git status` に変更がないのに git が「Your local changes would be
     overwritten」と言う、一時ディレクトリを作れない、など）は、まずディスクの空きを確かめる
     （`df -h / "$PWD" "${TMPDIR:-/tmp}"`）。コンテナのルートと `/tmp` の空きは、作業領域の空きとは別にある
     （契約の「コンテナの寿命」）。
4. 見分ける。
   - **ハーネスの問題**：契約で渡されるはずのものがない（渡される条件も契約にある）、契約どおりなのに道具が動かない（例：読み取り専用の設定を gh が
     書き換えようとして失敗する）、イメージに要る道具がない。
   - **権限の問題**：認証は通るが 403 などで拒まれる。エージェントの GitHub App や Slack アプリの権限が足りない。
   - **ターゲットの問題**：ターゲットのコード、設定、検査そのもの。
   - **資源の問題**：ハーネスもターゲットも契約どおりだが、動かしている手元の資源が足りない（コンテナのディスクに
     空きがない）。ターゲットのイメージに道具がないのは、ここではなくハーネスかターゲットの問題。

## 報告

- ハーネスや権限の問題は、自分では直せない。回答に「ハーネスの問題」か「権限の問題」と書き、打ったコマンド、
  エラーの全文、契約のどこと食い違うかを添える。依頼者が control-plane のリポジトリ（agent-control-plane）の
  Issue にする。
- セッションの中だけで回避できるなら（例：認証情報を書き込める場所に写して使う）、回避して作業を進めてよい。
  回避したことと、その方法を回答に書く。ハーネスの側を直したことにはならない。写した認証情報は control-plane が
  書き換えないので、トークンが失効したら写し直す。
- 資源の問題は Issue にしない。自分が作った一時ファイルやキャッシュで空けられるなら、空けて進め、そのことを回答に
  書く。空けられなければ、`df -h` の出力を添えて、依頼者に手元（Docker Desktop のディスクなど）を空けるよう頼む。
  `df` に空きがあっても、書き込みの失敗が説明できないまま続くなら、ホストのディスクが満ちていることがある（契約の
  「コンテナの寿命」）。依頼者にホストのディスクの空きを確かめるよう頼む。
- 推測で「設定を直してほしい」とだけ書かない。確かめたことと、確かめていないことを分けて書く。
